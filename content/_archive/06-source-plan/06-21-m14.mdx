*M14 · D14 (full) · Months 5–6*

`Release 2` · `4 items` · `15 conditions` · `26.5pd` · `0 high risk` · `Ops/Admin`

M3 records which recruiter was put on which vacancy, as decided on the morning call. This milestone makes the system do the deciding: work out which vacancies matter most based on how urgent, how valuable and how old they are, suggest which recruiter should take each one based on their current load and past success, and balance work across the team. It also adds an approval step so a vacancy can be checked before it goes live, which M3 deliberately does not have.

### Built once, used elsewhere

This changes M3 behaviour rather than adding new screens beside it. The fulfilment board and requisition record gain new fields and actions.

### Records this milestone owns

- PriorityScore — a score per vacancy and why it got that score.
- AllocationSuggestion — a recommended recruiter, with the reasoning and whether it was accepted.
- RecruiterCapacity — current load against the agreed norm of 15-16 vacancies.
- ApprovalRequest — a vacancy waiting to be approved before it goes live.

### How records move

- Requisition gains: created → awaiting approval → approved → open. Or rejected back to the raiser.
- AllocationSuggestion: generated → accepted or overridden, with a reason

### Not in this milestone

- Forcing an allocation. The system suggests; a person still decides.
- Forecasting demand.

### Needs to exist first

- M3 for the requisition and allocation records. M9 for the performance data the suggestions are based on.

### What breaks without it

- M9 gains better data on how allocation decisions turn out.

#### M14-I1 — Priority board

`D14` · `Screen` · `L · 3.0pd` · `AI High` · `Medium` · `SPEC` · `Low`

**Who uses it: Fulfilment lead, Shalu.** The fulfilment board, ordered by what the system thinks matters most rather than by age alone.

##### Screens to build

1. **Priority board**
  - Lists requisitions ordered by how important the platform scores them
  - Shows why each scored as it did
  - Overrides a priority by hand, with a reason

##### Conditions it must satisfy

- Each requisition shows why it scored where it did, not just a number
- A manual override is recorded with a reason
- The board can still be sorted the old way, so the change is not forced on day one
- Priority factors are configurable

#### M14-I2 — Suggested recruiter

`D14` · `Screen` · `L · 3.0pd` · `AI Medium` · `Medium` · `MODEL` · `Low`

**Who uses it: Fulfilment lead.** The system proposes which recruiter should take a vacancy. A person still decides.

##### Screens to build

1. **Suggested recruiter**
  - Suggests which recruiter should take a requisition
  - Shows how many requisitions that recruiter already holds
  - Accepts the suggestion or picks someone else, with a reason

##### Conditions it must satisfy

- The system suggests; it never assigns on its own
- Load is shown against the operating norm, which M3 records but does not enforce (M3 OI-M3-10)
- Suggestions are based on M9 performance data

#### M14-I3 — Requisition approval

`D14` · `Screen` · `L · 3.0pd` · `AI High` · `Medium` · `XMOD` · `Low`

**Who uses it: BD, Fulfilment lead.** An approval step before a vacancy goes live. M3 deliberately has none, so this is new behaviour on an existing record.

##### Screens to build

1. **Requisition approval**
  - Lists requisitions waiting to go live
  - Approves or rejects one with a reason

##### Conditions it must satisfy

- A requisition gains a new state between created and open (M3 state table extension)
- Approval rules are configurable by client, value or role
- An urgent bypass is possible but always audited
- Rejecting returns the requisition to whoever raised it with the reason

#### M14-I4 — Priority and load engine

`D14` · `Service` · `XL · 5.0pd` · `AI Medium` · `Medium` · `MODEL` · `Low`

**Who uses it: System.** Scoring vacancies and spreading work across the team.

##### Screens to build

1. **No screen**
  - Scores requisitions on urgency, value and age
  - Works out each recruiter's current load and suggests who should take the next one

##### Conditions it must satisfy

- Scoring inputs and weights are configurable
- Load balancing accounts for vacancies already held, not just new ones
- Suggestion outcomes feed back so the model can be tuned against evidence
- The engine never writes an allocation directly
