## 1. Purpose

Part 2 opened every path. Part 3 takes each one to full depth, moves everything Apollo already has into
the platform, makes the operation measurable, and hands it over.

Intake widens to each client's own spreadsheet format, voice notes and feeds from client HR systems.
The legacy system is profiled, moved, reconciled and switched off. Fill rate, time to fill, where
candidates drop out and how recruiters perform are all reportable. The client portal reaches full
width. Salary changes and advances run through proper approvals and overdue invoices are chased. Then
documentation, acceptance testing support, and the cutover.

**The claim Part 3 has to prove is that the old system can be switched off.**

### Explicitly out of scope

- Anything not in the client's 208 items. Feedback at a Part 3 gate that introduces new capability is a
  **change**, not a completion.
- A second market. The adapter interfaces make one possible; configuring one is not in this engagement.

### Explicitly not built

- A replacement for the finance system. Invoices are **exported to it**, not raised inside it.
- A payroll engine. Pay runs are **sent to a third-party engine** and results received back.
- Automatic merging of migrated duplicates. Every merge is a human decision, in Part 3 as in Part 2.

#### Screens

| # | Screen | Screen reference | What it is for |

| 1 | Migration status | `/admin/migration` — **not in POC** | Each run: records read, loaded, failed. **Progress observable while running** |

##### Migration record · elements

| Field | Datatype | Enumeration / rule |
|---|---|---|
| `source` | enum | On the candidate: `app` · `migration` · `ops` · `learner_record` — **a migrated record is always identifiable as one** |
| `consentBasis` | enum | `app` · `migrated_unverified` · `ops` — **migrated records carry no app consent, and the platform must never pretend they do** |

#### Scenarios

| # | Scenario | Expected |
|---|---|---|
| 1 | A batch is started | Progress is observable while it runs, not only at the end |
| 2 | It is paused and resumed | Resumable and re-runnable, with no double-loading |
| 3 | A record fails to load | The reason is given per record; the failing field can be corrected and resent |
| 4 | A record cannot be salvaged | Rejected with a reason and counted in reconciliation |
| 5 | A delta run happens before cutover | Only changes since the last run are moved |
| 6 | A migrated candidate later signs up on the app | Surfaced as a suspected duplicate. **Never merged automatically** |
| 7 | A duplicate is merged by a human | The merge is on the activity trail with both source records named |
| 8 | Reconciliation runs | Source total = loaded + exceptions + rejected, or the batch **does not reconcile and says so** |
| 9 | A migrated candidate is selected by a cadence | Suppressed on consent, because `consentBasis` is `migrated_unverified` |
| 10 | Cutover happens | The legacy system is read-only, then retired, with the date recorded |

#### Tested against

- **Happy** — a full load reconciling to source totals, with duplicates resolved by a human and the
  legacy system switched off.
- **All** — scenarios 1–10, plus: a batch resumed mid-run with no duplicates; a delta run after the
  main load; a migrated record correctly excluded from consent-gated sends; reconciliation failing
  loudly when totals disagree.
