The shape of the system and why it is that shape. Conventions that follow from it are in `01-standards/`.

## 1. Shape: a modular monolith with a separate worker

One deployable API process, one deployable worker process, one Postgres database with a **schema per
module**, and Redis for queues and cache. Not microservices.

**Why.** The plan's own couplings decide this. M6 cannot rank without M3, M4 and M5 all present
(`M6-I6`). M9 cannot invoice without reading the M2 contract version in force at the trigger date
(`M9-I14`). The day-90 record must be written in the same transaction as the link response
(`M8-I13`). Splitting these into services would replace transactions with sagas on a six-month
timeline with 10.8 average heads. Module boundaries are enforced in the repository (`01-01`) and in
the database (schema-per-module, `01-05`), not by a network hop.

**Why a separate worker.** Eight plan items are timers or queues (cadence runs, escalation windows,
deemed-approval countdowns, credential expiry, check-in generation, dunning, retries, migration
batches). Running them in the API process makes a cadence run over the whole Base B compete with an
interactive fulfilment board. Same code, same database, different process and different scaling.

Shared packages: `@apollo/contracts` (Zod schemas + inferred types, the single source of API truth),
`@apollo/ui` (design system, `02-05`), `@apollo/db` (pool, SQL helpers, migrations), `@apollo/events`
(event names and payload schemas, `02-11`), `@apollo/config` (typed env).

## 3. Stack decisions and the reason for each

| Layer | Decision | Reason |
|---|---|---|
| Language | TypeScript everywhere | One `@apollo/contracts` package types the API, the console, the portal, the link pages and the app. Six surfaces against 1,062 conditions cannot afford a type boundary per surface. |
| HTTP | **Fastify 5** | Schema-first routes; the JSON Schema that validates a request also generates the OpenAPI document (`01-04`), so the contract cannot drift from the handler. |
| Persistence | **`pg` + hand-written SQL. No ORM.** | Client directive. Every query is visible, which matters for the append-only tables (`AuditEntry`, `StatusTransition`, `RetentionRecord`) where an ORM's dirty-tracking would be actively wrong, and for the reporting marts (`03-12`) which are set-based. See `01-05` for the repository pattern and how N+1 is avoided without a lazy loader. |
| Migrations | Numbered plain-SQL files, forward-only, applied by a small in-repo runner | No ORM means no migration generator. Forward-only because `RetentionRecord` and `AuditEntry` must never be rewritten. (`AS-09`) |
| Cache / queue | Redis (ElastiCache) + BullMQ | One dependency covers the job runtime, the rate limiters (OTP `M4-I22`, provider limits `M5-I8`) and the idempotency keys. (`AS-08`) |
| Object store | S3, `ap-south-1`, SSE-KMS, versioning on | F06 requires versions, virus scanning, expiring links and Mumbai residency. (`AS-07` — object store was undecided) |
| Web | React 19 + Vite + TanStack Query + TanStack Router + shadcn/ui + Tailwind | Client directive; `02-05` builds the design system on shadcn primitives so console, portal and link pages share one visual language. |
| Mobile | React Native + Expo, EAS Build/Submit | Offline check-in queue, push, and OTA for non-native fixes — the plan flags store review as calendar risk that team size cannot remove (`OI-HS-08`, `04-12`). |
| Monorepo | Nx + npm workspaces | Client directive. Nx project graph enforces the module boundaries described in `01-01`. |
| Region | AWS `ap-south-1` (Mumbai), Apollo-owned account | F10 + F13. No personal data leaves the region, backups included (`M1-I5`, `M4-I27`). Account ownership pending `OI-HS-04`. |

## 4. Request paths

### Authenticated console request

```
Browser ──▶ CloudFront ──▶ ALB ──▶ Fastify
                                     │
                                     ├─ preHandler: session → Principal {userId, roles, siteIds, realm}
                                     ├─ preHandler: permission guard (02-01) — deny by default
                                     ├─ handler: Zod-validated body/query
                                     ├─ service: business logic, one transaction
                                     │     ├─ repository: hand-written SQL (01-05)
                                     │     ├─ audit.record(...)   ← 02-02, same transaction
                                     │     └─ events.emit(...)    ← 02-11, outbox row, same transaction
                                     └─ response: Zod-validated envelope (01-04)
```

The audit write and the event write are **in the same transaction as the change**. This is not
optional: `M9` reports on periods that have already passed, which is only possible if the event was
written when the work happened (`M3-I31`), and the day-90 invoice is defended by the audit trail
(`M0-I4`).

### Public tokenised link request (no account)

```
WhatsApp/email ──▶ https://links.<apollo-domain>/l/<token>
                     │
                     ├─ token lookup: unguessable, single-purpose, expiring (02-14)
                     ├─ Principal {realm: 'link', linkId, recipientId, clientId, scope: [one record]}
                     ├─ render: one question, one action, mobile first
                     └─ submit ──▶ link answer routing (M7-I18) ──▶ selection | trial | billing | timesheet
```

A link principal can reach exactly one record and exactly one action. Only the **day-90 type** may
carry the billing-trigger flag, and the flag is not editable on the day-30/day-60 types (`M7-I8`).

### Inbound message path (shared stack, `02-08`)

```
WhatsApp webhook ─┐
Email (SES→SNS)  ─┤
HRMS push        ─┼─▶ receiver ─▶ InboundRecord (raw payload retained forever)
Spreadsheet      ─┤                    │
Voice note       ─┘                    ▼
                              sender identity resolution (M3-I19)
                                       │
                        ┌──────────────┴──────────────┐
                     1 match                    0 or 2+ matches
                        │                             │
                        ▼                             ▼
              intent classification (M3-I21)    unmatched queue (M3-I2)
                        │
        ┌───────────────┼────────────────┐
   demand intent   candidate-response   below threshold
        │             intent                  │
        ▼               ▼                     ▼
   03-02 parsers    03-06 A14 handler   manual entry queue (M3-I3)
```

The receiver, queue, sender resolution, classification and retry are built **once**. A second consumer
registers an intent set and a target schema without touching any of them (`M3-I29`), and that
registration is the acceptance test.

### Job path

```
Scheduler (cron in worker) ─▶ enqueue ─▶ BullMQ queue ─▶ handler
                                             │              ├─ success → completed
                                             │              ├─ transient failure → backoff retry
                                             │              └─ permanent failure → dead-letter, visible & re-queueable
                                             └─ every run recorded: which rule, which rows, when (M5-I11)
```

## 5. Deployment topology

Docker images for everything, GitHub Actions to build and ship them, **EC2 for the long-running
processes and Lambda for the event-driven edges**. Details and the pipeline are in `01-09`; `02-15`
builds it.

```
                         ap-south-1 (Apollo-owned account, OI-HS-04)
   ┌────────────────────────────────────────────────────────────────────────────────┐
   │  CloudFront ── S3 (console, links, portal static bundles)                       │
   │       │                                                                         │
   │       └──▶ ALB ──▶ EC2 Auto Scaling Group  ── docker: @apollo/api               │
   │                    EC2 Auto Scaling Group  ── docker: @apollo/worker            │
   │                          │                                                      │
   │   Lambda (event edges)   │                                                      │
   │   ├─ SES inbound email ──┤        all Lambdas do one thing: validate, persist   │
   │   ├─ WhatsApp webhook ───┤        the raw payload, enqueue. No business logic.  │
   │   ├─ S3 object created ──┤                                                      │
   │   └─ EventBridge cron ───┤                                                      │
   │                          ▼                                                      │
   │                    ├──▶ RDS PostgreSQL 16, Multi-AZ, PITR                       │
   │                    ├──▶ ElastiCache Redis (BullMQ queues, cache, limiters)      │
   │                    ├──▶ S3 documents bucket (SSE-KMS, versioned)                │
   │                    ├──▶ Secrets Manager (provider credentials)                  │
   │                    └──▶ CloudWatch + OpenTelemetry traces                       │
   │                                                                                 │
   │  Environments: dev · qa · uat · prod  (F10 / M1-I16), non-prod anonymised       │
   └────────────────────────────────────────────────────────────────────────────────┘

   GitHub Actions ──▶ build Docker image (git SHA) ──▶ ECR ──▶ SSM deploy to EC2
                  └─▶ package Lambda container images ──▶ ECR ──▶ update function

   Expo EAS ──▶ App Store / Play Store   (Apollo-owned accounts, X12 / X13)
```

**Why EC2 for api and worker.** Both hold long-lived Postgres pools and Redis connections; the worker
runs cadence batches over the whole Base B and resumable migration batches (`M1-I11`) that must survive
minutes, not seconds. A container that owns a connection pool and a BullMQ consumer is a long-running
process, and running it on instances the team controls also keeps the deployment story simple in a
client-owned account whose ownership is still open (`OI-HS-04`).

**Why Lambda at the edges.** Four inbound paths are bursty, externally triggered and must never lose a
payload: SES email delivery, the WhatsApp webhook, S3 object-created (virus scan), and EventBridge
schedules. Each Lambda does exactly one thing — verify the signature, write the raw payload down,
enqueue — and returns. This keeps a provider retry storm off the API instances and satisfies
`M3-I18` ("a redelivered message does not create a duplicate `InboundRecord`") at the cheapest possible
place. **No business logic runs in a Lambda**; the work happens on the worker where the transaction,
audit write and event emit live together.

Four environments, one pipeline, no hand-edited configuration between them (`M1-I16`). Recovery
targets are unset (`OI-HS-12`) — until they are, the restore rehearsal has no pass condition, so
`02-15` carries the rehearsal as an explicit acceptance criterion with a placeholder target.

## 6. Boundaries that must not be crossed

| Rule | Enforced by | Because |
|---|---|---|
| No module reads another module's tables directly | Nx boundary rules + one Postgres role per schema (`01-05`) | Otherwise the monolith becomes a big ball of mud in month three |
| Every external provider sits behind an interface in `02-13` or its integration package | Contract tests (`01-08`) | Half the suppliers are unnamed; the plan requires replacement without domain change |
| `AuditEntry`, `StatusTransition`, `RetentionRecord`, `AllocationRecord`, `RecruiterOverride` are append-only | Table grants (no `UPDATE`/`DELETE`) + tests | Named in the plan as append-only; the day-90 invoice depends on it |
| Personal data never leaves `ap-south-1` | Bucket policy, RDS/backup region, provider selection | DPDP (`M4-I27`) |
| Candidate identity, staff identity and client-user identity are three separate realms | `02-01` | `AS-06`, and a portal leak between hospitals is the worst outcome in `M10-I8` |
| Anything measurable is emitted as an event, never scraped later | `02-11` | `M3-I31`: build it after M3 and the M9 reports cannot cover the earlier period at all |

## 7. What is deliberately not in the architecture

| Not built | Why |
|---|---|
| Microservices, service mesh, per-module deploy | Coupling above; six months |
| Event sourcing as the write model | The event spine is a reporting spine (F14), not a source of truth. Operational tables stay relational. |
| GraphQL | Six surfaces, one team, schema-first REST + generated OpenAPI is cheaper and the link pages need one endpoint each |
| A separate analytics warehouse | `03-12` materialises marts inside the same Postgres from the event spine (`M9-I17`). Revisit only if `OI-M3-14` sets targets it cannot meet. |
| Multi-region | DPDP residency argues against it; RPO/RTO unset (`OI-HS-12`) |
| Feature flags as a product | One `settings` table already carries every toggle the plan names (`02-03`) |
