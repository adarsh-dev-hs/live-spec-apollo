## 1. Purpose

How many vacancies get filled, how fast, where candidates drop out, how each recruiter and each intake
channel performs, how many placements survive to day 90, and how the rate agreed compares to the
standard rate. Seven report screens plus the monthly pack, all reading **marts materialised from the
event spine**, never from operational tables.

Every one of these reports depends on events having been written **when the work happened**. If `02-11`
had been built after `03-03`, none of them could cover the earlier period at all.

## 2. Scope

### In scope

- Funnel and stage conversion (`M9-I5`)
- Fill rate and time-to-fill, showing distribution rather than just an average (`M9-I6`)
- Trial survival across the full day 0–90 curve (`M9-I7`)
- Stage-level conversion loss by client and by recruiter (`M9-I8`)
- Channel and recruiter performance (`M9-I9`)
- The monthly MIS pack, generated on a schedule (`M9-I10`)
- Rate agreed against baseline by client, role, specialty and acuity (`M9-I11`)
- The mart layer that makes all of the above possible (`M9-I17`)

### Explicitly out of scope

- Billing — `03-11`. The two workstreams share nothing but the underlying event data and can be staffed
  independently.
- Event capture — `02-11`. This module reads.
- Operational counters inside working screens: parse accuracy, override rates, suggestion quality,
  usage counts. **Removed from the operating screens deliberately** — instrumenting every screen
  separately is a second reporting layer nobody asked for.

### Explicitly not built

- Any client-facing dashboard. Clients see links until Phase 6 and the portal after it.
- Demand forecasting. Not in this contract.
- Comparison, preview and trend views: side-by-side diffs, period-on-period comparison, trend lines.
  Useful, and none of them stops a release.
- Self-service report building. Seven defined reports plus the pack.
- Real-time dashboards. Marts refresh daily.

## 4. Dependencies

**Must exist first:** `02-11` — **and it must have been live since Phase 3**. Plus `03-03`
(`StatusTransition` and `AllocationRecord`, both append-only from day one), `03-07` (overrides),
`03-08` (structured rejection reasons), `03-09` (drop-out reasons and trial outcomes), `03-01` (rate
baselines), `02-03` (close reasons), `02-07`.

**Consumed by:** `03-18` reads performance data for its recruiter suggestions — which is why `03-18`
sits in Phase 6 and not next to `03-03`.

**External:** none.

**Hard dependency:** D28 stage-level loss **by recruiter cannot be produced at all** without the D14
owner and allocation fields in `03-03`.

## 5. Data model

```sql
-- All marts are rebuilt from events.platform_event. None queries an operational table.

CREATE TABLE reporting.mart_requisition_stage (
    requisition_id uuid NOT NULL,
    client_id uuid NOT NULL, location_id uuid NOT NULL,
    candidate_category text NOT NULL, care_setting text NOT NULL, service_line text NOT NULL,
    source_channel text NOT NULL,
    owner_id uuid, owner_name text,
    stage text NOT NULL,
    entered_at timestamptz NOT NULL, exited_at timestamptz,
    duration_seconds bigint,
    held_seconds bigint NOT NULL DEFAULT 0,          -- excluded from aging (M3 AC6)
    close_reason_code text,
    PRIMARY KEY (requisition_id, stage, entered_at)
);

CREATE TABLE reporting.mart_requisition_fill (
    requisition_id uuid PRIMARY KEY,
    client_id uuid NOT NULL, candidate_category text NOT NULL, source_channel text NOT NULL,
    owner_id uuid,
    positions_requested integer NOT NULL, positions_filled integer NOT NULL,
    first_complete_at timestamptz,                   -- time-to-fill measured FROM here
    filled_at timestamptz,
    time_to_fill_seconds bigint,                     -- excluding held time
    completeness_at_intake numeric(4,3),             -- the A1 value case (M9-I9)
    is_closed boolean NOT NULL DEFAULT false, close_reason_code text
);

CREATE TABLE reporting.mart_recruiter_allocation (   -- covers the PERIOD a recruiter held it
    requisition_id uuid NOT NULL,
    recruiter_id uuid NOT NULL, recruiter_name text NOT NULL,
    is_site_resident boolean NOT NULL,                -- comparability needs site attribution (M0-I2)
    allocated_at timestamptz NOT NULL, removed_at timestamptz,
    PRIMARY KEY (requisition_id, recruiter_id, allocated_at)
);

CREATE TABLE reporting.mart_candidate_stage_loss (
    requisition_id uuid NOT NULL, candidate_id uuid NOT NULL,
    client_id uuid NOT NULL, candidate_category text NOT NULL,
    recruiter_id uuid,                                -- from allocation at the time
    stage text NOT NULL,                              -- ranked | shortlisted | client_response
                                                      -- | interview | decision | offer | joined
    outcome text NOT NULL,                            -- progressed | lost
    reason_code text,                                 -- from the structured taxonomy, never free text
    occurred_at timestamptz NOT NULL,
    PRIMARY KEY (requisition_id, candidate_id, stage, occurred_at)
);

CREATE TABLE reporting.mart_trial_survival (
    placement_id uuid PRIMARY KEY,
    client_id uuid NOT NULL, candidate_category text NOT NULL, recruiter_id uuid,
    joining_date date NOT NULL,
    survived_to_day integer,                          -- the full 0→90 curve, not just the endpoint
    outcome text,                                     -- survived | ended
    end_reason_code text,
    retention_basis text,                             -- acknowledged | deemed
    invoice_value numeric(14,2)                       -- revenue at risk
);

CREATE TABLE reporting.mart_channel_performance (
    period_month date NOT NULL, source_channel text NOT NULL,
    client_id uuid, candidate_category text,
    requisitions integer NOT NULL, completeness_avg numeric(4,3),
    placements integer NOT NULL,
    PRIMARY KEY (period_month, source_channel, client_id, candidate_category)
);

CREATE TABLE reporting.mart_rate_variance (
    requisition_id uuid NOT NULL, invoice_line_id uuid,
    client_id uuid NOT NULL, role_code text NOT NULL,
    specialty text, acuity text,                      -- requires the A9 attribute set (M4-I26)
    baseline_rate numeric(14,2), agreed_rate numeric(14,2),
    variance_pct numeric(6,2),
    occurred_at timestamptz NOT NULL,
    PRIMARY KEY (requisition_id, occurred_at)
);

CREATE TABLE reporting.mart_refresh (
    mart text PRIMARY KEY,
    last_event_id uuid, last_refreshed_at timestamptz NOT NULL,
    rows integer, duration_ms integer
);

CREATE TABLE reporting.monthly_pack (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    period_month date NOT NULL UNIQUE,
    composition jsonb NOT NULL,                       -- configurable without a deployment
    document_id uuid,
    state text NOT NULL DEFAULT 'scheduled'
      CHECK (state IN ('scheduled','generating','ready','failed')),
    generated_at timestamptz
);
```

## 6. State machines

### `MonthlyPack`

`scheduled → generating → ready`, or `failed` with a reason. Composition is configurable, so the pack
can change **without a deployment**.

Everything else is derived data with no lifecycle. Marts are rebuilt idempotently from the event log;
a rebuild produces the same numbers.

## 7. API surface

| Method | Path | Permission | Purpose |
|---|---|---|---|
| `GET` | `/v1/reports/funnel?client=&category=&from=&to=` | `report:read` | Requisitions reaching each stage and the drop between |
| `GET` | `/v1/reports/fill?client=&category=&recruiter=&from=&to=` | `report:read` | Fill rate and time-to-fill with **distribution, not only an average** |
| `GET` | `/v1/reports/trial-survival?client=&category=&recruiter=` | `report:read` | The full day 0–90 curve, end reasons, revenue at risk |
| `GET` | `/v1/reports/stage-loss?by=client\|recruiter&from=&to=` | `report:read` | Where candidates are lost, with structured reasons |
| `GET` | `/v1/reports/performance?by=channel\|recruiter&from=&to=` | `report:read` | Placements by channel; requisitions held, fill rate, time-to-fill per recruiter |
| `GET` | `/v1/reports/rate-variance?client=&role=&specialty=&acuity=` | `report:read` | Agreed against baseline |
| `GET`/`POST` | `/v1/reports/monthly-pack` | `report:read` / `report:manage` | Composition and generation |
| `GET` | `/v1/reports/monthly-pack/:period/export` | `report:read` | The document |

Every report endpoint supports the `02-07` export, and every export is audited — a report leaving the
platform carries personal data.

## 8. Events and jobs

**Events emitted:** `reporting.mart.refreshed` · `reporting.monthly_pack.generated`.

**Events subscribed:** the five families in `01-06` §1 — `demand.requisition.*`, `demand.allocation.*`,
`matching.*`, `selection.*`, `placement.*` — plus `billing.invoice.raised` and
`timesheets.timesheet.approved`.

**Jobs**

| Job | Schedule | Purpose |
|---|---|---|
| `reporting.refresh-marts` | daily, and on demand | Incremental from the last processed event id |
| `reporting.rebuild-mart` | on demand | Full replay from the event log — the correctness backstop |
| `reporting.monthly-pack` | monthly | Generates and exports **without manual assembly** |

refresh**, so nobody mistakes a daily mart for live data.
