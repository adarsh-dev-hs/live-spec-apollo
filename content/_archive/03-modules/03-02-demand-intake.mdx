**Package** `@apollo/demand-intake` · **Schema** `demand` · **Plan** A1 · **Effort** ~58.0pd · **Risk** High `SPEC` / `MODEL` · **Build in** Phase 3 · **Release** Parts 2, 3

## 1. Purpose

Clients tell Apollo about vacancies in whatever way suits them — an email, a spreadsheet in their own
format, a WhatsApp message, a WhatsApp voice note, a feed from their own HR system, or by telling a
recruiter who sits in their hospital. This module turns all of them into one standard requisition
payload, scores it against what "complete" means for that candidate category, chases the client **on
the channel they used** for anything missing, and gives a person a queue for everything the machine
could not do.

The shared receive-resolve-classify stack is `02-08`. This module owns the demand half: the parsers,
the completeness rules, the chase, and the four screens where humans intervene.

## 2. Scope

### In scope

- The four operational queues: inbound list, unmatched senders, manual entry, suspected duplicates
- Channel configuration for six channels, one of which is enumerated but not enabled
- Per-client spreadsheet column mapping, set up without a deployment
- Required-field sets per candidate category, which define what "complete" means
- Follow-up configuration: message per channel, window, escalation target
- Parser dispatch and field extraction to the requisition schema (`M3-I20`)
- Completeness scoring and the follow-up chase loop (`M3-I22`)

### Explicitly out of scope

- The receive, sender-resolution, intent-classification and retry stack — `02-08`.
- The `Requisition` record itself, its versions, states and the fulfilment board — `03-03`. This module
  produces the payload; that one owns the object.
- The channel connectors — `04-01` WhatsApp, `04-03` email, `04-05` speech-to-text, `04-07` HRMS.
- Candidate response handling on the same stack — `03-06`.

### Explicitly not built

- **Automatic merging of duplicate requisitions.** A suspected duplicate is shown and a person decides,
  while `OI-M3-02` is open.
- The client portal as a channel — enumerated, not enabled (`AS-05`).
- Bulk reclassification of inbound messages. Nothing in the client documents asks for it.
- Parse-accuracy dashboards inside the operating screens. Measurement lives in `03-12`.
- Prioritisation or approval before a requisition goes live — `03-18`, Phase 6.

## 5. Data model

```sql
CREATE TABLE demand.channel (
    code text PRIMARY KEY,                   -- email | spreadsheet | whatsapp_text | whatsapp_voice
                                             -- | hrms | portal | verbal
    name text NOT NULL,
    is_available boolean NOT NULL,           -- portal: false in Release 1 (AS-05)
    is_enabled boolean NOT NULL DEFAULT false,
    config jsonb NOT NULL DEFAULT '{}'::jsonb,  -- mailbox, WhatsApp number, HRMS settings
    updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL
);
-- portal cannot be enabled while is_available is false
ALTER TABLE demand.channel ADD CONSTRAINT portal_not_enabled
  CHECK (is_available OR NOT is_enabled);

CREATE TABLE demand.spreadsheet_mapping (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    client_id uuid NOT NULL,
    name text NOT NULL,
    column_map jsonb NOT NULL,               -- { "Ward": "department", "Nos.": "positions_requested" }
    sample_document_id uuid,                 -- files.document — the file it was proven against
    is_active boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE demand.required_field_set (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    candidate_category text NOT NULL REFERENCES settings.list_entry(code),
    service_line text NOT NULL,
    fields text[] NOT NULL,                  -- field names that must be present to be 'complete'
    version integer NOT NULL DEFAULT 1,
    is_active boolean NOT NULL DEFAULT true,
    updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL,
    UNIQUE (candidate_category, service_line, version)
);

CREATE TABLE demand.parse_result (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    inbound_record_id uuid NOT NULL,         -- inbound.inbound_record(id)
    parser text NOT NULL,                    -- 'email_text' | 'spreadsheet' | 'whatsapp_text'
                                             -- | 'voice_transcript' | 'hrms_structured'
    row_index integer,                       -- one spreadsheet row → one requisition
    extracted jsonb NOT NULL,                -- fields mapped to the requisition schema
    unmapped jsonb NOT NULL DEFAULT '{}'::jsonb,  -- retained, never discarded (BR6)
    confidence numeric(4,3),
    outcome text NOT NULL CHECK (outcome IN ('parsed','row_failed','failed')),
    error text,
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON demand.parse_result (inbound_record_id, row_index);

CREATE TABLE demand.followup_config (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    channel text NOT NULL REFERENCES demand.channel(code),
    template_code text NOT NULL,             -- messaging.template
    updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL,
    UNIQUE (channel)
);

CREATE TABLE demand.followup_thread (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL,
    channel text NOT NULL,                   -- the channel the requisition ARRIVED on
    missing_fields text[] NOT NULL,
    opened_at timestamptz NOT NULL DEFAULT now(),
    window_days integer NOT NULL,
    window_source text NOT NULL CHECK (window_source IN ('client','platform_default')),
    due_at timestamptz NOT NULL,
    state text NOT NULL DEFAULT 'awaiting' CHECK (state IN ('awaiting','answered','escalated','closed')),
    escalated_to uuid,                       -- identity.user — the requisition owner
    closed_at timestamptz
);

CREATE TABLE demand.duplicate_suspicion (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL,            -- the first
    candidate_requisition_id uuid,           -- the second, if already created
    inbound_record_id uuid NOT NULL,
    match_keys jsonb NOT NULL,               -- configurable, so the confirmed rule drops in
    score numeric(4,3),
    state text NOT NULL DEFAULT 'suspected'
      CHECK (state IN ('suspected','merged','distinct')),
    decided_by uuid, decided_at timestamptz
);
```

## 6. State machines

### `FollowUpThread` (`M3-I22`, `AS-01`)

| From | Event | To | Rule |
|---|---|---|---|
| — | completeness scoring finds missing fields | `awaiting` | Chase issued **on the channel the requisition arrived on** |
| `awaiting` | client replies on that channel | `answered` → `closed` | The reply **merges onto the same requisition**, never creates a second |
| `awaiting` | window expires | `escalated` | **Escalates to the requisition owner; no value is deemed** |
| `escalated` | fields supplied by anyone | `closed` | |
| `awaiting` | one-way channel | `awaiting` | Falls back to the client contact (`AS-02`) |

A requisition at `awaiting_client` past its window **stays visible on the board and does not enter
matching** (`M3-I12` E4).

### `DuplicateSuspicion` (`M3-I4`)

`suspected → merged | distinct`, decided by a person, attributed and timestamped. **No automatic merge
occurs anywhere** while `OI-M3-02` is open — a negative test enforces it.

### `ParseResult`

`parsed` · `row_failed` (that row named, the rest of the file still produces requisitions) ·
`failed` (whole payload to the manual entry queue, payload intact).

## 8. Events and jobs

**Events emitted:** `demand.inbound.parsed` · `demand.requisition.completeness_scored` ·
`demand.followup.issued` · `.answered` · `.escalated` · `demand.duplicate.suspected` · `.decided`.

**Events subscribed:** `inbound.record.classified` (intent `demand`) → parse;
`inbound.record.received` on a follow-up thread → merge onto the existing requisition.

**Jobs**

| Job | Trigger | Purpose |
|---|---|---|
| `demand.parse` | on classification | Selects the parser by channel and content type; **an HRMS payload skips parsing and enters at completeness scoring** |
| `demand.score-completeness` | after parse, and on every revision | Scores against the category's required-field set |
| `demand.issue-followup` | when fields are missing | Sends on the originating channel through `02-09` |
| `demand.followup-escalation` | hourly | Window expiry → escalate to the owner, **never deem a value** |
| `demand.detect-duplicates` | on requisition creation | Configurable match keys; **surfaces, never merges** |
