**Package** `@apollo/identity` · **Schema** `identity` · **Plan** F01, F02, F03, D3 (auth), D12 (auth) · **Effort** ~36.5pd · **Risk** High `SPEC` · **Build in** Phase 1 · portal realm Phase 6 · **Release** Parts 1, 2, 3

## 1. Purpose

How anyone gets into the platform and what they are allowed to reach, for three separate populations —
Apollo staff, candidates and (from Phase 6) client users. The client's deliverable list asks for
"role-based access control" as a phrase but never says how anyone signs in, and requires a requisition
owner drawn from "the Apollo internal user list" without anything creating that list. This component
creates both, plus the permission model every screen in the platform is gated by and the data-scoping
predicate every list query carries.

## 2. Scope

### In scope

- Staff sign-in, sign-out, forgotten password, password reset, session and idle timeout (`M0-I1`)
- Staff user management: create, edit, role assignment, **site assignment**, deactivation, bulk import
  with row-level errors (`M0-I2`)
- The role and permission model, read-only on screen and held in configuration (`M0-I3`)
- Candidate identity: phone + OTP sign-in, rate limiting, number change and account recovery (`M4-I22`)
- Client user identity: invite, account set-up, sign-in, client-admin user management, Apollo-side
  suspension (`M10-I1`, `M10-I2`)
- **Portal data scoping**: every portal request limited to the signed-in user's client and sites,
  failing closed on a new endpoint (`M10-I8`)
- The `Principal` resolution and permission guard used by every route in the platform

### Explicitly out of scope

- Link authorisation. A `link` principal is issued and validated by `02-14`, not here.
- Business configuration of any kind — that is `02-03`.
- Audit storage — this component **writes** audit entries; `02-02` stores them.

### Explicitly not built

- Corporate SSO / identity-provider federation. Pending `X06`; email and password is a small build,
  federation is a different one, and retrofitting after ninety users are live is worse than either.
  The decision must be taken **before** this component is built.
- Self-service staff registration. Users are created by an administrator.
- Client-side login before Phase 6. D12 is deferred and A13 needs no account, so no client credential
  exists in Release 1 at all (`OI-A-04`).
- Multi-factor authentication for staff. Not named anywhere in the client documents; raised as
  `OI-HS-19` rather than assumed in.

## 4. Dependencies

**Must exist first:** nothing. This goes first, with `02-02` (audit) built alongside it — sign-in
events must be audited from the first login.

**Consumed by:** every component. `02-06` renders navigation from permissions. `02-07` applies
`scopeLocationIds` in every list query. `03-03` requires an owner from the active user list (`M3-I16`
V1) and an allocated user holding the recruiter role (V2). `03-12` reports by recruiter using site
attribution (`M9-I9`). `03-14` is unreachable without the `client_user` realm.

**External:** `X06` corporate SSO decision (month 1, changes what is built). `X18` DPAs before any
candidate personal data is handled.

## 5. Data model

```sql
CREATE TABLE identity.user (
    id             uuid PRIMARY KEY DEFAULT uuidv7(),
    email          citext NOT NULL UNIQUE,
    full_name      text NOT NULL,
    password_hash  text,                      -- null once SSO lands (X06)
    status         text NOT NULL DEFAULT 'invited'
                     CHECK (status IN ('invited','active','deactivated')),
    role_version   integer NOT NULL DEFAULT 1, -- bumped on any role change; sessions compare
    last_login_at  timestamptz,
    failed_logins  integer NOT NULL DEFAULT 0,
    locked_until   timestamptz,
    deactivated_at timestamptz,
    created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL
);

CREATE TABLE identity.role (                   -- seeded by migration, not editable on screen
    code        text PRIMARY KEY,              -- platform_admin | fulfilment_lead | recruiter | bd
                                               -- | verification | finance | leadership
    name        text NOT NULL,
    description text NOT NULL
);

CREATE TABLE identity.role_permission (        -- configuration, seeded and versioned by migration
    role_code  text NOT NULL REFERENCES identity.role(code),
    permission text NOT NULL,                  -- '<resource>:<action>'
    PRIMARY KEY (role_code, permission)
);

CREATE TABLE identity.user_role (
    user_id   uuid NOT NULL REFERENCES identity.user(id),
    role_code text NOT NULL REFERENCES identity.role(code),
    PRIMARY KEY (user_id, role_code)
);

CREATE TABLE identity.user_site (              -- distinguishes 15 site-resident from 7 floating
    user_id     uuid NOT NULL REFERENCES identity.user(id),
    location_id uuid NOT NULL,                 -- clients.location(id), FK added in Phase 2
    PRIMARY KEY (user_id, location_id)
);

CREATE TABLE identity.staff_session (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    user_id uuid NOT NULL REFERENCES identity.user(id),
    role_version integer NOT NULL,
    issued_at timestamptz NOT NULL DEFAULT now(),
    last_seen_at timestamptz NOT NULL DEFAULT now(),
    expires_at timestamptz NOT NULL,
    revoked_at timestamptz
);

CREATE TABLE identity.password_reset (
    token_hash text PRIMARY KEY,
    user_id    uuid NOT NULL REFERENCES identity.user(id),
    expires_at timestamptz NOT NULL,
    used_at    timestamptz                     -- single use (M0-I1)
);

-- ── candidate realm ─────────────────────────────────────────────────────────
CREATE TABLE identity.candidate_identity (
    id            uuid PRIMARY KEY DEFAULT uuidv7(),
    candidate_id  uuid UNIQUE,                 -- candidates.candidate(id), set on profile creation
    phone_e164    text NOT NULL UNIQUE,
    phone_changed_at timestamptz,
    status        text NOT NULL DEFAULT 'active' CHECK (status IN ('active','suspended')),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE identity.otp_challenge (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    phone_e164 text NOT NULL,
    code_hash  text NOT NULL,
    attempts   integer NOT NULL DEFAULT 0,
    expires_at timestamptz NOT NULL,
    consumed_at timestamptz,
    delivered_via text CHECK (delivered_via IN ('sms','whatsapp'))
);
CREATE INDEX ON identity.otp_challenge (phone_e164, expires_at DESC);

CREATE TABLE identity.candidate_token (        -- refresh tokens, rotating
    token_hash text PRIMARY KEY,
    candidate_identity_id uuid NOT NULL REFERENCES identity.candidate_identity(id),
    issued_at timestamptz NOT NULL DEFAULT now(),
    expires_at timestamptz NOT NULL,
    rotated_to text, revoked_at timestamptz
);

-- ── client-user realm (Phase 6) ─────────────────────────────────────────────
CREATE TABLE identity.client_user (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    client_id uuid NOT NULL,                   -- clients.client(id)
    email citext NOT NULL,
    full_name text NOT NULL,
    password_hash text,
    status text NOT NULL DEFAULT 'invited'
      CHECK (status IN ('invited','registered','active','suspended')),
    is_client_admin boolean NOT NULL DEFAULT false,
    suspended_by_apollo boolean NOT NULL DEFAULT false,
    invite_token_hash text, invite_expires_at timestamptz,
    created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
    UNIQUE (client_id, email)
);

CREATE TABLE identity.client_user_site (
    client_user_id uuid NOT NULL REFERENCES identity.client_user(id),
    location_id    uuid NOT NULL,
    PRIMARY KEY (client_user_id, location_id)
);

CREATE TABLE identity.portal_session (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    client_user_id uuid NOT NULL REFERENCES identity.client_user(id),
    issued_at timestamptz NOT NULL DEFAULT now(),
    last_seen_at timestamptz NOT NULL DEFAULT now(),
    expires_at timestamptz NOT NULL,
    revoked_at timestamptz,
    ip inet, user_agent text                   -- kept for audit (M10 entity note)
);
```

Indexes: `user(email)`, `user(status)`, `staff_session(user_id, expires_at)`,
`client_user(client_id, status)`, `candidate_identity(phone_e164)`.

## 6. State machines

### `User` (`M0-I2`)

| From | Event | To | Rule |
|---|---|---|---|
| — | administrator creates | `invited` | Role and site assignment permitted immediately |
| `invited` | first successful password set | `active` | |
| `active` | administrator deactivates | `deactivated` | Cannot sign in; **stays visible on records they created** |
| `deactivated` | administrator reactivates | `active` | Same identity, history preserved |

A `deactivated` user cannot be chosen as a requisition owner (`M3-I16` V1) but remains rendered on
historic allocations and audit entries.

### `ClientUser` (`M10-I1`)

| From | Event | To | Rule |
|---|---|---|---|
| — | Apollo or client-admin invites | `invited` | Invite token, expiring |
| `invited` | completes set-up from the invite | `registered` → `active` | An expired invite is **reissued without creating a second account** |
| `active` | client-admin removes, or Apollo suspends | `suspended` | Records they created are not removed |
| `suspended` | reinstated | `active` | |

### `OtpChallenge` (`M4-I22`)

| From | Event | To | Rule |
|---|---|---|---|
| — | code requested | `issued` | Rate-limited per number; resend limited and expiry enforced |
| `issued` | correct code | `consumed` | Single use |
| `issued` | wrong code | `issued` (attempts++) | Locked after N attempts |
| `issued` | expiry | `expired` | |

## 7. API surface

| Method | Path | Realm | Purpose |
|---|---|---|---|
| `POST` | `/v1/auth/staff/login` | public | Email + password → session cookie |
| `POST` | `/v1/auth/staff/logout` | staff | Revoke session |
| `POST` | `/v1/auth/staff/forgot-password` | public | Always 202, never reveals whether the address exists |
| `POST` | `/v1/auth/staff/reset-password` | public | Single-use token + new password |
| `GET` | `/v1/auth/me` | any | Principal, permissions and navigation entitlements |
| `GET` | `/v1/users` | staff `user:read` | List, filter by role/site/status, search by name or email |
| `POST` | `/v1/users` | staff `user:manage` | Create with roles and sites |
| `PATCH` | `/v1/users/:id` | staff `user:manage` | Edit; role change bumps `role_version` |
| `POST` | `/v1/users/:id/deactivate` | staff `user:manage` | |
| `POST` | `/v1/users/import` | staff `user:manage` | Bulk; returns **row-level** outcomes |
| `GET` | `/v1/roles` | staff `role:read` | Read-only role and permission matrix |
| `POST` | `/v1/auth/candidate/otp` | public | Request code; rate-limited per number |
| `POST` | `/v1/auth/candidate/verify` | public | Code → access + refresh token |
| `POST` | `/v1/auth/candidate/refresh` | candidate | Rotate refresh token |
| `POST` | `/v1/auth/candidate/change-phone` | candidate | Recovers the account without a duplicate |
| `POST` | `/v1/auth/portal/login` | public | Client user sign-in |
| `POST` | `/v1/auth/portal/accept-invite` | public | Set password, activate |
| `GET`/`POST`/`DELETE` | `/v1/portal/users` | client_user `portal_user:manage` | Client-admin manages **only their own client's** users |
| `POST` | `/v1/client-users/:id/suspend` | staff `client_user:manage` | Apollo suspends without going through the client |

Errors: `401` wrong realm or no session; `403` authenticated but lacking permission (never reveals
existence); `409` email already used; `422` deactivated user selected as owner; `429` OTP rate limit.

## 8. Events and jobs

**Events emitted**

| Event | When |
|---|---|
| `identity.user.created` / `.role_changed` / `.deactivated` | administrator action |
| `identity.staff.signed_in` / `.sign_in_failed` / `.locked_out` | every attempt (audited too) |
| `identity.candidate.registered` / `.phone_changed` | candidate action |
| `identity.client_user.invited` / `.activated` / `.suspended` | portal lifecycle |

**Subscribed:** none. Identity is a source, not a consumer.

**Jobs**

| Job | Schedule | Purpose |
|---|---|---|
| `identity.expire-sessions` | every 15 min | Reap expired staff and portal sessions |
| `identity.expire-otp` | every 5 min | Reap challenges |
| `identity.send-invite` | on demand | Through `02-09`; candidate OTP goes SMS-first with WhatsApp fallback |

## 10. Acceptance criteria

| # | Criterion | Traces to |
|---|---|---|
| AC1 | A user signs in and reaches the console with the navigation their role permits | `M0-I1` |
| AC2 | A session times out after the configured idle period and returns the user to login **without losing unsaved form state** | `M0-I1`, `M1-I1` |
| AC3 | A password reset link works once and expires | `M0-I1` |
| AC4 | Every login, failed login and lockout is written to the audit trail | `M0-I1` → `M0-I4` |
| AC5 | Candidate logins are completely separate from staff logins — a candidate token on a staff route is a 401 | `M0-I1`, `AS-06` |
| AC6 | A user can be created, assigned a role, and assigned to **one or more sites** | `M0-I2` |
| AC7 | A deactivated user cannot sign in but stays visible on the records they created | `M0-I2` |
| AC8 | A requisition owner can only be chosen from active users | `M0-I2`, `M3-I16` V1 |
| AC9 | An allocated user must hold a recruiter role | `M0-I2`, `M3-I16` V2 |
| AC10 | Site assignment distinguishes the 15 site-resident recruiters from the 7 floating ones | `M0-I2` |
| AC11 | Bulk import reports row-level errors and still loads the valid rows | `M0-I2` |
| AC12 | Removing a permission takes effect on the user's **next request**, not their next login | `M0-I3` |
| AC13 | A user with no role can sign in but reaches nothing, rather than seeing an error on every page | `M0-I3` |
| AC14 | Every permission change is written to the audit trail | `M0-I3` |
| AC15 | The role set covers Apollo internal users across every module, so no module builds its own access rules | `M0-I3` |
| AC16 | OTP delivery works over SMS **and** WhatsApp with a fallback | `M4-I22` |
| AC17 | Rate limiting prevents OTP flooding of a number | `M4-I22` |
| AC18 | A candidate changing their number recovers their account without creating a duplicate | `M4-I22` |
| AC19 | Candidate sessions expire and refresh without forcing frequent re-authentication | `M4-I22` |
| AC20 | A client user completes set-up from an invite and can sign in afterwards | `M10-I1` |
| AC21 | An expired invite can be reissued without creating a second account | `M10-I1` |
| AC22 | A client user cannot reach any Apollo internal screen | `M10-I1` |
| AC23 | A client admin sees and manages **only** users belonging to their own client | `M10-I2` |
| AC24 | Site-level access limits a portal user to their own hospitals | `M10-I2` |
| AC25 | Apollo can suspend a client user without going through the client | `M10-I2` |
| AC26 | Removing a portal user does not remove the records they created | `M10-I2` |
| AC27 | **No portal query returns data belonging to another client, under any parameter** | `M10-I8` |
| AC28 | A user limited to two sites cannot see a third | `M10-I8` |
| AC29 | A new portal endpoint added later **fails closed** if scoping is not applied | `M10-I8` |
| AC30 | Scoping is tested automatically, not by inspection | `M10-I8` |

## 11. Open questions

| Ref | Question | Working assumption | Blocks |
|---|---|---|---|
| `OI-HS-01` | Does a site-resident recruiter see only their own site's data, or the whole base? | `AS-18` — every scoped query takes `scopeLocationIds` from day one; the Release 1 resolver returns all active locations, so behaviour is "sees everything". Closing this changes one resolver, not twenty queries. | Every list in the platform; cheap now, expensive later |
| `X06` | Email and password, or federation to Apollo's identity provider? | Email + password with Argon2id (`AS-19`), with the credential layer isolated behind one interface so federation replaces it without touching sessions or permissions. **Decide before this is built.** | `M0-I1` |
| `OI-A-04` | Does Release 1 provisioning cover Apollo internal users only? | Yes — expected to confirm. No client credential exists before Phase 6. | `M2-D1` scope |
| `OI-HS-19` **[raised here]** | Is MFA required for staff, and for `finance` in particular? | Not built. No client document names it; the finance role can raise invoices, so it is worth a decision rather than an omission. | `M0-I1` |
