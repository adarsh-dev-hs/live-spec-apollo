## 1. Purpose

The shared visual language and the components built from it. There are five surfaces in this plan — Ops
console, candidate app, WhatsApp templates, voice scripts and client link pages. If each is designed
separately the work is done five times and looks like it. First needed for the console shell, which is
the first surface anyone designs, and **it must be complete before screen design is finalised, not
alongside it**.

## 2. Scope

### In scope

- Design tokens: colour, type, spacing, radius, elevation, motion — one set, consumed by web and native
- Web component library on Tailwind + shadcn primitives: buttons, inputs, selects, combo boxes, date
  and time pickers, tables, modals, drawers, tabs, toasts, badges, page layouts
- Native component library sharing the same tokens with native primitives
- **The standard empty, loading, error, no-permission and partial-failure patterns** (`01-03` §3)
- Inline validation and form-error patterns, so screens do not each invent their own
- The accessibility baseline and the tests that hold it
- Content patterns for the two non-visual surfaces: WhatsApp template structure and voice script tone

### Explicitly out of scope

- Screen design. Screens are assembled from these components in each module's §9.
- The console navigation frame — that is `02-06`, built on this.
- Charts. Recharts is used directly in `03-12`, themed by these tokens.

### Explicitly not built

- A public design-system website or Storybook deployment beyond the internal build. Storybook runs
  locally and in CI for visual regression; it is not a deliverable.
- Multiple themes or client white-labelling. One Apollo identity.
- A native design system for the WhatsApp and voice surfaces — those get content patterns, not code.

## 9. Frontend

The component is the deliverable. Grouped by what the plan actually needs:

| Group | Components | Driven by |
|---|---|---|
| Layout | `PageHeader`, `PageSection`, `SplitPane`, `DetailLayout`, `RecordSidebar` | Every record screen: requisition, candidate, placement |
| Data | `DataTable` (used by `02-07`), `KeyValueList`, `Timeline`, `StatCard`, `AgeIndicator` | Fulfilment board, activity trail, aging |
| Input | `FormField`, `TextInput`, `NumberInput`, `Select`, `ComboBox`, `DatePicker`, `TimeRangePicker`, `FileUpload`, `ReasonPicker` | `ReasonPicker` exists because five actions require a structured reason from a configured list |
| Feedback | `EmptyState`, `LoadingSkeleton`, `ErrorState`, `NoPermission`, `PartialFailureSummary`, `Toast`, `ConfirmDialog` | `01-03` §3 — the five states |
| Status | `StatusBadge`, `TrafficLight`, `ConfidenceMeter`, `PendencyChip` | Verification green/amber/red; availability freshness; queue pendency |
| Public | `LinkPageShell`, `SingleQuestion`, `LinkExpired`, `LinkAlreadyAnswered`, `LinkSubmitted` | `02-14` — mobile-first, one question, one action |

Three patterns worth naming because the plan requires them explicitly:

- **`PartialFailureSummary`** — "a spreadsheet with some bad rows reports each bad row by name and
  still loads the good ones" (`M1-I4`). Used by user import, site import, spreadsheet ingestion, bulk
  salary revision and attendance upload.
- **`TrafficLight`** — every verification outcome is green, amber or red on a common schema, whichever
  registry answered (`M1-I13`). One component, so the meaning never drifts.
- **`ReasonPicker`** — reads a list from `02-03`, enforces "reason required" at the component level, so
  close, cancel, reject, override and correction all behave identically.

## 10. Acceptance criteria

| # | Criterion | Traces to |
|---|---|---|
| AC1 | The Ops console, candidate app, WhatsApp templates, voice scripts and client link pages all draw from one set | `M1-I4` |
| AC2 | A new screen can be assembled from existing components rather than designed from scratch | `M1-I4` |
| AC3 | Every state a screen can be in has a defined pattern, so developers are not inventing them | `M1-I4` |
| AC4 | Components meet the agreed accessibility baseline: WCAG 2.2 AA contrast, keyboard operability, visible focus, labelled inputs, live regions, table semantics | `M1-I4`, `01-03` §6 |
| AC5 | **This is complete before screen design is finalised, not alongside it** | `M1-I4` |
| AC6 | The set includes patterns for inline validation, form errors, empty states, permission denied and partial failures | `M1-I4` |
| AC7 | A bulk operation with bad rows names each bad row and still loads the good ones, through one shared component | `M1-I4` |
| AC8 | Web and native share one token set — a colour or spacing change lands on both | `M1-I4` |
| AC9 | Every component has a Storybook entry covering its five states, and visual regression runs in CI | `01-08` |
| AC10 | Link-page components meet the ≤120KB gzipped budget on a 3G connection | `01-03` §9 |
