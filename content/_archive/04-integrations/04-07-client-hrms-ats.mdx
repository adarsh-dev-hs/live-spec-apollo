## 1. Purpose

Some clients push vacancies straight from their own HR or recruitment system rather than emailing them.
A structured payload arrives, **skips parsing entirely**, and enters at completeness scoring.

**Every client system is a separate connector** with its own payload shape, credentials and test data.
"Two clients" and "nine clients" are completely different pieces of work, and **nobody has said which
systems are in scope or how many.**

## 2. Scope

**In scope:** the connector framework — tenant registration, authentication, payload validation against
a declared shape, mapping to the requisition schema, per-tenant request and error logs; and the first
connector once a client system is named.

**Explicitly out of scope:** sender resolution and the inbound record (`02-08`); completeness scoring
and the chase (`03-02`); pushing anything **back** to a client system.

**Explicitly not built:** a generic integration platform; polling a client system; two-way sync;
candidate data exchange with a client ATS.

## 4. Dependencies

**Must exist first:** `02-08`, `03-01` (`SenderIdentity` with `identity_type = 'hrms_tenant'`),
`03-02` (completeness scoring is where these payloads enter).

**Consumed by:** `03-02`, `03-03`.

**External:** `X27` — **two hops, not one.** Apollo asks their client, the client's IT team agrees, and
only then can the work be sized. This blocks the estimate as well as the build.

## 5. Data model

No tables of its own.

```sql
-- 03-01: a tenant is a sender identity like any other
INSERT INTO clients.sender_identity (client_id, identity_type, identity_value)
VALUES (:clientId, 'hrms_tenant', :tenantKey);
```

```ts
interface HrmsConnector {
  tenantKey: string
  payloadSchema: JsonSchema                     // declared per system
  toRequisition(payload: unknown): RequisitionDraft
  verify(headers: Headers, body: Buffer): boolean
}
```

A **new client system whose payload shape is already supported is added as configuration**; a new shape
is a new connector.

## 6. State machines

Within `02-08`'s `InboundRecord`: `received → identified` (tenant resolves to exactly one client) →
**straight to `parsed`, skipping classification and parsing** → `consumed`. A tenant resolving to zero
or more than one client routes to the unmatched queue for manual selection.

## 7. API surface

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `POST` | `/hooks/hrms/:tenant` (via `edge-webhook`) | Per-tenant shared secret or signature | Accepts a structured requisition payload |
| `GET` | `/v1/hrms/tenants` | `settings:read` | Registered tenants and their connectors |
| `GET` | `/v1/hrms/tenants/:key/logs` | `settings:read` | **Request and error logs retrievable per tenant** |

## 8. Events and jobs

`hrms.ingest` on the `interactive` class — the payload is already structured, so there is nothing slow
to do. Events flow through `02-08`.

## 9. Frontend

Tenant registration appears in `03-02`'s channel settings; per-tenant logs are reachable from there.
No screen of its own.
