## 1. Purpose

Where raised invoices, credit notes and open receivables go. **Nobody has said which system it is.**
Part A gives a direct instruction rather than leaving it open: build the invoice object **addressable
by API or file export**, so the target attaches later without reopening the module.

## 2. Scope

**In scope:** a versioned export contract for invoices, lines, credit and debit notes and receivables;
an API endpoint and a scheduled file export against the same contract; export audit; re-export
protection.

**Explicitly out of scope:** invoice generation (`03-11`); payments and reconciliation (`03-20`); being
the book of record — the finance system stays that.

**Explicitly not built:** a connector to any named system; a general ledger; tax filing; posting rules
or chart-of-accounts mapping.

## 5. Data model

No tables of its own; `settings.export_run` (`02-07`) records each export.

```ts
// The versioned contract. Independent of the platform's release train (01-04 §7).
interface FinanceExportV1 {
  invoices: Array<{
    reference: string; type: 'permanent_placement' | 'shift'
    clientRef: string; clientGst: string | null
    contractVersionRef: string
    periodStart?: string; periodEnd?: string
    lines: Array<{ description: string; quantity: number; unitRate: string; amount: string }>
    subtotal: string; tax: string; total: string; currency: 'INR'
    raisedAt: string
    evidenceRef: string           // the billing trigger — what justifies the charge
  }>
  creditNotes: Array<{ reference: string; invoiceRef: string; amount: string; reasonCode: string }>
  receivables: Array<{ invoiceRef: string; amountDue: string; dueDate: string | null }>
}
```

## 6. State machines

`billing.invoice`: `raised → exported`. A **re-export does not duplicate in the target** — the contract
is keyed on `reference` and the export is idempotent by design, because it must be safe to re-run
against an unknown counterparty.

## 7. API surface

| Method | Path | Permission | Purpose |
|---|---|---|---|
| `GET` | `/v1/finance-export?from=&to=&format=json\|csv` | `invoice:export` | Pull, against the versioned contract |
| `POST` | `/v1/finance-export/runs` | `invoice:export` | Produce a file into `02-04`, delivered as an expiring link |
| `GET` | `/v1/finance-export/runs` | `invoice:read` | **Export activity is audited** |

Two routes, one contract. Whichever the eventual system prefers, both already exist.

## 8. Events and jobs

`billing.export` on raise; `finance.scheduled-export` daily if enabled.
Events: `billing.invoice.exported`.

## 9. Frontend

Export controls sit on `03-11`'s invoice list. No screen of its own.
