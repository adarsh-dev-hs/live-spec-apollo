Four client surfaces, one design system. React 19 + TypeScript everywhere; Vite for the three web
apps, Expo for the app.

## 1. Stack

| Concern | Choice | Note |
|---|---|---|
| Build | Vite 6 (web), Expo SDK 52+ (mobile) | |
| Routing | TanStack Router (web), Expo Router (mobile) | Type-safe routes; search params are schema-validated |
| Server state | **TanStack Query** | The only place server data lives. No duplication into a store. |
| Client state | React state, `useReducer`, Context for principal and theme | No Redux. Nothing in this product needs it. |
| Forms | React Hook Form + Zod resolver, schemas from `@apollo/contracts` | One schema validates on the client and the server |
| Styling | Tailwind + shadcn/ui primitives, wrapped in `@apollo/ui` | `02-05` |
| Mobile UI | `@apollo/ui/native` — same tokens, native primitives | Tokens shared, components not |
| Tables | `@apollo/list-engine` (`02-07`) | Around twenty screens are lists. None builds its own. |
| Charts | Recharts, in `03-12` only | |
| Dates | `date-fns` + `date-fns-tz`, display `Asia/Kolkata` | |
| i18n | `@apollo/ui` message catalogue; **English only in Release 1**, but no user-facing string is inlined | Candidate-facing language coverage is a live question in `04-04`/`04-05` |

## 2. Feature folder

```
apps/console/src/features/requisitions/
├── routes/                  # one file per route, thin
├── components/              # presentational, no data fetching
├── hooks/                   # useRequisitionBoard(), useHoldRequisition()
├── api.ts                   # generated client calls, typed from @apollo/contracts
└── index.ts
```

A component either fetches or renders, never both. Data enters through a hook; the component takes
props. This is what makes the empty, loading, error and no-permission states testable in isolation.

## 3. The five states every screen must have

`02-05` ships a pattern for each. A screen missing one is not done — the plan calls this out
explicitly (`M1-I4`: "every state a screen can be in has a defined pattern, so developers are not
inventing them").

| State | Rule |
|---|---|
| **Loading** | Skeleton matching the final layout. No spinner-on-blank-page. |
| **Empty** | Says what would put something here and offers the action that does it. Never a bare "No results". |
| **Error** | What failed, whether to retry, and the correlation id. Never a raw message from the server. |
| **No permission** | The nav entry is not rendered at all; a direct URL shows a permission page (`M0-I3`: "a user with no role can sign in but reaches nothing, rather than seeing an error on every page"). |
| **Partial failure** | A bulk action reports **row-level** outcomes and still applies the good rows (`M0-I2`, `M2-I3`, `M3-I6`, `M12-I4`). Never all-or-nothing. |

## 4. Data fetching

```ts
export function useRequisitionBoard(filter: BoardFilter) {
  return useQuery({
    queryKey: ['requisitions', 'board', filter],
    queryFn: () => api.listRequisitionBoard(filter),
    staleTime: 30_000,
    placeholderData: keepPreviousData,   // filter changes must not blank the board
  })
}

export function useHoldRequisition(requisitionId: string) {
  const qc = useQueryClient()
  return useMutation({
    mutationFn: (body: HoldRequisitionBody) => api.holdRequisition(requisitionId, body),
    onSuccess: () => {
      qc.invalidateQueries({ queryKey: ['requisitions'] })
      toast.success('Requisition held. Aging clock stopped.')
    },
  })
}
```

| Rule | Why |
|---|---|
| Query keys are `[module, resource, params]` | Invalidation by prefix works |
| Filter state lives in the **URL**, not component state | "Switching between modules preserves filter state within a session" (`M1-I1`); a filtered board is also a shareable link |
| No optimistic update on anything that writes an audit entry or a billing trigger | Showing success before the server agreed is the wrong lie on a screen finance depends on |
| Mutations invalidate; they do not hand-patch the cache | Except in the list engine's own row-level edit |
| A 403 renders the permission state; it never redirects to login | Only a 401 redirects |

## 5. Forms

- Zod schema from `@apollo/contracts` — the same object the API validates against.
- Validate on blur, re-validate on change once a field has errored. Never validate on every keystroke
  from empty.
- Server field errors map back onto the form by field name (`ValidationError.errors[].field`).
- **Unsaved-work rule**: session expiry must not lose unsaved form state (`M1-I1`). Draft state for
  long forms (requisition, contract, offer, candidate profile) is written to `sessionStorage` on
  change and restored after re-authentication.
- Destructive and irreversible actions confirm with the consequence stated: "Closing this requisition
  cannot be undone and requires a reason."

## 6. Accessibility baseline

Non-negotiable, and part of `02-05`'s acceptance criteria.

- WCAG 2.2 AA contrast on both themes.
- Every interactive element is reachable and operable by keyboard; visible focus ring.
- Every input has a programmatic label; errors are associated by `aria-describedby`.
- Live regions announce async results (save, bulk outcome, delivery status).
- Tables use real `<table>` semantics with a caption and scoped headers.
- Touch targets ≥ 44px on the app and the link pages.

## 7. Public link pages (`apps/links`, `02-14`)

These are opened from WhatsApp on a phone by a hospital contact who has never seen the product.

| Rule | Why |
|---|---|
| Mobile-first, single column, no navigation | It arrives as a link in a chat |
| **One question, one action** on the day-90 page | `M7-I11` states it explicitly |
| No login, no account, no cookie beyond the token session | `A13` |
| Expired / already-answered / revoked links render a **clear state**, never an error page | `M7-I10` |
| Bundle budget ≤ 120KB gzipped; usable on 3G | The recipient is on a hospital corridor connection |
| No third-party script, no analytics tag | The page carries candidate and placement data |

## 8. Candidate app (`apps/mobile`, `03-05`)

| Rule | Why |
|---|---|
| **Offline-first for check-in only.** Check-in and check-out queue locally and sync with the **original timestamp preserved** | `M4-I7`, `M8-I14`. Nothing else needs offline. |
| Sync is idempotent — a retried sync must not create a second attendance record | `M8-I14` |
| Sessions are long-lived with silent refresh | A low-engagement base must not be forced to re-authenticate (`M4-I22`) |
| Guided multi-step flows live **in the app**, never in WhatsApp | Plan convention (`M11-I4`) |
| Every screen states what is still missing rather than a percentage | `M4-I2`: completeness is expressed against what ranking actually needs |
| Native permission prompts (location, notifications) are asked in context with the reason, never at launch | Denial rate directly threatens the attendance chain |
| OTA updates for JS-only changes; EAS build for native changes | Store review is calendar risk (`04-12`) |

recorded against `OI-M3-14`, not treated as agreed.
