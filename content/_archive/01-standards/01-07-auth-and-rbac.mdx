**Package** `@apollo/identity` · **Schema** `identity` · **Plan** F01, F02, F03, D11, D12, A13 · **Effort** — · **Risk** High `SPEC` · **Build in** Phase 1 · **Release** Parts 1–3

Four principal kinds, one permission model, deny by default. `02-01` implements this; every other
component obeys it.

## 1. Realms

| Realm | Who | Credential | Built in | Never |
|---|---|---|---|---|
| `staff` | Apollo internal users | Email + password, sliding idle session (SSO pending `X06`) | Phase 1 | reaches a candidate or portal-only route |
| `candidate` | Healthcare professionals | Phone + OTP, long-lived refresh | Phase 2 | reaches any Ops route |
| `client_user` | Client portal users | Email + password, separate cookie and signing key | Phase 6 | reaches any Apollo internal screen (`M10-I1`) |
| `link` | A client contact holding a token | Opaque single-purpose token | Phase 4 | reaches more than one record or more than one action |

**Candidate identity is entirely separate from the Apollo internal user model** (`AS-06`, `M4-I22`),
and client identity is separate again. Three tables, three session mechanisms, three cookie/token
namespaces. A token from one realm presented to another is a **401**, never a 403.

## 2. Principal

```ts
type Principal =
  | { realm: 'staff';       userId: string; roles: RoleCode[]; siteIds: string[]; permissions: Set<Permission> }
  | { realm: 'candidate';   candidateId: string }
  | { realm: 'client_user'; clientUserId: string; clientId: string; siteIds: string[]; permissions: Set<Permission> }
  | { realm: 'link';        linkId: string; linkType: LinkType; recipientId: string; clientId: string;
                            subjectType: 'shortlist'|'placement'|'timesheet'; subjectId: string }
```

Resolved once in a `preHandler`. No handler re-reads a cookie or a token.

## 3. Permissions

Permission is `<resource>:<action>` — `requisition:hold`, `invoice:raise`, `candidate:merge`,
`settings:edit`, `link:issue`. Roles are **sets of permissions held in configuration**, not editable
on screen (`M0-I3`: the role list is read-only, and the permission set is configuration).

### Release 1 staff roles

| Role | Holds |
|---|---|
| `platform_admin` | Everything in `settings:*`, `channel:*`, `template:*`, `weights:*`, `adapter:*`, `user:*`, plus read everywhere |
| `fulfilment_lead` | Requisition, allocation, shortlist, interview, trial, timesheet — full; candidate read/write; reporting read |
| `recruiter` | Requisition read/write, allocation read, search, shortlist build, interview, selection decision |
| `bd` | Client, contract, rate card, client contact, link recipient — full; requisition create; reporting read |
| `verification` | Candidate, credential, verification case, document review — full; requisition read |
| `finance` | Invoice, receivable, billing evidence, timesheet, contract, placement — **read** and finance actions; **no recruiter permissions** (`M7-I13`, `M8-I2`) |
| `leadership` | Reporting read across everything, no write |
| *(none)* | Signs in, reaches nothing — a defined state, not an error on every page (`M0-I3`) |

A role change takes effect on the user's **next request**, not their next login (`M0-I3`). Sessions
carry a version stamp compared against the role set on every request.

## 4. Data scope — the unresolved one

> Does a site-resident recruiter see only their own site's requisitions and candidates, or the whole
> base? — **`OI-HS-01`**, open, and it touches every list in the platform.

Row-level scoping is a different build from screen-level permissions and is expensive to retrofit. The
position taken so the work is not blocked:

> **`AS-18`** — Every scoped query takes a `scopeLocationIds` predicate from the principal from day
> one. In Release 1 the resolver returns **all active locations** for every staff role, so behaviour is
> "sees everything" as today. Closing `OI-HS-01` in favour of site scoping changes one resolver, not
> twenty queries.

```ts
// every list repository, without exception
WHERE r.location_id = ANY(${principal.scopeLocationIds})
```

The predicate is **not optional and not a filter parameter**. A caller cannot widen it. A new list
endpoint without it fails the scope test suite, which asserts every `GET` collection route rejects a
cross-scope id.

| Realm | Scope |
|---|---|
| `staff` | `scopeLocationIds` per `AS-18` above |
| `candidate` | Their own records only, enforced by `candidate_id = principal.candidateId` |
| `client_user` | **`client_id = principal.clientId` AND `location_id = ANY(siteIds)`** — hard, tested automatically, fails closed on a new endpoint (`M10-I8`) |
| `link` | Exactly `subjectId`, exactly the one action the type allows |

## 5. Link authorisation (`02-14`)

| Rule | Plan ref |
|---|---|
| Tokens are unguessable (≥128 bits of entropy), stored hashed, single-purpose and expiring | `M7-I17` |
| Reissue invalidates the previous token | `M7-I13` |
| A link answer is timestamped **against an identified recipient** | `M7-I17`, and the invoice is not defensible without it (`OI-A-12`) |
| Only `day_90_retention` may carry `is_billing_trigger`; the flag is **not editable** on `day_30`/`day_60` | `M7-I8` |
| A second submission on a re-opened link returns the original answer and does not create a second response | `M7-I18` |
| Expiry without response → `deemed` **only** for `day_90_retention` and `timesheet_approval`, only after the per-client window with a platform default fallback | `M7-I17`, `OI-A-05` |

## 6. Session and credential rules

| Rule | Value | Source |
|---|---|---|
| Staff idle timeout | configurable in `02-03`; default 30 min | `M0-I1` |
| Password reset link | single use, expires | `M0-I1` |
| Password hashing | Argon2id | `AS-19` |
| Failed-login lockout | progressive, and **every login, failed login and lockout is audited** | `M0-I1` |
| Candidate OTP | 6 digits, short expiry, rate-limited per number, delivered over **SMS with WhatsApp fallback** | `M4-I22` |
| Candidate re-auth | long refresh — a low-engagement base must not be forced to sign in often | `M4-I22` |
| Number change | recovers the account without creating a duplicate | `M4-I22` |
| Client portal invite | expired invite is reissuable **without creating a second account** | `M10-I1` |
| Apollo can suspend a client user | without going through the client | `M10-I2` |

## 7. What is audited, always

Every one of these writes an `AuditEntry` (`02-02`) with actor, timestamp, before and after:

sign-in · failed sign-in · lockout · permission change · role assignment · user activation and
deactivation · every requisition status change · allocation · every selection decision with its
structured reason · every recruiter rank override with its reason · link issue, open, answer and deem ·
manual verification override · document accept/reject · attendance time correction · timesheet
correction after approval · invoice raise · export of an invoice or a report · credit and debit note ·
salary revision, advance and hold · payroll cycle lock and reopen · adapter configuration change ·
setting change.

## 8. Provisioning scope in Release 1

D1 includes "user provisioning with role-based access". Since D12 is deferred and A13 needs no login,
**Release 1 provisioning covers Apollo internal users only** (`OI-A-04`, expected to confirm). Client
identity arrives in Phase 6 with `03-14`. Until then no client-side credential exists anywhere in the
system, which is also why the link mechanism carries the entire client relationship.
