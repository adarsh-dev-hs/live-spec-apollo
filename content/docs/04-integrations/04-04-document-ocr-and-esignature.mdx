## 1. Purpose

Two unrelated capabilities from the same open item.

| Capability | Purpose |
|---|---|
| **Document OCR** | Read registration certificates and ID documents **so the verification team is not retyping them** |
| **Electronic signature** | Get offers signed |

> Three separate suppliers are needed and **neither client document names any of them.** — `OI-HS-07`
> (the third is the WhatsApp BSP, in `04-02`)

Both are Medium risk rather than High: the APIs in this space are well-trodden and largely
interchangeable, so the cost of a late choice is bounded. Neither blocks a module from being built,
tested or demoed.

## 2. Document OCR

### 2.1 What it reads

| Document | Extracted |
|---|---|
| Nursing registration certificate | Registration number, name, council, issue date, valid-to |
| Medical registration (NMC / state) | Registration number, name, council, qualification, dates |
| Allied health / pharmacy registration | Registration number, name, council, discipline |
| Aadhaar | Name, DOB, address — **C3, encrypted, never logged** |
| PAN | Number, name, DOB — **C3** |
| Degree / diploma certificate | Institution, qualification, year |
| Experience letter | Employer, role, dates |
| **CV** | Full profile extraction → `03-05 §7.2` |

### 2.2 Port

```ts
export const DocumentOcrPort = definePort({
  key: 'document_ocr',
  operations: {
    extract: {
      input: z.object({
        documentUrl: z.string(),            // presigned, short expiry
        documentType: documentTypeEnum,     // guides the extraction schema
        contentType: z.string(),
      }),
      output: z.object({
        fields: z.record(z.unknown()),
        confidence: z.record(z.number()),   // PER FIELD — not one overall score
        rawText: z.string().optional(),
        pageCount: z.number(),
        cost: z.object({ amount: z.number(), currency: z.string() }).optional(),
      }),
      redact: ['documentUrl'],
      timeout: 60_000,
      retryable: true,
    },
  },
  manualFallback: {
    supported: true,
    createTask: (input) => ({ kind: 'manual_data_entry', payload: input }),
  },
})
```

**Per-field confidence is a hard requirement, not a nice-to-have.** Both consumers depend on it:

- `03-06 §9.4` flags low-confidence fields for the reviewer, so attention goes where it is needed
- `03-05 §7.2` / `03-07 §9.2` shows the candidate which parsed fields to check

A supplier that returns only a document-level score makes both screens meaningfully worse. It is a
selection criterion.

### 2.3 Behaviour

| Rule | |
|---|---|
| **Never write extracted values silently** | A person confirms — the verification team (`03-06 §9.4`) or the candidate (`03-07 §9.2`) |
| `extracted` and `corrected` stored separately | Makes OCR accuracy measurable over time (`03-06 §5.3`) |
| Failure → manual entry | The verification team types it in; the document is already stored |
| C3 fields encrypted on write, never logged | Aadhaar and PAN numbers (`01-10 §5`) |
| Triggered by `platform.document.available` | Not by polling — the file must pass its virus scan first |

### 2.4 Cost

**Per page.** Drivers: new candidates × documents per candidate. Recorded on `adapter_call`.

## 3. Electronic signature

### 3.1 What it signs

Offers, and only offers, in Release 1. `03-17`'s statutory forms are captured as uploaded signed
documents (`AS-51`); if Apollo requires e-signature there, it reuses this port.

### 3.2 Port

```ts
export const ESignaturePort = definePort({
  key: 'esignature',
  operations: {
    createEnvelope: {
      input: z.object({
        documentUrl: z.string(),
        documentName: z.string(),
        signer: z.object({ name: z.string(), email: z.string().optional(), phone: z.string().optional() }),
        callbackUrl: z.string(),
        expiresInDays: z.number(),
      }),
      output: z.object({ envelopeId: z.string(), signingUrl: z.string(), expiresAt: z.string() }),
      redact: ['signer'],
      timeout: 30_000,
      retryable: true,
    },
    getStatus: {
      input: z.object({ envelopeId: z.string() }),
      output: z.object({
        status: z.enum(['sent','viewed','signed','declined','expired']),
        signedAt: z.string().optional(),
        signedDocumentUrl: z.string().optional(),
        auditTrailUrl: z.string().optional(),
      }),
    },
    cancel: { input: z.object({ envelopeId: z.string() }), output: z.object({ cancelled: z.boolean() }) },
  },
  manualFallback: {
    supported: true,
    createTask: () => ({ kind: 'manual_signature' }),   // print, sign, scan, upload
  },
})
```

### 3.3 Flow

```
03-10: offer generated → PDF stored via 02-04
   → createEnvelope → signingUrl
   → delivered over WhatsApp (04-02 template 'offer_delivery'), email fallback
   → candidate signs on their phone
   → POST /api/v1/webhooks/esignature
        → signature verified before parsing, raw persisted, 200 fast
        → signed document downloaded and stored via 02-04
        → offer → 'signed'
        → mapped to contract (M7-I16)
        → emits select.offer.signed → 03-11 can confirm joining
```

**The manual fallback matters more here than it looks.** Until a supplier is chosen, offers are sent
and signature is recorded manually by uploading a signed scan. The offer flow is complete and usable
without the integration — which is what keeps `03-10` unblocked.

### 3.4 Selection criteria

| Criterion | Why |
|---|---|
| **Aadhaar eSign / IndiaStack support** | Legally strongest option in India; some suppliers offer it, some do not |
| **Data residency** | Signed offers are personal data (`01-10 §3`) |
| **Mobile-first signing** | Candidates sign on a phone, over mobile data, often on a mid-range Android |
| **Audit trail** | The signing certificate is what makes the document defensible |
| Per-envelope pricing | Drives the cost model |
| Webhook reliability | |
| Sandbox | |

## 4. Acceptance criteria

| # | Criterion |
|---|---|
| 1 | OCR returns **per-field** confidence, not one document score |
| 2 | Extracted values are **never written without human confirmation** |
| 3 | Extractions and corrections are stored separately, so accuracy is measurable |
| 4 | OCR failure routes to manual entry; the document is already stored and viewable |
| 5 | C3 fields from OCR are encrypted on write and never logged |
| 6 | Extraction is triggered by `platform.document.available` — **after** the virus scan |
| 7 | An offer is signable on a phone from a WhatsApp link |
| 8 | The signed document and its audit trail are stored via `02-04` |
| 9 | A signed offer is mapped to the contract version M9 will read at day 90 |
| 10 | **Signature can be recorded manually by uploading a scan**, with no supplier |
| 11 | Envelope expiry aligns with the offer expiry set in `03-10` |
| 12 | Both fakes simulate success, timeout, malformed response, low confidence, decline and expiry |

## 6. Notes for the implementer

**OCR is an assistant, not an authority.** Every extracted value passes through a human — the
verification team for credentials, the candidate for a CV. The value of the integration is that
nobody retypes a registration number, not that nobody checks it. Build the review screens as the
primary experience and the extraction as an accelerator.

**Measure accuracy from day one.** Storing `extracted` and `corrected` separately costs one column
and turns "is the OCR any good" from an argument into a query. It is also what justifies or
challenges the per-page spend.

**Keep the manual signature path permanently.** Even with a supplier, some offers will be signed on
paper — a candidate without a smartphone, a provider outage, a document the platform did not
generate. Recording a signature by uploading a scan is not a fallback for the pre-supplier period; it
is a permanent path.
