**Package** `@apollo/integration-registries` · **Schema** `adapters` · **Plan** A12, D4, D16 · **Effort** ~19.0pd · **Risk** High `EXT` · **Build in** Phase 1–2 · **Release** Parts 1, 2

## 1. Purpose

The outside systems that say whether a healthcare professional is who they claim to be and holds the
registration they claim: the nursing councils via INC/NUID and NRTS, the NMC and state medical councils,
the allied health councils, the Pharmacy Council — and, through **one aggregator**, Aadhaar via
DigiLocker, PAN, EPFO and court checks.

**Several registries have no API at all** and resolve to document plus manual verification behind the
same interface. Aggregator-first is settled; **which aggregator is not.**

## 2. Scope

**In scope:** the India adapter implementations behind `02-13`'s three interfaces; the aggregator client
covering four check types; the manual-verification implementation that satisfies the same interface;
per-check cost recording; registry health and error-rate reporting.

**Explicitly out of scope:** the interface definitions and registry configuration (`02-13`); deciding
which checks a candidate needs (`03-04`); consent (`02-12`, asserted before every dispatch); document
OCR (`04-10`).

**Explicitly not built:** adapters for the US, Germany and Ireland; direct Aadhaar, PAN, EPFO or court
integrations; **any registry write** — the platform reads and records, it never registers anyone.

## 4. Dependencies

**Must exist first:** `02-13` (the interfaces and configuration), `02-12` (**consent before any
dispatch**), `02-10`, `02-04` (documents for the manual path).

**Consumed by:** `03-04` — **without this, no candidate can be verified at all.**

build**), `X15` DigiLocker and Aadhaar access (regulated; the consent framework is not a technical
detail), `X16` council and registry access (**which councils have no API, and who does the manual
checking**).

## 5. Data model

`adapters.registry` and `adapters.adapter_call` (`02-13`). One adapter module per registry:

```
integrations/registries/src/
├── india/
│   ├── inc-nuid.ts            # nurse registration → NRTS
│   ├── nmc.ts                 # doctors, national
│   ├── state-medical/*.ts     # doctors, per state council
│   ├── allied-health.ts       # several with no API → manual
│   ├── pharmacy-council.ts
│   └── manual.ts              # the document-plus-person implementation
├── aggregator/
│   ├── idfy.ts                # ─┐ one of these is chosen (OI-HS-06);
│   ├── authbridge.ts          # ─┘ the mapping to the common schema is isolated per file
│   └── index.ts
└── contract-tests/            # every adapter runs the same suite
```

**Every adapter returns the same traffic-light outcome**, including the manual ones. A caller cannot
tell from the type whether a council had an API.

## 6. State machines

`adapters.adapter_call` (`02-13`): `requested → responded(green|amber|red)`, or
`retrying → manual_fallback → responded(source: 'manual')`. **A disabled or API-less registry routes to
manual rather than failing the candidate.**

## 7. API surface

In-process through `02-13`'s `adapters.dispatch()` only. Aggregator callbacks arrive at
`POST /hooks/verification/:provider` via `edge-webhook` for asynchronous check types.

## 8. Events and jobs

`adapters.check` and `adapters.poll-async` (`provider` class, `02-13`). Per-check cost recorded on every
call. `adapters.health-sweep` surfaces a registry outage as a **spike in awaiting-registry pendency** in
`03-04`.

## 9. Frontend

**N/A** — registry configuration and health are `02-13`; the verification queue, detail and manual
outcome entry are `03-04`.
