## 1. Two systems at the end of two chains

| | Payroll engine | Finance system |
|---|---|---|
| Chain | Attendance → timesheet → **pay** | Placement/timesheet → invoice → **receivable** |
| Direction | We send inputs, receive results | We push invoices out |
| Supplier | Hirecraft or PayBooks — **unconfirmed** | **Not named** |
| Module | `03-19` | `03-13`, `03-21` |

Neither is a system of record for us. **We do not calculate pay, and we are not the accounting book
of record.** Both integrations are about handing correct data to a system that owns that domain.

## 2. Payroll engine

### 2.1 What we send and what we get back

> **We do not build a payroll calculator** — Hirecraft and PayBooks are the candidate engines.
> — `M13-I5`

| We send | We receive |
|---|---|
| Employee code, worked minutes, overtime minutes, leave days | Gross pay |
| Base salary and any approved revision | Deductions: PF, ESIC, TDS, advance recovery, other |
| Advance recovery due this cycle | Net pay |
| Hold flag | Employer PF and ESIC contributions |
| Adjustments | The payslip document |
| | **Rejections, with reasons** |

### 2.2 Port

```ts
export const PayrollEnginePort = definePort({
  key: 'payroll_engine',
  operations: {
    submitCycle: {
      input: z.object({
        cycleReference: z.string(),
        periodStart: z.string(), periodEnd: z.string(), payDate: z.string(),
        employees: z.array(z.object({
          employeeCode: z.string(),
          workedMinutes: z.number(),
          overtimeMinutes: z.number(),
          leaveDays: z.number(),
          baseSalary: z.string(),              // decimal as string — never a float
          advanceRecovery: z.string(),
          isHeld: z.boolean(),
          adjustments: z.array(z.object({ code: z.string(), amount: z.string() })),
        })),
      }),
      output: z.object({ engineReference: z.string(), acceptedCount: z.number(),
                         rejected: z.array(z.object({ employeeCode: z.string(), reason: z.string() })) }),
      timeout: 120_000,
      retryable: false,                        // A RETRIED PAY RUN PAYS PEOPLE TWICE
    },
    fetchResults: { /* → gross, deductions, net, employer contributions, payslip refs */ },
    fetchPayslip: { /* → the payslip document for one employee */ },
  },
  manualFallback: {
    supported: true,
    createTask: () => ({ kind: 'manual_payroll_file' }),   // export a file, upload the results
  },
})
```

**`retryable: false` is the most important line in this document.** An automatically retried
submission pays people twice. `03-19`'s job configuration reinforces it: concurrency 1, distributed
lock, no auto-retry, alarm on failure, a human decides (`01-06 §6`).

### 2.3 Field mapping is configuration

`M13-I2`: *"Maps the platform's fields to the payroll engine's fields."* and *"Input mapping can
change when the engine changes, **without touching the platform**."*

The mapping lives in P03 (`bill.payroll.field_mapping`), so switching from Hirecraft to PayBooks — or
absorbing a schema change from either — is a settings change plus an adapter, not a module rewrite.

### 2.4 Reconciliation

`M13-I5`: **"Every person sent is accounted for in the results, or reported as an exception."**

Sent 412, received 409 → the three missing are an exception report, not a discrepancy to investigate
later. This check is what catches an engine silently dropping records, and it runs before the cycle
can close.

### 2.5 Statutory reports

`M13-I3` — PF ECR, ESIC return, and the challans. Produced from the engine's results, reconciling to
the pay run they came from.

**Filing is explicitly not in scope.** We generate; someone else files. Say so on the screen.

### 2.6 Selection criteria

| Criterion | Why |
|---|---|
| **API vs file-based** | A file-based engine is a materially different integration; both are supportable through the port, but the estimate differs |
| **Statutory report generation** | If the engine produces PF ECR and ESIC returns, `M13-I3` becomes retrieval rather than construction |
| **Payslip generation** | Same — do they produce the PDF, or do we? |
| Per-employee-per-cycle pricing | Cost model |
| Rejection detail | A rejection reason of "invalid data" is unusable; per-field detail is what makes `M13-I1`'s correct-and-resend work |
| Sandbox with realistic statutory calculation | |
| **Data residency** | Salary and bank data (`01-10 §3`) |

## 3. Finance system

### 3.1 The instruction

> The chain ends at invoice raised and receivable recorded. **The finance system invoices post to has
> not been named; Apollo will confirm. Regardless of the answer, build the invoice object addressable
> by API or file export so the target system attaches later without reopening the module.**
> — `OI-A-14` / M9 module note

So the design is settled even though the supplier is not: **build both routes, now.**

### 3.2 Port

```ts
export const FinanceExportPort = definePort({
  key: 'finance_export',
  operations: {
    pushInvoice: {
      input: InvoiceExportSchema,              // the stable, documented shape
      output: z.object({ externalReference: z.string(), status: z.string() }),
      timeout: 30_000,
      retryable: true,                          // idempotent on invoice reference
    },
    pushCreditNote: { input: CreditNoteExportSchema, output: /* ... */ },
    fetchPaymentStatus: { input: z.object({ externalReference: z.string() }),
                          output: z.object({ status: z.string(), paidAmount: z.string() }) },
  },
  manualFallback: { supported: true, createTask: () => ({ kind: 'manual_invoice_export' }) },
})
```

### 3.3 Three routes, all built

| Route | Detail |
|---|---|
| **API** | `GET /api/v1/invoices/:id/export` — a stable, versioned, documented JSON shape |
| **File** | Scheduled CSV/XLSX per period to S3, or an SFTP drop once a target is named |
| **Push** | Webhook to a configured endpoint, behind the port |

`pushInvoice` is **idempotent on the invoice reference**, which is what makes it safely retryable —
unlike payroll.

### 3.4 The export shape is a contract

Whatever system is eventually named will consume this shape. It carries everything a finance system
needs to post the entry **and everything anyone needs to understand it**:

```
invoice reference, type, date, due date, client (name, GSTIN, billing address),
lines (description, quantity, unit, rate, amount, tax rate, tax amount),
subtotal, tax, total, currency, place of supply,
contract reference and version, billing trigger reference,
placement or timesheet reference, and — for a placement fee —
the retention record reference and whether it was a deemed confirmation.
```

That last element matters: an invoice whose evidence was a deemed confirmation is a different
commercial conversation, and the finance system should be able to see it without asking us
(`03-13 §5.1`).

Credit and debit notes (`03-21`) export alongside invoices, referencing the invoice they correct.

## 6. Notes for the implementer

**Payroll is the one integration where "fail and wait" is unambiguously correct.** No retries, one
at a time, locked, alarm on failure, human decides. Every instinct that makes a resilient integration
elsewhere — retry, backoff, self-healing — pays someone twice here.

**Build the finance export before a system is named, and treat the shape as a published contract.**
It is one of the few pieces of this platform whose consumer is genuinely outside our control, and
whose release cycle is not ours (`01-04 §14`). Version it, document it in `M1-I6`, and do not break
it casually.

**Decimal strings across both boundaries.** Money crosses these two integrations in both directions.
A JSON number is a double, and a double is not a rupee. Send `"45000.00"`, parse to `decimal`,
never to `Number`.

**Escalate payroll engine selection in week one.** It is 11pd, it is XXL, it is Low confidence, it
sits behind `03-17`, `03-18` and `03-21`, and it is the last module in the plan. Every week of delay
in naming it lands directly on the most exposed item in the six months.
