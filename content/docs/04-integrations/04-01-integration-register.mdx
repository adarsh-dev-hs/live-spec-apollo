## 2. What "not named" means for the build

It does **not** mean blocked. It means:

| | |
|---|---|
| The **port** is designed and built | From what we need, not from a supplier's API |
| A **fake adapter** implements it, including failures | Timeout, 500, malformed, rate limit, and the manual fallback |
| The **module is complete, tested and demoable** | Against the fake |
| The **real adapter** is bounded, separately-estimated work | Once the supplier is named |
| The **cost** is unmodellable until then | Which is a commercial exposure, not a build one |

What it does block is **pricing**. Five of the seven estimate-blocking open items are supplier or
count questions (`05-03`).

## 3. Cost drivers — the question Apollo asked

> Part B asks us for message and API volumes per requisition across WhatsApp, email and transcription,
> so running costs can be modelled. WhatsApp is billed per conversation and **the contact schedule
> drives the volume**, so this cannot be answered until the M5 cadence design settles (`OI-HS-05`).
> Payroll and voice add further per-unit costs.

**The platform is built to answer it.** Cost is recorded per message (`02-07 §5`), per adapter call
(`02-12 §5.2`) and per voice call (`03-08 §5.4`), from the first one sent. The consumption report
(`02-07 §9`) and the cadence preview (`03-08 §9.3`) turn that into a per-scenario model.

**None of that can be backfilled.** If the first three months of messages carry no cost data, those
months are unanswerable. This is why cost recording is a phase-3 requirement rather than a phase-7
report.

| Cost | Unit | Driven by |
|---|---|---|
| WhatsApp | Per conversation | Cadence frequency × base size × channel mix |
| SMS | Per segment | Fallback volume |
| Speech-to-text | Per minute | How many clients send voice notes |
| Intent classification | Per inbound | Total inbound volume |
| Outbound voice | Per minute + inference | Escalation rate × base size |
| Verification | Per check | New candidates × checks per category |
| OCR | Per page | Documents uploaded |
| E-signature | Per envelope | Offers made |
| Payroll | Per employee per cycle | Associate headcount |

## 4. Common integration rules

Every integration, without exception, follows these. They are not per-supplier decisions.

| Rule | Where |
|---|---|
| Behind a port owned by us | `02-12 §7.1` |
| A fake adapter implementing **success and every failure mode** | `01-08 §5` |
| Every call logged: request, response, latency, outcome, cost | `02-12 §5.2` |
| Sensitive fields redacted from the log per the port's rules | `01-02 §12` |
| Credentials in Secrets Manager, referenced by ARN — **never in the database** | `01-07 §10` |
| Timeout, retry with backoff, circuit breaker shared across tasks | `02-12 §8` |
| **A defined manual fallback**, where one is possible | `02-12 §7.1` |
| Webhooks: verify signature **before parsing**, dedupe, **persist raw**, return fast | `01-04 §12` |
| A runbook for its failure modes | `01-09 §13` |
| **Data residency assessed before selection** | `01-10 §3` |

That last one is a supplier-selection criterion, not an engineering control. A voice or OCR provider
that processes Indian personal data outside India breaks the DPDP position the day it is chosen.

## 5. Failure modes and what the platform does

| System | Failure | Behaviour |
|---|---|---|
| WhatsApp | Provider down | Messages queue and retry; template fallback to SMS where configured; **inbound is lost — the provider retries to us** |
| WhatsApp | Template not approved | Send blocked with a clear error; the template screen shows approval status (`03-08 §5.1`) |
| Email inbound | SES/Lambda failure | Mail stays in S3; reprocessed on recovery |
| Speech-to-text | Down or low confidence | Voice note lands in the **manual entry queue** with the audio playable (`03-03 §9.5`) |
| Classification | Below threshold | Human classification queue (`02-08 §9`) |
| HRMS feed | Client sends malformed payload | Raw payload persisted, unmatched/unparseable queue, client notified |
| Voice provider | Down | Cadence continues on other channels; escalation deferred |
| Verification registry | No API at all | **Manual fallback — document plus a person, behind the same interface** |
| Verification aggregator | Down | Cases sit `awaiting_registry`, retried every 4h, visible in the queue with pendency |
| OCR | Down | Document uploads succeed; extraction queued; manual entry available |
| E-signature | Down | Offer sent; signature recorded manually with the signed document uploaded |
| Finance system | Not named / down | Invoices raise regardless; export queued; **API and file both available** |
| Payroll engine | Rejects records | Exception report; correct and resend; **cycle does not close** |
| Payroll engine | Down | Cycle stays `inputs_locked`; **no auto-retry** |
| Virus scanner | Down | File stays **unavailable** — a failed scan is never treated as clean |
| App store | Review delay | **No mitigation. Calendar time. This is why enrolment starts in month 2.** |

## 6. Calendar dependencies

The ones that no amount of engineering removes:

| Dependency | Lead time | Start by | Blocks |
|---|---|---|---|
| **WhatsApp template approval** | Weeks, per template, provider-controlled | Month 3 | The entire M5 contact schedule going live |
| **WhatsApp number registration + BSP onboarding** | Weeks | Month 2 | All WhatsApp, inbound and outbound |
| **Apple developer enrolment** (needs a **D-U-N-S in Apollo's name**) | Days–weeks | Month 2 | App submission → attendance → shift invoicing |
| **First app store review** | Slower than later updates | Month 4 | Same chain |
| **CPAL data access** | Apollo-provided | **Month 1** | All of A10; go-live has no date without it |
| **Supplier selection** ×8 | Apollo decision | See `05-03` | Pricing, not building |
| **Apollo AWS account + credential boundary** | Apollo/PMO decision | Kick-off | Phase 0 entirely |

**Every one of these should be started in the first two weeks**, regardless of when the code that
needs it is scheduled.
