## 1. Purpose

Prove that a candidate is who they say they are and holds the registration they claim.

> INC/NUID, NMC and state medical councils, allied health councils, Pharmacy Council, Aadhaar via
> DigiLocker, PAN, EPFO, court checks. **Several registries have no API and resolve to document plus
> manual verification behind the same interface.** Aggregator-first (IDfy / AuthBridge) recommended.

And a longer-range constraint from A12:

> The interface must accept **US, Germany and Ireland later without change to core domain logic.**

---

## 2. Three ports, not seventeen adapters

`M1-I13`: *"Three interfaces — identity, certification, qualification — that any country's registries
must fit behind."*

| Port | Answers | India examples |
|---|---|---|
| `identity_verification` | Is this person who they say they are? | Aadhaar (DigiLocker), PAN, EPFO employment history, court records |
| `certification_registry` | Do they hold a valid professional registration? | INC/NUID, state nursing councils, NMC, state medical councils, allied health councils, Pharmacy Council |
| `qualification_registry` | Do they hold the qualification they claim? | University and institution verification |

**Ports are shaped around the capability, not around a supplier's API.** The test for whether the
abstraction is real (`OI-A-01`): could a German nursing registry with a completely different data
model implement `certification_registry` without changing anything in `03-06`? If not, the port is
leaking Indian specifics.

---

## 3. Aggregator-first

Rather than seventeen direct registry integrations, one aggregator fronts as many as it covers.

```
03-06 → certification_registry port
            ├─ AggregatorAdapter  (IDfy / AuthBridge)  → covers what it covers
            ├─ DirectAdapter      (a specific council with its own API)
            └─ ManualAdapter      (no API exists — a person checks a document)
```

Selection is by `port_key + market + scope_key` with priority ordering, falling through to the manual
adapter (`02-12 §7.3`). Adding a council is a configuration row, not a code change — provided an
adapter for its *kind* already exists.

**`M1-I15` is "one supplier who fronts Aadhaar, PAN, EPFO and court checks, so we build one
integration instead of five."** That is the aggregator, and it is why the estimate is XL rather than
five separate XLs.

---

## 4. The manual path is a first-class path

> Several registries **have no API and resolve to document plus manual verification behind the same
> interface.** — `M1-I3`, `M1-I14`

This is not an error branch. Several Indian state councils have no API and never will. Their
"adapter" is:

```
adapters.call('certification_registry','verifyRegistration', input, { market:'IN', scopeKey:'TN_NURSING' })
   → ManualAdapter
   → returns { kind: 'manual_fallback', task: {...} }
   → 03-06 creates a VerificationCase in 'manual_review'
   → verification team opens the certificate document, checks it, resolves green/amber/red
   → the SAME outcome vocabulary as an API result
```

Downstream — `03-09`'s eligibility rules, the candidate record, the verification summary — cannot
tell the difference, and should not need to.

**Configuring a registry as manual is a settings change** (`02-12 §9`): set `adapter_key = 'manual'`.
Likewise, *"disabling an adapter routes checks to the manual fallback rather than failing them"*
(`M1-I3`).

## 5. Port definitions

```ts
export const CertificationRegistryPort = definePort({
  key: 'certification_registry',
  operations: {
    verifyRegistration: {
      input: z.object({
        registrationNumber: z.string(),
        councilCode: z.string(),          // 'INC' | 'TN_NURSING' | 'NMC' | ...
        candidateName: z.string(),
        dateOfBirth: z.string().optional(),
      }),
      output: z.object({
        outcome: z.enum(['green','amber','red']),
        matchedName: z.string().optional(),
        registrationStatus: z.string().optional(),   // 'active'|'expired'|'suspended'|'not_found'
        validTo: z.string().optional(),
        qualification: z.string().optional(),
        providerReference: z.string(),
        cost: z.object({ amount: z.number(), currency: z.string() }).optional(),
      }),
      redact: ['registrationNumber','dateOfBirth'],
      timeout: 30_000,
      retryable: true,
    },
  },
  manualFallback: {
    supported: true,
    createTask: (input) => ({ kind: 'manual_registration_check', payload: input }),
  },
})
```

`identity_verification` and `qualification_registry` follow the same shape. All three share the
**green / amber / red** outcome vocabulary — defined by the port, not by each adapter.

| Outcome | Meaning |
|---|---|
| **green** | Verified — registration active and the name matches |
| **amber** | Partial — name mismatch on spelling, registration found but expiry unclear, or the registry was unreachable and a person accepted the document with a note |
| **red** | Failed — not found, suspended, or a material mismatch |

**Amber is the interesting one.** It is what a real Indian verification process produces most often —
a name spelled differently on a certificate and an Aadhaar card is not fraud, and it needs a human,
not a rejection.

## 6. Consent gate

**Every call in this document is gated on consent** (`01-10 §4`, `03-06 §7.1`):

```ts
async runChecks(candidateId, actor) {
  await consent.assertValid(candidateId, 'verification')   // throws if absent or withdrawn
  ...
}
```

Enforced in the service, not by a UI checkbox. This is the one place in the platform where a missing
check is a regulatory problem rather than a bug.

**This has a real consequence for `03-15`:** migrated CPAL candidates arrive with **no consent
evidence**, so verification cannot run on them until a re-consent campaign or a documented
legitimate-use position exists (`AS-44`). That is the bulk of the candidate base at go-live.

---

## 7. Cost

**Per check.** Drivers: new candidates × required checks per category (`03-06 §5.4`) — roughly five
per nurse, five per doctor, four per allied health.

Recorded on `platform.adapter_call.cost_amount`. Reported per provider per month (`02-12 §9`).

Aggregator pricing varies materially between IDfy and AuthBridge, and per check type. `OI-HS-06`
names the pricing question explicitly.

## 8. Selection criteria

For when Apollo chooses between IDfy and AuthBridge:

| Criterion | Why it matters |
|---|---|
| **Registry coverage** | Which councils are covered directly vs which fall to manual. This is the single biggest driver of verification-team workload. |
| **Response schema** | *"Selecting late means rework in the adapter layer"* (`OI-HS-06`) |
| **Per-check pricing** by type | Drives the cost model |
| **Data residency** | Aadhaar and PAN processing must stay in India (`01-10 §3`) |
| Turnaround time per check | Feeds the pendency SLA in `03-06` |
| Webhook vs polling | Affects `awaiting_registry` handling |
| Sandbox | Without one the adapter cannot be built before contracts are signed |

**Coverage is the criterion that matters most operationally.** Every council the aggregator does not
cover becomes manual work for the verification team, every day, forever.

## 11. Notes for the implementer

**Design the ports before you know the supplier — that is the entire point.** Write
`certification_registry` from the question *"does this person hold a valid registration"*, not from
IDfy's response body. Then implement two fakes: an Indian one and a deliberately foreign-shaped one.
If the second requires changing anything in `03-06`, the port is wrong and it is far cheaper to find
that out in phase 0 than in year two.

**Build the manual adapter first.** It is the one that definitely works, it unblocks `03-06`
completely, and several councils will use it permanently. Everything else is an optimisation on top
of a process Apollo already runs by hand.

**Amber deserves real design attention.** It will be the most common non-green outcome, it always
needs a human, and how well the verification detail screen presents "the registry says Priya Sharma,
the certificate says Priya S. Sharma" determines whether this module saves the team time or creates
work.
