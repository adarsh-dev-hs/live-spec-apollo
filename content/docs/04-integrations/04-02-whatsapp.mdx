## 1. Why this is the most important integration

WhatsApp is how Apollo already talks to both sides of its business. It carries:

| Direction | Traffic |
|---|---|
| **Inbound** | Client vacancies as text · client vacancies as **voice notes** · candidate availability replies |
| **Outbound** | Missing-field follow-up · the whole availability cadence (**every 3–4 days across the shift pool**) · offer delivery · **client link delivery — shortlist, day 30/60/90, timesheet approval** · trial check-in prompts · payslips |

Two consequences:

1. **It is on the revenue path twice.** The day-90 retention link and the timesheet approval link both
   travel over WhatsApp. If it stops, invoices stop.
2. **It is the dominant running cost.** Billed per conversation, and the volume is set by the cadence
   configuration (`OI-HS-05`).

## 2. One number, one template set

> **A single registered number and template set shared across A1 and D10 — not two.** — plan
> integration register

`02-07` owns sending on that number. `02-08` owns receiving on it. Both go through the same BSP
adapter. Two numbers would double the cost, double the template approval work, and confuse every
recipient.

The consequence is that **inbound must distinguish a client sending a vacancy from a candidate
answering an availability question** on the same number — which is exactly what `02-08 §7.2`'s
message-type detection does.

## 3. The template approval problem

> The WhatsApp Business Solution Provider **carries every message the platform sends** and also has to
> **approve each message template before it can be used — which takes weeks and is outside our
> control.** — `OI-HS-07`

> This is worse than an estimate problem: **template approval is a calendar dependency that no amount
> of team size removes, and it gates the whole contact schedule going live in M5.**

**How the platform handles it:**

- `approval_status` is a first-class field on the template record (`03-08 §5.1`):
  `not_required → draft → submitted → approved | rejected`
- Sending against an unapproved template **fails with a clear error**, not a silent drop
- The template screen has a "blocking go-live" filter
- Submission date and waiting time are visible, so "which templates are we waiting on" is a query

**What the team must do:** submit every WhatsApp template **at the start of phase 5**, not when the
code that uses it is ready. Draft them from the message catalogue below in phase 3.

## 5. Port definition

```ts
export const WhatsAppOutboundPort = definePort({
  key: 'whatsapp_outbound',
  operations: {
    sendTemplate: {
      input: z.object({
        to: z.string(),                    // E.164
        templateName: z.string(),
        languageCode: z.string(),
        variables: z.record(z.string()),
        buttons: z.array(z.object({ id: z.string(), title: z.string() })).optional(),
        mediaUrl: z.string().optional(),   // presigned, short expiry
      }),
      output: z.object({
        providerMessageId: z.string(),
        conversationId: z.string().optional(),   // billing unit
        cost: z.object({ amount: z.number(), currency: z.string() }).optional(),
      }),
      redact: ['to'],
      timeout: 15_000,
      retryable: true,
    },
    getMediaUrl: { input: z.object({ mediaId: z.string() }), output: z.object({ url: z.string() }) },
    getTemplateStatus: { input: z.object({ templateName: z.string() }),
                         output: z.object({ status: z.enum(['pending','approved','rejected']) }) },
  },
  manualFallback: { supported: false },      // no manual path — this IS the channel
})
```

**`cost` on the send response is why cost recording works.** It cannot be reconstructed later
(`02-07 §12`).

## 6. Inbound webhook

`POST /api/v1/webhooks/whatsapp`

Handles four payload kinds:

| Kind | Handling |
|---|---|
| **Text message** | → `inbound.receive()` (`02-08`) → sender match → type detection |
| **Voice note** | Media downloaded, stored via `02-04`, → `inbound.receive()` → transcription (`04-03`) |
| **Interactive reply** (button / list) | → `inbound.receive()`, classified `candidate_response` with confidence 1.0 |
| **Status update** | → `messaging.receipt` queue (`02-07`) |

Every one of them, without exception (`01-04 §12`):

1. **Verify the signature before parsing the body**
2. Dedupe on the provider's message id
3. **Persist the raw payload immediately**
4. Return 200 fast — enqueue, never process inline
5. Zod-parse before trusting the shape

## 7. The 24-hour session window

WhatsApp permits free-form replies only within 24 hours of a user-initiated message; outside it, only
approved templates may be sent.

**What this means for the platform:**

- Every proactive message uses an approved template. There is no "just send a quick note" path.
- A candidate's reply opens a 24-hour window — useful for a follow-up question in a trial check-in
  conversation, but never relied upon.
- **The cadence engine cannot assume a window is open.** Every cadence send is a template send, which
  is also why every cadence send is a billable conversation (`OI-HS-05`).

Encode this in the adapter: attempting a free-form send outside a window is an error, not a
best-effort attempt.

## 8. Cost model

| Element | Note |
|---|---|
| Billing unit | **Per conversation** (a 24-hour window), not per message |
| Category | Utility / authentication / marketing rates differ — every template is classified at submission |
| Recorded | `engage.message.cost_amount`, `cost_unit = 'conversation'` (`02-07 §5`) |
| Reported | `02-07 §9` consumption report, `03-08 §9.3` cadence preview |

**The dominant variable is cadence frequency × base size.** A shift pool of 5,000 contacted every
3.5 days is roughly 43,000 conversations a month before any other traffic. That number, multiplied by
the per-conversation rate, is the figure Apollo is asking for — and it is why `OI-HS-05` notes that
*"per-conversation cost could exceed the build cost of the module that sends the messages."*

---

## 9. Rate limits and throughput

BSPs impose throughput tiers based on quality rating and phone-number status. Exceeding them gets
messages **dropped, not queued**.

Handled in `02-07 §8`: a token-bucket rate limiter in Redis, per provider, configured from P03, shared
across all worker tasks. Cadence runs also carry a `daily_cap` (`03-08 §5.3`) as a second control.

**Quality rating matters commercially.** A number marked low-quality by users blocking or reporting it
gets throttled. Respecting opt-out at send time (`02-07 §6`) is not only a compliance requirement —
it protects the channel Apollo's whole contact model depends on.

## 12. Notes for the implementer

**Build the fake first and build it well.** It carries eight modules through development and the whole
of phases 3–6. It must simulate inbound text, inbound voice, inbound button replies, delivery
receipts, read receipts, rate limiting and an unapproved template — because every one of those is a
code path that must work before a supplier exists.

**Persist before you interpret.** The webhook's only job is to get the raw payload into Postgres and
return 200. Everything else is a job. A BSP retrying because we were slow to acknowledge produces
duplicate messages you then have to dedupe.

**Treat the template list as a deliverable with a lead time.** Write it in phase 3, get the wording
agreed with Apollo, submit in phase 5. Discovering in month five that eleven templates are pending
approval is the single most avoidable schedule failure in this project.
