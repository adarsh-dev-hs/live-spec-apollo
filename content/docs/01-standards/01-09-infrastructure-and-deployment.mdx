**Package** `infra` (Terraform), `.github/workflows` · **Schema** `n/a` · **Plan** F10, D11 · **Effort** — · **Risk** Medium `EXT` · **Build in** Phase 1

Everything runs in **AWS `ap-south-1` (Mumbai)** in an Apollo-owned account. Docker images for every
service, **GitHub Actions** for CI/CD, **EC2** for the long-running processes and **Lambda** for the
event-driven edges. `02-15` builds it; this page is the standard it is built to.

## 1. Environments

| Env | Purpose | Data | Deploy |
|---|---|---|---|
| `dev` | Integration of merged work | Anonymised | Automatic on merge to `main` |
| `qa` | Test team | Anonymised | Automatic after `dev` smoke passes |
| `uat` | Apollo acceptance (`M1-I8`) | Anonymised, refreshed on request | Manual promote (GitHub Environment approval) |
| `prod` | Live | Real | Manual promote, approved release |

Four environments provisioned **consistently from the same Terraform modules with different variable
files**. A build moves from `dev` to `prod` without hand-editing configuration (`M1-I16`). Non-production
environments carry anonymised data only, and the anonymiser is a pipeline stage, not a manual step.

## 2. Compute topology

| Workload | Runs on | Why |
|---|---|---|
| `@apollo/api` | **Docker on EC2**, Auto Scaling Group behind an ALB, ≥2 instances in prod across AZs | Long-lived Postgres pool; predictable latency for the fulfilment board |
| `@apollo/worker` | **Docker on EC2**, separate ASG, one service per queue class | Batches run for minutes (cadence over the whole Base B, resumable migration `M1-I11`); a 15-minute function ceiling is the wrong shape |
| `@apollo/edge` handlers | **AWS Lambda**, container images | Bursty, externally triggered, must never drop a payload |
| Static sites | S3 + CloudFront | `console`, `links`, `portal` |

### The four Lambda handlers

Each does exactly one thing — verify, persist the raw payload, enqueue — and returns. **No business
logic, no transaction spanning more than the raw write.**

| Handler | Trigger | Does | Plan ref |
|---|---|---|---|
| `edge-email-inbound` | SES → SNS | Writes the `InboundRecord` with the raw MIME and attachments in S3, enqueues `inbound.parse` | `M3-I25` |
| `edge-webhook` | API Gateway (WhatsApp, voice, e-sign, verification aggregator callbacks) | Verifies the provider signature, deduplicates on provider message id, writes the raw payload, enqueues | `M3-I18`, `M3-I24`, `M5-I12`, `M7-I15` |
| `edge-object-created` | S3 `ObjectCreated` on the documents bucket | Kicks off the virus scan and marks the document `scanned` or `quarantined` | `M0-I6` |
| `edge-schedule` | EventBridge Scheduler | Enqueues the scheduled jobs listed in `01-06` §2 — a **thin trigger**; the work runs on the worker | `01-06` |

**Why the split matters.** A provider retry storm hits Lambda, not the instances serving the console.
Deduplication happens at the cheapest possible place, satisfying "a redelivered message does not create
a duplicate `InboundRecord`" (`M3-I18`) before anything expensive runs. And because the handler only
enqueues, the transaction, the audit write and the event emit still happen together on the worker where
`01-02` requires them.

**Lambda is never used for:** anything holding a database transaction beyond a single insert, anything
calling a third-party API and waiting, anything that must resume from a checkpoint, or anything needing
the full permission and scope stack.

## 3. Docker

| Image | Base | Notes |
|---|---|---|
| `apollo/api` | `node:22-alpine`, multi-stage, non-root | Distroless-style final layer; only the built `dist/` and production deps |
| `apollo/worker` | same base, same build stage | One image, `CMD` selects the queue class |
| `apollo/edge-*` | `public.ecr.aws/lambda/nodejs:22` | Lambda container images so the build path is identical to the services |
| Web apps | Not containerised | Built to static assets and synced to S3 |

Rules: multi-stage builds with an `npm ci --omit=dev` runtime layer; images tagged with the **git SHA**,
never `latest`; `.dockerignore` excludes `docs/`, tests and local env files; a healthcheck endpoint
(`/healthz` liveness, `/readyz` including a database ping) on the API image; images scanned by ECR on
push and a high severity blocks promotion.

### Local development

`docker compose up` starts Postgres 16, Redis, LocalStack (S3 + SES + EventBridge) and MailHog. The
api and worker run **on the host** with hot reload against those containers — containerising the app in
development costs rebuild time and buys nothing.

```yaml
# compose.yaml (excerpt)
services:
  postgres:   { image: postgres:16-alpine, ports: ['5432:5432'] }
  redis:      { image: redis:7-alpine,     ports: ['6379:6379'] }
  localstack: { image: localstack/localstack, environment: { SERVICES: 's3,ses,events' } }
  mailhog:    { image: mailhog/mailhog,    ports: ['8025:8025'] }
```

## 4. CI/CD — GitHub Actions

```
.github/workflows/
├── pr.yml           # every pull request
├── main.yml         # merge to main → build, publish, deploy dev → qa
├── promote.yml      # manual dispatch → uat → prod, GitHub Environment approvals
├── migrate.yml      # migration step, called by main.yml and promote.yml
└── nightly.yml      # E2E gate journeys, load smoke, dependency audit
```

### `pr.yml`

```yaml
jobs:
  verify:
    runs-on: ubuntu-latest
    services:
      postgres: { image: postgres:16-alpine, env: { POSTGRES_PASSWORD: test } }
      redis:    { image: redis:7-alpine }
    steps:
      - uses: actions/checkout@v4        # with fetch-depth: 0 for nx affected
      - uses: actions/setup-node@v4      # node 22, npm cache
      - run: npm ci
      - run: npx nx affected -t lint typecheck test build --base=origin/main
      - run: npm run test:scope          # every collection route rejects a cross-scope id
      - run: npm run test:append-only    # UPDATE/DELETE on audited tables raises
      - run: npm run test:residency      # no configured endpoint outside ap-south-1
      - run: npm run test:pii-logs       # no personal data in any log line
      - run: npm run test:criteria-diff  # every §10 acceptance criterion has a named test
      - run: npm run bundle:budget
      - run: npm audit --audit-level=high
```

The five named suites are the ones `01-08` calls non-negotiable. `test:criteria-diff` is what makes
1,062 conditions a build gate rather than a number in a plan.

### `main.yml`

```
build image (git SHA) ──▶ push ECR ──▶ migrate dev ──▶ deploy dev ──▶ smoke + E2E gate journeys
                                   └─▶ package Lambda images ──▶ update functions
                                                                     └──▶ auto-promote qa
```

### Deploying to EC2

No SSH, no manual step. GitHub Actions assumes a role by **OIDC** (no long-lived AWS keys in GitHub),
then runs an **SSM** document against the ASG that pulls the new image, drains the instance from the
ALB target group, restarts the container and waits for `/readyz`. Rolling, one instance at a time,
automatically halted if health checks fail.

| Rule | Detail |
|---|---|
| One artefact promoted through all four environments | Never rebuilt per environment; the SHA is the release identity |
| Migrations run as a pipeline step **before** the new containers start | Additive-first (`01-05`) makes this safe |
| Rollback is redeploying the previous SHA | Forward-only migrations mean a rollback never un-migrates — deliberate (`M1-I5`: "rollback to the prior release is possible without data loss") |
| Release approval is an Apollo-visible act | GitHub Environment protection rules; who may approve depends on `OI-HS-04` |
| **No Hiresense-held credential is required at runtime** once handover completes | `M1-I5` — OIDC federation, instance roles, Secrets Manager; nothing personal to a Hiresense engineer |
| Secrets in Actions come from GitHub OIDC → AWS role, never from repository secrets holding AWS keys | |

## 5. Infrastructure as code

Terraform, one module per concern (`network`, `data`, `compute`, `edge`, `observability`,
`static-sites`), one root stack per environment with a variable file. State in S3 with DynamoDB
locking. `terraform plan` runs on every PR touching `infra/`; `apply` runs only from `main` behind the
same environment approvals as a release.

## 6. Observability and alerting

| Signal | Alert |
|---|---|
| API 5xx rate, p95 latency, ALB target health | page |
| EC2 ASG healthy-host count below minimum | page |
| Lambda error rate and throttles per handler | page — a throttled webhook handler silently loses inbound demand |
| Queue depth and oldest job age per class | page — a stalled cadence queue silently stops candidate contact |
| Dead-letter count (BullMQ and Lambda DLQ) | ticket; the operator UI (`02-10`) lists them re-queueable |
| Provider error rate per integration | ticket; an outage routes to the manual fallback rather than failing candidates (`M1-I15`) |
| Outbox lag | page — reporting correctness depends on it (`M3-I31`) |
| Deemed-window job not running | page — a stalled `links.expire-and-deem` silently stops invoicing |
| Verification pendency by cause | dashboard — a registry outage must surface as a spike in awaiting-registry (`M4-I11`) |
| Per-provider consumption units | dashboard — `OI-HS-05` |

"A failure in production raises an alert rather than being found by a user" (`M1-I16`) is an acceptance
criterion, not an aspiration.

## 7. Backup and recovery

| Item | Policy |
|---|---|
| Database | Automated snapshots + PITR; retention **unset pending `OI-HS-12`**, working assumption 35 days (`AS-20`) |
| Objects | S3 versioning + lifecycle to Glacier per the retention policy in `02-12` |
| Restore rehearsal | Rehearsed and **evidenced before go-live** (`M1-I16`), as a scripted GitHub Actions workflow so it is repeatable |
| RPO / RTO | **Not stated anywhere** (`OI-HS-12`). Working assumption RPO 15 min, RTO 4 h (`AS-21`) — without agreed targets the rehearsal has no pass condition |
| Backup residency | `ap-south-1` only, snapshots included — DPDP applies to backups (`M1-I5`) |

Backup retention and the DPDP erasure policy may conflict; that conflict is `OI-HS-02` and is
reconciled explicitly rather than by whichever job runs last.

## 8. Configuration and secrets

- All configuration is environment variables validated by `@apollo/config` at boot; a missing variable
  fails the container start rather than surfacing at 3am.
- Provider credentials live in Secrets Manager, fetched at boot by instance and Lambda execution roles.
  Rotation does not require a code change and nothing is baked into an image.
- Business configuration — windows, cadences, thresholds, weights, lists — is **not** environment
  configuration. It lives in `02-03` and is edited by Apollo, not by a deploy (`M0-I5`).

## 9. Cost and scale posture

| Driver | Note |
|---|---|
| Compute | Small. 22 recruiters and a candidate base in the tens of thousands. Two small EC2 ASGs cover it; Lambda cost is negligible at webhook volume. |
| Metered providers | The real cost: WhatsApp per conversation, voice per minute, transcription per minute, OCR per page, verification per check, AI inference per inbound. Volume is set by cadence **configuration** (`OI-HS-05`), so `02-03` carries a projection preview before a cadence is enabled. |
| Provider account ownership | `X10` — Apollo's or Hiresense's, recharged at cost either way, decided deliberately rather than discovered at the first invoice |

## 10. Open infrastructure decisions

| Item | Effect |
|---|---|
| `OI-HS-04` | Whether "client-hosted AWS Mumbai" means an Apollo-owned account changes who holds credentials, who is on call, and who may approve a GitHub Environment |
| `OI-HS-12` | No RPO, RTO or backup retention target ⇒ no pass condition for the restore rehearsal |
| `X06` | SSO vs email and password changes what `02-01` builds; decide before it is built |
| `X07` | AWS account and billing ownership; a reseller changes how accounts are provisioned |
| `OI-M3-14` | No latency or load targets for ingestion, the unmatched queue or the fulfilment board ⇒ no performance acceptance test and no basis for instance sizing |
