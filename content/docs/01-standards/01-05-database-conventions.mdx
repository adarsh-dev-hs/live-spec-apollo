**One Postgres role per schema.** `app_demand` has `USAGE` on `demand` and `SELECT` on the specific
cross-schema views it is granted. It has no rights at all on `billing`. A module reaching into another
module's tables fails at the database, not at review.

Cross-schema reads go through an explicit, granted view named `<schema>.v_<thing>_for_<consumer>` —
for example `clients.v_contract_terms_for_billing`. Adding one is a deliberate act with a migration
and a reviewer.

## 2. Table conventions

```sql
CREATE TABLE demand.requisition (
    id                  uuid PRIMARY KEY DEFAULT uuidv7(),
    reference           text NOT NULL UNIQUE,              -- REQ-2026-000431
    client_id           uuid NOT NULL REFERENCES clients.client(id),
    location_id         uuid NOT NULL REFERENCES clients.location(id),
    department_id       uuid     NULL REFERENCES clients.department(id),  -- null for home healthcare
    service_line        text NOT NULL CHECK (service_line IN ('permanent','contractual')),
    candidate_category  text NOT NULL REFERENCES settings.list_entry(code),
    care_setting        text NOT NULL REFERENCES settings.list_entry(code),
    status              text NOT NULL,
    positions_requested integer NOT NULL CHECK (positions_requested > 0),
    positions_filled    integer NOT NULL DEFAULT 0 CHECK (positions_filled >= 0),
    completeness        jsonb NOT NULL DEFAULT '{"missing":[]}'::jsonb,
    first_complete_at   timestamptz,                       -- aging starts here (M3 BR4)
    held_seconds        bigint NOT NULL DEFAULT 0,          -- accumulated hold, excluded from aging
    owner_id            uuid REFERENCES identity.user(id),
    source_channel      text NOT NULL,                     -- immutable after creation (M3 BR2)
    inbound_record_id   uuid REFERENCES inbound.inbound_record(id),
    created_at          timestamptz NOT NULL DEFAULT now(),
    created_by          uuid NOT NULL,
    updated_at          timestamptz NOT NULL DEFAULT now(),
    updated_by          uuid NOT NULL,
    CONSTRAINT positions_filled_within_requested CHECK (positions_filled <= positions_requested)
);
```

| Rule | Detail |
|---|---|
| Primary key | `uuid` v7 named `id` — time-ordered, so it indexes like a serial without leaking a count |
| Human reference | separate `reference` column, generated, unique, shown in the UI |
| Table names | singular, snake_case |
| Booleans | `is_`/`has_` prefix, `NOT NULL DEFAULT` always |
| Enums | `text` + `CHECK`, or a FK to `settings.list_entry` when the client can edit the list. **Never** a Postgres `ENUM` type — the plan has nine configurable lists and altering an enum type is a lock. |
| Money | `numeric(14,2)` + a `currency` column |
| Timestamps | `timestamptz` in UTC; business dates as `date` |
| JSONB | only for genuinely open shapes: raw inbound payload, parsed field bag, category attribute values, rank rationale, event payload. Every one has a Zod schema in code and a documented shape in its spec. |
| Nullable | means "not known"; never overloaded to mean "not applicable" — use a discriminator column |
| FKs | always declared, `ON DELETE RESTRICT` by default. Nothing cascades into audited data. |

## 3. Append-only tables

`audit.audit_entry`, `demand.status_transition`, `demand.allocation_record`,
`matching.recruiter_override`, `events.platform_event`, `placement.retention_record`,
`adapters.adapter_call`, `messaging.notification_log`.

```sql
REVOKE UPDATE, DELETE ON audit.audit_entry FROM app_audit, app_demand, app_billing /* … */;
```

Enforced by grant, tested by a suite that asserts an `UPDATE` raises. `RetentionRecord` additionally
snapshots the contract terms it read rather than referencing them, so a later contract amendment
cannot change what an invoice was justified by (`M9-I13`).

## 4. Indexing

| Pattern | Index |
|---|---|
| Every FK | b-tree on the referencing column |
| List screens | composite covering the default filter + sort, e.g. `(status, days_aged DESC) INCLUDE (client_id)` |
| Data scope | every scoped table indexes its scope column (`location_id`, `client_id`) **first** in the composite |
| Free-text search | `pg_trgm` GIN on candidate name, client name, requisition reference |
| Structured candidate search (`M6-I1`) | GIN on `candidates.candidate.attributes` jsonb + b-tree on `(category, base, availability_confidence DESC)` |
| Time-series marts | BRIN on `occurred_at` |
| Uniqueness that matters | partial unique indexes: one active `SenderIdentity` per address, one open `Placement` per accepted `Offer`, one `Invoice` per `BillingTrigger` |

`SELECT` without a bounded `LIMIT` or a scope predicate on a table expected to exceed 100k rows fails
review. Volume for the migrated base is unknown (`OI-A-02`), so the assumption is that it is large.

## 5. Migrations

```
migrations/
  0001_create_identity_schema.sql
  0002_create_audit_schema.sql
  …
  0043_add_requisition_care_setting.sql
```

| Rule | Why |
|---|---|
| Plain SQL, numbered, **forward-only**. No down migrations. | A down migration against append-only billing evidence is a data-loss tool. Roll forward with a new file. |
| Applied by the in-repo runner inside a transaction, recorded in `public.schema_migration` | |
| Additive first, destructive later: add nullable → backfill in a job → set `NOT NULL` → drop old in a later release | Zero-downtime, and the four-environment pipeline (`M1-I16`) requires it |
| `CREATE INDEX CONCURRENTLY` outside a transaction, in its own file | An index build must not lock the fulfilment board |
| Every migration is reversible **by data**, i.e. nothing drops a column containing candidate or billing data in the same release it stops being written | |
| Seed data (roles, the nine settings lists, categories, care settings) is a migration, not a script | `M0-I5` requires categories to exist as data on day one |

## 6. Transactions and isolation

- Default `READ COMMITTED`.
- `SELECT … FOR UPDATE` before any state transition. Two recruiters holding the same requisition, two
  syncs of the same offline check-in, two link submissions — all real (`M8-I14`, `M7-I18`).
- `SERIALIZABLE` for the three places where a uniqueness rule spans rows: raising an invoice against a
  trigger (`M9-I12` "cannot raise a second invoice for the same placement"), locking a payroll cycle,
  and merging duplicate candidates.
- Transactions are short. No provider call, no S3 call, no user wait inside one.
- Advisory locks for singleton jobs: a migration batch "cannot be started twice concurrently"
  (`M1-I2`); a cadence run must not overlap itself.

## 7. Soft state, never deletion

| Kind | Rule |
|---|---|
| Reference list entry | `deactivated_at` — stays readable on records that already used it (`M0-I5`) |
| User | `deactivated_at` — cannot sign in, stays visible on their past records (`M0-I2`) |
| Client, location, contract | status transition; open records are never orphaned (`M2-I2`, `M2-I3`) |
| Candidate | **never deleted.** A losing duplicate is merged with lineage to both source ids (`M1-I12`, `M4-I21`) |
| Document | superseded, previous version retained (`M0-I6`) |
| Erasure request | handled by `02-12` as a defined policy, not an ad-hoc delete — and unresolved against the retained pool (`OI-HS-02`) and finance retention (`OI-HS-14`) |

## 8. Reporting reads

`03-12` reads `reporting.*` marts materialised from `events.platform_event`. It never queries
operational tables (`M9-I17`). This keeps a leadership dashboard from competing with the fulfilment
board, and it is what makes a report over an already-elapsed period possible at all.

## 9. Local and non-production data

- Local dev: Postgres 16 in Docker, `npm run db:reset` recreates from migrations plus the demo seed.
- Integration tests: testcontainers, real Postgres, migrations applied, transaction rolled back per test.
- **dev, qa and uat carry anonymised data only** (`M1-I16`). Production personal data never leaves
  production, and the anonymiser is part of the pipeline rather than a manual step.
