**Package** `@apollo/testing` · **Schema** `n/a` · **Plan** D11, all AC sets · **Effort** — · **Risk** Medium · **Build in** Phase 1 · **Release** Parts 1–3

The plan carries **1,062 conditions** across 208 items. Each is a statement an item must satisfy, and
each becomes at least one automated test. That mapping is the quality strategy; everything below serves
it.

## 1. The condition-to-test rule

Every acceptance criterion in a spec's §10 carries a plan reference. Every one gets a test named after
it.

```ts
// modules/requisitions/test/integration/hold.spec.ts
describe('M3-I15 hold, revise and close', () => {
  it('AC3 · placing a requisition on hold stops the aging clock', …)
  it('AC3 · releasing the hold resumes aging from the held value, not from zero', …)
  it('AC4 · closing without a reason is rejected and the requisition remains in its prior state', …)
  it('BR5 · a requisition reaching filled does not close automatically', …)   // OI-M3-12 pending
})
```

A spec's acceptance criteria and its test file names are diffed in CI. A criterion with no test fails
the build. This is what makes "1,062 conditions" a measurable thing rather than a number in a plan.

## 2. Layers

| Layer | Tool | Covers | Speed |
|---|---|---|---|
| Unit | Vitest | `domain/` — state machines, invariants, scoring, date and money maths. Pure, no I/O. | ms |
| Integration | Vitest + testcontainers Postgres | service + real SQL + real transactions + audit + outbox | seconds |
| Contract | Vitest | what one module promises another; what an adapter promises the core | seconds |
| API | Vitest + Fastify inject | route, auth, permission, scope, error shape | seconds |

| E2E | Playwright | the seven gate journeys in `00-05` only | minutes |
| Mobile | Jest + RN Testing Library; Maestro for check-in flows | offline queue, sync, permissions | minutes |
| Load | k6 | fulfilment board, inbound ingestion, cadence run | on demand |

## 3. Non-negotiable test suites

These exist because the plan says something cannot be allowed to happen. They run on every PR.

| Suite | Asserts | Plan ref |
|---|---|---|
| **Scope** | Every collection route rejects a cross-scope id, for every realm. A new route without a scope predicate fails. | `M10-I8`, `OI-HS-01` |
| **Append-only** | `UPDATE`/`DELETE` on each append-only table raises | `M0-I4`, `M3-I28`, `M9-I13` |
| **Billing trigger** | Only `day_90_retention` can carry `is_billing_trigger`; day-30/60 cannot be configured to; a duplicate trigger cannot produce a second invoice for the same placement | `M7-I8`, `M9-I12` |
| **Intent registration** | A second consumer registers an intent set and target schema **without modifying** the receiver, queue, sender resolution or retry — demonstrated by A14 registering | `M3-I29`, `M5-I14` |
| **Adapter contract** | Every adapter returns the common traffic-light schema; a core change that breaks an existing adapter fails | `M1-I13` |
| **Channel parity** | The same requirement on all five live channels produces requisitions differing **only** in source channel and raw payload | `M3-I20` AC1 |
| **Response parity** | An availability answer from app, WhatsApp and voice produces one identical structured payload, and a response on two channels reconciles to one record | `M4-I10`, `M5-I16` |
| **Deemed paths** | Deemed confirmation and deemed approval are valid invoice inputs, visibly distinguished, and fall back to the platform default when a client has no window | `M8-I16`, `M9-I15`, `OI-A-05` |
| **Idempotency** | Webhook redelivery, offline check-in re-sync and duplicate link submission each produce exactly one record | `M3-I18`, `M8-I14`, `M7-I18` |
| **Partial failure** | A spreadsheet or bulk import with bad rows names each bad row and still loads the good ones | `M1-I4`, `M2-I3`, `M3-I6`, `M12-I4` |
| **Negative — no engine** | Nothing suggests, computes or optimises a recruiter allocation anywhere in Phase 3 | `M3-I16` BR1 |
| **Negative — no auto-merge** | No automatic requisition merge occurs anywhere while `OI-M3-02` is open | `M3-I4` |
| **PII in logs** | No log line contains a phone, email, name, Aadhaar, PAN, account number or document text | `01-02`, `02-12` |
| **Residency** | No configured bucket, database, backup or provider endpoint is outside `ap-south-1` | `M1-I5`, `M4-I27` |

## 4. Coverage and gates

| Gate | Threshold |
|---|---|
| Line coverage, `domain/` | 95% |
| Line coverage, `services/` | 85% |
| Line coverage overall | 80% |
| Every acceptance criterion | has a named test |
| Every append-only table | in the append-only suite |
| Every list endpoint | in the scope suite |
| Every provider call | has a failure-path test asserting the manual fallback, not a crash |

Coverage percentages are a floor, not a goal. The criterion-to-test diff is the real gate.

## 5. Test data

- Factories in `@apollo/testing`, one per aggregate, with sensible defaults and explicit overrides.
- **Never** shared mutable fixtures. Every test builds what it needs.
- Personal data in tests is synthetic and obviously so. No production data in any test, ever.
- The `seed:demo` fixture — one client, one contract, one requisition, one nurse — is the G1
  demonstration and the E2E baseline.
- Provider responses are recorded fixtures from sandbox, not hand-written optimism. Where no supplier
  is named (voice, OCR, e-sign, STT, HRMS, payroll), the integration ships with a **stub adapter plus a
  contract test**, and the fixture set is a named gap in that integration's §11.

## 6. Static quality

| Tool | Rule |
|---|---|
| TypeScript | `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. No `any` across a module boundary. |
| ESLint | Nx boundary rules; no floating promises; no raw SQL string concatenation; no `process.env` outside `@apollo/config`; no `console.*` |
| Prettier | Formatting is not reviewed |
| `npx nx affected` | CI runs lint, typecheck, test and build only on what the diff touches |
| Dependency audit | `npm audit` + Dependabot; a high severity blocks release |
| Bundle budgets | Enforced in CI per `01-03` §9 |

## 7. Definition of done for one spec

1. Every §10 acceptance criterion has a passing named test.
2. Every state in §6 is reachable only from its declared predecessor, tested.
3. Every §8 event is emitted inside the business transaction, tested.
4. Every §7 endpoint has auth, permission, scope and error-shape tests.
5. Every §9 screen has its five states.
6. Migrations run forward on a copy of the previous release's schema.
7. New queries over a large table carry an `EXPLAIN ANALYZE` in the PR.
8. Any open question in §11 that turned out to be blocking is raised in `05-03`, not worked around.
9. `docs/` is updated in the same PR when the shipped behaviour differs from the spec.

## 8. UAT (`M1-I8`)

Apollo-run, Hiresense-supported. Severity definitions and turnaround windows are agreed **before**
testing starts, not negotiated during it. Sign-off criteria are agreed per module beforehand. Retest of
a fixed defect is evidenced. Named recruiters have protected time — they carry 15–16 vacancies each and
will not test otherwise (`X22`).
