**Package** `@apollo/data-protection` · **Schema** `dp` · **Plan** F13, F06, F04, D4, D16, A13 · **Effort** — · **Risk** High `COMP` · **Build in** Phase 1

The platform holds personal and **health-related** data about healthcare professionals in India, plus
billing evidence that must survive a dispute years later. `02-12` implements consent, residency and
retention; this page is the standard the whole platform obeys.

## 1. Data classes

| Class | Examples | Rules |
|---|---|---|
| **Identity** | Name, phone, email, Aadhaar reference, PAN, date of birth | Consent before storage; encrypted at rest; never logged; masked in non-production |
| **Credential** | Council registration, qualification, verification outcome | Consent before any check is dispatched; retained while the candidate is in the base |
| **Sensitive financial** | Bank account, UAN, PF, salary, advances | Encrypted at column level; access restricted to `finance` and `payroll` roles; every read audited |
| **Health-adjacent** | Specialty, acuity, case-mix, competency | Treated as personal data; not exposed to clients beyond what a shortlist shows |
| **Content** | CVs, certificates, ID scans, voice notes, signed offers | `02-04`: virus-scanned, versioned, expiring links, Mumbai only |
| **Billing evidence** | `RetentionRecord`, approved timesheets, invoices | **Immutable**, longest retention, must answer a query years later |
| **Operational** | Requisitions, allocations, events | Ids only in events; no personal data in a payload |

## 2. Consent (`M4-I27`)

| Rule | Detail |
|---|---|
| Consent is captured **before** personal data is stored | At sign-up in the app (`M4-I1`), before the profile exists |
| A separate consent is captured **before any verification check is dispatched** | `M4-I24` verifies it, `02-13` refuses to call without it |
| Consent evidence is retrievable later if challenged | Version of the notice, timestamp, channel, IP/device |
| Withdrawal is recorded and honoured forward | Statutory and contractual messages remain sendable and are distinguished from cadence messages (`M4-I9`, `M5-I2`) |
| Migrated candidates | Consent basis for the CPAL base is **not established** and must be, before cadence contacts them — raised under `OI-HS-02` |

## 3. Residency

**No personal data leaves `ap-south-1`.** Database, replicas, snapshots, object store, logs, traces,
queues and every provider endpoint. This is what makes the DPDP position hold (`M1-I5`, `M4-I27`,
`M0-I6`), and it is a selection criterion for every unnamed supplier — WhatsApp BSP, voice, STT, OCR,
e-sign, verification aggregator, AI inference. A provider that cannot process in-region is not a
candidate, regardless of price.

The residency test suite asserts no configured endpoint or bucket is outside the region (`01-08`).

## 4. Retention

| Data | Period | Source |
|---|---|---|
| Candidate record | **Indefinite** — the Retained Pool convention | Apollo practice; conflicts with erasure (`OI-HS-02`) |
| Candidate documents | With the candidate record, versioned | `M0-I6` |
| `InboundRecord` raw payload | Kept forever, including after the requisition is created, so a disputed requirement traces to what the client actually sent | `M3-I1` |
| Audit trail | Fixed policy, not a configuration screen | Plan scope note |
| Billing evidence | Finance retention period, likely years, **may exceed candidate retention** | `OI-HS-14` |
| Voice recordings and transcripts | Retention applied per `02-12`; residency enforced | `M5-I12` |
| Backups | Per `01-09`; erasure must reconcile with backup retention | `OI-HS-12`, `OI-HS-02` |

**The two unresolved conflicts are stated, not resolved silently:**

- `OI-HS-02` — a subject erasure request and an indefinite retained pool cannot both be honoured
  without a defined policy. Working assumption `AS-22`: an erasure request **pseudonymises** the
  candidate record (identity fields replaced with a one-way token, operational history retained) rather
  than deleting it, pending Apollo legal.
- `OI-HS-14` — a billing trigger record must survive a dispute years later; a candidate may request
  erasure sooner. Working assumption `AS-23`: `RetentionRecord` and `Invoice` retain the **recipient
  and placement identifiers plus the snapshotted terms** and survive pseudonymisation, because the
  invoice is otherwise not defensible.

Both assumptions are held explicitly and carried in `05-03`.

## 5. Access control and least privilege

- Deny by default; permission checked in a `preHandler`, never inside a handler (`01-07`).
- One Postgres role per schema; a module cannot read another module's tables (`01-05`).
- Sensitive financial columns are encrypted with a separate KMS key; decryption is a service call that
  writes an audit entry.
- Production database access by a human is break-glass: time-boxed, approved, logged, and announced.
- No production data in any non-production environment, ever.

## 6. Application security

| Control | Detail |
|---|---|
| Input validation | Zod at every boundary — HTTP, webhook, queue payload, file parse |
| SQL injection | Parameterised only; string concatenation of input is a lint failure |
| XSS | React escaping; no `dangerouslySetInnerHTML`; a strict CSP on all three web apps |
| CSRF | `SameSite=Lax` cookies plus a token on state-changing form posts |
| File upload | Presigned S3 URL, content-type and size limits, **virus scan before the file becomes available**, quarantine on failure (`M0-I6`) |
| Download | Expiring links only; a shared link does not stay open indefinitely (`M0-I6`) |
| Rate limiting | Per IP, per principal, per link token, per phone number for OTP |
| Webhooks | Signature verified per provider; unsigned providers are IP-allowlisted with a shared secret; replay-protected by message id |
| Secrets | Secrets Manager only; scanning in CI blocks a commit containing a credential |
| Dependencies | Audited on every PR; a high severity blocks release |

## 7. The link surface — the biggest exposure

A tokenised link is sent over WhatsApp to a hospital contact and can be forwarded. It therefore:

- reaches exactly one record and permits exactly one action;
- carries ≥128 bits of entropy, is stored hashed, and expires;
- is invalidated on reissue (`M7-I13`);
- is rate-limited per token;
- exposes **no** internal reason codes, ranking scores, weights or notes (`M4-I6`, `M10-I4`);
- has no collection endpoint of any kind — enumeration of another client's shortlist is the worst
  failure mode in the platform.

The day-90 page in particular carries one question and one action (`M7-I11`), which is a security
property as much as a usability one.

## 8. Data processing agreements (`X18`)

Every named supplier processes personal data on Apollo's behalf. The paperwork is a chain and each new
supplier adds a link. Three suppliers are still unnamed (`OI-HS-07`) and two more are unconfirmed
(`OI-A-09`, `X23`); none may be called with real candidate data until its DPA is in place. This is a
month-1 dependency because it gates *any* handling of candidate data, not just a particular module.

## 9. Incident response

- Every request, job and provider call carries a correlation id, propagated end to end.
- The audit trail can export **everything touching one record for a given period** (`M0-I4`) — this is
  the primary forensic tool and it exists because the day-90 invoice must be defensible.
- A suspected personal-data breach follows Apollo's DPDP notification duties; the platform's job is to
  answer *what was accessed, by whom, when*, which the audit trail and access logs must be able to do
  without reconstruction.
