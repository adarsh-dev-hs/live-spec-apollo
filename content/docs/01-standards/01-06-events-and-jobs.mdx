**Package** `@apollo/events`, `@apollo/jobs` · **Schema** `events`, `jobs` · **Plan** F14, F07, D29, A4 · **Effort** — · **Risk** High `DATA` · **Build in** Phase 1 (runtime), Phase 3 (spine)

Two separate mechanisms that are often confused. **Events** are a record that something happened, kept
for reporting (`F14`). **Jobs** are work to be executed later (`02-10`). A job may be triggered by an
event; an event is never a job.

## 1. Events — the one thing that cannot be retrofitted

> "If this is built after M3 rather than before it, the reports in M9 cannot be produced for the
> earlier period at all." — `M3-I31`

Every module emits an event as work happens, inside the business transaction, through the outbox.

### Naming and payload

`<schema>.<entity>.<past_tense_verb>` — `demand.requisition.status_changed`,
`placement.retention.confirmed`, `billing.invoice.raised`.

```ts
// packages/events/src/demand.ts
export const RequisitionStatusChanged = defineEvent({
  name: 'demand.requisition.status_changed',
  version: 1,
  payload: z.object({
    requisitionId: z.string().uuid(),
    clientId: z.string().uuid(),
    locationId: z.string().uuid(),
    candidateCategory: z.string(),
    careSetting: z.string(),
    serviceLine: z.enum(['permanent', 'contractual']),
    from: z.string(), to: z.string(),
    ownerId: z.string().uuid().nullable(),
    actorId: z.string().uuid().nullable(),   // null = system
    occurredAt: z.string().datetime(),
  }),
})
```

| Rule | Why |
|---|---|
| Payload is **self-contained**: it carries the dimensions a report will group by, denormalised | A mart must not have to join back to an operational table that has since changed |
| No personal data in a payload — ids only | `02-12`; the event log is long-lived |
| Versioned. A change is a new version; old versions keep being read | A taxonomy change must not silently alter historic scores or counts (`M6-I7`) |
| Emitted **inside** the business transaction via the outbox | An event that did not happen when the change did is worse than no event |
| Emitted once, from the owning service — never re-derived from a database trigger | Triggers hide causality and cannot see the actor |

### Outbox

```
service transaction ──▶ INSERT events.outbox (event, payload, occurred_at)
                                   │
worker (02-10) polls ──────────────┴──▶ publish to events.platform_event (append-only)
                                            └──▶ subscribers: 03-12 marts, job triggers
```

At-least-once delivery. Every subscriber is idempotent on `(event_id, subscriber)`.

### The five event families reporting depends on

| Family | Emitted by | Without it |
|---|---|---|
| `demand.requisition.*` (created, status_changed, revised, closed) | 03-03 | No funnel, no time-to-fill, no stage loss (`M9-I5`, `M9-I6`, `M9-I8`) |
| `demand.allocation.*` (recorded, removed) | 03-03 | **Loss by recruiter cannot be produced at all** (`M9-I8`) |
| `matching.*` (set_generated, override_applied, shortlist_submitted) | 03-07 | No override analysis, no ranking quality signal |
| `selection.*` (decided, offered, signed, declined) | 03-08 | No conversion, no rejection-reason analysis |
| `placement.*` (joined, dropped_out, trial_event_answered, retention_confirmed) | 03-09 | No trial survival, no revenue-at-risk (`M9-I7`) |

## 2. Jobs — the runtime (`02-10`)

BullMQ on Redis, one worker process, queues grouped by class so a cadence run over the whole Base B
cannot starve an interactive retry.

| Queue class | Queues | Concurrency | Note |
|---|---|---|---|
| `interactive` | `messaging.send`, `links.issue`, `files.scan` | high | user is waiting or nearly |
| `provider` | `adapters.check`, `ocr.extract`, `voice.call`, `stt.transcribe`, `esign.send` | per-provider rate limit | limits respected, not discovered through throttling (`M5-I8`) |
| `batch` | `engagement.cadence-run`, `migration.load`, `reporting.refresh`, `timesheets.build` | low | long-running, resumable |
| `schedule` | timers below | 1 | singleton, advisory-locked |

### Job rules

| Rule | Detail |
|---|---|
| Idempotent, keyed | `idempotencyKey` on enqueue; a repeat is a no-op, not a second send |
| Retry policy is per queue class | transient → exponential backoff, max 5; permanent → straight to dead-letter, no retry (`M5-I9`) |
| Dead letters are **visible and re-queueable by an operator** | `M3-I30` requires exactly this |
| Every run is recorded: which rule, which rows, when | `M5-I11` — a cadence run must be auditable |
| A batch resumes from its last checkpoint | `M1-I11` migration, `M1-I2` pause/resume |
| A singleton job takes a Postgres advisory lock | Two cadence runs at once would double-contact the base |
| Volume is projectable **before** execution | `M5-I5`, `M5-I11` — the cost preview exists because WhatsApp is billed per conversation (`OI-HS-05`) |
| A job never assumes the world it saw at enqueue time | Re-read state at execution; a candidate may have opted out since |

## 3. Which mechanism to use

| Need | Use |
|---|---|
| A report will need to count this later | **Event** |
| Another module must react | **Event** subscribed by a job |
| Something must happen at a time | **Scheduled job** |
| Something must happen after a wait | **Delayed job**, keyed so it can be cancelled |
| A provider must be called | **Job** on the `provider` class, never inline |
| Something must be undoable | Neither — a state machine transition with an audit entry |

## 4. Cost instrumentation (`OI-HS-05`)

Every provider job records its cost unit on completion — WhatsApp conversations, voice minutes,
transcription minutes, OCR pages, verification checks, e-sign envelopes, AI tokens — attributed to the
**cause**: `demand.followup`, `engagement.cadence`, `selection.offer`, `placement.checkin`.

This is not optional instrumentation. Apollo has asked for a running-cost figure and cannot produce one
without it, and per-conversation cost could exceed the build cost of the module that sends the
messages if Base B is larger than assumed.
