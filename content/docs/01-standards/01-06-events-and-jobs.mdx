Transactional outbox · BullMQ on Redis · append-only event store

---

## 1. Why this matters more than usual here

Two constraints from the delivery plan drive this entire document:

> **F14 · Event recording.** "Every module writes an event as things happen, and the reports in M9
> read those events later. **This is the one prerequisite that cannot be added afterwards.**"

> **M3-I28 · Status change log.** "Append-only transition record. D28 stage-level conversion loss
> **cannot be computed retrospectively** without it."

A module that ships without emitting its events makes the entire period before that ship date
permanently unreportable. There is no backfill. Build P09 in phase 3, before any module that
depends on it, and treat "does it emit its events" as a merge blocker.

---

## 2. Transactional outbox

**Problem:** you cannot atomically write to Postgres and publish to Redis. Publish first and the
transaction may roll back — you have announced something that did not happen. Publish after and the
process may die — the thing happened and nobody knows.

**Solution:** write the event to a table inside the same transaction, and relay it separately.

```
┌── transaction ────────────────────────────┐
│  UPDATE demand.requisition SET status=... │
│  INSERT INTO demand.status_transition ... │
│  INSERT INTO platform.audit_entry ...     │
│  INSERT INTO platform.outbox ...          │   ← the event
└───────────────────────────────────────────┘
                    │ commit
                    ▼
        outbox relay (worker, polls every 1s)
                    │
     ┌──────────────┼──────────────────┐
     ▼              ▼                  ▼
 event_store    BullMQ topic      (delete from outbox)
 (append-only)       │
                     ▼
              module subscribers
```

```sql
CREATE TABLE platform.outbox (
  id             uuid PRIMARY KEY,
  event_name     text NOT NULL,
  aggregate_type text NOT NULL,
  aggregate_id   uuid NOT NULL,
  payload        jsonb NOT NULL,
  actor_id       uuid,
  occurred_at    timestamptz NOT NULL DEFAULT now(),
  published_at   timestamptz
);
CREATE INDEX idx_outbox__unpublished ON platform.outbox (occurred_at) WHERE published_at IS NULL;
```

Delivery is **at-least-once**. Every subscriber must be idempotent. There is no exactly-once, and
pretending otherwise produces subtler bugs than accepting it.

## 3. Event naming and payloads

```
<module>.<aggregate>.<past-tense-verb>
```

| Rule | |
|---|---|
| Past tense, always | It already happened; a subscriber cannot veto it |
| Payload carries **IDs and the few facts a subscriber needs to decide whether it cares** | Not the whole entity |
| Payloads are versioned by addition only | Never remove or repurpose a field |
| A schema (zod) per event, in the module's `events/` folder | Validated on emit |
| Events are **facts, not commands** | `demand.requisition.closed`, never `matching.please_rerank` |

```ts
// packages/modules/requisitions/src/events/index.ts
export const events = defineEvents({
  'demand.requisition.created': z.object({
    requisitionId: z.string().uuid(),
    clientId:      z.string().uuid(),
    category:      candidateCategory,
    positions:     z.number().int().positive(),
    source:        intakeChannel,
  }),
  'demand.requisition.held': z.object({
    requisitionId: z.string().uuid(),
    reasonCode:    z.string(),
  }),
})
```

## 5. Subscribers

```ts
// packages/modules/requisitions/src/subscribers/on-dropout-recorded.ts
export const onDropoutRecorded = defineSubscriber({
  event: 'place.dropout.recorded',
  name:  'requisitions.reopen-position',           // unique — used as the idempotency key
  handler: async ({ payload }) => {
    await RequisitionService.reopenPosition({
      requisitionId: payload.requisitionId,
      reason: 'candidate_dropout',
    })
  },
})
```

| Rule | |
|---|---|
| Idempotent. Always. | At-least-once delivery. Key on `(subscriberName, eventId)`. |
| Runs in the worker, never in the API process | |
| Failure retries with backoff, then dead-letters and alerts | Never silently dropped |
| A subscriber may **not** emit a synchronous chain more than 2 deep | Depth 3 means the boundary is wrong |
| Slow work is enqueued, not done in the handler | |
| No subscriber may write another module's tables | It calls that module's service |

## 6. Queues

BullMQ. One queue per unit of work, named `<module>.<verb>`.

| Queue | Concurrency | Attempts | Backoff | Notes |
|---|---|---|---|---|
| `platform.outbox-relay` | 1 | ∞ | 1s fixed | Single consumer, ordering matters |
| `platform.event-dispatch` | 10 | 5 | exp 2s | Fan-out to subscribers |
| `files.virus-scan` | 5 | 3 | exp 10s | Blocks file availability |
| `inbound.receive` | 20 | 5 | exp 5s | Webhook → InboundRecord |
| `intake.parse` | 10 | 3 | exp 30s | Model-dependent; failures → manual entry queue |
| `intake.transcribe` | 5 | 3 | exp 60s | Per-minute billed — do not retry blindly |
| `messaging.send` | 20 | 5 | exp 30s | Rate-limited per provider |
| `messaging.receipt` | 20 | 3 | exp 10s | Delivery receipts |
| `engagement.cadence-run` | 2 | 2 | exp 5m | Whole-base sweeps; heavy |
| `engagement.decay` | 1 | 2 | exp 5m | Scheduled |
| `matching.rank` | 5 | 3 | exp 30s | CPU-bound |
| `credentials.verify` | 10 | 3 | exp 5m | External registries, often slow |
| `placements.checkin-fire` | 10 | 3 | exp 5m | Day 0/7/30/60/90 |
| `attendance.timesheet-build` | 5 | 3 | exp 60s | |
| `billing.raise-invoice` | 2 | 3 | exp 60s | **Low concurrency deliberately** — money |
| `analytics.project` | 5 | 5 | exp 30s | Event → projection |
| `migration.batch` | 1 | 1 | — | Locked; one batch at a time, resumable, no auto-retry |
| `payroll.run` | 1 | 1 | — | Locked; manual retry only |

**`migration.batch`, `billing.raise-invoice` and `payroll.run` deliberately do not auto-retry
aggressively.** A blind retry there duplicates money or data. They fail loudly and a human decides.

## 7. Job rules

| Rule | Why |
|---|---|
| Payloads carry **IDs, not entities** | State may have changed since enqueue; re-read it |
| Every job has a deterministic `jobId` | BullMQ dedupes; the same work never queues twice |
| Every consumer is idempotent | Retries are normal, not exceptional |
| Jobs are small; large work fans out into per-item jobs | One job per migration *record*, not per batch |
| Progress is reported for anything a user watches | `M1-I2` requires observable progress mid-run |
| Every queue has a DLQ, an alarm on DLQ depth, and a documented replay path | A job that fails permanently is never silently dropped |
| No job runs longer than 15 minutes | Split it |

## 8. Schedulers

BullMQ repeatable jobs, registered once at worker boot. **Never `node-cron`, never a `setInterval`,
never an OS cron** — schedules must survive a deploy and must not double-fire across tasks.

| Schedule | Cadence | Owner | Does |
|---|---|---|---|
| `engagement.decay` | Hourly | engagement | Decays availability confidence per base schedule (A3) |
| `engagement.cadence-select` | Every 4h | engagement | Selects who to contact next, enqueues sends (A4) |
| `requisitions.age-tick` | Hourly | requisitions | Recomputes age, respecting hold pauses |
| `intake.follow-up-chase` | Hourly | intake | Chases incomplete requisitions on their origin channel |
| `intake.follow-up-escalate` | Hourly | intake | Escalates to the owner after the configured window |
| `placements.checkin-due` | Daily 06:00 IST | placements | Fires day 0/7/30/60/90 check-ins |
| `placements.retention-deem` | Daily 06:00 IST | placements | Applies the deemed-confirmation window |
| `attendance.timesheet-close` | Daily 02:00 IST | attendance | Builds timesheets for closed periods |
| `attendance.approval-deem` | Daily 06:00 IST | attendance | Applies the deemed-approval window |
| `credentials.expiry-warn` | Daily 07:00 IST | credentials | Warns before a credential expires |
| `contracts.renewal-alert` | Daily 07:00 IST | contracts | Alerts before a contract runs out |
| `analytics.project` | Every 15 min | analytics | Refreshes projections |
| `analytics.mis-pack` | Monthly, 1st 05:00 IST | analytics | Generates the leadership pack |
| `collections.dunning` | Daily 09:00 IST | collections | Chases overdue invoices (M15) |
| `platform.token-expiry` | Hourly | links | Expires unanswered links |

All IST times are computed from UTC with `Asia/Kolkata` — Apollo operates on Indian business hours,
and a check-in that fires at 06:00 UTC arrives at 11:30 in the morning, which is not what "daily
morning" means to anyone using the system.

**The two deeming schedulers are revenue-critical.** If `retention-deem` or `approval-deem` stops
running, invoices silently stop being raised and nobody notices until month end. Both have a
heartbeat alarm on last-successful-run, not just on failure.

## 9. Event store and projections

```sql
CREATE TABLE platform.event_store (
  id             uuid PRIMARY KEY,
  event_name     text NOT NULL,
  aggregate_type text NOT NULL,
  aggregate_id   uuid NOT NULL,
  payload        jsonb NOT NULL,
  actor_id       uuid,
  occurred_at    timestamptz NOT NULL,
  sequence       bigserial
);
CREATE INDEX idx_event_store__aggregate ON platform.event_store (aggregate_type, aggregate_id, sequence);
CREATE INDEX idx_event_store__name_time ON platform.event_store (event_name, occurred_at DESC);
```

Append-only, by grant. Retained for the full contract period and beyond — a billing query may land
years later (`OI-HS-14`).

**Projections** are reporting tables derived by replaying events (`02-09`, `03-14`):

| Rule | |
|---|---|
| Rebuildable from `event_store` alone, from zero, at any time | This is the test that the events are sufficient |
| Never written by a business module — only by the projector | |
| A projection bug is fixed by fixing the projector and replaying, never by patching the table | |
| Reports read projections, never operational tables | |

**Event sourcing is not the write model.** Current state lives in normal tables. Events exist for
reporting and for reaction. Do not reconstruct a requisition by replaying its events.

---

## 10. Ordering

Events are ordered **per aggregate**, not globally.

- `event_store.sequence` gives a total order for replay
- Dispatch is concurrent, so two subscribers may see events out of order relative to each other
- If a subscriber needs ordering, it partitions by `aggregate_id` (BullMQ group key)
- **Never assume** `demand.requisition.completed` arrives before `demand.requisition.allocated` in a
  different subscriber

Where ordering genuinely matters — invoice raising, payroll — the work is serialised by a distributed
lock on the aggregate, not by hoping the queue behaves.

## 11. Observability

| Signal | Alarm |
|---|---|
| Queue depth per queue | > 1000 for 5 min |
| DLQ depth | > 0 |
| Outbox lag (oldest unpublished) | > 60s |
| Job failure rate | > 5% over 15 min |
| Scheduler heartbeat | Missed run for any revenue-critical schedule |
| Event dispatch latency p95 | > 10s |

Every job logs start, finish and duration with its `jobId`. A BullMQ dashboard is exposed in `dev`,
`qa` and `uat`; in `prod` it is behind admin permission and read-only.

## 12. Local development

```bash
pnpm dev:worker           # runs consumers and schedulers against local Redis
pnpm jobs:trigger <name>  # fire a scheduled job immediately
pnpm jobs:replay <id>     # replay one DLQ job
pnpm events:tail          # tail the event store
pnpm events:reproject     # rebuild all projections from scratch
```

`pnpm events:reproject` runs in CI against the seed dataset. If projections cannot be rebuilt from
events alone, the events are incomplete — and that is the failure the plan warns cannot be fixed
retrospectively.
