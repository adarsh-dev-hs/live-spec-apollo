**Package** `@apollo/api`, `@apollo/worker` · **Schema** all · **Plan** D11 · **Effort** — · **Risk** Low · **Build in** Phase 1

Fastify 5 on Node 22, TypeScript strict, **no ORM**. These rules are assumed by every spec's §7 API
surface and §8 events and jobs.

## 1. The four layers

```
route      validate input · resolve principal · call one service · shape one response   (no logic)
service    business rules · owns the transaction · writes audit · emits events           (no SQL)
repository hand-written SQL · maps rows to domain types                                  (no rules)
domain     entities, state machines, invariants — pure, no I/O, unit-tested alone
```

A route that contains an `if` about business state is in the wrong layer. A repository that decides
anything is in the wrong layer.

## 2. Route definition

Schema-first. The JSON Schema that validates the request is the same object that generates the
OpenAPI document (`01-04`), so the contract cannot drift from the handler.

```ts
// modules/requisitions/src/routes/hold-requisition.ts
import { HoldRequisitionBody, RequisitionResponse } from '@apollo/contracts'

export const holdRequisition: FastifyPluginAsyncZod = async (app) => {
  app.post('/v1/requisitions/:id/hold', {
    schema: {
      operationId: 'holdRequisition',
      tags: ['requisitions'],
      params: RequisitionIdParams,
      body: HoldRequisitionBody,
      response: { 200: RequisitionResponse, 409: ProblemDetails },
    },
    preHandler: [app.authenticate, app.requirePermission('requisition:hold')],
  }, async (req, reply) => {
    const requisition = await app.services.requisitions.hold({
      requisitionId: req.params.id,
      reasonId: req.body.reasonId,
      actor: req.principal,
    })
    return reply.send(requisition)
  })
}
```

Rules: `operationId` on every route (the client generator uses it); every route declares its error
responses; `preHandler` carries auth and permission — **never** an `if` inside the handler;
one service call per route.

## 3. Services and transactions

A service method is one unit of work. It opens one transaction and the audit write and the event
outbox write happen inside it.

```ts
async hold({ requisitionId, reasonId, actor }: HoldInput): Promise<Requisition> {
  return this.db.tx(async (tx) => {
    const current = await this.repo.findForUpdate(tx, requisitionId)
    if (!current) throw new NotFoundError('requisition', requisitionId)

    // domain layer decides — pure, testable without a database
    const next = requisitionMachine.apply(current, { type: 'HOLD', reasonId, at: actor.now })

    await this.repo.updateState(tx, next)
    await this.repo.insertStatusTransition(tx, {          // append-only (M3-I28)
      requisitionId, from: current.status, to: next.status, actor: actor.id, at: actor.now,
    })
    await this.audit.record(tx, {                          // 02-02, same transaction
      entity: 'requisition', entityId: requisitionId, action: 'hold',
      actor, before: current, after: next,
    })
    await this.events.emit(tx, 'demand.requisition.held', { // 02-11 outbox, same transaction
      requisitionId, clientId: next.clientId, reasonId, at: actor.now,
    })
    return next
  })
}
```

| Rule | Why |
|---|---|
| One transaction per service method, never nested | Predictable rollback |
| Audit and event writes are **inside** the transaction | An action that happened but was not recorded is worse than one that failed |
| No HTTP call inside a transaction | A provider timeout must not hold a row lock. Enqueue a job instead. |
| `SELECT … FOR UPDATE` before any state transition | Two recruiters pressing Hold at once |
| Idempotency key on every externally triggered write | Webhook redelivery is normal (`M3-I18`) |

## 4. No ORM — what replaces it

`pg` (node-postgres) with a thin `@apollo/db` layer. Nothing generates SQL.

```ts
// modules/requisitions/src/repositories/requisition-repository.ts
export class RequisitionRepository {
  async findBoardRows(tx: Queryable, filter: BoardFilter): Promise<BoardRow[]> {
    const { rows } = await tx.query<BoardRowDto>(sql`
      SELECT r.id, r.reference, r.status, r.category, r.care_setting,
             r.positions_requested, r.positions_filled,
             r.positions_requested - r.positions_filled AS positions_open,
             r.days_aged, r.rate_matched,
             c.name AS client_name, l.name AS location_name,
             owner.full_name AS owner_name,
             COALESCE(a.recruiters, '[]'::jsonb) AS allocated_recruiters
        FROM demand.requisition r
        JOIN clients.client   c     ON c.id = r.client_id
        JOIN clients.location l     ON l.id = r.location_id
        LEFT JOIN identity.user owner ON owner.id = r.owner_id
        LEFT JOIN LATERAL (
              SELECT jsonb_agg(jsonb_build_object('id', u.id, 'name', u.full_name)) AS recruiters
                FROM demand.allocation_record ar
                JOIN identity.user u ON u.id = ar.recruiter_id
               WHERE ar.requisition_id = r.id AND ar.removed_at IS NULL
        ) a ON TRUE
       WHERE r.status = ANY(${filter.statuses})
         AND (${filter.clientId}::uuid IS NULL OR r.client_id = ${filter.clientId})
         AND (${filter.unallocatedOnly} = FALSE OR a.recruiters IS NULL)
         AND r.location_id = ANY(${filter.scopeLocationIds})   -- data scope, never optional
       ORDER BY r.days_aged DESC
       LIMIT ${filter.limit} OFFSET ${filter.offset}
    `)
    return rows.map(toBoardRow)
  }
}
```

| Rule | Detail |
|---|---|
| Every query is parameterised through the `sql` tagged template | String concatenation of user input is a build failure (lint rule) |
| One repository per aggregate, one method per query shape | The fulfilment board's query is written once, not assembled |
| **No N+1.** A list endpoint issues exactly one query | Use `LATERAL` + `jsonb_agg` for children, as above |
| Row DTO → domain type mapping is explicit (`toBoardRow`) | `snake_case` never leaks past the repository |
| Repositories accept a `Queryable` (pool or transaction) as the first argument | The service decides the transaction, not the repository |
| Query timeout: 5s interactive, 60s job | A slow board query fails visibly instead of hanging the console |
| `EXPLAIN ANALYZE` in the PR description for any new query over a table expected past 100k rows | Migrated base volume is unknown (`OI-A-02`) |

## 5. Errors

`@apollo/errors` defines the taxonomy; every route returns RFC 9457 Problem Details (`01-04`).

| Class | HTTP | Use |
|---|---|---|
| `ValidationError` | 400 | Schema or business validation, with `errors[]` naming each field |
| `AuthenticationError` | 401 | No or invalid principal |
| `PermissionError` | 403 | Authenticated but not allowed — never leaks whether the record exists |
| `NotFoundError` | 404 | Also returned instead of 403 where existence itself is sensitive |
| `ConflictError` | 409 | Illegal state transition, duplicate, concurrent edit |
| `PreconditionError` | 422 | Valid request the domain refuses — "close requires a reason" (`M3-I15`) |
| `UpstreamError` | 502 | A named provider failed; `retryable` boolean decides whether the job retries |
| `UpstreamUnavailableError` | 503 | Provider down; routes to the manual fallback (`02-13`) rather than failing the candidate |

Never throw a bare `Error` in a service. Never catch and swallow. An unexpected error is a 500 with a
correlation id and a full log entry, and the response body carries nothing else.

## 6. Logging, tracing, config

- Structured JSON via `@apollo/observability` (pino). **Never** log personal data: no name, phone,
  email, Aadhaar, PAN, bank details or document content. Log ids.
- Every request carries `x-correlation-id`, generated if absent, propagated into jobs and provider
  calls, and returned on the response.
- OpenTelemetry spans around HTTP handlers, SQL calls, queue handlers and provider calls. Provider
  spans record cost units — conversations, minutes, pages, checks — because `OI-HS-05` needs them.
- Config is read **once** at boot through `@apollo/config`, Zod-validated, and fails to start on a
  missing variable. `process.env` appears nowhere else.
- Secrets come from AWS Secrets Manager at boot; nothing is baked into an image.

## 7. Async work

Anything that calls a provider, takes more than 200ms, or must survive a restart is a job (`02-10`),
never a floating promise. Fire-and-forget is a lint failure.

```ts
// wrong — lost on deploy, invisible when it fails
void this.whatsapp.send(message)

// right — retried, dead-lettered, observable, and it survives a restart
await this.jobs.enqueue('messaging.send', { messageId }, { idempotencyKey: messageId })
```
