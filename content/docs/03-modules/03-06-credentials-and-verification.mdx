## 1. Purpose

The credential object — issuer, validity period, verification method — shared across both supply
bases, with document OCR, identity verification behind the M1 adapter layer, and a verification queue
with pendency tracking.

This is the module that decides whether Apollo can put a person in front of a hospital. A nurse with
an expired registration placed into an ICU is a clinical and legal problem, not a data-quality one.

## 5. Data model

### 5.1 Credential

```sql
CREATE TABLE supply.credential (
  id                uuid PRIMARY KEY,
  candidate_id      uuid NOT NULL REFERENCES supply.candidate(id),
  credential_type   credential_type_enum NOT NULL,   -- 'nursing_registration'|'medical_registration'|
                                                     -- 'allied_registration'|'pharmacy_registration'|
                                                     -- 'degree'|'diploma'|'identity'|'pan'|
                                                     -- 'experience'|'training'
  issuer_code       text,                            -- 'INC'|'NMC'|'TN_NURSING_COUNCIL'|'UIDAI'|...
  issuer_name       text NOT NULL,
  registration_number text,                          -- C3 for identity types
  issued_on         date,
  valid_from        date,
  valid_to          date,                            -- NULL = does not expire
  status            credential_status_enum NOT NULL,
  verification_method verification_method_enum NOT NULL, -- 'registry_api'|'aggregator'|
                                                          -- 'document_manual'|'self_declared'
  verified_at       timestamptz,
  verified_by       uuid,
  outcome           verification_outcome_enum,       -- 'green'|'amber'|'red'
  outcome_note      text,
  document_id       uuid,                            -- platform.document
  is_active         boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL
);
CREATE INDEX idx_credential__candidate ON supply.credential (candidate_id) WHERE is_active;
CREATE INDEX idx_credential__expiry ON supply.credential (valid_to)
  WHERE is_active AND valid_to IS NOT NULL AND status = 'verified';
```

**One credential set per candidate, shared across both bases** (A2). A nurse moving from the shift
pool to a permanent placement does not get re-verified.

### 5.2 Verification case

```sql
CREATE TABLE supply.verification_case (
  id               uuid PRIMARY KEY,
  reference        text NOT NULL UNIQUE,             -- 'VER-2026-009214'
  candidate_id     uuid NOT NULL,
  credential_id    uuid,                             -- NULL for identity checks not tied to a credential
  check_type       check_type_enum NOT NULL,
  status           verification_case_status_enum NOT NULL,
  outcome          verification_outcome_enum,
  method_used      verification_method_enum,
  adapter_call_id  uuid,                             -- platform.adapter_call — the evidence
  queued_at        timestamptz NOT NULL DEFAULT now(),
  started_at       timestamptz,
  resolved_at      timestamptz,
  assigned_to      uuid,
  resolution_note  text,
  -- PENDENCY: the number the verification team is measured on
  pendency_seconds bigint GENERATED ALWAYS AS
    (EXTRACT(EPOCH FROM (COALESCE(resolved_at, now()) - queued_at))::bigint) STORED,
  sla_breached     boolean NOT NULL DEFAULT false
);
CREATE INDEX idx_verification_case__queue ON supply.verification_case (status, queued_at ASC)
  WHERE status IN ('queued','in_progress','awaiting_registry','manual_review');
CREATE INDEX idx_verification_case__candidate ON supply.verification_case (candidate_id);
```

### 5.3 Document extraction

```sql
CREATE TABLE supply.document_extraction (
  id             uuid PRIMARY KEY,
  document_id    uuid NOT NULL,                     -- platform.document
  candidate_id   uuid NOT NULL,
  extracted      jsonb NOT NULL,                    -- { registrationNumber:'...', name:'...', validTo:'...' }
  confidence     jsonb NOT NULL,                    -- PER FIELD
  adapter_call_id uuid,
  reviewed_at    timestamptz,
  reviewed_by    uuid,
  corrected      jsonb,                             -- what the human changed
  status         extraction_status_enum NOT NULL    -- 'extracted'|'reviewed'|'rejected'
);
```

**Per-field confidence, and the corrections kept separately.** *"Check what the OCR read against the
actual document, and correct it"* (`M4-I14`). Keeping `extracted` and `corrected` apart is what makes
OCR accuracy measurable over time rather than a matter of opinion.

### 5.4 Required checks per category

Configured in P03 as `supply.required_checks.<category>`:

## 6. State machines

**Credential:** `claimed → submitted → checking → verified (green) | flagged (amber) | rejected (red) → expired`

| Transition | Rules |
|---|---|
| `claimed → submitted` | A document is attached |
| `submitted → checking` | A verification case is opened |
| `checking → verified` | Registry or aggregator returned green, or a human verified the document |
| `checking → flagged` | Amber — partial match, or the registry was unreachable and a person accepted the document with a note |
| `checking → rejected` | Red — mismatch, forgery suspected, registration not found |
| `verified → expired` | `valid_to` passed. **Automatic.** |
| `expired → checking` | A renewed credential is submitted |

**VerificationCase:** `queued → in_progress → resolved` \| `awaiting_registry` \| `manual_review`

`awaiting_registry` and `manual_review` are distinct because they have different owners and different
resolution times. A registry that is down resolves itself; a manual review needs a person.

**Jobs**

| Job | Cadence | Notes |
|---|---|---|
| `credentials.run-check` | On demand | Through `02-12`; **manual fallback where a registry has no API** |
| `credentials.extract` | On document available | OCR port |

| `credentials.retry-registry` | Every 4h | Retries `awaiting_registry` cases |

## 9. Frontend — `/verification`

### 9.1 Verification queue (`M4-I11`)

*"The verification team's work queue."*

`<DataTable/>`: reference, candidate, category, check type, status, **pendency (how long it has been
waiting)**, assigned to, SLA state. Default sort: oldest first. Filter by status, check type,
category, assignee, SLA breach.

Pendency is the number this team is measured on, so it is a first-class column with visual banding,
not a computed detail.

### 9.2 Verification detail (`M4-I12`)

*"One candidate's checks, each showing green, amber or red, with the evidence behind it."*

Per check: outcome, method, when, by whom, and **the evidence** — the adapter call (request and
response, redacted) linked through to `02-12`'s call log, or the document and its extraction.

Actions: re-run a check, resolve manually with a note, request a document from the candidate (via
`02-07`).

### 9.3 Credentials (`M4-I13`)

*"A candidate's registrations and qualifications: who issued them, when they expire, how they were
checked."*

Per credential: type, issuer, registration number, validity dates, status with outcome colour,
verification method, document. Expiring credentials are visually prominent — an expiring
registration is a candidate about to become unplaceable.

### 9.4 Document review (`M4-I14`)

Split view: the document on one side, the extracted fields on the other. **Low-confidence fields are
flagged.** A reviewer corrects and confirms; corrections are stored separately from the extraction so
accuracy is measurable.

### 9.5 Pendency report

Cases by age band, by check type, by assignee. SLA breaches. This is what `M9` reports on and what a
verification lead uses to allocate work.

## 12. Notes for the implementer

**Consent first, always.** `runChecks` must throw if there is no valid, unwithdrawn `verification`
consent for that candidate. This is the one place where a missing check is a regulatory problem
rather than a bug, and it is trivially easy to omit under time pressure.

**Manual fallback is the normal path for several registries, not an error branch.** Some Indian
councils have no API and never will. The verification team resolving a case by looking at a
certificate is a first-class outcome that produces the same green/amber/red vocabulary as an API
call. Build the manual path with as much care as the automated one — it will carry real volume.

**The evidence link matters more than the outcome.** When a hospital asks "how do you know this nurse
is registered", the answer is the adapter call log or the reviewed document, not a green badge. Make
that reachable in one click from the verification detail screen.

**Expiry is a background job, not a computed property.** A credential that expired at midnight must
change state, emit an event, warn the candidate and reach the ranking engine — none of which happens
if expiry is only ever evaluated when someone opens the record.
