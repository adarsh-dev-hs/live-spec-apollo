## 1. Purpose

The candidate mobile app: self-registration, resume upload and parsing, job and shift discovery,
application tracking, document upload, availability answering, and **shift check-in**.

The plan flags this as a three-way shared build and a hard dependency:

> D3 sits in M4, but **shift discovery, acceptance and check-in serve M8**, and its response surface
> is one of the two A14 channels in M5. Because **shift attendance is captured by app check-in with
> no alternative route, D3 is a hard dependency of the contractual invoice chain — no app, no
> attendance, no shift invoice.** Sequence it against all three consumers.

**App store enrolment and first review are calendar time that no amount of team size removes.**
Start in month 2.

## 5. Data model

Most state lives in `03-05` and `03-12`. This module owns two things.

### 5.1 Check-in (`M4-I7`)

```sql
CREATE TABLE supply.app_check_in (
  id                uuid PRIMARY KEY,
  candidate_id      uuid NOT NULL,
  shift_demand_line_id uuid NOT NULL,
  shift_acceptance_id  uuid NOT NULL,
  kind              check_in_kind_enum NOT NULL,     -- 'in' | 'out'
  recorded_at       timestamptz NOT NULL,            -- when the CANDIDATE pressed it
  received_at       timestamptz NOT NULL DEFAULT now(),  -- when the SERVER got it
  -- location: RECORDED, NOT ENFORCED in R1 (enforcement is M12)
  geo_lat           numeric(9,6),
  geo_lng           numeric(9,6),
  geo_accuracy_m    numeric(8,2),
  geo_source        text,                            -- 'gps'|'network'|'unavailable'
  device_id         text,
  is_offline_sync   boolean NOT NULL DEFAULT false,
  client_event_id   text NOT NULL,                   -- IDEMPOTENCY across offline retries
  UNIQUE (candidate_id, client_event_id)
);
CREATE INDEX idx_check_in__shift ON supply.app_check_in (shift_demand_line_id, kind);
```

**`recorded_at` and `received_at` are separate, and both matter.** A nurse checks in at 19:00 in a
hospital basement with no signal; the phone syncs at 22:30. The shift started at 19:00 and that is
what gets billed and paid — but the gap is visible and auditable.

**`client_event_id` is the idempotency key.** An offline queue retrying on reconnect must not produce
three check-ins.

**Location is recorded, not enforced** (`M8` CLOSED decision): *"Release 1 records a location stamp
against each check-in without enforcing a boundary; geo-fencing moves off the exclusion list to a
named Phase 2 item so the field exists when enforcement is specified."* `03-18` switches enforcement
on with **no data change**.

### 5.2 Device registration

```sql
CREATE TABLE supply.candidate_device (
  id            uuid PRIMARY KEY,
  candidate_id  uuid NOT NULL,
  device_id     text NOT NULL,
  platform      text NOT NULL,                   -- 'ios'|'android'
  push_token    text,
  app_version   text,
  last_seen_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (candidate_id, device_id)
);
```

## 8. Events and jobs

**Emits:** `supply.candidate.registered` · `supply.application.created` ·
`supply.shift.accepted` / `.cancelled` · **`supply.check_in.recorded`** (consumed by `03-12`) ·
`engage.availability.responded` (consumed by `03-08`)

**Subscribes:** `demand.shift_line.created` → push notification to matching Base B candidates ·
`select.offer.sent` → push · `place.trial_event.due` → push · `supply.credential.expiring` → push

**Jobs:** `app.notify-new-shifts` (every 30 min) — batched push for newly opened shift lines matching
a candidate's profile. Batched deliberately: a nurse receiving eleven separate notifications in a
minute uninstalls the app, and the app is on the revenue critical path.

## 9. Frontend — `apps/mobile` (React Native)

### 9.1 Sign up (`M4-I1`)

Phone → OTP → category → **consent**. Consent is purpose-specific and versioned; the notice text is
shown, not linked (`01-10 §4`). Minimum friction: a shift nurse abandoning at step four costs Apollo
a supply record.

### 9.2 Build profile (`M4-I2`)

Two paths, both offered: **upload a CV** (parsed, then corrected) or **type it in**. Parsed fields
are pre-filled and **low-confidence fields are visually flagged** so the candidate knows what to
check. Nothing is written until the candidate confirms.

### 9.3 Specialty details (`M4-I3`)

The category-specific attributes, rendered from `03-05`'s definitions. The screen states plainly that
these determine which jobs and shifts they are matched to — *"these are exactly what M6 ranks on"*.

### 9.4 Jobs (`M4-I4`) — Base A

Permanent roles: title, location, salary band, requirements. **Whether the hospital is named depends
on the client's `disclose_identity_to_candidates` flag** (`OI-HS-13`, `03-01 §11`).

### 9.5 Shifts (`M4-I5`) — Base B

*"This is the reason shift workers open the app regularly."*

Open shifts by date, distance and rate. Calendar and list views. Accept, and see it appear in "my
shifts". Cancellation within a configurable window; later cancellations require contacting Ops.

This screen is the app's retention mechanism. If it is slow or empty, the whole Base B model —
including attendance and therefore shift invoicing — degrades.

### 9.6 My applications (`M4-I6`)

*"Where a candidate sees what is happening with their applications and shifts."* Status per
application in plain language: applied → shortlisted → interview → offer → joined. Upcoming shifts,
past shifts, earnings summary.

### 9.7 Shift check-in (`M4-I7`)

**The most important screen in the app — it is the only way attendance reaches the platform.**

Requirements beyond the obvious:

| | |
|---|---|
| **Works offline** | Queue locally, sync on reconnect, show a clear pending state. Hospital basements have no signal and this cannot be a failure mode. |
| **Records the candidate's timestamp** | `recorded_at`, not server time |
| **Idempotent** | `clientEventId` survives retries |
| **Location captured, never blocking** | Recorded with accuracy and source; a refused permission or no fix does not prevent check-in in R1 |
| Large targets, one hand, gloves | Used at a ward door at shift change |
| Obvious state | "Checked in at 19:02" — no ambiguity about whether it worked |
| Raise an issue | Wrong shift, ward changed, cannot start — reaches `03-12`'s issue path |

### 9.8 My documents (`M4-I8`)

Which documents are needed, which are uploaded, which are verified, which were rejected **and why**.
Camera capture with client-side compression (`02-04 §9`).

### 9.9 Notification settings (`M4-I9`)

Which channels the candidate accepts. **`03-08` must respect this on every send** — enforced at send
time, not enqueue time (`02-07 §6`).

### 9.10 Am I available (`M4-I10`)

The availability question, answered in the app. *"Same answer format as the WhatsApp version"* — one
schema, two channels, and a test that asserts both produce identical records (`03-08`).

## 12. Notes for the implementer

**Start in month 2, before the backend is ready.** App store enrolment, the D-U-N-S registration and
the first review are the long poles, and they are all administrative. The app can be built against
fakes and the seed dataset.

**Check-in is the revenue path — build it first and build it defensively.** Offline queue,
idempotency key, candidate-side timestamp, unambiguous confirmation. Every other screen can degrade
gracefully; this one cannot, because a lost check-in is an unbilled shift and an unpaid nurse.

**One availability schema, two channels.** Write the test that submits the same answer through
`/me/availability-response` and through the WhatsApp webhook, and asserts the resulting
`AvailabilityResponse` rows are structurally identical. That is A14's actual requirement, and it is
the kind of thing that quietly diverges.

**Assume a mid-range Android on a poor connection.** Compress images before upload, paginate
everything, cache aggressively, and never block a screen on a network call that is not essential to
it.
