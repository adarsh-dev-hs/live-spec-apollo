## 1. Purpose

The requisition object and its lifecycle: creation, versioning, hold, revise, close; shift templates
and demand lines; the fulfilment board and aging. Plus the owner field and the record of the
allocation made on the daily morning call.

This is the operational heart of the platform. **The fulfilment board is the highest-traffic screen
in the system**, and the requisition is what M6 ranks against, M7 quotes, M8 counts placements
against, and M9 reports by.

---

## 2. Scope

**In** — requisition object, states, versioning · manual creation and verbal capture entry · the
requisition record view with source evidence · fulfilment board with live demand, aging and fill ·
shift templates and shift demand lines · hold / revise / close · owner and allocation record ·
append-only status transition log

**Out** — intake channels and parsing → `03-03` · **prioritisation engine, recruiter suggestion and
approval workflow → `03-20` (M14)** — R1 carries an owner field and a record of a decision made
outside the system, not an assignment engine · ranking → `03-09` · placements → `03-11`

**Explicitly not built in R1** (stated in the plan): working out which vacancies matter most · any
approval step before a vacancy goes live · the system suggesting or balancing recruiter allocation ·
enforcing a cap on how many vacancies a recruiter holds (the 15–16 norm is **not enforced**) ·
automatic merging of duplicate requisitions.

## 5. Data model

### 5.1 Requisition

```sql
CREATE TABLE demand.requisition (
  id                uuid PRIMARY KEY,
  reference         text NOT NULL UNIQUE,             -- 'REQ-2026-00142'
  client_id         uuid NOT NULL,
  location_id       uuid NOT NULL,
  department_id     uuid,
  engagement_type   engagement_type_enum NOT NULL,    -- 'permanent' | 'contractual'
  category          candidate_category_enum NOT NULL, -- 'nurse'|'doctor'|'allied'
  role_code         text NOT NULL,
  positions         integer NOT NULL CHECK (positions > 0),
  positions_filled  integer NOT NULL DEFAULT 0,
  attributes        jsonb NOT NULL DEFAULT '{}',      -- A9 per-category set — see §11
  start_date        date,
  end_date          date,
  rate_card_line_id uuid,                             -- resolved at creation, frozen
  agreed_rate       numeric(14,2),                    -- may differ from baseline → M9 variance
  status            requisition_status_enum NOT NULL,
  completeness_score numeric(4,3),
  missing_fields    text[] NOT NULL DEFAULT '{}',
  source_channel    inbound_channel_enum NOT NULL,
  source_inbound_id uuid,                             -- the evidence
  owner_user_id     uuid,                             -- D14 thin: an owner field
  priority          integer,                          -- populated by M14 only
  -- age clock
  age_started_at    timestamptz,
  age_paused_at     timestamptz,
  age_accumulated_seconds bigint NOT NULL DEFAULT 0,
  -- close
  close_reason_code text,
  closed_at         timestamptz,
  hold_reason_code  text,
  current_version_id uuid,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL,
  version integer NOT NULL DEFAULT 1,

  CONSTRAINT ck_requisition__close_reason
    CHECK (status <> 'closed' OR close_reason_code IS NOT NULL)
);
CREATE INDEX idx_requisition__board ON demand.requisition (status, client_id, created_at DESC)
  WHERE status IN ('open','in_fulfilment','partially_filled');
CREATE INDEX idx_requisition__owner ON demand.requisition (owner_user_id, status);
CREATE INDEX idx_requisition__client ON demand.requisition (client_id, status);
```

**The age clock is three columns, not one.** `age_started_at` + `age_paused_at` +
`age_accumulated_seconds` is what makes *"putting it on hold stops the age counter; releasing it
restarts from where it stopped, not from zero"* (`00-03 §4`) correct. A single `created_at`-based
calculation cannot express a pause.

```
ageSeconds = age_accumulated_seconds
           + (age_paused_at IS NULL AND age_started_at IS NOT NULL
              ? now() - age_started_at : 0)
```

### 5.2 Versions (`M3-I11`)

```sql
CREATE TABLE demand.requisition_version (
  id             uuid PRIMARY KEY,
  requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
  version_number integer NOT NULL,
  snapshot       jsonb NOT NULL,          -- full requisition at this version
  change_summary jsonb NOT NULL,          -- field-level diff
  change_source  text NOT NULL,           -- 'manual'|'channel_revision'|'system'
  source_inbound_id uuid,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  UNIQUE (requisition_id, version_number)
);
```

*"Revision is a versioning event, not an edit"* (`M3-I11`). A client emailing "make that 4 nurses,
not 2" creates a version, keeps the original, and links the new inbound record.

### 5.3 Shift templates and demand lines

```sql
CREATE TABLE demand.shift_template (
  id            uuid PRIMARY KEY,
  client_id     uuid NOT NULL,
  location_id   uuid,
  name          text NOT NULL,                -- 'ICU Night — 12h'
  start_time    time NOT NULL,
  end_time      time NOT NULL,
  crosses_midnight boolean NOT NULL DEFAULT false,
  break_minutes integer NOT NULL DEFAULT 0,
  days_of_week  integer[] NOT NULL,           -- 0=Sun
  is_active     boolean NOT NULL DEFAULT true
);

CREATE TABLE demand.shift_demand_line (
  id             uuid PRIMARY KEY,
  requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
  template_id    uuid REFERENCES demand.shift_template(id),
  shift_date     date NOT NULL,
  start_at       timestamptz NOT NULL,
  end_at         timestamptz NOT NULL,
  positions      integer NOT NULL DEFAULT 1,
  positions_filled integer NOT NULL DEFAULT 0,
  status         shift_line_status_enum NOT NULL,  -- 'open'|'partially_filled'|'filled'|'cancelled'|'expired'
  rate_card_line_id uuid,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX idx_shift_line__open ON demand.shift_demand_line (shift_date, status)
  WHERE status IN ('open','partially_filled');
CREATE INDEX idx_shift_line__req  ON demand.shift_demand_line (requisition_id, shift_date);
```

Contract staffing only. Expanding a template over a date range generates lines *"without manual entry
per shift"* (`M3-I13`). Consumed downstream by `03-09` for shift-level ranking and `03-12` for
attendance.

### 5.4 Allocation (`M3-I16`)

```sql
CREATE TABLE demand.allocation_record (
  id             uuid PRIMARY KEY,
  requisition_id uuid NOT NULL,
  recruiter_user_id uuid NOT NULL,
  allocated_at   timestamptz NOT NULL DEFAULT now(),
  allocated_by   uuid NOT NULL,
  allocation_note text,
  unallocated_at timestamptz,                 -- correction = a NEW row, plus closing this one
  source         text NOT NULL DEFAULT 'morning_call'
);
REVOKE UPDATE, DELETE ON demand.allocation_record FROM apollo_app;
```

**Append-only.** *"Rows are only ever added, never changed"* (`00-03 §3`). This is *"a record, not an
assignment engine"* (`M3-I16`) — the decision is made on the daily morning call and captured here.

### 5.5 Status transitions (`M3-I28`)

```sql
CREATE TABLE demand.status_transition (
  id             uuid PRIMARY KEY,
  requisition_id uuid NOT NULL,
  from_status    requisition_status_enum,
  to_status      requisition_status_enum NOT NULL,
  reason_code    text,
  note           text,
  actor_type     actor_type_enum NOT NULL,
  actor_id       uuid,
  occurred_at    timestamptz NOT NULL DEFAULT now()
);
REVOKE UPDATE, DELETE ON demand.status_transition FROM apollo_app;
CREATE INDEX idx_status_transition__req ON demand.status_transition (requisition_id, occurred_at);
CREATE INDEX idx_status_transition__stage ON demand.status_transition (to_status, occurred_at DESC);
```

**Append-only, and it cannot be added later.** *"D28 stage-level conversion loss cannot be computed
retrospectively without it"* (`M3-I28`).

## 6. State machine

| From | To | Rules |
|---|---|---|
| — | `incomplete` \| `complete` | On creation, by completeness score |
| `incomplete` | `awaiting_client` | Chase started (`03-03`) |
| `awaiting_client` | `complete` | Missing fields supplied |
| `complete` | `open` | Explicit publish. **Age clock starts here.** |
| `open` | `in_fulfilment` | First shortlist sent or first candidate submitted |
| `in_fulfilment` | `partially_filled` | `positions_filled` > 0 and &lt; `positions` |
| `partially_filled` | `filled` | `positions_filled` = `positions` |
| `in_fulfilment` \| `partially_filled` \| `open` | `on_hold` | **Age clock pauses.** Hold reason from the configured list. |
| `on_hold` | previous status | **Age clock resumes from where it stopped** |
| any | `closed` | **Close reason mandatory**, from the configured list |
| `filled` | ? | **Open (`OI-M3-12`)** — does it auto-close, or does close remain an explicit act? |

**Revise** is not a state — it is a version (`§5.2`), available in any non-closed state.

Whether `filled → closed` is automatic *"affects the state machine, not just the UI"* (`OI-M3-12`).
Working assumption `AS-22`: **close remains an explicit act.** A filled requisition stays visible on
the board as filled-not-closed, because a drop-out before joining returns positions to it and an
auto-closed requisition would have to be reopened.

## 9. Frontend — `/requisitions`, `/fulfilment`

### 9.1 Requisition form (`M3-I9`)

The manual creation path **and the entry point for verbal capture** — *"not an edge case with fifteen
site-resident recruiters"*.

Client → location → department → engagement type → category → role → positions → **category-specific
attributes** (rendered from `03-05`'s definitions) → start date → rate (resolved from the rate card,
overridable with a reason → feeds M9 variance).

Optimised for speed: keyboard-first, sensible defaults from the last requisition for that client,
inline creation of a department if missing.

### 9.2 Requisition record (`M3-I10`)

*"The single record view, carrying its source evidence so a disputed requirement can be traced to
what the client actually sent."*

Header: reference, client, site, role, positions filled/total, status, **age**, owner, allocated
recruiters. Tabs: Details · **Source** (the raw inbound, including audio for a voice note) ·
Versions · Shifts · Candidates (`03-09`) · Activity (`02-02`).

Actions: revise, hold, release, close, allocate, publish.

### 9.3 Requisition versions (`M3-I11`)

What changed, when, who, and from which channel. Diff between any two versions.

### 9.4 Fulfilment board (`M3-I12`)

**The operational heart of M3 and the highest-traffic screen in the module.**

`<DataTable/>`, virtualised: reference, client, site, role, category, positions filled/total,
**age with a visual band**, status, owner, allocated recruiters, last activity.

Filters: status, client, site, category, owner, allocated recruiter, age band, engagement type.
Saved views (P06) — "My requisitions", "Aged over 14 days", "Unallocated".

Grouping toggle: by client, by site, by owner, by age band.

**Recruiter load display** — showing how many requisitions each recruiter holds against the 15–16
operating norm — is **open (`OI-M3-10`)**. Built as an optional column, default off. *Display only;
capacity is explicitly not enforced in R1.*

Performance: p95 &lt; 2s at 5,000 open requisitions (`AS-14`).

### 9.5 Shift templates (`M3-I13`)

Per client and site: name, start/end time, midnight crossing, break, days of week. Preview of what a
week expands to.

### 9.6 Shift demand lines (`M3-I14`)

Per-shift view: date, times, positions filled/total, status, assigned candidates. Calendar and list
views. Bulk cancel a date range.

### 9.7 Hold, revise and close (`M3-I15`)

Three actions with distinct rules, each stated on the dialog:

- **Hold** — reason from the list; **the age clock stops**; states so plainly
- **Revise** — creates a version; shows what will change
- **Close** — reason mandatory; **warns how many open positions are being abandoned**, and that
  candidates in flight will need handling

### 9.8 Owner and allocation (`M3-I16`)

Owner picker: **active users only** (`M0-I2`). Allocation: multi-select recruiters, **recruiter role
required** (`M0-I2`), with a note. History shown as append-only rows.

The screen states what it is: *"Records the decision made on the daily morning call. A record, not an
assignment engine."*

## 10. Acceptance criteria

| # | Criterion | Source |
|---|---|---|
| 1 | A requisition normalises demand from any channel into one schema, carrying its source | `M3-I10`, A1 |
| 2 | Source evidence is reachable from the record, including audio for a voice note | `M3-I10` |

## 12. Notes for the implementer

**Get the age clock right first, and test it hard.** It appears on the board, drives aging alerts,
feeds time-to-fill reporting in M9, and is the thing a fulfilment lead looks at all day. Hold and
release with resume-from-where-it-stopped is easy to get subtly wrong and hard to notice.

**Status transitions are not optional bookkeeping.** Every transition writes a row, and that table is
the *only* source for M9's stage-level conversion loss. It cannot be reconstructed. Write the
transition in the same transaction as the status change, or the two will drift.

**Keep the assignment engine out.** It is genuinely tempting to add "suggest a recruiter" here. The
plan puts it in M14, deliberately, because the suggestion needs M9 performance data that does not
exist until month five. Building it early means building a suggestion engine against data that does
not exist.
