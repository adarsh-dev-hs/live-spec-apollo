## 1. Purpose

Produce a ranked candidate set against a requisition, **exposing the rationale for each rank together
with unmet or partially met criteria**, applying different weightings per candidate category and
supply base, with search, saved searches, talent segments and recruiter override. Consume selection
outcomes and structured rejection reasons from M7 so subsequent ranking reflects them.

The rationale is not decoration. A recruiter defending a shortlist to a hospital needs to say *why*
this nurse is ranked first and what she does not meet — and a ranked list nobody can explain is a
list nobody uses.

---

## 2. Scope

**In** — advanced candidate search · saved searches and talent segments · ranking engine with
rationale and unmet criteria · weight sets per category per base · ranking input assembly · weight
set selection · shortlist building and sending · recruiter override with reason · outcome write-back
from M7 (A8) · shift-level ranking

**Out** — the candidate record → `03-05` · credentials → `03-06` · availability → `03-08` ·
interviews, decisions, offers → `03-10` · client-facing shortlist page → `03-10` (uses `02-10`)

**Explicitly not built:** automatic model retraining — *"we apply a configured set of weights;
continuous learning is not in this contract"* · showing candidates their own match score — *"ranking
is an internal tool only"* · sending a shortlist to a client without a recruiter pressing the button ·
using the clinical/communication rating — nothing produces it (`OI-A-07`)

## 5. Data model

### 5.1 Ranked set

```sql
CREATE TABLE match.ranked_set (
  id             uuid PRIMARY KEY,
  requisition_id uuid,
  shift_line_id  uuid,                        -- shift-level ranking (M6-I10)
  weight_set_id  uuid NOT NULL,
  status         ranked_set_status_enum NOT NULL,  -- 'generating'|'current'|'stale'
  candidate_pool_size integer NOT NULL,       -- how many were CONSIDERED
  ranked_count   integer NOT NULL,
  generated_at   timestamptz NOT NULL DEFAULT now(),
  generated_by   uuid,
  stale_reason   text,
  engine_version text NOT NULL,               -- what produced this — reproducibility
  CHECK ((requisition_id IS NULL) <> (shift_line_id IS NULL))
);

CREATE TABLE match.rank_entry (
  id             uuid PRIMARY KEY,
  ranked_set_id  uuid NOT NULL REFERENCES match.ranked_set(id),
  candidate_id   uuid NOT NULL,
  rank           integer NOT NULL,
  score          numeric(6,4) NOT NULL,
  -- THE RATIONALE — required, not optional
  rationale      jsonb NOT NULL,   -- [{factor,weight,candidateValue,requirementValue,contribution}]
  unmet_criteria jsonb NOT NULL,   -- [{criterion, required, actual, severity:'unmet'|'partial'}]
  is_eligible    boolean NOT NULL, -- FALSE = excluded by a hard filter, kept for transparency
  exclusion_reason text,
  status         rank_entry_status_enum NOT NULL,  -- 'ranked'|'shortlisted'|'sent_to_client'|'outcome_recorded'
  UNIQUE (ranked_set_id, candidate_id)
);
CREATE INDEX idx_rank_entry__set ON match.rank_entry (ranked_set_id, rank);
```

**Ineligible candidates are kept with a reason rather than dropped.** A recruiter asking "why is
Priya not in this list" gets an answer instead of a silence, and that answer is often "her
registration expired last week" — which is actionable.

### 5.2 Recruiter override

```sql
CREATE TABLE match.recruiter_override (
  id            uuid PRIMARY KEY,
  ranked_set_id uuid NOT NULL,
  candidate_id  uuid NOT NULL,
  from_rank     integer,
  to_rank       integer,
  action        override_action_enum NOT NULL,   -- 'promote'|'demote'|'include'|'exclude'
  reason        text NOT NULL,                   -- MANDATORY
  actor_id      uuid NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now()
);
REVOKE UPDATE, DELETE ON match.recruiter_override FROM apollo_app;
```

Append-only. Overrides are also a **signal**: a factor recruiters consistently override against is a
weight that is wrong, and `03-14` reports on it.

### 5.3 Weight sets (`M6-I5`)

```sql
CREATE TABLE match.weight_set (
  id            uuid PRIMARY KEY,
  name          text NOT NULL,
  category      candidate_category_enum NOT NULL,
  base          supply_base_enum NOT NULL,
  engagement_type engagement_type_enum,
  version       integer NOT NULL,
  is_active     boolean NOT NULL DEFAULT false,
  weights       jsonb NOT NULL,
  -- eligibility: FILTER vs WEIGHT — see OI-HS-10
  hard_filters  jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  UNIQUE (category, base, engagement_type, version)
);
```

**At least six sets** — three categories × two bases — *"so the weight sets multiply accordingly, and
the inputs themselves differ by category"*.

```json
{
  "weights": {
    "credential_match": 0.25,
    "specialty_match":  0.20,
    "acuity_match":     0.15,
    "experience":       0.15,
    "availability_confidence": 0.10,
    "location_proximity":      0.10,
    "past_outcome_signal":     0.05
  },
  "hard_filters": {
    "credential_expired":      "exclude",
    "credential_red":          "exclude",
    "verification_pending":    "weight",
    "availability_stale_days": { "action": "weight", "threshold": 14 },
    "category_mismatch":       "exclude",
    "opted_out":               "exclude"
  }
}
```

`hard_filters` is where `OI-HS-10` lives: each condition is configured as `exclude` or `weight`, so
the filter-vs-weight question is answerable without a rebuild.

### 5.4 Saved searches and segments

```sql
CREATE TABLE match.saved_search (
  id uuid PRIMARY KEY, user_id uuid NOT NULL, name text NOT NULL,
  criteria jsonb NOT NULL, is_shared boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE match.talent_segment (
  id uuid PRIMARY KEY, key text NOT NULL UNIQUE, name text NOT NULL,
  definition jsonb NOT NULL,
  is_dynamic boolean NOT NULL DEFAULT true,     -- dynamic = re-evaluated; static = a fixed list
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);
```

*"Named groups of candidates, **shared with the contact groups in M5**"* (`M6-I2`) — `03-08`'s
segments and these are the same objects, so a "Chennai ICU nurses" group defined once serves both
cadence and search.

### 5.5 Outcome write-back (A8, `M6-I9`)

```sql
CREATE TABLE match.outcome_signal (
  id             uuid PRIMARY KEY,
  candidate_id   uuid NOT NULL,
  requisition_id uuid,
  rank_entry_id  uuid,
  outcome        outcome_type_enum NOT NULL,    -- 'selected'|'rejected'|'withdrawn'|
                                                -- 'joined'|'dropped_out'|'trial_survived'
  rejection_reason_code text,                   -- from the SHARED taxonomy (03-10)
  rejection_stage text,                         -- 'shortlist'|'interview'|'offer'
  client_id      uuid,
  recorded_at    timestamptz NOT NULL DEFAULT now(),
  applied_to_ranking boolean NOT NULL DEFAULT false
);
CREATE INDEX idx_outcome_signal__candidate ON match.outcome_signal (candidate_id, recorded_at DESC);
```

**The schema must be agreed with D6 before either is built** (A8) — the rejection reason taxonomy is
shared between `03-10`'s selection decision and this table. One list, in P03, used by both.

## 6. State machines

**RankedSet:** `generating → current → stale`

Goes stale when the requisition is revised, its category or attributes change, or **new outcome data
arrives**. A stale set is still viewable, clearly marked, with a regenerate action — a recruiter
mid-shortlist should not have the list vanish underneath them.

**RankEntry:** `ranked → shortlisted → sent_to_client → outcome_recorded`

**OutcomeSignal:** `captured → written back → included in the next ranking run`. *"This happens in the
background and does not hold anything up"* (`00-03 §4`).

### 7.2 Ranking engine (`M6-I6`)

*"Score and order the candidates, **and produce the reasoning at the same time**."*

```
for each eligible candidate:
    for each factor in weight_set.weights:
        factorScore   = scoreFactor(factor, candidate, requisition)   // 0..1
        contribution  = factorScore × weight
        rationale.push({ factor, weight, candidateValue, requirementValue, contribution })
        if factorScore < 1: unmet.push({ criterion, required, actual, severity })
    score = Σ contribution
```

**Rationale is generated in the same pass, not reconstructed afterwards.** A post-hoc explanation of
a score is a different computation from the one that produced it, and they drift.

Deterministic and reproducible: the same inputs and the same `engine_version` produce the same
output. This is not a learned model — it is a configured weighted score, which is what the contract
scopes.

### 7.3 Ranking inputs (`M6-I7`)

*"Pull credentials, category fields, availability and past outcomes into a form the scorer can use."*

| Input | From | Notes |
|---|---|---|
| Credentials, verification outcomes, expiry | `03-06` | `verificationSummary` |
| Category attributes | `03-05` | Only where `is_rankable` |
| Availability confidence | `03-08` | Per base |
| Location and preferences | `03-05` | |
| Experience | `03-05` | |
| Past outcomes | §5.5 | Aggregated per candidate |
| Requisition requirements | `03-04` | Attributes, role, location, dates |

Assembled in one batched pass over the candidate pool. **No N+1** — a pool of 10,000 candidates
means seven queries, not seventy thousand.

### 7.4 Weight set selection (`M6-I8`)

`(requisition.category, candidate.base, requisition.engagementType)` → the active weight set.
No match → the platform default, with a warning surfaced on the ranked set.

### 7.5 Shift ranking (`M6-I10`)

Same engine, different subject: rank against a single shift line rather than a permanent vacancy.
Extra factors: shift date availability, distance to site, recent shift history, no-show record.

## 9. Frontend — `/matching`

### 9.1 Candidate search (`M6-I1`)

`<DataTable/>` over candidates with filters on skill, location, experience, **credentials**,
**availability**, category attributes. Save a search; share it.

### 9.2 Talent segments (`M6-I2`)

Named groups, dynamic or static, **shared with M5's contact groups**.

### 9.3 Ranked candidates (`M6-I3`)

The core screen. For each candidate: rank, name, score, **the rationale** and **what they do not
meet**.

| Element | |
|---|---|
| Rationale | Per-factor contribution, expandable — not a bare number |
| Unmet criteria | Prominent, with severity: unmet vs partially met |
| Ineligible candidates | Shown collapsed, **with the exclusion reason** |
| Weight set used | Named, with a link to it — so an odd ranking is diagnosable |
| Staleness | Banner if the set is stale, with regenerate |
| Override | Promote, demote, include, exclude — **reason mandatory** |
| Compare | Two or three candidates side by side |

### 9.4 Build shortlist (`M6-I4`)

Select candidates, review, add a note, send. **A recruiter presses the button** — nothing is sent
automatically. Sending issues an `02-10` shortlist link to the client's link recipient.

Whether hand-assembly survives independently of the ranked set is **open (`OI-A-10`)** — see §11.

### 9.5 Ranking weights (`M6-I5`)

Per category per base: factor weights, hard filters. **Simulate against a past requisition and
compare the resulting order** before activating — changing weights blind, across a live pool of
recruiters, is not a thing anyone should do.

## 11. Open questions

| ID | Question | Impact | Working assumption |
|---|---|---|---|
| **`OI-A-11`** | **The ranking input weighting model across credentials, specialty and acuity, availability confidence and written-back outcomes — and its configurability.** | **The largest unspecified design in Release 1.** Three categories × two bases multiplies the weight sets, and the inputs themselves differ by category. | **`AS-32`** — the weights in §5.3 are a **starting proposal, explicitly provisional**, fully configurable, with a simulation tool so Apollo can tune against real requisitions during UAT rather than specifying blind now. **Run a weighting workshop in phase 4, before M6 build.** |
| **`OI-HS-10`** | **Does an expired credential, a pending verification or a stale availability value exclude a candidate, or only reduce their score?** | *"The difference between a filter and a weight changes what a recruiter sees and what can be defended to a client."* | **`AS-27`** — configured per condition in `hard_filters`. Default: **expired or red registration excludes** (clinical and legal); pending verification and stale availability **reduce score**. Changing it is configuration. |
| **`OI-A-10`** | **Does hand-assembly of a shortlist survive as a recruiter fallback, or is override on the ranked set the only manual path?** | *"Materially different screen and a different change-management story for 22 recruiters."* | **`AS-33`** — **both.** Search → select → shortlist works without generating a ranked set, and override works within one. The screens share components, so supporting both is marginal; removing one later is trivial, adding one later is not. |
| `OI-A-07` | Clinical and communication rating — nothing produces it | Whether D18 weights it is unstated | **Excluded from ranking** (`is_rankable = false`). Present on the record, unpopulated, with a note. |
| `OI-HS-09` | Can a candidate be in both bases? | Which weight set applies | **`AS-25`** — rank per base; a candidate in both appears in both rankings with different scores. Correct, and it is what the base-specific weight sets are for. |

## 12. Notes for the implementer

**The rationale is the product.** A ranked list without a defensible explanation will not be used by
22 recruiters who currently do this in their heads, and *"exposing the rationale for each rank
together with unmet or partially met criteria"* is the literal deliverable text. Build the rationale
first and the score around it.

**Run the weighting workshop before you build.** `OI-A-11` is the largest unspecified design in
Release 1. Do not resolve it by picking numbers in code — build the configuration and the simulator,
then sit with Shalu and a set of real past requisitions.

**Agree the rejection taxonomy with `03-10` before either module starts.** A8 says so explicitly, and
the plan sequences a joint session for exactly this. One list in P03, used by the selection decision
and by the outcome signal. If they fork, the write-back loop produces noise.

**Batch the input assembly.** The naive implementation issues a credential query per candidate. At
10,000 candidates that is the difference between 20 seconds and 20 minutes.
