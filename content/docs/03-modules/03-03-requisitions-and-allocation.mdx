## 1. Purpose

The requisition: the single structured record every channel normalises to, and the object every module
downstream quotes. It tracks the vacancy through its life — open, in fulfilment, paused, revised, partly
filled, filled, closed — counts how long it has been open **excluding held days**, and records who owns
it and which recruiters were put on it at the daily morning call.

The allocation half is deliberately a **record, not an assignment engine**. The morning call already
makes the decision; Release 1 writes it down. Prioritisation, suggestion and approval are `03-18`.

## 2. Scope

### In scope

- The requisition form: manual creation and the verbal-capture entry point
- The requisition record view, carrying its source evidence so a disputed requirement traces back
- Version history — revision is a **versioning event, not an edit**
- The fulfilment board: live demand, aging and fill in one view, the highest-traffic screen in the module
- Shift templates and the shift demand lines they generate
- Hold, revise and close, each with distinct rules about the aging clock and mandatory reasons
- Owner and allocation, append-only
- The requisition state machine and the append-only status-change log

### Explicitly out of scope

- Getting the demand in — `03-02` and `02-08`.
- Ranking candidates against a requisition — `03-07`.
- Prioritisation, recruiter suggestion, load balancing and pre-live approval — `03-18`, Phase 6.

### Explicitly not built

- **Any suggestion, computation or optimisation of allocation.** Enforced by a negative test (`M3-I16`
  BR1).
- Enforcing the 15–16 vacancy operating norm. Recorded, not enforced.
- An approval step before a requisition goes live. `03-18` adds the state; Phase 3 has none.
- Changing candidate category after creation — blocked pending `OI-M3-09`, because category drives the
  attribute set and the ranking weight set.

## 5. Data model

The `demand.requisition` table is shown in full in `01-05` §2. The rest:

```sql
CREATE TABLE demand.requisition_version (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    version integer NOT NULL,
    snapshot jsonb NOT NULL,                 -- the whole record as it stood
    changed_fields text[] NOT NULL,
    change_source text NOT NULL,             -- 'manual' | 'inbound_revision' | 'system'
    inbound_record_id uuid,                  -- when a channel revision caused it
    created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
    UNIQUE (requisition_id, version)
);

CREATE TABLE demand.category_attributes (    -- the A9 requisition-side values (AS-04)
    requisition_id uuid PRIMARY KEY REFERENCES demand.requisition(id),
    attribute_set_version integer NOT NULL,  -- candidates.category_attribute_set version consumed
    values jsonb NOT NULL                    -- { specialty: 'icu', acuity: 'level_3' }
);

CREATE TABLE demand.shift_template (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    client_id uuid, name text NOT NULL,
    pattern jsonb NOT NULL,                  -- days of week, start/end times, positions per shift
    is_active boolean NOT NULL DEFAULT true,
    created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE demand.shift_demand_line (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    shift_date date NOT NULL,
    starts_at time NOT NULL, ends_at time NOT NULL,
    positions_requested integer NOT NULL CHECK (positions_requested > 0),
    positions_filled integer NOT NULL DEFAULT 0,
    visit_address jsonb,                     -- home healthcare: the workplace changes per shift
    visit_geo_point point,                   -- what geo-fencing checks against (03-16, OI-HS-17)
    generated_from_template_id uuid REFERENCES demand.shift_template(id),
    state text NOT NULL DEFAULT 'open'
      CHECK (state IN ('open','partially_filled','filled','held','cancelled')),
    created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON demand.shift_demand_line (requisition_id, shift_date);
CREATE INDEX ON demand.shift_demand_line (shift_date, state) WHERE state IN ('open','partially_filled');

CREATE TABLE demand.allocation_record (      -- append-only; rows are added, never changed
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    recruiter_id uuid NOT NULL REFERENCES identity.user(id),
    allocated_at timestamptz NOT NULL DEFAULT now(),
    allocated_by uuid NOT NULL REFERENCES identity.user(id),
    removed_at timestamptz,                  -- removal preserves the historical row
    removed_by uuid
);
CREATE INDEX ON demand.allocation_record (requisition_id, allocated_at);
CREATE INDEX ON demand.allocation_record (recruiter_id, allocated_at);   -- D28 by recruiter
REVOKE DELETE ON demand.allocation_record FROM PUBLIC;

CREATE TABLE demand.status_transition (      -- append-only; D28 cannot be computed retrospectively without it
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    from_status text, to_status text NOT NULL,
    reason_code text,
    actor_id uuid, actor_type text NOT NULL,
    occurred_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON demand.status_transition (requisition_id, occurred_at);
REVOKE UPDATE, DELETE ON demand.status_transition FROM PUBLIC;

CREATE TABLE demand.hold_period (            -- what makes "aging excluding held days" computable
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    held_at timestamptz NOT NULL, released_at timestamptz,
    hold_reason_code text
);
```

## 6. State machines

### `Requisition` (`M3-I27`) — the full table

| From | Event | To | Rule |
|---|---|---|---|
| — | created (any channel or manual) | `incomplete` or `complete` | Scored against the category's required-field set |
| `incomplete` | follow-up issued | `awaiting_client` | Visible on the board, **excluded from matching** |
| `awaiting_client` | client supplies fields | `complete` | Reply merges onto the same requisition |
| `awaiting_client` | window expires | `awaiting_client` | Escalates to the owner; **no value is deemed** |
| `incomplete`/`awaiting_client` | all required fields present | `complete` | **`first_complete_at` set — aging starts here** |
| `complete` | published | `open` | |
| `open` | owner set and work begins | `in_fulfilment` | **Cannot enter without an owner** (`M3-I16` V3) |
| `in_fulfilment` | hold | `on_hold` | **Aging clock stops** |
| `on_hold` | release | `in_fulfilment` | **Aging resumes from the held value, not from zero** |
| any editable state | revise | same state, version + 1 | Re-scores completeness |
| `in_fulfilment` | placement confirmed, positions remain | `partially_filled` | `positions_filled` incremented by `03-09` |
| `partially_filled` | last position confirmed | `filled` | **Does not auto-close** — pending `OI-M3-12` |
| `partially_filled`/`filled` | drop-out in `03-09` | `in_fulfilment` | Position returns to open |
| any | close | `closed` | **Reason mandatory**, from the configured list; rejected without one |

`03-18` inserts `awaiting_approval` between `created` and `open` in Phase 6. Nothing else changes.

### Aging (`M3-I27`, `M3-I12`)

```
days_aged = (now − first_complete_at) − Σ(hold_period durations)
```

Measured from **first reaching complete**, not from inbound receipt. Held days are excluded, and a
release resumes from the held value.

### `ShiftDemandLine`

`open → partially_filled → filled`, plus `held` and `cancelled`. **Holding a line does not hold the
parent requisition**; a cancelled line does not appear in ranking.

## 8. Events and jobs

**Events emitted**

| Event | Consumed by |
|---|---|
| `demand.requisition.created` | `03-12` funnel and channel performance |
| `demand.requisition.status_changed` | `03-12` stage loss, time-to-fill; `02-09` triggers |
| `demand.requisition.revised` | `03-07` marks ranked sets stale |
| `demand.requisition.held` / `.released` / `.closed` | `03-12` |
| `demand.allocation.recorded` / `.removed` | **`03-12` — loss by recruiter is impossible without this** |
| `demand.shift_line.generated` | `03-07` shift ranking |

**Events subscribed:** `placement.placement.joined` → decrement positions open;
`placement.dropout.recorded` → return the position to open;
`demand.requisition.completeness_scored` (from `03-02`) → state transition.

**Jobs:** none scheduled of its own. Aging is computed on read, not by a nightly job, so the board is
never stale.
