## 1. Purpose

Interview slot proposal and confirmation, reschedule and cancellation, feedback capture, the
accept / hold / reject decision with **mandatory structured rejection reasons**, then offer
generation, delivery, tracking, expiry, digital signature and offer-to-contract mapping. Plus the
client-facing shortlist response page.

Two constraints shape everything here:

- **Neither the candidate nor the client has a login.** Interview slots are proposed through the app
  and through messaging; the client responds through a tokenised link (`02-10`).
- **Rejection reasons are structured, mandatory and shared with ranking.** Free text cannot feed back
  into M6, which is the whole point of A8.

> *"Without offer management the permanent chain stops after selection."* — D20

---

## 2. Scope

**In** — interview proposal, confirmation, reschedule, cancellation · structured interview feedback ·
accept / hold / reject with mandatory reason · offer templates by state, role and skill · offer
creation, delivery, tracking, expiry, reminders · electronic signature · offer-to-contract mapping ·
**the client shortlist response page**

**Out** — the link *mechanism* → `02-10` · ranking and shortlist building → `03-09` · placements and
the joining event → `03-11` · client trial check-in and timesheet pages → `03-11`, `03-12` ·
contracts → `03-02`

**Explicitly not built:** any client login or account · AI video interviews · connecting to
interviewers' external calendars — *"slots are proposed and confirmed inside the platform"* ·
background checks at offer stage — *"verification happens earlier, in M4"*

## 5. Data model

### 5.1 Interview

```sql
CREATE TABLE select.interview (
  id             uuid PRIMARY KEY,
  reference      text NOT NULL UNIQUE,
  candidate_id   uuid NOT NULL,
  requisition_id uuid NOT NULL,
  application_id uuid NOT NULL,
  format         interview_format_enum NOT NULL,   -- 'in_person'|'video'|'phone'
  status         interview_status_enum NOT NULL,
  scheduled_at   timestamptz,
  duration_minutes integer,
  location_note  text,
  panel          jsonb NOT NULL DEFAULT '[]',      -- [{name, role, isApolloUser, userId?}]
  round          integer NOT NULL DEFAULT 1,
  cancel_reason  text,
  reschedule_count integer NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE select.interview_slot (
  id            uuid PRIMARY KEY,
  interview_id  uuid NOT NULL REFERENCES select.interview(id),
  proposed_at   timestamptz NOT NULL,
  duration_minutes integer NOT NULL,
  status        slot_status_enum NOT NULL,         -- 'proposed'|'accepted'|'declined'|'withdrawn'
  accepted_by   text,                              -- 'candidate'|'client'
  responded_at  timestamptz
);
```

Several slots are proposed; the first acceptance from each side confirms. Neither party has a login,
so the candidate responds in the app and the client through a link.

### 5.2 Feedback (`M7-I3`)

```sql
CREATE TABLE select.interview_feedback (
  id             uuid PRIMARY KEY,
  interview_id   uuid NOT NULL REFERENCES select.interview(id),
  interviewer_name text NOT NULL,
  interviewer_user_id uuid,
  is_client_side boolean NOT NULL DEFAULT false,
  -- STRUCTURED, because free text cannot feed back into ranking
  scores         jsonb NOT NULL,      -- { clinical: 4, communication: 3, attitude: 5 }
  recommendation feedback_recommendation_enum NOT NULL,  -- 'strong_yes'|'yes'|'neutral'|'no'|'strong_no'
  notes          text,                                    -- supplementary only
  submitted_at   timestamptz NOT NULL DEFAULT now()
);
```

*"Capture interview feedback in fixed fields, **because free text cannot feed back into ranking**"*
(`M7-I3`). The score dimensions are configurable in P03.

### 5.3 Selection decision (`M7-I4`)

```sql
CREATE TABLE select.selection_decision (
  id             uuid PRIMARY KEY,
  candidate_id   uuid NOT NULL,
  requisition_id uuid NOT NULL,
  application_id uuid NOT NULL,
  decision       selection_decision_enum NOT NULL,   -- 'accepted'|'held'|'rejected'
  -- MANDATORY on reject, from the SHARED taxonomy (03-09 A8)
  rejection_reason_code text,
  rejection_stage text,                              -- 'shortlist'|'interview'|'offer'
  rejection_note text,
  decided_by     uuid NOT NULL,
  decided_at     timestamptz NOT NULL DEFAULT now(),
  decided_via    text NOT NULL,                      -- 'ops'|'client_link'
  link_id        uuid,
  CONSTRAINT ck_decision__reject_reason
    CHECK (decision <> 'rejected' OR rejection_reason_code IS NOT NULL)
);
```

**The constraint enforces the requirement.** *"Accept, hold or reject, with a reason from a list.
This is what feeds back into M6"* (`M7-I4`).

### 5.4 Offers

```sql
CREATE TABLE select.offer_template (
  id            uuid PRIMARY KEY,
  name          text NOT NULL,
  state         text,                              -- offer terms vary by Indian state
  role_code     text,
  skill_code    text,
  category      candidate_category_enum,
  body_template text NOT NULL,                     -- variable substitution
  variables     text[] NOT NULL DEFAULT '{}',
  is_active     boolean NOT NULL DEFAULT true
);

CREATE TABLE select.offer (
  id               uuid PRIMARY KEY,
  reference        text NOT NULL UNIQUE,           -- 'OFR-2026-001284'
  candidate_id     uuid NOT NULL,
  requisition_id   uuid NOT NULL,
  application_id   uuid NOT NULL,
  contract_id      uuid,                           -- M7-I16 — the terms M9 reads at day 90
  contract_version_id uuid,
  status           offer_status_enum NOT NULL,
  current_version_id uuid,
  expires_at       timestamptz NOT NULL,
  sent_at timestamptz, opened_at timestamptz, signed_at timestamptz,
  declined_at timestamptz, decline_reason text,
  signed_document_id uuid,
  esign_reference  text,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE select.offer_version (
  id             uuid PRIMARY KEY,
  offer_id       uuid NOT NULL REFERENCES select.offer(id),
  version_number integer NOT NULL,
  template_id    uuid NOT NULL,
  terms          jsonb NOT NULL,                   -- salary, joining date, location, role, notice
  rendered_body  text NOT NULL,
  document_id    uuid,                             -- the generated PDF
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  UNIQUE (offer_id, version_number)
);
```

Offers are versioned because a revised offer must not destroy the one already sent — the candidate
may be holding it.

## 6. State machines

**Interview:** `proposed → confirmed → held → feedback_recorded` \| `rescheduled` \| `cancelled(reason)`

**SelectionDecision:** `pending → accepted | held | rejected(reason)`

**Offer:** `draft → generated → sent → opened → signed` \| `expired` \| `declined` → **linked to contract**

| Transition | Rules |
|---|---|
| `draft → generated` | Template resolved, terms validated, PDF produced |
| `generated → sent` | Delivered via `02-07` (WhatsApp, email fallback) |
| `sent → opened` | Candidate opened it |
| `opened → signed` | E-signature completed; signed copy stored |
| `sent`\|`opened` → `expired` | `expires_at` passed. Reminders fired first. |
| any active → `declined` | Candidate declined, with a reason → feeds `03-09` |
| `signed` → mapped | `03-11` creates the placement; `03-13` will read the contract version at day 90 |

## 7. API surface

### 7.1 Exported service

```ts
export const SelectionService = {
  proposeInterview(input, actor): Promise<Interview>
  respondToSlot(slotId, accepted, respondedBy): Promise<Interview>

  cancel(interviewId, reason, actor): Promise<Interview>
  submitFeedback(interviewId, feedback, actor): Promise<InterviewFeedback>

  /** Rejection reason MANDATORY, from the taxonomy shared with 03-09. */
  decide(input: { candidateId, requisitionId, decision, rejectionReasonCode?, ... }): Promise<SelectionDecision>

  createOffer(input, actor): Promise<Offer>
  reviseOffer(offerId, terms, actor): Promise<OfferVersion>
  sendOffer(offerId, actor): Promise<Offer>
  recordSignature(offerId, signedDocumentId, esignRef): Promise<Offer>
  declineOffer(offerId, reason, by): Promise<Offer>

  /** M7-I16 — link the signed offer to the contract whose terms M9 reads at day 90. */
  mapToContract(offerId, contractId, actor): Promise<Offer>
}
```

### 7.2 Client shortlist link (`M7-I10`)

### 7.3 Offer delivery (`M7-I14`)

Through `02-07`: WhatsApp with the PDF, **email as fallback**. Delivery, open and read receipts feed
offer tracking.

### 7.4 Offer to contract (`M7-I16`)

Resolves the client's active contract for the engagement type and freezes `contract_version_id` on
the offer. **This is the link `03-13` follows at day 90** to find the terms that applied.

## 9. Frontend — `/selection`

### 9.1 Propose interview (`M7-I1`)

*"Offer interview times to the candidate and the client, **neither of whom has a login**."*
Several slots, format, panel, location. Candidate responds in the app; client via link or a recruiter
records it on their behalf.

### 9.2 Interview list (`M7-I2`)

All interviews across the team: scheduled, held, **waiting on feedback**. Filter by recruiter, client,
date, status.

### 9.3 Interview feedback (`M7-I3`)

Structured scores plus a recommendation. Free-text notes are supplementary and clearly marked as not
feeding ranking.

### 9.4 Selection decision (`M7-I4`)

Accept, hold or reject. **Rejection requires a reason from the configured taxonomy** — and the screen
states that the reason feeds back into ranking, which is what makes recruiters pick a real one
instead of always choosing the first option.

### 9.5 Offer templates (`M7-I5`)

By state, role and skill. Variable preview.

### 9.6 Create offer (`M7-I6`)

*"Build the offer, check it, send it. **A mistake here becomes a legal document.**"*

So: template auto-selected by state/role/skill, terms pre-filled from the requisition and rate card,
a **full preview of the rendered document**, and an explicit confirmation step naming the candidate,
the salary and the joining date before sending.

### 9.7 Offer tracking (`M7-I7`)

Offers sent, opened, signed, or about to expire. Expiry countdown prominent.

### 9.8 Client page: shortlist (`M7-I10`) — `apps/links`

*"A client page reached from a WhatsApp or email link, with no password. They accept, reject or ask
for an interview."*

Per candidate: the frozen shortlist payload — summary, key credentials, experience, why they were
put forward. Three actions per candidate. Optional comment. One submit.

Constraints from `01-03 §9`: **&lt; 150 KB, works at 320px, large touch targets, no auth provider.**
The client-side view shows only what the shortlist payload contains — not the full candidate record.

## 12. Notes for the implementer

**Agree the rejection taxonomy with `03-09` before either module starts.** The plan schedules a joint
session for exactly this (*"Schedule the ranking-schema and rejection-taxonomy session with M7 before
either starts"*). One list in P03, used by both. If they fork, A8's write-back produces noise instead
of signal.

**Build offer-to-contract mapping early and test it against a versioned contract.** At day 90, `03-13`
follows `offer.contract_version_id` to find the terms that applied. If that link is wrong or missing,
the invoice is wrong or impossible — and it will be discovered three months after the offer was sent.

**The offer preview is not a nicety.** A mistake here becomes a legal document sent to a nurse over
WhatsApp. Full rendered preview, explicit confirmation naming candidate, salary and joining date.

**The client shortlist page is a revenue surface.** It is the first thing a hospital sees from this
platform, opened on a phone from a WhatsApp message. It gets the same care as the day-90 page.
