**Package** `@apollo/engagement` · **Schema** `engagement` · **Plan** D29, A3, A4, A5, A14 · **Effort** ~74.0pd · **Risk** High `SPEC` / `EXT` · **Build in** Phase 4

## 1. Purpose

Apollo needs to know which nurses are actually available right now. This module decides **who** to
contact, **how often**, on **which channel** and with **which question set**, delivers through
`02-09`, captures the answer on one structured schema whichever channel it arrived on, writes it back
to the candidate record and **resets a freshness score** that otherwise decays. If nobody hears from a
candidate the score falls and `03-07` ranks them lower.

Part A is explicit that A3, A4, A5 and A14 form a **closed loop and none of the four is independently
operable** — build any three and none does anything useful. They are estimated and sequenced as one
unit.

## 2. Scope

### In scope

- Segments and contact schedules: **six segments** (three categories × two bases), each with its own
  cadence, channel, question set and staleness threshold
- Send windows and frequency caps, with a projected volume and cost preview before enabling
- Voice campaigns: segment, question set, call window, retry policy
- The review queue for free-text replies the platform was not confident about, and the call log
- Availability confidence: decay on six schedules, reset on a confirmed response
- Cadence selection: who to contact next, applying opt-outs and send windows **at selection**
- Candidate response capture across WhatsApp, app and voice, on one schema
- Registration of the candidate-response intent set against `02-08`
- Write-back to the M4-owned availability field, reconciling a response arriving on two channels

### Explicitly out of scope

- Templates, the sender, retry, receipts, delivery log and preferences — `02-09`.
- The receive/resolve/classify stack — `02-08`. This module **registers** against it.
- The app's availability screen — `03-05`. Same schema, different surface.
- The voice provider integration itself — `04-04`.
- Campaign performance reporting — `03-12`.

### Explicitly not built

- Handling replies to SMS and email. Both are outbound-only in Release 1 (`OI-A-17`).
- Step-by-step guided conversations over WhatsApp. Templates and fixed buttons only; guided flows are
  in the app.
- The phone-call service itself. Apollo buys it; this builds the integration and answer extraction —
  **and Apollo has not said from whom** (`OI-A-09`).
- Automatic segment discovery or optimisation of cadence. Configured, not learned.

**Consumed by:** `03-07` **ranks on the freshness score**; `03-09` sends trial check-ins through this
layer; `03-05` and `04-01` are the two response surfaces.

**External:** `04-04` outbound voice (**provider unnamed**), `04-01` WhatsApp (**template approval is a

## 5. Data model

```sql
CREATE TABLE engagement.segment (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    code text NOT NULL UNIQUE,               -- 'nurse_base_b' | 'doctor_base_a' | …  (six)
    candidate_category text NOT NULL REFERENCES settings.list_entry(code),
    base text NOT NULL CHECK (base IN ('base_a','base_b')),
    name text NOT NULL,
    talent_segment_id uuid,                  -- matching.talent_segment — defined once, shared (M6-I2)
    is_enabled boolean NOT NULL DEFAULT false
);

CREATE TABLE engagement.cadence_rule (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    segment_id uuid NOT NULL REFERENCES engagement.segment(id),
    interval_days numeric(4,1) NOT NULL,     -- Base B: 3–4 across the whole base. Configurable.
    channel_order text[] NOT NULL,
    question_set_code text NOT NULL,
    staleness_threshold numeric(4,3) NOT NULL,   -- confidence below which a candidate is selected
    reminder_schedule jsonb NOT NULL DEFAULT '[]'::jsonb,
    decay_half_life_days numeric(5,1) NOT NULL,  -- per segment: six schedules, not two
    is_enabled boolean NOT NULL DEFAULT false,
    updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL
);

CREATE TABLE engagement.send_window (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    segment_id uuid REFERENCES engagement.segment(id),   -- null = platform-wide ceiling
    earliest time NOT NULL, latest time NOT NULL,
    timezone text NOT NULL DEFAULT 'Asia/Kolkata',
    max_messages_per_candidate integer NOT NULL,
    per_period_days integer NOT NULL
);

CREATE TABLE engagement.cadence_run (        -- auditable: which rule, which candidates, which date
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    cadence_rule_id uuid NOT NULL REFERENCES engagement.cadence_rule(id),
    run_date date NOT NULL,
    selected_count integer NOT NULL,
    suppressed_optout integer NOT NULL DEFAULT 0,
    suppressed_frequency integer NOT NULL DEFAULT 0,
    suppressed_consent integer NOT NULL DEFAULT 0,
    projected_cost_units numeric(12,4),
    started_at timestamptz NOT NULL DEFAULT now(), finished_at timestamptz,
    UNIQUE (cadence_rule_id, run_date)
);

CREATE TABLE engagement.cadence_selection (
    cadence_run_id uuid NOT NULL REFERENCES engagement.cadence_run(id),
    candidate_id uuid NOT NULL,
    confidence_at_selection numeric(4,3) NOT NULL,
    message_id uuid,                         -- messaging.message
    PRIMARY KEY (cadence_run_id, candidate_id)
);

CREATE TABLE engagement.availability_response (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    candidate_id uuid NOT NULL,
    channel text NOT NULL CHECK (channel IN ('app','whatsapp','voice')),
    inbound_record_id uuid,                  -- null for app (direct API)
    voice_call_id uuid,
    payload jsonb NOT NULL,                  -- ONE schema across all three channels
    is_structured boolean NOT NULL,          -- template button / app form vs parsed free text
    confidence numeric(4,3),
    state text NOT NULL DEFAULT 'received' CHECK (state IN
      ('received','understood','needs_review','confirmed','rejected')),
    reviewed_by uuid, reviewed_at timestamptz, review_correction jsonb,
    reconciled_with uuid REFERENCES engagement.availability_response(id),  -- two channels, one record
    received_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON engagement.availability_response (candidate_id, received_at DESC);
CREATE INDEX ON engagement.availability_response (state) WHERE state = 'needs_review';

CREATE TABLE engagement.voice_campaign (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    segment_id uuid NOT NULL REFERENCES engagement.segment(id),
    question_set_code text NOT NULL,
    call_window_start time NOT NULL, call_window_end time NOT NULL,
    max_retries integer NOT NULL DEFAULT 2,
    languages text[] NOT NULL,               -- must match operating reality, not a default
    is_enabled boolean NOT NULL DEFAULT false
);

CREATE TABLE engagement.voice_call (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    voice_campaign_id uuid REFERENCES engagement.voice_campaign(id),
    candidate_id uuid NOT NULL,
    state text NOT NULL DEFAULT 'queued' CHECK (state IN
      ('queued','dialling','connected','completed','no_answer','failed')),
    attempt integer NOT NULL DEFAULT 1,
    duration_seconds integer,
    recording_document_id uuid,              -- files.document, residency + retention applied
    transcript text,
    extraction jsonb, extraction_confidence numeric(4,3),
    cost_units numeric(12,4),                -- per-minute plus AI inference (OI-HS-05)
    provider_call_id text,
    started_at timestamptz, ended_at timestamptz
);
```

**`availability_confidence` and `availability_last_confirmed_at` are columns on
`candidates.candidate`** (`03-04`), written **only** through this module's service. That ownership
boundary is Part A coupling 3 and is deliberate.

## 6. State machines

### `AvailabilityConfidence` (`M5-I10`)

```
confirmed (1.0) ──decay on the segment's half-life──▶ decaying ──▶ stale (< threshold)
      ▲                                                                    │
      └───────── confirmed response resets to 1.0 ◀── selected by cadence ─┘
```

Six schedules, one per segment — not two. A response **below the confidence threshold does not silently
reset confidence**; it goes to review first.

### `AvailabilityResponse` (`M5-I7`, `M5-I16`)

| From | Event | To | Rule |
|---|---|---|---|
| — | structured template button or app form | `understood` → `confirmed` | **Writes back without review** |
| — | free text, confidence ≥ threshold | `understood` → `confirmed` | |
| — | free text or voice, confidence &lt; threshold | `needs_review` | **Queued for a person; confidence is not reset** |
| `needs_review` | reviewer accepts or corrects | `confirmed` | Resets confidence **identically to a structured response** |
| `needs_review` | reviewer rejects | `rejected` | No write-back |
| any | a second response on another channel | `confirmed`, `reconciled_with` set | **One record, not two resets** |

### `VoiceCall` (`M5-I6`)

`queued → dialling → connected → completed`, or `no_answer → retry` per the campaign policy, within
the call window and without breaching frequency caps.

## 8. Events and jobs

**Events emitted:** `engagement.cadence.run_completed` · `engagement.candidate.selected` ·
`engagement.availability.confirmed` · `.needs_review` · `engagement.confidence.decayed` ·
`engagement.voice_call.completed`.

**Events subscribed:** `inbound.record.classified` (`candidate_response`) → handle the reply;
`candidates.candidate.base_changed` → re-evaluate segment membership;
`messaging.opt_out.recorded` → exclude from the next selection.

**Jobs**

| Job | Schedule | Purpose |
|---|---|---|
| `engagement.decay` | daily | Applies the six decay schedules |
| `engagement.cadence-run` | daily per enabled rule | Selects on confidence, applies opt-outs, consent basis, frequency caps and send windows **at selection**, records the run, enqueues sends |
| `engagement.handle-response` | on inbound dispatch | Normalises WhatsApp, app and voice answers to one schema |
| `engagement.voice-dial` | on campaign schedule | Places calls through `04-04` within the window |
| `engagement.extract-voice-answer` | on call completion | Turns the spoken answer into the same shape; low confidence → review |
| `engagement.write-back` | on confirmation | Resets confidence and the last-confirmed timestamp on the M4 record |

## 11. Open questions

| Ref | Question | Working assumption | Blocks |
|---|---|---|---|
| `OI-A-09` | **Which provider will make the automated phone calls?** Providers differ enormously in conversation handling, transcript shape and Indian language coverage | The integration and extraction are built against an interface with a stub adapter; the provider cannot be sized. Also affects M3: if the same provider does speech-to-text for inbound voice notes we build one integration, otherwise two. **Estimate blocker.** | `M5-I12`, `M5-I13`, `M5-I6`, `M5-I7`, `M3-I23` |
