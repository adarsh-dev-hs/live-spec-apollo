## 1. Purpose

Paying the shift workers. This connects the platform to a **third-party payroll engine — we do not
build a payroll calculator.** It sends the inputs the engine needs, configures the pay cycle, produces
the PF and ESIC reports and challans, and delivers payslips in the app and over WhatsApp.

> Until this exists, payroll is done by hand, which **puts a hard ceiling on how many shift workers
> Apollo can take on** (`OI-A-16`).

**This module is last, behind three others.** It needs `03-17` forms, `03-18` approvals and
`03-12`/`03-21` timesheets. The plan says so plainly: *"if the contractual line matters commercially,
it is the item most exposed to everything upstream of it."*

---

## 2. Scope

**In** — pay cycle configuration and lifecycle · payroll input assembly from approved timesheets,
revisions, advances and holds · third-party engine integration behind an interface · results
ingestion · PF and ESIC reports and challans · payslip delivery in-app and over WhatsApp

**Out** — **calculating pay** — a third-party engine does that; *Hirecraft and PayBooks are the
candidates* · **submitting statutory filings** — we produce reports and challans, someone else files ·
timesheets → `03-12`, `03-21` · salary changes → `03-18` · onboarding → `03-17` · client invoicing →
`03-13`

## 5. Data model

```sql
CREATE TABLE bill.payroll_cycle (
  id             uuid PRIMARY KEY,
  reference      text NOT NULL UNIQUE,             -- 'PAY-2026-11'
  period_start   date NOT NULL,
  period_end     date NOT NULL,
  pay_date       date NOT NULL,
  frequency      payroll_frequency_enum NOT NULL,  -- 'monthly'|'fortnightly'|'weekly'
  status         payroll_cycle_status_enum NOT NULL,
  input_count    integer NOT NULL DEFAULT 0,
  blocked_count  integer NOT NULL DEFAULT 0,
  total_gross    numeric(14,2), total_deductions numeric(14,2), total_net numeric(14,2),
  locked_at timestamptz, locked_by uuid,
  sent_at timestamptz, results_received_at timestamptz,
  payslips_issued_at timestamptz, closed_at timestamptz,
  engine_reference text,
  UNIQUE (period_start, period_end, frequency)
);

CREATE TABLE bill.payroll_input (
  id             uuid PRIMARY KEY,
  cycle_id       uuid NOT NULL REFERENCES bill.payroll_cycle(id),
  associate_id   uuid NOT NULL,
  candidate_id   uuid NOT NULL,
  employee_code  text NOT NULL,
  -- FROZEN AT LOCK — 'the figures sent match the figures recorded'
  worked_minutes integer NOT NULL,
  overtime_minutes integer NOT NULL DEFAULT 0,
  leave_days     numeric(5,2) NOT NULL DEFAULT 0,
  base_salary    numeric(14,2) NOT NULL,
  salary_revision_id uuid,
  advance_recovery numeric(14,2) NOT NULL DEFAULT 0,
  advance_ids    uuid[],
  is_held        boolean NOT NULL DEFAULT false,
  hold_id        uuid,
  adjustments    jsonb NOT NULL DEFAULT '[]',
  timesheet_ids  uuid[] NOT NULL,
  status         payroll_input_status_enum NOT NULL,
  reject_reason  text,
  UNIQUE (cycle_id, associate_id)
);

CREATE TABLE bill.payroll_output (
  id             uuid PRIMARY KEY,
  cycle_id       uuid NOT NULL,
  input_id       uuid NOT NULL REFERENCES bill.payroll_input(id),
  associate_id   uuid NOT NULL,
  gross_pay      numeric(14,2) NOT NULL,
  deductions     jsonb NOT NULL,       -- { pf, esic, tds, advance, other }
  net_pay        numeric(14,2) NOT NULL,
  employer_pf    numeric(14,2), employer_esic numeric(14,2),
  payslip_document_id uuid,
  payslip_delivered_at timestamptz,
  engine_reference text,
  UNIQUE (cycle_id, associate_id)
);

CREATE TABLE bill.statutory_report (
  id             uuid PRIMARY KEY,
  cycle_id       uuid NOT NULL,
  report_type    statutory_report_type_enum NOT NULL,  -- 'pf_ecr'|'esic_return'|'pf_challan'|'esic_challan'
  period         date NOT NULL,
  document_id    uuid NOT NULL,
  total_amount   numeric(14,2),
  record_count   integer NOT NULL,
  generated_at timestamptz NOT NULL DEFAULT now(), generated_by uuid NOT NULL
);
```

**`payroll_input` is frozen at lock.** *"Inputs are frozen at lock so the figures sent match the
figures recorded"* (`M13-I1`) — the row is a snapshot, not a view over live data. A salary revision
applied after lock affects the next cycle, not this one.

### 5.4 Settings (`M13-I2`)

In P03: `bill.payroll.frequency` · `bill.payroll.cut_off_day` · `bill.payroll.pay_day` ·
`bill.payroll.field_mapping` (platform field → engine field) · `bill.payroll.deduction_rates`.

*"Statutory deduction rates come from configuration so they can be updated without a release"* —
which matters, because PF and ESIC thresholds change by government notification, not by our release
cycle.

## 6. State machine

**PayrollCycle:** `open → inputs_locked → sent_to_engine → results_received → payslips_issued → closed`

| Transition | Rules |
|---|---|
| `open → inputs_locked` | **Cannot lock while associates are blocked on incomplete onboarding** (`M11-I5`). Inputs frozen. |
| `inputs_locked → sent_to_engine` | Through the port. Distributed lock — one pay run at a time. |
| `sent_to_engine → results_received` | **Every person sent is accounted for, or reported as an exception** |
| `results_received → payslips_issued` | Payslips generated and delivered |
| `payslips_issued → closed` | |
| `closed → open` | **Only with an audited override** through `02-11` |

**PayrollInput:** `draft → validated → sent` \| `rejected(reason)` — *"a rejected input from the
engine is shown with its reason and can be corrected and resent"*.

## 7. API surface

### 7.1 Exported service

```ts
export const PayrollService = {
  createCycle(input, actor): Promise<PayrollCycle>
  assembleInputs(cycleId): Promise<{ assembled: number; blocked: BlockedAssociate[] }>
  lock(cycleId, actor): Promise<PayrollCycle>       // throws if any associate is blocked
  send(cycleId, actor): Promise<PayrollCycle>       // 202 + job, locked
  ingestResults(cycleId, results): Promise<void>
  correctInput(inputId, patch, actor): Promise<PayrollInput>
  resend(cycleId, inputIds, actor): Promise<void>
  generateStatutoryReports(cycleId, actor): Promise<StatutoryReport[]>
  issuePayslips(cycleId, actor): Promise<void>
  close(cycleId, actor): Promise<PayrollCycle>
  reopen(cycleId, approvalRequestId, actor): Promise<PayrollCycle>   // audited override
}
```

**Input assembly** (`M13-I5`): *"Inputs are assembled from approved timesheets, approved salary
revisions, advances and holds."*

```
for each active associate in the period:
  block if OnboardingService.isPayrollBlocked(candidateId)        ← 03-17
  worked/overtime/leave  ← approved timesheets (03-12 + 03-21)
  base salary            ← current approved revision (03-18)
  advance recovery       ← due instalments (03-18)
  isHeld                 ← active hold (03-18)
```

### 7.2 The engine port (`M13-I5`)

```ts
export const PayrollEnginePort = definePort({
  key: 'payroll_engine',
  operations: {
    submitCycle: { input: PayrollSubmission, output: SubmissionAck, timeout: 60_000 },
    fetchResults: { input: { engineReference }, output: PayrollResults },
    fetchPayslip: { input: { engineReference, employeeCode }, output: { document } },
  },
  manualFallback: { supported: true },   // upload the engine's own file, in the worst case
})
```

*"The engine sits behind an interface so it can be replaced without changing the platform"* — the same
pattern as the registry adapters in M1. Engine selection is **not yet confirmed**; Hirecraft and
PayBooks are the candidates.

## 9. Frontend — `/payroll`

### 9.1 Pay run (`M13-I1`)

*"Running a pay period: open it, lock the inputs, send it, get the results back, close it."*

A staged screen following the cycle state, with **the blocked list shown before locking** —
*"lists associates blocked from the run and why"*, which is `03-17`'s `listBlockedForPayroll`.
The lock button is disabled while anyone is blocked, with the reasons enumerated.

After results: totals, per-associate outputs, and **rejected inputs with their reason**, correctable
and resendable.

Reopening a closed cycle requires an approval through `02-11` and is audited.

### 9.2 Payroll settings (`M13-I2`)

Frequency, cut-off, pay date. **Field mapping from platform fields to the engine's fields** — so
changing engine is configuration, not a release. Statutory deduction rates.

### 9.3 Statutory reports (`M13-I3`)

PF ECR, ESIC return, and the challans for a period. Download.

The screen states clearly that **filing with the authorities is not in scope** — we produce, someone
else files. Reports reconcile to the pay run they came from, and generation is audited.

### 9.4 App: payslips (`M13-I4`) — `apps/mobile`

*"Payslips in the mobile app and over WhatsApp, **which is how most of this workforce will read
them**."*

List by period, open, download. Past periods retained and downloadable. A query routes to finance
**without changing the payslip**.

Delivery reuses `02-07`, not a separate sender (`M13-I4`).

## 12. Notes for the implementer

**Nothing in this module auto-retries.** A retried submission pays people twice; a retried result
ingestion double-counts. Every failure stops the cycle and alarms, and a person decides. This is the
one place where "fail loudly and wait" is unambiguously correct.

**Freeze the inputs, genuinely.** `payroll_input` is a snapshot table, not a view. If someone applies
a salary revision, resolves an attendance mismatch, or approves a late timesheet after lock, this
cycle must be unaffected. That is what makes the pay run reconcilable to what was actually sent.

**Reconcile every person, every time.** Sent 412, received 409 — the three missing people are an
exception report, not a rounding difference. `M13-I5` states this explicitly, and it is the check that
catches an engine silently dropping records.

**This module is last and most exposed.** It needs `03-17`, `03-18` and `03-21` complete. If the
schedule compresses, this is the item that slips — and the plan already names it as the one most
exposed to everything upstream (`00-05 §6`). Flag that early rather than discovering it in month six.
