## 1. Purpose

Funnel and conversion, fill rate, time-to-fill, trial survival, stage-level conversion loss by client
and by recruiter, channel and recruiter performance, the monthly MIS pack, and rate agreed against
baseline.

The plan notes this is a **separate workstream** from billing, sharing nothing beyond the underlying
event data: *"this module holds two workstreams with no shared component beyond the underlying event
data — a billing engine covering two distinct invoice paths, and a reporting layer. They can be
staffed and sequenced independently."*

One hard dependency worth stating up front: **D28's stage-level loss by recruiter cannot be produced
without the D14 owner field in M3**, and none of it can be produced at all without the events written
from phase 3 onwards (`02-09`).

## 5. Data model — projections

All tables in `report`, all **rebuildable from `event_store` alone** (`02-09 §7.4`), all written only
by the projector.

```sql
-- One row per requisition, its full journey. The backbone of most reports.
CREATE TABLE report.requisition_journey (
  requisition_id   uuid PRIMARY KEY,
  client_id uuid NOT NULL, location_id uuid, owner_user_id uuid,   -- D14 owner: REQUIRED for D28
  category candidate_category_enum NOT NULL,
  engagement_type engagement_type_enum NOT NULL,
  source_channel  inbound_channel_enum NOT NULL,
  positions integer NOT NULL,
  created_at timestamptz NOT NULL,
  published_at timestamptz, first_shortlist_at timestamptz,
  first_interview_at timestamptz, first_offer_at timestamptz,
  first_placement_at timestamptz, filled_at timestamptz, closed_at timestamptz,
  close_reason_code text,
  -- age EXCLUDING holds (03-04 §5.1)
  active_seconds_to_fill bigint,
  hold_seconds bigint NOT NULL DEFAULT 0,
  positions_filled integer NOT NULL DEFAULT 0,
  candidates_shortlisted integer NOT NULL DEFAULT 0,
  candidates_interviewed integer NOT NULL DEFAULT 0,
  offers_made integer NOT NULL DEFAULT 0,
  placements integer NOT NULL DEFAULT 0,
  dropouts integer NOT NULL DEFAULT 0
);

-- One row per candidate per requisition. Stage-level loss lives here.
CREATE TABLE report.candidate_stage (
  id uuid PRIMARY KEY,
  candidate_id uuid NOT NULL, requisition_id uuid NOT NULL,
  client_id uuid NOT NULL, owner_user_id uuid, recruiter_user_id uuid,
  category candidate_category_enum NOT NULL, base supply_base_enum,
  ranked_at timestamptz, shortlisted_at timestamptz, sent_to_client_at timestamptz,
  interviewed_at timestamptz, offered_at timestamptz, offer_signed_at timestamptz,
  joined_at timestamptz, trial_survived_at timestamptz,
  lost_at_stage text,                        -- WHERE it stopped
  loss_reason_code text,                     -- WHY — the shared taxonomy
  UNIQUE (candidate_id, requisition_id)
);

CREATE TABLE report.placement_outcome (
  placement_id uuid PRIMARY KEY,
  candidate_id uuid NOT NULL, requisition_id uuid NOT NULL, client_id uuid NOT NULL,
  owner_user_id uuid, category candidate_category_enum NOT NULL,
  joining_date date NOT NULL,
  survived_day_7 boolean, survived_day_30 boolean,
  survived_day_60 boolean, survived_day_90 boolean,
  ended_at date, end_reason_code text,
  retention_source text,                     -- 'client_link'|'ops_recorded'|'deemed'
  invoiced boolean NOT NULL DEFAULT false,
  invoice_amount numeric(14,2)
);

CREATE TABLE report.channel_performance (
  period_month date NOT NULL,
  source_channel inbound_channel_enum NOT NULL,
  client_id uuid,
  requisitions_received integer NOT NULL DEFAULT 0,
  requisitions_parsed_ok integer NOT NULL DEFAULT 0,
  requisitions_manual integer NOT NULL DEFAULT 0,
  requisitions_filled integer NOT NULL DEFAULT 0,
  placements integer NOT NULL DEFAULT 0,
  avg_seconds_to_fill bigint,
  PRIMARY KEY (period_month, source_channel, COALESCE(client_id,'00000000-0000-0000-0000-000000000000'::uuid))
);

CREATE TABLE report.recruiter_performance (
  period_month date NOT NULL,
  recruiter_user_id uuid NOT NULL,
  requisitions_held integer NOT NULL DEFAULT 0,
  requisitions_filled integer NOT NULL DEFAULT 0,
  candidates_submitted integer NOT NULL DEFAULT 0,
  interviews_held integer NOT NULL DEFAULT 0,
  offers_made integer NOT NULL DEFAULT 0,
  placements integer NOT NULL DEFAULT 0,
  trial_survivals integer NOT NULL DEFAULT 0,
  avg_seconds_to_fill bigint,
  PRIMARY KEY (period_month, recruiter_user_id)
);
```

**`owner_user_id` on `requisition_journey` and `candidate_stage` is the D14 owner field.** The plan
records this as a hard dependency: *"D28 stage-level loss by recruiter cannot be produced without the
D14 owner field in M3."*

## 7. API surface

### 7.1 Projectors (`M9-I17`)

*"Reshape events from every module into the tables the reports read."*

| Projector | Reads | Writes |
|---|---|---|
| `requisition-journey` | `demand.requisition.*`, `match.shortlist.sent`, `select.*`, `place.placement.created`, `place.dropout.recorded` | `requisition_journey` |
| `candidate-stage` | `match.ranked_set.generated`, `match.shortlist.sent`, `select.interview.completed`, `select.decision.recorded`, `select.offer.*`, `place.*` | `candidate_stage` |
| `placement-outcome` | `place.placement.created`, `place.trial_event.responded`, `place.retention.confirmed`, `bill.invoice.raised` | `placement_outcome` |
| `channel-performance` | `demand.inbound.*`, `demand.requisition.*` | `channel_performance` |
| `recruiter-performance` | `demand.requisition.allocated`, `select.*`, `place.*` | `recruiter_performance` |
| `rate-variance` | `bill.rate_variance.recorded` | reads `bill.rate_variance` directly |

Every projector is **idempotent and replayable from sequence 0**. `pnpm events:reproject` is a CI
gate (`02-09 §10`).

### 7.2 Query service

```ts
export const AnalyticsService = {
  funnel(filter): Promise<FunnelResult>
  fillRate(filter): Promise<FillRateResult>
  timeToFill(filter): Promise<TimeToFillResult>
  trialSurvival(filter): Promise<SurvivalResult>
  stageLoss(filter): Promise<StageLossResult>
  channelPerformance(filter): Promise<ChannelPerformanceResult>
  recruiterPerformance(filter): Promise<RecruiterPerformanceResult>
  rateVariance(filter): Promise<RateVarianceResult>

}
```

All filters share a shape: date range, client, location, category, engagement type, recruiter,
channel. **All reads go to the read replica** (`01-05 §13`).

## 9. Frontend — `/reports`

Charts follow the `dataviz` conventions: one visual system, accessible in both themes, colour never
the sole carrier of meaning.

### 9.1 Funnel (`M9-I5`)

*"Where vacancies turn into placements, and where they do not."*
Requisitions → shortlisted → sent to client → interviewed → offered → signed → joined → survived day
90. Absolute numbers **and** stage conversion rates. Filter by client, category, channel, period.

### 9.2 Fill and time to fill (`M9-I6`)

Fill rate by client, site, category, recruiter. Time-to-fill distribution — **median and p90, not just
a mean**, because a handful of six-month vacancies makes a mean meaningless.

**Time excludes hold periods** (`03-04 §5.1`). A requisition on hold for three weeks was not taking
three weeks to fill.

### 9.3 Trial survival (`M9-I7`)

*"How many people last to day 90, **which is also when Apollo gets paid**."*
Survival curve at day 7/30/60/90, by client, category, recruiter. Drop-out reasons.

This is the report that connects operations to revenue, and it should say so.

### 9.4 Where candidates drop out (`M9-I8`)

*"Where candidates drop out, **by client and by recruiter**."*
Stage-level loss with reasons from the shared taxonomy. Comparison across clients and recruiters.

**Depends on the D14 owner field.** Where an older requisition has no owner, the report says
"unattributed" rather than silently omitting it.

### 9.5 Channel and recruiter performance (`M9-I9`)

*"Which intake channels and which recruiters actually produce placements."*
Per channel: volume, parse success, manual-queue rate, fill rate, time to fill, placements. Per
recruiter: load, submissions, conversion, placements, trial survival.

Consumed by `03-20` for allocation suggestions.

### 9.6 Monthly pack (`M9-I10`)

*"The monthly pack for Apollo leadership, generated on a schedule rather than assembled by hand."*

A PDF combining the above with month-on-month movement and commentary placeholders. Generated on the
1st, stored via `02-04`, delivered to a configured list.

### 9.7 Rate variance (`M9-I11`)

*"What was agreed against the standard rate, by client, role, specialty and acuity."*
Variance amount and percentage, aggregated and per-instance. Outliers surfaced.

## 11. Open questions

| Question | Impact | Working assumption |
|---|---|---|
| **Reporting period before go-live** | Reports can only cover the period since events began being written. **There is no backfill.** | State it plainly on every report: "Data available from *date*." Better than a chart that silently starts mid-story. This is the practical consequence of `M3-I31`. |
| **Migrated CPAL history** | Migrated candidates arrive with no event history, so pre-migration placements do not appear in the funnel | **`AS-42`** — emit **synthetic historical events** during migration (`03-15`) for records with usable dates, tagged `source: 'migration'`, and let reports filter them out. Partial history clearly labelled beats no history and beats fake precision. |
| `OI-M3-10` | Recruiter load against the 15–16 norm | Displayed on the board (`03-04`); reported here | Load is reported regardless — it is a performance measure here, not an enforcement |
| **Report access and scope** | A recruiter seeing every recruiter's performance is a management decision, not a technical one | **`AS-43`** — `leadership` and `platform_admin` see all; `fulfilment_lead` sees their team; `recruiter` sees only their own. Configurable via permissions. **Confirm with Apollo** — it is a sensitive default either way. |
| `OI-HS-01` | Row-level scoping | Affects what a scoped user sees in reports | **`AS-02`** — the same scope resolver applies to report queries |

## 12. Notes for the implementer

**This module is only as good as the events written months earlier.** Before building anything here,
verify against `01-06 §4` that every listed event is actually emitted with the documented payload. A
missing `demand.requisition.allocated` means recruiter reporting silently reports nothing, and by
phase 7 the gap is unrecoverable for the period already elapsed.

**Projections, never live joins.** It is tempting to compute the funnel with a query across `demand`,
`match`, `select` and `place`. It works on seed data and falls over on real volume, and it couples
the reporting layer to five modules' schemas. Project once, read many.

**Build the funnel first.** It exercises every projector and every event, so if the event catalogue is
incomplete, you find out on day two of this module rather than day twenty.

**Say what the data covers.** Every report carries its coverage window and, where relevant, the count
of unattributed records. A leadership pack that quietly omits half the requisitions because they
predate the owner field is worse than one that says so.
