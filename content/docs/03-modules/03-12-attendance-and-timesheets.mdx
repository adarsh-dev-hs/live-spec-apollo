## 1. Purpose

Shift-level attendance captured by check-in on the candidate app, and the timesheet — which carries an
approval state set by the client through a tokenised link, and which `03-13` invoices against.

Two plan decisions define the shape:

> **CLOSED — Shift attendance capture mechanism.** Attendance is captured by **check-in on the
> candidate app**, replacing the Excel import in the original D22. Release 1 **records a location
> stamp against each check-in without enforcing a boundary**; geo-fencing moves off the exclusion list
> to a named Phase 2 item so the field exists when enforcement is specified.

> **CLOSED — Client timesheet approval.** The timesheet carries an approval state set by the client
> through an A13 link type — the same mechanism as the day-90 confirmation, second instance.
> **D25 invoices against an approved timesheet rather than raw attendance.**

This is the **thin slice**. Leave categorisation, overtime treatment and internal approval routing
remain in `03-21` (M15), and the thin slice must not be built in a way that blocks them.

## 2. Scope

**In** — shift attendance built from app check-ins · expected vs actual · no-show and issue handling ·
timesheet build for a period, priced against the right contract version · client timesheet approval
via link · **deemed approval after the contract window** · timesheet tracking

**Out** — the app check-in screen → `03-07` · the link mechanism → `02-10` · invoicing → `03-13` ·
**leave categorisation, overtime rules and internal approval routing → `03-21`** · geo-fence
enforcement → `03-18` · payroll → `03-19`

## 5. Data model

### 5.1 Shift attendance

```sql
CREATE TABLE place.shift_attendance (
  id                uuid PRIMARY KEY,
  candidate_id      uuid NOT NULL,
  shift_demand_line_id uuid NOT NULL,
  shift_acceptance_id  uuid NOT NULL,
  client_id         uuid NOT NULL,
  location_id       uuid NOT NULL,
  shift_date        date NOT NULL,
  -- expected, from the shift line
  expected_start_at timestamptz NOT NULL,
  expected_end_at   timestamptz NOT NULL,
  -- actual, from app check-in
  actual_start_at   timestamptz,
  actual_end_at     timestamptz,
  check_in_id       uuid, check_out_id uuid,
  -- location: RECORDED, NOT ENFORCED in R1
  check_in_geo      jsonb,      -- { lat, lng, accuracyM, source }
  check_out_geo     jsonb,
  geo_within_fence  boolean,    -- computed if a fence exists; NEVER blocks in R1
  status            attendance_status_enum NOT NULL,
  worked_minutes    integer,
  break_minutes     integer NOT NULL DEFAULT 0,
  issue_code        text, issue_note text,
  issue_resolved_by uuid, issue_resolved_at timestamptz,
  -- pricing, frozen at build time
  rate_card_line_id uuid,
  bill_rate         numeric(14,2),
  timesheet_id      uuid,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (candidate_id, shift_demand_line_id)
);
CREATE INDEX idx_attendance__period ON place.shift_attendance (client_id, shift_date)
  WHERE timesheet_id IS NULL;
CREATE INDEX idx_attendance__issue ON place.shift_attendance (shift_date DESC)
  WHERE status = 'issue_raised';
```

**`geo_within_fence` is computed and stored, never acted on in R1.** `03-18` switches enforcement on
by reading the same column — *"the location field already exists from M8, so switching this on needs
no data change"* (`M12-I5`).

### 5.2 Timesheet

```sql
CREATE TABLE place.timesheet (
  id                uuid PRIMARY KEY,
  reference         text NOT NULL UNIQUE,             -- 'TSH-2026-004412'
  client_id         uuid NOT NULL,
  location_id       uuid,
  period_start      date NOT NULL,
  period_end        date NOT NULL,
  status            timesheet_status_enum NOT NULL,
  shift_count       integer NOT NULL DEFAULT 0,
  total_worked_minutes integer NOT NULL DEFAULT 0,
  total_amount      numeric(14,2) NOT NULL DEFAULT 0,
  currency          text NOT NULL DEFAULT 'INR',
  contract_version_id uuid NOT NULL,                  -- frozen at build
  -- client approval, via 02-10
  link_id           uuid,
  sent_at           timestamptz,
  approved_at       timestamptz,
  approved_by_recipient_id uuid,
  approver_name     text,                             -- denormalised, survives contact changes
  -- deemed approval
  is_deemed_approved boolean NOT NULL DEFAULT false,
  deemed_window_days integer,
  deemed_at         timestamptz,
  queried_at        timestamptz, query_note text,
  invoice_id        uuid,
  built_at          timestamptz NOT NULL DEFAULT now(),
  version           integer NOT NULL DEFAULT 1
);
CREATE INDEX idx_timesheet__pending ON place.timesheet (status, sent_at)
  WHERE status IN ('sent_for_approval');

CREATE TABLE place.timesheet_line (
  id             uuid PRIMARY KEY,
  timesheet_id   uuid NOT NULL REFERENCES place.timesheet(id),
  attendance_id  uuid NOT NULL,
  candidate_id   uuid NOT NULL,
  shift_date     date NOT NULL,
  worked_minutes integer NOT NULL,
  bill_rate      numeric(14,2) NOT NULL,
  bill_unit      text NOT NULL,
  amount         numeric(14,2) NOT NULL,
  -- M15 extends here without restructuring
  leave_type_code text,
  overtime_minutes integer NOT NULL DEFAULT 0,
  overtime_amount  numeric(14,2) NOT NULL DEFAULT 0
);
```

**`leave_type_code`, `overtime_minutes` and `overtime_amount` exist now, unused.** `03-21` populates
them. Adding columns to a table that already carries approved and invoiced timesheets is far more
awkward than leaving three nullable columns empty for two months.

## 6. State machines

**ShiftAttendance:** `expected → checked_in → checked_out` \| `no_show` \| `issue_raised → resolved`

| Transition | Rules |
|---|---|
| `expected → checked_in` | App check-in received (may arrive late via offline sync) |
| `checked_in → checked_out` | Check-out received |
| `expected → no_show` | Shift end passed with no check-in. Automatic, and reversible by Ops with a reason. |
| any → `issue_raised` | Candidate or Ops flags a problem |
| `issue_raised → resolved` | **Audited — it changes what gets invoiced and paid** |

**Timesheet:** `building → built → sent_for_approval → approved | deemed_approved → invoiced`
Plus `queried` (client raised a query) → `built` after correction.

**M15 extends this to** `built → internally_approved → sent_for_approval → …` — an extra state in
front, not a restructure (`03-21`).

### 7.2 Check-in receiver (`M8-I13`)

*"Receive check-ins from the app, **including ones taken with no signal and synced later**."*

| Rule | |
|---|---|
| Idempotent on `clientEventId` | Offline retries must not duplicate |
| Uses the **candidate's** timestamp, not the server's | A 19:00 check-in synced at 22:30 is a 19:00 check-in |
| Late arrivals reopen a `no_show` | With an audit entry showing it was corrected by a sync, not by a person |
| Out-of-range timestamps are flagged, not rejected | A check-in dated three days ago is an issue for a human, not a 400 |

### 7.3 Timesheet build (`M8-I14`)

*"Turn attendance into a timesheet, **priced against the right contract version**."*

1. Collect attendance for the client and period where `timesheet_id IS NULL`
2. Resolve the contract version **as at the period end** (`03-02 §7.1`)
3. Resolve the rate line per shift **as at the shift date**
4. Compute worked minutes less breaks
5. Freeze rates onto the lines; total; link the attendance rows

R1 applies **no leave or overtime treatment** — that is `03-21`. The line columns exist and stay zero.

### 7.4 Timesheet waiting period (`M8-I15`)

*"The clock that lets invoicing proceed when a client simply never replies."*

`deemed_at = sent_at + ContractService.getWindow(clientId, 'timesheet_approval')` — client value,
else platform default, **never undefined**.

## 8. Events and jobs

**Emits:** `place.attendance.recorded` · `.no_show` · `.issue_raised` / `.resolved` ·
`place.timesheet.built` · `.sent_for_approval` · **`place.timesheet.approved`** (→ **`03-13`**,
`03-19`) · `.deemed_approved` · `.queried`

**Subscribes:** `supply.check_in.recorded` (from `03-07`) → record ·
`platform.link.answered` (`timesheet_approval`) → approve or query ·
`platform.link.deemed_agreed` (`timesheet_approval`) → **deemed approve**

**Jobs**

| Job | Cadence | Notes |
|---|---|---|
| `attendance.no-show-sweep` | Hourly | Shifts ended with no check-in → `no_show` |
| `attendance.timesheet-close` | Daily 02:00 IST | Builds timesheets for periods that closed |
| **`attendance.approval-deem`** | Daily 06:00 IST | Applies the contract window. **Revenue-critical — heartbeat alarm.** |
| `attendance.approval-remind` | Daily 09:00 IST | Reminds before the deemed date, stops on approval |

## 9. Frontend — `/attendance`, `/timesheets`

### 9.1 Shift attendance (`M8-I7`)

*"Every shift, expected and actual, built from app check-ins."*

`<DataTable/>`: date, candidate, client, site, expected vs actual times, worked hours, status,
**location captured** (a subtle indicator — recorded, not enforced), issues.

Filter by client, site, date range, status, issue. Adjustments are permitted, require a reason, and
are audited — *"it changes what gets invoiced and paid"*.

### 9.2 Timesheet (`M8-I8`)

*"The period summary the client approves and M9 invoices against."*

Header: client, period, shifts, hours, total, status, approval state and how it was reached.
Lines: candidate, date, hours, rate, amount. The columns for leave and overtime exist and are marked
as arriving in a later phase, rather than being invisible.

Actions: send for approval, record a manual approval (distinct permission, audited), correct and
rebuild.

### 9.3 Timesheet tracking (`M8-I9`)

*"Which timesheets are out, approved, queried, or **about to be treated as approved**."*

The last one is the important column: a countdown to the deemed date, so finance can chase before an
invoice fires on a client who was simply slow. Filter by client, status, days-to-deemed.

### 9.4 Client page: timesheet (`M7-I12`) — `apps/links`

*"The client approves a timesheet from a link. M9 invoices against the approved version, not raw
attendance."*

Period summary, per-candidate lines with hours, total. Two actions: **Approve** or **Query** with a
note. States plainly what approval means and — importantly — that if they do not respond by a stated
date, it will be treated as approved. That sentence is what makes the deemed path defensible.

`< 150 KB, works at 320px` (`01-03 §9`).

## 10. Acceptance criteria

| # | Criterion | Source |
|---|---|---|
| 1 | Attendance is captured **by app check-in**, with no alternative route in R1 | Plan CLOSED |
| 2 | A location stamp is recorded against each check-in and **never enforced** | Plan CLOSED |
| 3 | Switching enforcement on in M12 requires **no data change** | `M12-I5` |
| 4 | Offline check-ins sync later without duplicating, using the candidate's timestamp | `M8-I13` |
| 5 | A late-synced check-in reverses a `no_show`, audited as a sync correction | §7.2 |
| 6 | A timesheet is built from attendance and priced against the **contract version and rate in force then** | `M8-I14` |

| 9 | A deemed approval is distinguishable from a real one everywhere it appears | §5.2 |

| 11 | Attendance adjustments require a reason and are audited | `M8-I7` |

## 12. Notes for the implementer

**The check-in receiver is where the correctness lives.** Idempotency on `clientEventId`, the
candidate's timestamp rather than the server's, and reversing a `no_show` on a late sync. Get those
three right and everything downstream is arithmetic.

**Freeze the rate at build time.** A rate card published after a timesheet is built must not change
that timesheet's amounts. Resolve as at the shift date, store on the line, never recompute.

**Leave the M15 columns in place from day one.** Three nullable columns cost nothing now.
Restructuring a table carrying approved and invoiced timesheets in month six costs a great deal.

**Say the deemed rule out loud on the client page.** "If we do not hear from you by 14 March, this
timesheet will be treated as approved." That single sentence is the difference between a defensible
deemed approval and a disputed invoice.
