**Package** `@apollo/requisitions` (extension) · **Schema** `demand` · **Plan** D14 (full) · **Effort** ~26.5pd · **Risk** Low `MODEL` · **Build in** Phase 6 · **Release** Part 3

## 1. Purpose

`03-03` records which recruiter was put on which vacancy, as decided on the morning call. This module
makes the system do the deciding: score which vacancies matter most on urgency, value and age; suggest
which recruiter should take each one based on current load and past success; and add an approval step
before a vacancy goes live, which `03-03` deliberately does not have.

**The system suggests; a person still decides.** Nothing here writes an allocation directly.

It sits in Phase 6 rather than next to `03-03` for one reason: the priority scoring and the recruiter
suggestion **read performance data that `03-12` produces**, and `03-12` does not exist until Phase 6.
Building it earlier would mean building a suggestion engine against data that does not exist yet.

## 2. Scope

### In scope

- Priority scoring per requisition, with the reasoning shown
- The priority board, and manual override of a priority with a reason
- Suggested recruiter with current load shown against the operating norm
- The requisition approval workflow — a new state between created and open
- The scoring and load-balancing engine

### Explicitly out of scope

- The requisition, allocation record and fulfilment board — `03-03`. This module **changes M3
  behaviour rather than adding screens beside it**.
- The performance data itself — `03-12`.

### Explicitly not built

- **Forcing an allocation.** The engine never writes one.
- Forecasting demand.
- Enforcing the 15–16 vacancy norm. Load is **displayed**, not enforced.
- Automatic model retraining. Suggestion outcomes are captured so the model can be tuned against
  evidence, by a person.

## 5. Data model

```sql
CREATE TABLE demand.priority_score (
    requisition_id uuid PRIMARY KEY REFERENCES demand.requisition(id),
    score numeric(6,3) NOT NULL,
    factors jsonb NOT NULL,          -- {urgency, value, age} with each contribution — WHY it scored
    weight_version integer NOT NULL,
    manual_override numeric(6,3),
    override_reason text, overridden_by uuid, overridden_at timestamptz,
    computed_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE demand.priority_config (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    version integer NOT NULL,
    factors jsonb NOT NULL,          -- weights per factor; configurable
    is_active boolean NOT NULL DEFAULT true,
    updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL
);

CREATE TABLE demand.recruiter_capacity (
    recruiter_id uuid NOT NULL,
    as_at date NOT NULL,
    open_requisitions integer NOT NULL,
    operating_norm integer NOT NULL DEFAULT 16,   -- 15–16, DISPLAYED not enforced
    fill_rate_90d numeric(5,4),                   -- from 03-12
    avg_time_to_fill_days numeric(6,2),
    PRIMARY KEY (recruiter_id, as_at)
);

CREATE TABLE demand.allocation_suggestion (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    suggested_recruiter_id uuid NOT NULL,
    rationale jsonb NOT NULL,        -- load, past fill rate on this category and client
    state text NOT NULL DEFAULT 'generated'
      CHECK (state IN ('generated','accepted','overridden','expired')),
    chosen_recruiter_id uuid,        -- when overridden
    override_reason text,
    decided_by uuid, decided_at timestamptz,
    generated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE demand.approval_request (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    requisition_id uuid NOT NULL REFERENCES demand.requisition(id),
    rule_matched text,               -- by client, value or role
    state text NOT NULL DEFAULT 'pending'
      CHECK (state IN ('pending','approved','rejected','bypassed')),
    decided_by uuid, decided_at timestamptz, decision_reason text,
    bypass_reason text,              -- an urgent bypass is possible but ALWAYS audited
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE demand.approval_rule (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    client_id uuid, min_value numeric(14,2), role_code text,
    required_role text NOT NULL,
    is_enabled boolean NOT NULL DEFAULT true
);
```

## 6. State machines

### `Requisition`, extended (`M14-I3`)

```
 created ──▶ awaiting_approval ──▶ approved ──▶ open      ← NEW in Phase 6
        └──▶ rejected, returned to whoever raised it, with the reason
        └──▶ bypassed (urgent) ──▶ open                    ← always audited
```

This is a **new state on an existing record**, added by extending `03-03`'s state machine rather than
by building a parallel one. Requisitions created before this ships are unaffected.

### `AllocationSuggestion`

`generated → accepted | overridden`, or `expired`. Either way a person decides, and the outcome is
recorded so the model can be tuned against evidence.

## 8. Events and jobs

**Events emitted:** `demand.priority.computed` · `.overridden` · `demand.allocation_suggestion.generated`
· `.accepted` · `.overridden` · `demand.requisition.approval_requested` · `.approved` · `.rejected` ·
`.bypassed`.

**Events subscribed:** `demand.requisition.created` → raise an approval request if a rule matches;
`demand.requisition.status_changed` → recompute priority; `reporting.mart.refreshed` → refresh capacity.

**Jobs**

| Job | Schedule | Purpose |
|---|---|---|
| `demand.compute-priority` | hourly | Scores open requisitions on urgency, value and age |
| `demand.refresh-capacity` | daily | Load and performance from `03-12` |
| `demand.suggest-allocation` | on requisition open | Generates a suggestion; **never writes an allocation** |
