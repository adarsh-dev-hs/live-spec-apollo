## 1. Purpose

The React Native app healthcare professionals use: sign up with a phone number, build a profile from a
CV, find permanent jobs and shifts, apply and accept, track what is happening, upload documents, answer
availability questions, and **check in and out of a shift**.

D3 is a three-way shared build and a hard dependency. It sits in M4, but shift discovery, acceptance
and check-in serve M8, and it is one of the two channels A14 captures responses on in M5. Because
**shift attendance is captured by app check-in with no alternative route, no app means no attendance,
no timesheet and no shift invoice.** Plan it against all three consumers, not just this module.

## 2. Scope

### In scope

- Sign up, phone + OTP, category selection, DPDP consent (`M4-I1`)
- Profile building from a CV with review-and-correct, or by hand (`M4-I2`, `M4-I20`)
- Category-specific attribute capture (`M4-I3`)
- Job discovery and application — Base A (`M4-I4`)
- Shift discovery, acceptance, clash prevention — Base B (`M4-I5`)
- Application and shift tracking, interview confirmation, offer acceptance (`M4-I6`)
- **Shift check-in and check-out with an offline queue** (`M4-I7`)
- Document upload for verification (`M4-I8`)
- Notification settings and the per-user message log (`M4-I9`)
- The in-app availability answer, on the same schema as WhatsApp (`M4-I10`)
- The app shell: navigation, offline handling, push, release pipeline, help content

### Explicitly out of scope

- The candidate record, credentials and verification queue — `03-04`.
- Candidate authentication mechanics — `02-01`.
- Availability decay and cadence selection — `03-06`.
- Attendance exceptions, timesheets and pricing — `03-10`.
- The onboarding flow (`M11-I4`) and payslips (`M13-I4`). Those screens are **owned by `03-15` and
  `03-17`** and built against this app's shell, per the confirmed scope decision.

### Explicitly not built

- Blocking a check-in based on location. The stamp is **recorded, not enforced**; enforcement is
  `03-16` (`M12-I5`).
- Candidate-visible match scores. Ranking is an internal tool only.
- Guided flows over WhatsApp. Anything guided happens here.
- Web or PWA version. Store distribution only.
- In-app chat with a recruiter.

## 5. Data model

Owned by `03-04` and `02-01`. This module adds:

```sql
CREATE TABLE candidates.application (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    candidate_id uuid NOT NULL REFERENCES candidates.candidate(id),
    requisition_id uuid NOT NULL,
    state text NOT NULL DEFAULT 'applied' CHECK (state IN
      ('applied','shortlisted','interviewing','offered','joined','rejected','withdrawn')),
    applied_at timestamptz NOT NULL DEFAULT now(),
    source text NOT NULL DEFAULT 'app',      -- 'app' | 'recruiter'
    UNIQUE (candidate_id, requisition_id)
);

CREATE TABLE candidates.shift_acceptance (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    candidate_id uuid NOT NULL REFERENCES candidates.candidate(id),
    shift_demand_line_id uuid NOT NULL,
    state text NOT NULL DEFAULT 'accepted'
      CHECK (state IN ('accepted','declined','cancelled','worked','no_show')),
    accepted_at timestamptz NOT NULL DEFAULT now(),   -- timestamped confirmation
    channel text NOT NULL DEFAULT 'app',              -- 'app' | 'whatsapp'
    UNIQUE (candidate_id, shift_demand_line_id)
);
-- a candidate cannot hold two accepted shifts that overlap in time (M4-I5)
CREATE INDEX ON candidates.shift_acceptance (candidate_id, state);

CREATE TABLE candidates.cv_parse (
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    candidate_id uuid NOT NULL REFERENCES candidates.candidate(id),
    document_id uuid NOT NULL,
    extracted jsonb NOT NULL,                -- per-field values
    confidence jsonb NOT NULL,               -- per-field confidence, drives what is highlighted
    accepted jsonb,                          -- what the candidate confirmed after correcting
    outcome text NOT NULL CHECK (outcome IN ('parsed','failed')),
    created_at timestamptz NOT NULL DEFAULT now()
);
```

Offline state lives on the device: a durable check-in queue in SQLite (Expo SQLite), replayed on
reconnect with the **original timestamp preserved**.

## 6. State machines

### `Application` (`M4-I6`)

`applied → shortlisted → interviewing → offered → joined`, or `rejected` / `withdrawn`.
The app shows a **client-appropriate stage and never an internal rejection reason code**.

### `ShiftAcceptance` (`M4-I5`)

| From | Event | To | Rule |
|---|---|---|---|
| — | candidate accepts | `accepted` | **Assigned to a named candidate with a timestamped confirmation**; a clashing shift is blocked or warned |
| `accepted` | candidate or Ops cancels | `cancelled` | Position returns to the shift line |
| `accepted` | checked in and out | `worked` | Handled by `03-10` |
| `accepted` | shift passes with no check-in | `no_show` | **An exception in `03-10`, not silent absence** |

An acceptance arriving on both app and WhatsApp **reconciles to one record** (`A14`).

### Offline check-in (`M4-I7`, `M8-I14`)

```
tap check-in ──▶ write to local queue with device timestamp + location
             ──▶ optimistic UI: "checked in, will sync"
             ──▶ on reconnect: POST with the ORIGINAL timestamp and an idempotency key
                     ├─ accepted → local row cleared
                     └─ duplicate → server returns the original; no second attendance record
```

## 8. Events and jobs

**Events emitted:** `candidates.application.created` · `candidates.shift.accepted` · `.declined` ·
`candidates.attendance.checked_in` · `.checked_out` · `candidates.availability.answered` (app channel).

**Events subscribed:** `selection.interview.proposed`, `selection.offer.sent`,
`placement.trial_event.due` → push notification and an in-app item;
`candidates.credential.expiring` → re-upload prompt.

**Jobs**

| Job | Trigger | Purpose |
|---|---|---|
| `candidates.parse-cv` | on upload | `04-06`; **failure retains the file and falls back to manual entry** |
| `candidates.push` | on subscribed events | Expo push through `02-09` |
