## 1. Purpose

Move Apollo's existing candidate data out of CPAL and into the platform, after which **the platform
becomes the system of record and the old tool is switched off.**

> **We have never seen this data.** We do not know how many records there are, how complete they are,
> how many duplicates it contains, or whether fields map cleanly onto the new model. Part A says a
> joint profiling exercise will settle this, and Apollo will provide access. **It has not happened
> yet.** — `OI-A-02`

> A10 cannot be sized at all. The figures shown against these items are **placeholders to hold the
> shape of the plan, not estimates. This is the single largest unpriced item in the six months.**

Everything below is therefore written as a *shape*, not a *plan*. The shape is right; the numbers are
not, and will not be until profiling runs.

## 5. Data model

```sql
CREATE TABLE supply.migration_batch (
  id              uuid PRIMARY KEY,
  reference       text NOT NULL UNIQUE,             -- 'MIG-2026-0007'
  source_system   text NOT NULL DEFAULT 'cpal',
  entity_type     text NOT NULL,                    -- 'candidate'|'credential'|'document'|'application'
  status          migration_batch_status_enum NOT NULL,
  source_file_id  uuid,
  -- counts that MUST reconcile to the source total
  count_source    integer NOT NULL DEFAULT 0,
  count_extracted integer NOT NULL DEFAULT 0,
  count_mapped    integer NOT NULL DEFAULT 0,
  count_loaded    integer NOT NULL DEFAULT 0,
  count_exception integer NOT NULL DEFAULT 0,
  count_rejected  integer NOT NULL DEFAULT 0,
  count_duplicate integer NOT NULL DEFAULT 0,
  checkpoint      jsonb,                            -- resume point
  started_at timestamptz, paused_at timestamptz, completed_at timestamptz,
  reconciled_at   timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE supply.migration_record (
  id              uuid PRIMARY KEY,
  batch_id        uuid NOT NULL REFERENCES supply.migration_batch(id),
  source_id       text NOT NULL,                    -- CPAL's own id
  source_row      jsonb NOT NULL,                   -- RAW, retained
  mapped_payload  jsonb,
  status          migration_record_status_enum NOT NULL,
  target_id       uuid,                             -- the created candidate
  duplicate_of_id uuid,
  error_field     text, error_message text,
  reject_reason   text,
  processed_at    timestamptz,
  resolved_by     uuid, resolved_at timestamptz,
  UNIQUE (batch_id, source_id)
);
CREATE INDEX idx_migration_record__exception ON supply.migration_record (batch_id, status)
  WHERE status IN ('exception','rejected');

CREATE TABLE supply.migration_profile (
  id              uuid PRIMARY KEY,
  entity_type     text NOT NULL,
  profiled_at     timestamptz NOT NULL DEFAULT now(),
  total_records   integer NOT NULL,
  field_stats     jsonb NOT NULL,   -- per field: populated %, distinct, sample, inferred type
  duplicate_estimate jsonb NOT NULL,-- by match key
  mapping_feasibility jsonb NOT NULL,-- fields with NO target in the new model
  notes           text
);
```

**`UNIQUE (batch_id, source_id)` is what makes re-running safe.** *"A re-run of a completed batch
produces no duplicate records"* (`M1-I11`) — a stated acceptance criterion, and this is the mechanism.

**`source_row` is retained raw.** When a candidate's data looks wrong six months after cutover, the
question "what did CPAL actually hold" needs an answer.

## 6. State machines

**MigrationBatch:** `staged → profiled → transformed → loaded → reconciled → cut_over`
Plus `paused` (resumable) and `failed`.

| Transition | Rules |
|---|---|
| `staged → profiled` | Profiling complete; `migration_profile` written |
| `profiled → transformed` | Mapping applied; exceptions raised |
| `transformed → loaded` | Records written to `supply` |
| `loaded → reconciled` | **All counts reconcile to the source total** |
| `reconciled → cut_over` | Platform becomes system of record for this entity |
| any → `paused` | **Resumes without reprocessing already-loaded records** |

**MigrationRecord:** `extracted → mapped → loaded`
\| `extracted → exception → resolved → loaded`
\| `rejected(reason)` — *"so it is counted and not lost"*
\| `duplicate → merged`

## 7. API surface

### 7.1 Profiling (`M1-I10`) — **a blocker, not a task**

```ts
export const ProfilingService = {
  profile(sourceFileId, entityType): Promise<MigrationProfile>
}
```

Produces:

| Output | Why it matters |
|---|---|
| **Volume** | Nothing can be estimated without it |
| **Field completeness** | Which fields are usable and which are mostly empty |
| **Distinct values and samples** | Whether a free-text field maps to a configured list |
| **Duplicate rate** by match key | Drives `M1-I12`'s size entirely |
| **Mapping feasibility** — fields with **no target** | Every one is a decision: map, drop, or extend the model |

*"The output is sufficient to estimate the remainder of A10"* (`M1-I10`). Until it runs, every number
in this document is a placeholder.

### 7.2 Pipeline (`M1-I11`)

```ts
export const MigrationService = {
  createBatch(input, actor): Promise<MigrationBatch>
  start(batchId, actor): Promise<void>       // 202 + job. DISTRIBUTED LOCK: one at a time.
  pause(batchId, actor): Promise<void>
  resume(batchId, actor): Promise<void>      // from checkpoint, no reprocessing
  listExceptions(batchId, request): Promise<Page<MigrationRecord>>
  correctRecord(recordId, patch, actor): Promise<MigrationRecord>   // → back to load
  rejectRecord(recordId, reason, actor): Promise<MigrationRecord>   // counted, not lost
  reconcile(batchId): Promise<ReconciliationReport>
}
```

| Rule | |
|---|---|
| **Idempotent** | `UNIQUE (batch_id, source_id)`. Re-run produces no duplicates. |
| **Resumable** | Checkpointed; resume skips loaded records |
| **Single-threaded per batch** | Distributed lock — *"a batch cannot be started twice concurrently"* (`M1-I2`) |
| **No auto-retry** | A failed batch stops and a human decides (`01-06 §6`) |
| **Progress observable mid-run** | *"not only on completion"* (`M1-I2`) |

### 7.3 Duplicate resolution (`M1-I12`)

*"Find people who appear twice in the imported data and merge them **without deleting either
record**."*

Uses `03-05`'s dedupe and merge mechanism, run as a bulk scan (`AS-26`, `OI-A-03`) — one
implementation, and ongoing dedupe stays in place for the legacy base afterwards.

Two passes: within the migrated set, and migrated against already-existing platform records.

## 9. Frontend — `/settings/migration` (`M1-I2`)

### Migration status

*"Lists each migration run with how many records were read, loaded and failed."*

Per batch: entity, status, source count, extracted, mapped, loaded, exceptions, rejected, duplicates,
**live progress bar**, elapsed. Start, pause, resume.

A prominent reconciliation panel: **do the counts add up to the source total?** Green or red, with
the difference itemised. This is the gate for cutover.

### Failed records

*"Lists records that did not load, with the reason. Opens one to correct the field that failed and
send it back to load. Rejects a record with a reason so it is counted and not lost."*

`<DataTable/>` of exceptions: source id, error field, error message, raw row. Inline correction, then
requeue. Reject with a reason. Bulk-correct where the same field fails the same way across many rows —
which, on real legacy data, is the common case.

### Profile report

Per entity: volume, per-field completeness, distinct values, duplicate estimate, and **the list of
fields with no target in the new model**. This report is the deliverable of `M1-I10` and the input to
every subsequent estimate.

## 12. Notes for the implementer

**Run profiling in phase 2, before anything else in this module.** It is explicitly *"a blocker, not
a task"*, and every number attached to A10 is a placeholder until it completes. If Apollo has not
provided access by the end of month one, that is a schedule risk to escalate, not a task to
reschedule.

**Build the pipeline generically, against the profile.** Field mapping is configuration
(`mapped_payload` from a mapping definition), not hardcoded transforms. Real legacy data will require
mapping changes after the first dry run, and probably after the second.

**Dry-run into a scratch environment first.** Load into `qa` against a copy of the real extract,
reconcile, inspect the exceptions, fix the mapping, repeat. The idempotency guarantee is what makes
this affordable, and it is why it is a stated acceptance criterion rather than a nicety.

**Parallel run before retirement.** *"The legacy tool is retired only after the parallel-run period
closes"* (`M1-I9`). Both systems live, both being written to by Apollo, differences reported daily.
It is tedious and it is the only way anyone will trust the switch.

**The consent gap is a genuine finding, not a technicality.** Neither client document addresses it,
and it means the migrated pool — the bulk of the candidate base at go-live — cannot be verification-
checked until it is resolved. Raise it early with Apollo legal.
