## 1. Purpose

What Apollo charges, and what the signed agreement says. **M9 reads these terms at the moment it
raises an invoice, so errors here become billing errors.**

The plan sequences this early rather than late, for one reason: *"D13 contract terms are sequenced
early, not late, because M9 cannot invoice without them"* — and there is no fallback.

This module also holds the three per-client waiting periods that let revenue proceed when a client
never replies.

**In** — rate cards, versioned, by role/skill/location with effective dates · **as-at rate lookup** ·

## 5. Data model

### 5.1 Rate cards

```sql
CREATE TABLE clients.rate_card (
  id            uuid PRIMARY KEY,
  client_id     uuid NOT NULL REFERENCES clients.client(id),
  reference     text NOT NULL UNIQUE,
  name          text NOT NULL,
  engagement_type engagement_type_enum NOT NULL,   -- 'permanent' | 'contractual'
  current_version_id uuid,
  is_active     boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE clients.rate_card_version (
  id             uuid PRIMARY KEY,
  rate_card_id   uuid NOT NULL REFERENCES clients.rate_card(id),
  version_number integer NOT NULL,
  status         rate_version_status_enum NOT NULL,  -- 'draft'|'in_effect'|'superseded'
  effective_from date NOT NULL,
  effective_to   date,                               -- NULL = still in force
  approved_by    uuid,
  approved_at    timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  UNIQUE (rate_card_id, version_number)
);
CREATE INDEX idx_rate_version__asat
  ON clients.rate_card_version (rate_card_id, effective_from DESC);

CREATE TABLE clients.rate_card_line (
  id             uuid PRIMARY KEY,
  version_id     uuid NOT NULL REFERENCES clients.rate_card_version(id),
  role_code      text NOT NULL,                   -- from the configured role list
  skill_code     text,                            -- specialty / discipline; NULL = any
  category       candidate_category_enum,         -- 'nurse'|'doctor'|'allied'; NULL = any
  location_id    uuid,                            -- NULL = all locations for this client
  -- permanent
  fee_percent    numeric(6,3),                    -- 5.000 – 6.000 % of annual salary
  fee_minimum    numeric(14,2),
  -- contractual
  bill_rate      numeric(14,2),                   -- per shift or per hour
  bill_unit      text,                            -- 'shift'|'hour'
  overtime_multiplier numeric(6,3),
  currency       text NOT NULL DEFAULT 'INR',
  notes          text
);
CREATE INDEX idx_rate_line__lookup
  ON clients.rate_card_line (version_id, role_code, skill_code, location_id);
```

**Versions are never deleted** (`M2-I9`): *"an old requisition must still price against the rate that
applied when it was raised."*

Line resolution is **most-specific-wins**: exact location + skill + category, then progressively
wildcarded, then the client default. Ambiguity — two lines equally specific — is a **configuration
error surfaced at save time**, not a silent pick at invoice time.

### 5.2 Contracts

```sql
CREATE TABLE clients.contract (
  id             uuid PRIMARY KEY,
  client_id      uuid NOT NULL REFERENCES clients.client(id),
  reference      text NOT NULL UNIQUE,            -- 'CTR-2026-0087'
  title          text NOT NULL,
  engagement_types engagement_type_enum[] NOT NULL,
  status         contract_status_enum NOT NULL,
  current_version_id uuid,
  signed_document_id uuid,                        -- platform.document
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  version integer NOT NULL DEFAULT 1
);

CREATE TABLE clients.contract_version (
  id                uuid PRIMARY KEY,
  contract_id       uuid NOT NULL REFERENCES clients.contract(id),
  version_number    integer NOT NULL,
  effective_from    date NOT NULL,
  effective_to      date,
  renewal_date      date,
  notice_period_days integer,
  -- terms M9 reads at the moment a trigger fires
  placement_fee_percent      numeric(6,3),
  placement_fee_basis        text,                -- 'annual_ctc'|'annual_gross'
  guarantee_period_days      integer,             -- OI-A-13 — see §11
  retention_confirm_day      integer NOT NULL DEFAULT 90,
  payment_terms_days         integer NOT NULL,
  rate_card_id      uuid REFERENCES clients.rate_card(id),
  terms             jsonb NOT NULL,               -- full structured terms, frozen per version
  signed_document_id uuid,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  UNIQUE (contract_id, version_number)
);
CREATE INDEX idx_contract_version__asat
  ON clients.contract_version (contract_id, effective_from DESC);
```

### 5.3 Client waiting periods (`M2-I10`)

```sql
CREATE TABLE clients.client_window_config (
  id          uuid PRIMARY KEY,
  client_id   uuid NOT NULL REFERENCES clients.client(id),
  window_key  client_window_enum NOT NULL,        -- 'retention_confirmation'
                                                  -- 'timesheet_approval'
                                                  -- 'requisition_follow_up'
  days        integer NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now(),
  updated_by  uuid NOT NULL,
  UNIQUE (client_id, window_key)
);
```

**Resolution: client value → platform default from P03 → never undefined.**
*"Three waiting periods per client, each with a platform-wide fallback so an unconfigured client
never stalls invoicing"* (`M2-I10`).

## 6. State machines

**Contract:** `draft → active → renewed (creates a new version) → expired` \| `→ terminated (reason)`

| Transition | Rules |
|---|---|
| `draft → active` | Requires effective date, payment terms, and a rate card for each engagement type |
| `active → renewed` | **Creates a new version.** The previous version gets `effective_to`; it is never edited. |
| `active → expired` | Automatic when `effective_to` passes with no renewal |
| `active` → `terminated` | Reason required. Existing placements continue; new requisitions blocked. |

**RateCardVersion:** `draft → in_effect → superseded`

Publishing a new version sets `effective_to` on the previous one to the day before the new
`effective_from`. **Gaps and overlaps are rejected at save time** — a gap means an unpriceable
requisition, and an overlap means two possible answers to "what is the rate".

## 7. API surface

### 7.1 Exported service — the two lookups everything depends on

```ts
export const ContractService = {
  /** M9 calls this AT THE MOMENT A BILLING TRIGGER FIRES. Never 'today'. */
  getTermsAsAt(clientId: string, asAt: Date, engagementType): Promise<ContractTerms>

  /** Given role, skill, location and DATE, return the right line from the right version. */
  getRateAsAt(input: {
    clientId, roleCode, skillCode?, category?, locationId?, asAt: Date, engagementType
  }): Promise<RateCardLine>

  /** Client value → platform default. NEVER undefined. */
  getWindow(clientId: string, windowKey: ClientWindow): Promise<number>

  getContract(id): Promise<Contract>
  getActiveContract(clientId, engagementType): Promise<Contract | null>
  listVersions(contractId): Promise<ContractVersion[]>
}
```

Both `asAt` parameters are **required, with no default**. A signature that defaults to `now()` is how
an invoice ends up priced at today's rate instead of the rate that applied when the requisition was
raised (`01-05 §6.2`).

## 9. Frontend

### 9.1 Rate card (`M2-I5`) — `/clients/:id/rate-cards`

Version selector with effective dates. Lines in a `<DataTable/>`: role, skill, category, location,
fee % or bill rate, currency.

Editing creates a **draft version** — never edits an in-effect one. Publishing asks for the effective
date and shows what it supersedes. A **diff against the previous version** is shown before publish,
because a rate card change is a commercial act.

### 9.2 Contract list (`M2-I7`)

`<DataTable/>`: reference, client, types, status, effective from/to, **renewal date**, payment terms.
Default view highlights *"which ones are coming up for renewal"*.

### 9.3 Contract details (`M2-I8`)

The terms M9 reads. The screen carries a plain warning: **errors here become billing errors.**

Fields: effective dates, renewal date, notice period, placement fee % and basis, guarantee period,
retention confirmation day (default 90), payment terms days, linked rate card, signed document
upload.

### 9.4 Contract versions (`M2-I9`)

Version history with effective ranges and a diff between any two. Read-only. The screen states:
*"an invoice must read the version that applied at the time, not today's."*

### 9.5 Client waiting periods (`M2-I10`)

Three windows, each showing: platform default, this client's value if set, and the **effective**
value. Clearing a value falls back to the default, and the UI says so explicitly.

Each window carries a one-line explanation of what expiring means — because "14 days" is meaningless
without "after which we invoice anyway".

## 10. Acceptance criteria

| # | Criterion | Source |
|---|---|---|
| 1 | Given a role, skill, location and **date**, the lookup returns the rate line from the version in force **then** | `M2-I11` |
| 2 | An old requisition prices against the rate that applied when it was raised, not today's | `M2-I9` |
| 3 | Rate card versions are never deleted | `M2-I9` |
| 4 | Publishing a version with a gap or overlap against the previous one is rejected | §6 |
| 5 | Two equally-specific rate lines are rejected at save time, not resolved arbitrarily at invoice time | §5.1 |
| 6 | Renewal creates a new contract version; the previous version is never edited | `M2-I9` |
| 7 | `getTermsAsAt` returns the terms in force at the trigger date, not today's | `M2-I12`, `M9-I14` |
| 8 | Three waiting periods per client, each with a platform-wide fallback | `M2-I10` |
| 9 | **A client with no configured window resolves to the platform default and never stalls invoicing** | `M2-I10`, `OI-A-05` |
| 10 | An alert fires before a contract runs out | `M2-I13` |
| 11 | A client with an active contract and no in-effect rate version is flagged daily | §8 |
| 12 | Neither `getTermsAsAt` nor `getRateAsAt` compiles without an explicit `asAt` | §7.1 |

| ID | Question | Impact | Working assumption |
|---|---|---|---|
| **`OI-A-13`** | **How long is the guarantee period, and does it run past day 90?** | **This changes scope, not just a number.** Apollo invoices at day 90, which removes the need to reverse an invoice if someone leaves early. But if the contract guarantees a replacement for six months, a candidate leaving in month five means an invoice already raised must be corrected — **which requires credit and debit notes, currently out of scope until M15.** | **`AS-20`** — `guarantee_period_days` exists on the contract version and defaults to 90, so the data model supports either answer. **If Apollo confirms a longer period, `03-21` credit notes move into phase 6 and this becomes a scope change with a number attached.** Estimate blocker — escalate. |

## 12. Notes for the implementer

**The `asAt` parameter is the whole point of this module.** Two functions — `getTermsAsAt` and
`getRateAsAt` — are read by billing at the moment money is decided. Make `asAt` required in the type
signature, and write the test that proves a rate published today does not change an invoice raised
last month.

**Freeze resolved values onto the invoice.** Even a correct as-at lookup can give a different answer
later if someone back-dates a version. `03-13` resolves once at trigger time and stores the resolved
numbers on the invoice (`01-05 §6.2`). This module provides the lookup; that one provides the freeze.

**Build the rate-gap check.** A client with an active contract and no in-effect rate version produces
an invoice failure at the worst possible moment — when a placement has survived 90 days and finance
is expecting to bill. A daily report is far cheaper than that phone call.
