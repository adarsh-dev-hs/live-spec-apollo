## 1. Purpose

Two things left out of the thin slices.

**First, the full timesheet:** leave types, overtime rules, and an internal approval route inside
Apollo before it goes to the client. `03-12` sends straight to the client; this adds a step in front.

**Second, the money coming back in:** payments received, matched against invoices including
part-payments and TDS, an overdue report, automatic reminders and chasing, and credit and debit notes.

> Together these turn the platform from one that raises invoices into one that tracks whether Apollo
> actually got paid.

## 5. Data model

### 5.1 Leave and overtime

```sql
CREATE TABLE place.leave_type (
  id             uuid PRIMARY KEY,
  code           text NOT NULL UNIQUE,
  name           text NOT NULL,
  is_paid        boolean NOT NULL,
  pay_percent    numeric(5,2) NOT NULL DEFAULT 100,
  counts_towards_attendance boolean NOT NULL DEFAULT false,
  requires_approval boolean NOT NULL DEFAULT true,
  is_active      boolean NOT NULL DEFAULT true
);

CREATE TABLE place.leave_record (
  id             uuid PRIMARY KEY,
  candidate_id   uuid NOT NULL,
  leave_type_id  uuid NOT NULL REFERENCES place.leave_type(id),
  from_date date NOT NULL, to_date date NOT NULL,
  days           numeric(5,2) NOT NULL,
  reason         text,
  status         leave_status_enum NOT NULL,       -- 'requested'|'approved'|'rejected'|'cancelled'
  approval_request_id uuid,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);

CREATE TABLE place.overtime_rule (
  id             uuid PRIMARY KEY,
  name           text NOT NULL,
  client_id      uuid,                             -- rules differ BY CLIENT
  state          text,                             -- and BY STATE
  daily_threshold_minutes integer,
  weekly_threshold_minutes integer,
  multiplier     numeric(5,2) NOT NULL,
  applies_on_holidays boolean NOT NULL DEFAULT false,
  effective_from date NOT NULL,
  effective_to   date,                             -- TEMPORAL: a rule change must not alter approved timesheets
  is_active      boolean NOT NULL DEFAULT true
);

CREATE TABLE place.timesheet_approval_route (
  id             uuid PRIMARY KEY,
  client_id      uuid,
  location_id    uuid,
  min_amount     numeric(14,2),
  required_permission text NOT NULL,
  sequence       integer NOT NULL DEFAULT 1,
  is_active      boolean NOT NULL DEFAULT true
);
```

`overtime_rule` is **temporal** (`01-05 §6.2`) because *"a rule change does not alter timesheets
already approved"* (`M15-I1`).

### 5.2 Payments

```sql
CREATE TABLE bill.payment (
  id             uuid PRIMARY KEY,
  reference      text NOT NULL UNIQUE,             -- 'PAY-2026-000512'
  client_id      uuid NOT NULL,
  amount_received numeric(14,2) NOT NULL,
  -- TDS recorded SEPARATELY so gross and net are both visible
  tds_amount     numeric(14,2) NOT NULL DEFAULT 0,
  tds_certificate_ref text,
  gross_amount   numeric(14,2) NOT NULL,           -- amount_received + tds_amount
  currency       text NOT NULL DEFAULT 'INR',
  received_on    date NOT NULL,
  payment_method text,
  bank_reference text,
  amount_allocated numeric(14,2) NOT NULL DEFAULT 0,
  amount_unallocated numeric(14,2) NOT NULL,
  status         payment_status_enum NOT NULL,     -- 'unallocated'|'part_allocated'|'allocated'
  notes          text,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);
CREATE INDEX idx_payment__unallocated ON bill.payment (client_id, received_on DESC)
  WHERE status <> 'allocated';

CREATE TABLE bill.payment_allocation (
  id             uuid PRIMARY KEY,
  payment_id     uuid NOT NULL REFERENCES bill.payment(id),
  invoice_id     uuid NOT NULL,
  amount         numeric(14,2) NOT NULL CHECK (amount > 0),
  tds_amount     numeric(14,2) NOT NULL DEFAULT 0,
  allocated_at   timestamptz NOT NULL DEFAULT now(),
  allocated_by   uuid NOT NULL
);
REVOKE UPDATE, DELETE ON bill.payment_allocation FROM apollo_app;
```

**Many-to-many by design:** *"a payment can be matched across several invoices, and an invoice can
take several payments"* (`M15-I3`).

**Append-only allocations.** Matching *"changes what appears as outstanding"* and is audited;
a correction is a reversing allocation, not an edit.

       {afterDaysOverdue: 14, action:'reminder',       template:'invoice_reminder_2'},
       {afterDaysOverdue: 30, action:'escalate_owner', template:'invoice_escalation'},

`dunning_action` is what makes *"chase history shows what has already been sent so a client is not

## 6. State machines

**Timesheet (extended from `03-12`):**

```
BEFORE:  building → built → sent_for_approval → approved | deemed_approved → invoiced
AFTER:   building → built → internally_approved → sent_for_approval → approved | deemed → invoiced
                       │
                       └→ returned(reason) → built
```

**A state added in front, not a restructure.** *"Internal routing sits before the client link, not
instead of it"* (`M15-I6`), and *"the client-side waiting period only starts once the client link is
actually sent"* (`M15-I2`) — which the extra state makes correct automatically.

**Invoice (extended from `03-13`):** `raised → part_paid → paid` \| `credited`
**Payment:** `received → part_allocated → allocated`, with any remainder **left unmatched**
**CreditNote:** `draft → pending_approval → issued` \| `cancelled`
**LeaveRecord:** `requested → approved | rejected | cancelled`

### 7.2 Full timesheet build (`M15-I6`)

*"Applies leave and overtime rules **on top of** the shift attendance. Produces **one timesheet used
by both invoicing and payroll**."*

```
1. Start from 03-12's attendance-derived lines — DO NOT REPLACE THEM
2. Apply leave records over the period → populate leave_type_code
3. Apply the overtime rule in force AS AT the shift date → overtime_minutes, overtime_amount
4. Recalculate totals
5. Route for internal approval
```

Three stated constraints:

| | |
|---|---|
| Leave and overtime are applied **on top of** M8 attendance **without replacing it** | `M15-I6` |
| A recalculation after a correction produces a **consistent** result | `M15-I6` |
| **The same timesheet feeds both the client invoice and the payroll input, with no second calculation** | `M15-I6` |

That third one is the important one. Two calculations — one for billing, one for pay — is how a
staffing business ends up billing a client for hours it did not pay its worker.

## 9. Frontend

### 9.1 Leave and overtime rules (`M15-I1`)

*"The categories and rules the thin-slice timesheet in M8 deliberately leaves out."*
Leave types with pay treatment. Overtime rules **by client and by state**, with effective dates.
The screen states that a rule change does not alter timesheets already approved.

### 9.2 Internal timesheet approval (`M15-I2`)

*"Lists timesheets waiting for Apollo approval before they go to the client. Approves one, or returns
it with a reason."*

Uses `02-11`'s engine. **Returning stops it reaching the client until corrected.** The screen notes
that the client-side waiting period only starts once the link is actually sent.

### 9.3 Payments received (`M15-I3`)

Record a payment, then allocate it. The allocation interface handles the real cases: one payment
across several invoices, several payments against one invoice, **TDS recorded separately so gross and
net are both visible**, and a remainder that stays unallocated.

*"An unmatched payment sits in a queue rather than being forced onto the nearest invoice"* — a
prominent unallocated queue, not a hidden state.

### 9.4 Overdue invoices (`M15-I4`)

*"What is overdue, by how long, and what is being done about it."*

Ageing buckets computed **from the contract's payment terms, not a flat rule**. Chase history per
invoice so a client is not chased twice. Escalation routes to the named client owner from `03-01`.

The screen makes the M9 → M15 relationship explicit: *"M9 shows ageing but does nothing with it; this
is where it becomes actionable."*

### 9.5 Credit and debit notes (`M15-I5`)

Raise a note against an invoice with a reason. **Issuing requires approval, because it changes
revenue.** A credit note reduces the receivable and is linked to the invoice it corrects. Notes export
to the finance system alongside invoices.

**`replacement_within_guarantee` is a named reason code**, present from the outset because of
`OI-A-13`.

## 12. Notes for the implementer

**One timesheet, one calculation.** `M15-I6` states it and it is the constraint that matters most in
this module. The billing path and the payroll path read the same timesheet lines. Two calculations
diverge, and the divergence shows up as billing a client for hours the nurse was not paid for — which
is discovered by the nurse, not by finance.

**Internal approval goes in front, not instead.** The client still approves through the `02-10` link.
Adding the internal step must not change `03-12`'s client-approval mechanism or its deemed window;
it only delays when the link is sent — and the deemed clock correctly starts from that later moment.

**Allocation is where the arithmetic gets fiddly.** Part-payment across three invoices with TDS on
each, a credit note against one of them, and a remainder left unallocated is a normal Tuesday. Model
allocations as append-only rows and derive the invoice's paid amount, rather than maintaining a
running total that can drift.

**Ageing from contract terms.** A flat "30 days" rule is the obvious implementation and it is wrong
for a business where payment terms are negotiated per client and stored per contract version. Read
them (`03-02 §7.1`).
