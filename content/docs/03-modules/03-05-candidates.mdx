## 1. Purpose

The candidate as one record spanning two supply bases against a shared credential object, covering
three categories, with a per-category attribute set that is configuration rather than columns.

Two design decisions carry most of the weight here:

1. **A2 — two supply bases, one record.** Base A (permanent) and Base B (the shift pool) are
   *separate supply bases against a shared credential record, not a status flag.* One person, one
   credential set, one or more base assignments.
2. **A9 — per-category attributes as configuration.** Specialty and acuity for nurses; specialty,
   case-mix and grade for doctors; discipline, equipment and technique for allied health. These are
   exactly what `03-09` ranks on, and they are served from **one place** so that the app, Ops, the
   requisition form and the ranking engine cannot drift apart.

**In** — candidate record and lifecycle · base assignment (A2) · category attribute definitions and
values (A9) · candidate list and record screens · duplicate detection and merge · CV reading ·

**Out** — credentials and verification → `03-06` · the mobile app UI and its endpoints → `03-07` ·

**Explicitly not built** (stated in the plan): bulk candidate loads from campuses or partners,
walk-in registration, referral tagging (Apollo handles these by hand) · face recognition, biometrics,
cheating detection · producing the clinical and communication rating (**the field exists and nothing
fills it in** — `OI-A-07`)

## 5. Data model

### 5.1 Candidate

```sql
CREATE TABLE supply.candidate (
  id               uuid PRIMARY KEY,
  reference        text NOT NULL UNIQUE,             -- 'CAN-2026-018342'
  full_name        text NOT NULL,                    -- C2
  phone_e164       text NOT NULL,                    -- C2 — the identifier
  email            citext,                           -- C2
  date_of_birth    date,                             -- C3
  gender           text,
  category         candidate_category_enum NOT NULL, -- 'nurse'|'doctor'|'allied'
  status           candidate_status_enum NOT NULL,
  -- location and preferences
  current_city     text,
  current_state    text,
  preferred_cities text[],
  willing_to_relocate boolean,
  total_experience_months integer,
  -- availability (written by 03-08, read by 03-09)
  availability_confidence numeric(4,3),
  availability_confirmed_at timestamptz,
  last_contacted_at timestamptz,
  -- descoped D17 field: present, unpopulated (OI-A-07)
  clinical_rating   numeric(3,1),
  communication_rating numeric(3,1),
  -- provenance
  source            candidate_source_enum NOT NULL,  -- 'app'|'migration'|'ops'|'referral'
  migrated_from_id  text,                            -- CPAL id
  merged_into_id    uuid REFERENCES supply.candidate(id),
  is_active         boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL,
  version integer NOT NULL DEFAULT 1
);
CREATE UNIQUE INDEX uq_candidate__phone ON supply.candidate (phone_e164)
  WHERE is_active AND merged_into_id IS NULL;
CREATE INDEX idx_candidate__cadence ON supply.candidate
  (category, availability_confidence ASC, last_contacted_at ASC) WHERE is_active;
CREATE INDEX idx_candidate__search ON supply.candidate
  USING gin (to_tsvector('simple', full_name || ' ' || coalesce(current_city,'')));
```

**`merged_into_id` rather than deletion.** A merged record survives and points at the survivor, so
every historical reference still resolves (`M4-I20`: *"neither record is deleted"*).

### 5.2 Base assignment (A2)

```sql
CREATE TABLE supply.candidate_base (
  id            uuid PRIMARY KEY,
  candidate_id  uuid NOT NULL REFERENCES supply.candidate(id),
  base          supply_base_enum NOT NULL,       -- 'base_a' (permanent) | 'base_b' (shift pool)
  status        base_status_enum NOT NULL,       -- 'active'|'paused'|'exited'
  joined_at     timestamptz NOT NULL DEFAULT now(),
  exited_at     timestamptz,
  exit_reason   text,
  -- availability semantics differ per base
  availability_confidence numeric(4,3),
  confirmed_at  timestamptz,
  UNIQUE (candidate_id, base)
);
```

**A separate table, not a column on the candidate.** The plan is explicit: *"Base A and Base B as
separate supply bases against a shared credential record, **not a status flag**."*

This also makes `OI-HS-09` answerable either way. *"A nurse in both needs one credential record and
two availability states, or an explicit rule that this is not permitted."* The table supports two
rows; a check constraint can forbid it if Apollo says so. A column could not.

Note that `availability_confidence` exists **both** on the candidate (the effective value, for
convenience and indexing) and per base (the authoritative value). `03-08` writes both.

### 5.3 Category attributes (A9)

```sql
CREATE TABLE supply.category_attribute_definition (
  id            uuid PRIMARY KEY,
  category      candidate_category_enum NOT NULL,
  key           text NOT NULL,                   -- 'specialty'|'acuity'|'case_mix'|'grade'|
                                                 -- 'discipline'|'equipment'|'technique'
  label         text NOT NULL,
  value_type    attr_value_type_enum NOT NULL,   -- 'single_select'|'multi_select'|'text'|'number'|'boolean'
  option_list_key text,                          -- platform.list_definition key
  applies_to    text[] NOT NULL,                 -- ['candidate','requisition'] — A9 spans BOTH
  is_required_for_candidate boolean NOT NULL DEFAULT false,
  is_rankable   boolean NOT NULL DEFAULT true,   -- 03-09 reads this
  sort_order    integer NOT NULL DEFAULT 0,
  is_active     boolean NOT NULL DEFAULT true,
  UNIQUE (category, key)
);

CREATE TABLE supply.candidate_attribute (
  candidate_id  uuid NOT NULL REFERENCES supply.candidate(id),
  values        jsonb NOT NULL DEFAULT '{}',     -- { specialty:['icu','ccu'], acuity:'high' }
  updated_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (candidate_id)
);
CREATE INDEX idx_candidate_attribute__values ON supply.candidate_attribute USING gin (values);
```

**Definitions are tables; values are jsonb** (`01-05 §8`). The definitions are queried by four
consumers and must be joinable; the values differ per category and are read as a unit.

`applies_to` is the mechanism that resolves `OI-M3-01` — the same definition serves both the
candidate record and the requisition form, so they cannot diverge.

### 5.4 Duplicates

```sql
CREATE TABLE supply.duplicate_candidate (
  id             uuid PRIMARY KEY,
  candidate_a_id uuid NOT NULL,
  candidate_b_id uuid NOT NULL,
  match_score    numeric(4,3) NOT NULL,
  match_reasons  jsonb NOT NULL,               -- which keys matched, with weights
  status         dup_status_enum NOT NULL,     -- 'open'|'merged'|'not_duplicate'
  detected_by    text NOT NULL,                -- 'signup'|'migration'|'manual'|'scan'
  resolved_by    uuid, resolved_at timestamptz, resolution_note text,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK (candidate_a_id < candidate_b_id)      -- one row per pair, not two
);

CREATE TABLE supply.candidate_merge (
  id            uuid PRIMARY KEY,
  survivor_id   uuid NOT NULL,
  merged_id     uuid NOT NULL,
  field_choices jsonb NOT NULL,                -- which record won each field
  merged_at     timestamptz NOT NULL DEFAULT now(),
  merged_by     uuid NOT NULL
);
REVOKE UPDATE, DELETE ON supply.candidate_merge FROM apollo_app;
```

## 6. State machines

**Candidate:** `registered → profile_complete → verification_pending → verified | partly_verified | failed`

Plus `→ merged` (terminal, `merged_into_id` set) and `→ inactive` (dormant or erased).

**CandidateBase:** `active → paused → exited`. Pausing stops cadence contact without removing history.

**Application:** `applied → shortlisted → interviewing → offered → joined` \| `rejected` \| `withdrawn`

**ShiftAcceptance:** `accepted → completed` \| `cancelled` \| `no_show`

## 9. Frontend — `/candidates`

### 9.1 Candidate list (`M4-I15`)

`<DataTable/>`: name, reference, category, base(s), city, experience, verification status,
**availability confidence**, last contacted. Filter by category, base, city, state, verification
status, confidence band, credential expiry, category attributes.

### 9.2 Candidate record (`M4-I16`)

*"Everything about one candidate on one page."*

Header: name, reference, category, base badges, verification status, confidence.
Tabs: Profile · **Category details** (A9) · Credentials (`03-06`) · Documents (`03-06`) ·
Applications & shifts · Contact history (`03-08`) · Activity (`02-02`).

The clinical and communication rating fields appear **with an explicit note that nothing produces
them** (`OI-A-07`) — better than a silently empty field that looks like missing data.

### 9.3 Pool assignment (`M4-I17`)

Which base(s) a candidate belongs to, with the consequence stated: *"This drives how often M5
contacts them and how M6 ranks them."* Assign, pause, exit with a reason.

If `OI-HS-09` resolves to "one base only", the second assignment is blocked with an explanation
rather than the screen being rebuilt.

### 9.4 Category fields (`M4-I18`) — `/settings/category-attributes`

Per category: the attribute set, value type, option list, whether it applies to candidate and/or
requisition, whether it is required, whether it is rankable.

The screen states its reach: **M3 and M6 both read this.** Changing a definition affects the
requisition form and the ranking inputs, and the UI says so before saving.

### 9.5 Duplicates (`M4-I20`)

Side-by-side comparison with matched keys highlighted and a field-by-field chooser for the merge.
Preview of what the merged record will look like. Explicit statement that **neither record is
deleted** and that the merged record's history remains reachable.

## 10. Acceptance criteria

| # | Criterion | Source |
|---|---|---|
| 1 | Base A and Base B are separate supply bases against a shared credential record, **not a status flag** | A2 |
| 2 | One candidate has one credential set regardless of base | A2, `03-06` |
| 3 | Category attributes are configuration, defined once and served to app, Ops, M3 and M6 | `M4-I18`, `M4-I25` |
| 4 | A definition marked `applies_to: requisition` appears on the requisition form without M3 redefining it | `OI-M3-01` |
| 5 | CV parsing returns per-field confidence and never writes silently — the candidate confirms | `M4-I19` |
| 6 | Duplicate detection surfaces pairs; merging **deletes neither record** | `M4-I20` |
| 7 | After a merge, every historical reference to the merged id still resolves | §5.1 |
| 8 | A merge is append-only recorded with which record won each field | §5.4 |
| 9 | Availability confidence is stored per base and on the record, written by M5, read by M6 | A3, §5.2 |
| 10 | The clinical/communication rating fields exist and are visibly unpopulated | `OI-A-07` |
| 11 | Phone number is unique across active, unmerged candidates | §5.1 |
| 12 | Category attribute values are searchable and filterable on the candidate list | §9.1 |

## 11. Open questions

| ID | Question | Impact | Working assumption |
|---|---|---|---|
| **`OI-HS-09`** | **Can one candidate serve both supply bases, and if so how is that modelled without duplicating the record?** | A2 defines two bases with different availability semantics and cadences. A nurse in both needs one credential record and two availability states, or an explicit rule forbidding it. | **`AS-25`** — the `candidate_base` table permits both, with **per-base availability confidence**. If Apollo forbids it, add a check constraint; nothing else changes. **This is why it is a table and not a column.** |
| **`OI-M3-01`** | Does M3 or M4 define the requisition-side attribute set? | Blocks the requisition schema | **`AS-23`** — **this module owns the definitions**, with `applies_to` marking which surface each appears on. M3 renders and stores values. Resolves the ownership question in the direction that prevents drift. |
| `OI-A-07` | Clinical and communication rating — D17 is descoped but the attribute remains, with no producing system | Whether D18 ranking weights it is unstated | Fields exist, unpopulated, **excluded from ranking** (`is_rankable = false`) until a producing system is specified. Visible on screen with a note. |
| `OI-A-03` | Is the migrated CPAL base deduped through this mechanism or a one-time migration process? | Two different builds. The migration-side option is cheaper but leaves no ongoing dedupe for the legacy base. | **`AS-26`** — **use this mechanism**, run as a bulk scan during migration (`03-15`). Reuses one implementation and leaves ongoing dedupe in place. Slightly more expensive up front. |
| `OI-HS-13` | Does a candidate see which hospital a role is with? | Awkward to retrofit once listings are live | Flag on the client record (`03-01 §11`); read by `03-07`. Built now. |
| `OI-HS-02` | DPDP erasure vs the indefinite Retained Pool | | **`AS-08`** — erasure anonymises in place (`01-10 §6`) |

## 12. Notes for the implementer

**Attribute definitions before anything else in this module.** Four consumers depend on them —
`03-04`'s requisition form, `03-07`'s app profile, `03-09`'s ranking inputs, and this module's own
record screen. Getting them served from one place is what `M4-I25` is for, and retrofitting that
after four consumers have each made assumptions is expensive.

**Merge is harder than it looks.** Applications, shift acceptances, credentials, documents, messages,
audit entries and events all reference a candidate id. `CandidateService.get` following
`merged_into_id` transparently is what keeps every one of those working without a data migration per
merge. Write that test first.

**Do not let base become a boolean.** It will be tempting, because in the first weeks most candidates
will be in exactly one base. The plan explicitly forbids it, and `OI-HS-09` is the reason.
