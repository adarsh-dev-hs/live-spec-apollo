**Package** `@apollo/portal` · **Schema** `clients`, `identity` · **Plan** D12 · **Effort** ~26.0pd · **Risk** Low `XMOD` · **Build in** Phase 6

## 1. Purpose

A logged-in website for clients. Until Phase 6 clients have only had one-off links with no password;
this gives them accounts so they can raise vacancies themselves, see how their vacancies are
progressing, review shortlists, approve timesheets and download invoices. Once it exists, the portal
also becomes the **sixth intake channel**, which `03-02` already enumerates and leaves switched off.

Everything the portal shows already exists. This module adds screens and a tenancy boundary, not new
business logic.

## 2. Scope

### In scope

- Raise a requisition, producing **the same record as one arriving by email**, marked source `portal`
- My requisitions: status and fill, client-appropriate
- Shortlists: the logged-in version of the shortlist link, same decisions and same taxonomy
- Timesheets: the logged-in version of the approval link, same state and same window rule
- Invoices: download their own, view rate card and contract read-only
- Enabling the portal channel in `03-02` as configuration

### Explicitly out of scope

- Client identity, portal users and **portal data scoping** — `02-01` (`M10-I1`, `M10-I2`, `M10-I8`).
  The tenancy boundary is a security concern and lives with the rest of authorisation.
- The tokenised links — `02-14`. Both routes stay open; a client who never signs in still uses links.
- Every underlying record — owned by `03-01`, `03-03`, `03-07`, `03-10`, `03-11`.

### Explicitly not built

- Clients editing their own rate card or contract terms. Those stay with Apollo.
- Clients seeing candidate personal data beyond what the shortlist already shows.
- Client-facing analytics or dashboards.
- Client-side interview feedback (`OI-HS-11`).

## 5. Data model

No tables of its own. `ClientUser`, `ClientUserRole` and `PortalSession` are `02-01`. Two additions
elsewhere:

```sql
-- 03-02: the portal channel flips available, which is configuration not a schema change (AS-05)
UPDATE demand.channel SET is_available = true WHERE code = 'portal';

-- 03-03: source_channel already accepts 'portal'; no migration needed
```

That the portal requires **no schema change** anywhere is the test of whether `03-02` and `03-03` were
built correctly in Phase 3.

## 6. State machines

**N/A** — the portal drives existing state machines. A requisition raised here enters
`demand.requisition` at `incomplete`/`complete` exactly as an emailed one does; a shortlist response
sets `matching.shortlist_entry.client_response`; a timesheet approval sets
`timesheets.timesheet.approved`.

`ClientUser` (`invited → registered → active → suspended`) is specified in `02-01`.

## 7. API surface

Every endpoint runs in the `client_user` realm and is scoped to `clientId` **and** `siteIds` by
`02-01`. Scope is not a parameter.

| Method | Path | Permission | Purpose |
|---|---|---|---|
| `POST` | `/v1/portal/requisitions` | `portal:requisition:create` | Same fields as the internal form, sites limited to the client's own |
| `GET` | `/v1/portal/requisitions?state=` | `portal:requisition:read` | Status and positions filled |
| `GET` | `/v1/portal/requisitions/:id` | `portal:requisition:read` | Client-appropriate detail, **no internal notes** |
| `GET` | `/v1/portal/shortlists` | `portal:shortlist:read` | Candidates put forward per requisition |
| `POST` | `/v1/portal/shortlists/:id/respond` | `portal:shortlist:respond` | Accept, reject with a reason, or request interview |
| `GET` | `/v1/portal/timesheets?state=awaiting` | `portal:timesheet:read` | Awaiting approval |
| `POST` | `/v1/portal/timesheets/:id/approve` · `/query` | `portal:timesheet:approve` | Same state as the link version |
| `GET` | `/v1/portal/invoices` | `portal:invoice:read` | Their own only |
| `GET` | `/v1/portal/invoices/:id/download` | `portal:invoice:read` | **Downloads are logged for audit** |
| `GET` | `/v1/portal/contract` | `portal:contract:read` | Rate card and contract **visible, not editable** |

Response payloads omit internal reason codes, ranking scores, recruiter notes and margin.

## 8. Events and jobs

**Events emitted:** `portal.requisition.raised` (source channel `portal`, feeding `03-12` channel
performance) · `portal.invoice.downloaded` (audited) · `portal.shortlist.responded` ·
`portal.timesheet.approved`.

**Events subscribed:** none. The portal reads current state.

**Jobs:** none of its own.

## 9. Frontend

`apps/portal`, a separate Vite build on its own subdomain with its own cookie namespace.

| Screen | Route | Item |
|---|---|---|
| Raise a requisition — same fields as internal; sites and departments limited to the client; **completeness checked at submit so the chase loop is rarely needed** | `/requisitions/new` | `M10-I3` |
| My requisitions — status and fill; **age matches the internal aging rule, excluding held days** | `/requisitions` | `M10-I4` |
| Shortlists — candidates per requisition; accept, reject with a reason, request interview | `/shortlists` | `M10-I5` |
| Timesheets — awaiting approval; approve, or query a line with a reason | `/timesheets` | `M10-I6` |
| Invoices — list and download; rate card and contract read-only | `/invoices` | `M10-I7` |
| Portal users | `/settings/users` | `M10-I2` (`02-01`) |

Built from `02-05`, so the portal looks like the rest of the platform without a second design pass.
