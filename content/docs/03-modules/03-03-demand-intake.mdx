## 1. Purpose

Five live channels plus verbal capture, all normalising to one requisition schema, with the source
retained, completeness scored against required fields, and follow-up routed back through the
originating channel.

Clients do not log in to raise vacancies — there is no client login until M10. Requirements arrive
however the client already works: an email, a spreadsheet in their own format, a WhatsApp message, a
voice note, or a push from their HR system. **All of it becomes one requisition object.**

This module sits on top of the shared pipeline (`02-08`) and owns the channel-specific half:
adapters, parsers, completeness scoring, and the recovery queues where humans fix what automation
could not.

## 2. Scope

**In** — channel adapters (email, WhatsApp text, WhatsApp voice, spreadsheet, HRMS) · channel
configuration · **per-client spreadsheet mapping** · parser dispatch and field extraction ·
completeness scoring against a per-category required-field set · **follow-up chase on the originating
channel** with escalation · manual entry queue · suspected duplicates queue · verbal capture entry

**Out** — the pipeline itself (receiver, sender matching, type detection, registration) → `02-08` ·
the requisition object and lifecycle → `03-04` · candidate response handling → `03-08` (the *other*
consumer of the same pipeline) · the client portal channel → `03-16` (enumerated here, switched on
there)

## 5. Data model

### 5.1 Channel configuration (`M3-I5`)

```sql
CREATE TABLE demand.channel_config (
  id             uuid PRIMARY KEY,
  channel        inbound_channel_enum NOT NULL UNIQUE,
  is_enabled     boolean NOT NULL DEFAULT false,
  is_available   boolean NOT NULL DEFAULT true,   -- FALSE for 'portal' in R1: enumerated, not built
  settings       jsonb NOT NULL DEFAULT '{}',
  adapter_key    text,
  updated_at     timestamptz NOT NULL DEFAULT now(),
  updated_by     uuid NOT NULL
);
```

`is_available = false` is how the portal channel is *"specified but not built"* (`OI-A-06`) rather
than dropped from A1. It appears in the list, disabled, with an explanatory note.

### 5.2 Spreadsheet mapping (`M3-I6`)

```sql
CREATE TABLE demand.spreadsheet_mapping (
  id             uuid PRIMARY KEY,
  client_id      uuid NOT NULL,
  name           text NOT NULL,
  header_row     integer NOT NULL DEFAULT 1,
  sheet_name     text,
  multi_row_mode text NOT NULL DEFAULT 'one_per_row',  -- several vacancies per file
  column_map     jsonb NOT NULL,     -- { "Ward": "departmentName", "Nos": "positions", ... }
  value_map      jsonb,              -- { "category": { "S/N": "nurse", "Staff Nurse": "nurse" } }
  sample_file_id uuid,               -- the file this mapping was built and tested against
  is_active      boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);
```

**One mapping per client format.** The mapping screen is built once; each client's format then needs
its own mapping and its own sample file to test against. **The number of formats is unknown
(`OI-M3-04`)** — this is an estimate blocker, and the data model makes the per-format work visible
and countable rather than hidden.

### 5.3 Required fields (`M3-I7`)

Stored in P03 as `supply.required_fields.<category>`:

```json
{
  "nurse":  { "required": ["clientId","locationId","roleCode","positions","specialty","acuity","startDate"],
              "weight": { "specialty": 2, "acuity": 2 } },
  "doctor": { "required": [] },
  "allied": { "required": ["clientId","locationId","roleCode","positions","discipline"] }
}
```

**`doctor` is deliberately empty.** `OI-M3-07` records that nurses and allied health sit with a named
owner and **no doctors owner is named**. Completeness scoring for doctors cannot be configured until
one is nominated, and an empty set scoring everything as complete is the honest behaviour — with a
visible warning on the settings screen.

### 5.4 Follow-up settings (`M3-I8`)

```sql
CREATE TABLE demand.follow_up_config (
  id                uuid PRIMARY KEY,
  client_id         uuid,                      -- NULL = platform default
  first_chase_hours integer NOT NULL DEFAULT 4,
  repeat_hours      integer NOT NULL DEFAULT 24,
  max_chases        integer NOT NULL DEFAULT 3,
  escalate_after_hours integer NOT NULL,       -- → clients.client_window_config.requisition_follow_up
  escalate_to       text NOT NULL DEFAULT 'owner',
  template_key      text NOT NULL
);
```

### 5.5 Duplicate candidates for requisitions (`M3-I4`)

```sql
CREATE TABLE demand.suspected_duplicate (
  id                uuid PRIMARY KEY,
  requisition_id    uuid NOT NULL,
  candidate_requisition_id uuid,               -- the possible duplicate, if already created
  inbound_id        uuid,                      -- or the inbound not yet converted
  match_score       numeric(4,3) NOT NULL,
  match_reasons     jsonb NOT NULL,            -- which keys matched
  status            text NOT NULL,             -- 'open'|'merged'|'not_duplicate'
  resolved_by       uuid,
  resolved_at       timestamptz,
  resolution_note   text
);
```

## 6. State machines

Intake does not own a lifecycle of its own — it advances `InboundRecord` (`02-08 §6`) and creates
`Requisition` (`03-04 §6`).

The one state it does own: **chase**.

| From | To | Trigger |
|---|---|---|
| — | `chase_pending` | Requisition scored incomplete |
| `chase_pending` | `chased` | First chase sent on the originating channel |
| `chased` | `chased` | Repeat, up to `max_chases` |
| `chased` | `escalated` | `escalate_after_hours` passed with no response |
| any | `resolved` | Missing fields supplied, by any route |
| any | `abandoned` | Requisition closed or withdrawn |

## 7. API surface

### 7.1 Parsers (`M3-I20`)

```ts
interface RequisitionParser {
  channel: InboundChannel
  canHandle(record: InboundRecord): boolean
  parse(record: InboundRecord): Promise<ParseResult>
}

type ParseResult =
  | { kind: 'parsed'; fields: Partial<RequisitionDraft>; confidence: Record<string, number> }
  | { kind: 'multiple'; drafts: Partial<RequisitionDraft>[] }     // one spreadsheet, several vacancies
  | { kind: 'unparseable'; reason: string }
```

Dispatch is by channel and content type. Parsers registered:

| Parser | Handles |
|---|---|
| `EmailParser` | Free text + attachments. LLM extraction against the requisition schema. |
| `SpreadsheetParser` | Applies the client's `spreadsheet_mapping`. Deterministic — no model. |
| `WhatsAppTextParser` | Short free text. LLM extraction. |
| `VoiceNoteParser` | Transcript from `04-03`, then the text parser |
| `HrmsParser` | Structured payload → schema mapping. **Bypasses parsing entirely.** |
| `ManualParser` | Verbal capture — a person typed it in. Confidence 1.0. |

**Per-field confidence is returned and stored**, so the requisition record can show which fields were
read by a machine and which by a person (`03-04 §9`).

### 7.2 Completeness scoring and chase (`M3-I22`)

```ts
export const IntakeService = {
  scoreCompleteness(draft, category): Promise<{
    score: number
    missing: string[]
    isComplete: boolean
  }>
  startChase(requisitionId): Promise<void>       // on the ORIGINATING channel
  resolveChase(requisitionId, actor): Promise<void>
}
```

*"Scores the parsed object against the required-field set for its category and chases what is missing
**on the originating channel**"* (`M3-I22`). A vacancy that arrived by WhatsApp is chased on
WhatsApp, not by email — that is the whole point of retaining the channel.

## 8. Events and jobs

**Emits:** `demand.intake.parsed` · `demand.intake.unparseable` · `demand.intake.chase_sent` ·
`demand.intake.chase_escalated` · `demand.intake.duplicate_suspected`

**Subscribes:** `demand.inbound.classified` (type `demand`) → parse ·
`platform.document.available` → parse spreadsheet or transcribe voice note ·
`demand.requisition.updated` → re-score completeness, resolve chase if now complete

**Jobs**

| Job | Cadence | Notes |
|---|---|---|
| `intake.parse` | On event | 10 concurrency, 3 attempts → then `unparseable`, never lost |
| `intake.transcribe` | On event | **Per-minute billed — do not retry blindly** |
| `intake.spreadsheet` | On upload | One job per file, one draft per row |
| `intake.follow-up-chase` | Hourly | First chase, repeats, respecting `max_chases` |
| `intake.follow-up-escalate` | Hourly | To the requisition owner after the window |
| `intake.duplicate-scan` | On requisition create | Match keys per `AS-04` |

## 9. Frontend — `/intake`

### 9.1 Channel settings (`M3-I5`)

Each channel: enabled, adapter, configuration, health, volume this month. **The portal channel is
listed and permanently disabled in R1**, with a note that it arrives with M10 (`OI-A-06`).

### 9.2 Spreadsheet mapping (`M3-I6`)

Per client: upload a sample file, see detected columns, map each to a requisition field, define value
translations ("S/N" → nurse), set header row and multi-row mode. **Test against the sample and show
the parsed result before saving.**

*"Maps each client's own spreadsheet layout onto the requisition schema without a code change"* —
the test-before-save step is what makes that true in practice rather than in principle.

### 9.3 Required fields (`M3-I7`)

Per category: which fields make a requisition complete, and their weight. **A visible warning where
no set is configured** — currently doctors (`OI-M3-07`).

### 9.4 Follow-up settings (`M3-I8`)

What the chase message says, how long the client has, how many times, and who it escalates to.
Platform default plus per-client overrides.

### 9.5 Manual entry queue (`M3-I3`)

Payloads the parser could not read. Each row shows the raw content — **including an audio player for
voice notes** — alongside a requisition form. A person reads and types.

*"Recovery path for payloads the parser could not read, so that a parse failure never loses a
requirement"* (`M3-I3`). Queue depth is the operational cost of parser accuracy, and it is reported
weekly (`OI-M3-06`).

### 9.6 Suspected duplicates (`M3-I4`)

The same requirement arriving on two channels, side by side, with the matched keys highlighted.
Actions: merge (keeping both inbound records linked to one requisition), or mark not-duplicate.

**No automatic merge.** The dedupe rule is unset (`OI-M3-02`), and a wrongly merged vacancy is worse
than a queue entry.

### 9.7 Verbal capture

Not a separate screen — the requisition form in `03-04` with source `manual`. **15 of 22 recruiters
are site-resident, so this is a primary path, not an edge case** (`M3-I9`), and it is documented for
them in the user guides (`M1-I7`).

## 12. Notes for the implementer

**This is the largest single module in the plan (84pd) and the one with the most open items.** Build
it in the order: pipeline consumption → requisition creation from a clean structured payload → HRMS →
email → WhatsApp text → spreadsheet → voice notes. Each channel added is independently valuable, and
the hardest two (spreadsheet formats, voice) are also the two blocked on unanswered counts.

**Parsing is a job, never a request.** A model call taking eight seconds must not hold an HTTP
connection, and a provider outage must not lose a vacancy.

**The manual queue is a feature, not a failure.** Design it to be pleasant to work — raw content and
form side by side, keyboard-first — because at a 0.80 threshold a real fraction of inbound will land
there, and its depth is the number that tells Apollo whether the threshold is right.
