## 1. Purpose

The client entity with its locations and departments, the people at the client, and the list of
addresses each client sends demand from. Every requisition, offer, placement and invoice hangs off
this record.

Two things here are load-bearing for other modules and easy to under-build:

1. **Sender identities.** `03-03` checks every inbound message against this list to work out which
   client sent a vacancy. Without it, everything lands in the unmatched queue.
2. **Client contacts.** `02-10` sends the day-90 retention link to a person, and the invoice is
   defensible only because we know who answered.

---

## 2. Scope

**In** — client CRUD and lifecycle · locations and departments · client contacts · sender identities
(email, WhatsApp number, HRMS tenant) · client list and detail screens · client lookup service

**Out** — rate cards and contracts → `03-02` (same schema, different module) · client portal login →
`03-16` · credit limits and credit control (billing stops at invoice raised) · writing contracts from
a template — in Release 1 contracts are *recorded*, not drafted

## 5. Data model

```sql
CREATE TABLE clients.client (
  id              uuid PRIMARY KEY,
  reference       text NOT NULL UNIQUE,          -- 'CLI-00042'
  legal_name      text NOT NULL,
  display_name    text NOT NULL,
  client_group    text,                          -- 'Apollo Hospitals' — several clients may share one
  status          client_status_enum NOT NULL DEFAULT 'draft',
  gstin           text,
  pan             text,
  registered_address jsonb,
  billing_address jsonb,
  owner_user_id   uuid,                          -- Apollo account owner; M15 escalates to them
  onboarded_at    date,
  closed_at       date,
  close_reason    text,
  is_active       boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid NOT NULL,
  version    integer NOT NULL DEFAULT 1
);

CREATE TABLE clients.location (
  id            uuid PRIMARY KEY,
  client_id     uuid NOT NULL REFERENCES clients.client(id),
  reference     text NOT NULL UNIQUE,            -- 'LOC-00318'
  name          text NOT NULL,                   -- 'Apollo Hospital Greams Road'
  city          text NOT NULL,
  state         text NOT NULL,                   -- drives state-specific rate cards and offer templates
  address       jsonb,
  geo_lat       numeric(9,6),                    -- for M12 geo-fencing; recorded now, used later
  geo_lng       numeric(9,6),
  is_active     boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);
CREATE INDEX idx_location__client ON clients.location (client_id) WHERE is_active;

CREATE TABLE clients.department (
  id            uuid PRIMARY KEY,
  location_id   uuid NOT NULL REFERENCES clients.location(id),
  name          text NOT NULL,                   -- 'ICU', 'Emergency', 'Radiology'
  specialty_code text,                           -- maps to the A9 specialty list
  is_active     boolean NOT NULL DEFAULT true
);

CREATE TABLE clients.client_contact (
  id             uuid PRIMARY KEY,
  client_id      uuid NOT NULL REFERENCES clients.client(id),
  location_id    uuid REFERENCES clients.location(id),
  full_name      text NOT NULL,
  role_title     text,
  email          citext,
  phone_e164     text,
  is_primary     boolean NOT NULL DEFAULT false,
  purposes       text[] NOT NULL DEFAULT '{}',   -- 'shortlist'|'retention'|'timesheet'|'billing'|'general'
  is_active      boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);
CREATE INDEX idx_client_contact__client ON clients.client_contact (client_id) WHERE is_active;

CREATE TABLE clients.sender_identity (
  id            uuid PRIMARY KEY,
  client_id     uuid NOT NULL REFERENCES clients.client(id),
  location_id   uuid REFERENCES clients.location(id),
  department_id uuid REFERENCES clients.department(id),
  kind          sender_kind_enum NOT NULL,       -- 'email'|'whatsapp'|'hrms'
  address       text NOT NULL,                   -- NORMALISED: lowercased email / E.164 / tenant key
  label         text,
  is_active     boolean NOT NULL DEFAULT true,
  verified_at   timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid NOT NULL
);
CREATE UNIQUE INDEX uq_sender_identity__address
  ON clients.sender_identity (kind, address) WHERE is_active;
```

**`uq_sender_identity__address` is the important constraint.** One address maps to at most one active
client — which is what makes `03-03`'s resolution deterministic. An attempt to register the same
address against a second client fails loudly rather than producing an ambiguous match later.

`purposes` on the contact is what `02-10` reads to decide who receives which link type
(`AS-05`, `OI-A-12`).

## 6. State machines

**Client:** `draft → active → suspended → closed`

| Transition | Rules |
|---|---|
| `draft → active` | Requires at least one location and one contact. Sender identities become live. |
| `active → suspended` | New requisitions blocked; existing work continues; a reason is required |
| `suspended → active` | |
| `active` \| `suspended` `→ closed` | Reason required. Blocks new requisitions. **Does not affect existing invoices or placements.** |

**Location / Department / Contact / SenderIdentity:** `active → retired`. Never deleted — a closed
requisition must still show the site it was for.

## 7. API surface

### 7.1 Exported service

```ts
export const ClientService = {
  getById(id): Promise<Client | null>
  getMany(ids): Promise<Client[]>                       // batch, avoids N+1
  getLocation(id): Promise<Location | null>
  getDepartment(id): Promise<Department | null>

  /** Used by 03-03 on EVERY inbound message. Exact match on a normalised address. */
  resolveSender(kind, address): Promise<SenderMatch>    // { matches: SenderIdentity[] }

  listContacts(clientId, opts?: { purpose?, locationId? }): Promise<ClientContact[]>
  lookup(q, opts?): Promise<ClientSummary[]>            // capped, for pickers
  assertActive(clientId): Promise<Client>               // throws if suspended or closed
}
```

`resolveSender` returns **all** matches, not a best guess. Zero or many both mean "unmatched" to
`03-03`, and it is that module's job to queue it for a human (`02-08 §6`).

### 7.2 HTTP — `/api/v1/clients`

| Method | Path | Permission |
|---|---|---|
| GET | `/` | `clients.client.read` — list |
| POST | `/` · GET `/:id` · PATCH `/:id` | `clients.client.write` |
| POST | `/:id/activate` · `/suspend` · `/close` | `clients.client.write` |
| GET | `/lookup?q=` | any authenticated |
| GET/POST | `/:id/locations` · PATCH/POST `/locations/:id/retire` | `clients.location.write` |
| GET/POST | `/locations/:id/departments` | `clients.location.write` |
| GET/POST | `/:id/contacts` · PATCH · retire | `clients.contact.write` |
| GET/POST | `/:id/senders` · PATCH · retire | `clients.sender.write` |
| POST | `/:id/senders/verify` | Sends a test message to confirm an address reaches the client |

## 8. Events and jobs

**Emits**

| Event | Consumed by |
|---|---|
| `clients.client.created` / `.activated` / `.suspended` / `.closed` | `03-04` (block new requisitions), `03-03` |
| `clients.sender_identity.created` | `03-03` — **reprocess unmatched inbounds from this address** |
| `clients.contact.created` / `.retired` | `02-10` (link recipients) |
| `clients.location.created` | `03-04`, `03-18` (geo-fence setup) |

**Subscribes:** `platform.user.deactivated` → clears `owner_user_id` and flags the client for
reassignment.

**Jobs:** `clients.reprocess-unmatched` — when a sender identity is created, re-run every unmatched
inbound from that address (`02-08 §9.2`). A new client emailing for the first time typically produces
several before anyone notices.

## 9. Frontend — `/clients`

### 9.1 Client list (`M2-I1`)

`<DataTable/>`: name, group, status, locations, open requisitions, active contract, owner. Filter by
status, state, owner. Search by name or reference.

*"Showing enough that a user does not have to open each one"* — so open-requisition count and
contract status are columns, not detail-page facts.

### 9.2 Client detail (`M2-I2`)

Tabs: Overview · Locations & departments · Contacts · Senders · Rate cards (`03-02`) · Contracts
(`03-02`) · Requisitions (`03-04`) · Invoices (`03-13`) · Activity (`02-02`).

Overview holds legal and billing details, GSTIN/PAN, owner, and the lifecycle actions.

### 9.3 Sites and departments (`M2-I3`)

Locations with their departments nested. Add, edit, retire. Each location carries city, state and
address; state matters because rate cards and offer templates vary by it.

*"A requisition must attach to one of these"* — so retiring a location warns if open requisitions
reference it.

### 9.4 Client contacts (`M2-I4`)

Name, role, email, phone, purposes, primary flag, location. The **purposes** field is explained
inline: which of these people receives shortlist links, retention confirmations, timesheet approvals
and invoices.

### 9.5 Client senders (`M2-I6`)

The list of email addresses, WhatsApp numbers and HR system accounts belonging to each client.
`<DataTable/>`: kind, address, label, location/department, active, verified.

The screen states plainly why it matters: **M3 checks every inbound message against this**. Adding an
address offers to reprocess unmatched inbounds from it. Attempting to add an address already mapped
to another client shows which client holds it, rather than a constraint error.

## 12. Notes for the implementer

**Normalise sender addresses on write, not on read.** Lowercase emails, E.164 phone numbers, trimmed
tenant keys. `03-03` performs this lookup on every single inbound message; it must be an index hit on
an exact value, not a function call over the table.

**`client_group` is not a hierarchy.** Apollo has several legal entities under one brand. A group is
a label for reporting and search, not a parent record with inherited rate cards. Do not build a tree.

**Build `disclose_identity_to_candidates` now** (§11). It is one boolean column and one condition in
`03-07`, and the plan explicitly flags it as awkward to retrofit once job listings are live.
