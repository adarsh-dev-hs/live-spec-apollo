### Where the mapping deliberately differs from the plan

| Plan says | We do | Why |
|---|---|---|
| M3 owns messaging (F07) and events (F14) | P07 and P09 are platform components | Six modules send messages; every module writes events. Owning them inside M3 makes M3 a bottleneck for everything downstream. |
| M2 owns the shared list component (F08) | P06 is a platform component | ~20 list screens across nine modules |
| M7 owns the link mechanism (A13) | P10 is a platform component, link *pages* stay in B10/B11/B12 | Three modules instantiate link types. The plan itself says "price the mechanism once and each type as an instance" — this is that, structurally. |
| M12 owns the approval engine | P11 is a platform component | M15 reuses it; the plan says build it first of the two |
| M1 owns adapters (A12) | P12 is the framework; the India adapters stay in B06 | The framework is generic; the registries are credential-specific |

Nothing is added or removed — only relocated so that shared things are built once.

## 4. Frontend surface mapping

| Surface | Features (mirrors backend modules) |
|---|---|
| `apps/ops` | iam-admin, settings, clients, contracts, intake, requisitions, candidates, credentials, engagement, matching, selection, placements, attendance, billing, analytics, migration, workforce, onboarding, payroll, demand-ops, collections |
| `apps/links` | shortlist-response, trial-checkin, timesheet-approval |
| `apps/portal` | auth, requisitions, shortlists, timesheets, invoices, users |
| `apps/mobile` (RN) | signup, profile, jobs, shifts, applications, check-in, documents, availability, onboarding, payslips |

**Rule:** a frontend feature folder never talks to a backend module other than its own, except
through that module's API. If the requisitions screen needs client names, it calls
`GET /api/v1/requisitions/:id` and the *backend* composes them — the browser does not fan out
across modules.

## 5. What each component may assume already exists

When you implement any component spec, assume these are done and working. Do not rebuild them:

| Assume | Provided by |
|---|---|
| `req.user` with resolved permissions and site scope | P01 middleware |
| `requirePermission('module.resource.action')` | P01 |
| `audit.record({...})` | P02 |
| `config.get(key, { clientId })` with per-client override and platform default | P03 |
| `files.upload()`, `files.presignedUrl()`, `files.attach()` | P04 |
| Every UI primitive, empty/loading/error/no-permission state | P05 |
| `<DataTable/>` with filter, sort, page, column chooser, saved views, export | P06 |
| `messaging.send({ templateKey, channel, recipient, vars })` respecting opt-out | P07 |
| Inbound webhook receipt, sender matching, raw payload retention | P08 |
| `events.emit(name, payload)` writing to outbox in your transaction | P09 |
| `links.issue({ type, recipient, payload })` and answer routing | P10 |
| `approvals.request({ type, before, after })` with maker≠checker enforced | P11 |
| `adapters.call(port, method, args)` with logging, retry and manual fallback | P12 |
| `jobs.enqueue()`, `jobs.schedule()`, DLQ, idempotency | P13 |

If a spec asks you to build something in this list, that is a bug in the spec — flag it.
