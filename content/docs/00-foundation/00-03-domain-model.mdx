**Package** `@apollo/db` · **Schema** all · **Plan** all · **Effort** — · **Risk** — · **Build in** Phase 0

Every entity in the platform in one place: what owns it, what reads it, and where its lifecycle is
specified. Column-level detail lives in each component's **§5 Data model**; this page is the index and
the ownership contract.

**Ownership rule.** Exactly one component writes an entity. Everything else reads it through that
component's service or a view. Where the plan leaves ownership contested it is called out below with
its open item.

## 2. Core relationships

```
 Client 1──n Location 1──n Department
   │  1──n ClientContact ──n LinkRecipient ──n ClientLink ──1 LinkResponse
   │  1──n SenderIdentity  ◀── resolved by every InboundRecord
   │  1──n RateCard 1──n RateCardVersion 1──n RateCardLine
   │  1──n Contract 1──n ContractVersion ──▶ read at every billing trigger
   │  1──1 ClientWindowConfig  (retention · timesheet · follow-up windows, defaults in Setting)
   │
   └──n Requisition ──1 RequisitionVersion(current)
          │  n──1 category (nurse|doctor|allied)   n──1 care_setting (hospital|home)
          │  1──n ShiftDemandLine   (contractual only; carries visit_address for home care)
          │  1──n AllocationRecord  (append-only)   1──n StatusTransition (append-only)
          │  1──n RankedSet 1──n RankEntry ──1 Candidate
          │  1──n Shortlist 1──n ShortlistEntry ──▶ ClientLink(type=shortlist)
          │
          └──n Application ──1 Candidate
                 │ 1──n Interview 1──n InterviewFeedback
                 │ 1──1 SelectionDecision ──▶ OutcomeSignal ──▶ next RankedSet
                 │ 1──1 Offer 1──n OfferVersion ──1 OfferContractMapping ──1 ContractVersion
                 └──1 Placement
                        │ 1──n TrialEvent 1──1 TrialResponse
                        │ 1──1 RetentionRecord (immutable) ──▶ BillingTrigger ──▶ Invoice(permanent)
                        └──1 DropOut ──▶ position returns to Requisition

 Candidate 1──n Credential ──n VerificationCase ──n AdapterCall
   │ 1──n CandidateDocument ──1 Document
   │ 1──n SupplyBaseMembership (Base A and/or Base B — OI-HS-09)
   │ 1──1 AvailabilityConfidence (column on Candidate, written by 03-06)
   │ 1──n ShiftAcceptance ──1 ShiftDemandLine
   │ 1──n ShiftAttendance ──n TimesheetLine ──1 Timesheet ──▶ Invoice(shift)
   └──1 AssociateProfile 1──n StatutoryForm ──▶ PayrollInput ──1 PayrollCycle
```

## 3. Lifecycles that cross components

Full transition tables live in the owning spec's §6. These three cross enough boundaries to belong here.

### `Requisition` (owner 03-03, `M3-I27`)

```
                   ┌───────────── revise (new version, re-score) ──────────────┐
                   ▼                                                            │
 incomplete ──▶ awaiting_client ──▶ complete ──▶ open ──▶ in_fulfilment ──▶ partially_filled ──▶ filled
      │              │  (escalates to owner on window expiry, AS-01)   ▲   │
      │              └──────────────────────────────────────────┐      │   │
      └── complete ──────────────────────────────────────────┐  │      │   │
                                                              ▼  ▼      │   │
                                        (M14 only) awaiting_approval ───┘   │
                                                                            │
                    in_fulfilment ◀──── release (aging resumes from held) ──┤
                              │                                             │
                              └──▶ on_hold (aging clock stops)              │
                                                                            │
 any state ──▶ closed   (reason mandatory, from 02-03 list; OI-M3-11)  ◀────┘
```

Aging counts from **first reaching `complete`**, excluding held days (`M3` BR4, AC3). Auto-close on
`filled` is configurable and unresolved (`OI-M3-12`). The `awaiting_approval` state is added by 03-18
and does not exist in Phase 3.

### `ClientLink` (owner 02-14, `M7-I17`)

```
 issued ──▶ sent ──▶ opened ──▶ answered ──▶ routed (M7-I18)
    │                   │
    │                   └──▶ resubmitted → treated as the same answer, no second response
    └──▶ expired ──▶ deemed   ← ONLY for link_type ∈ {day_90_retention, timesheet_approval}
                              and only after the per-client window from ClientWindowConfig,
                              falling back to the platform default (OI-A-05)
```

`day_30_check_in` and `day_60_check_in` can never reach `deemed` and can never carry
`is_billing_trigger` — the flag is not editable on those types (`M7-I8`).

### `Timesheet` → `Invoice` (owners 03-10 → 03-11)

```
 ShiftAttendance(resolved) ──▶ Timesheet.building ──▶ built
        │                                              │
        │                        (03-19 adds: ──▶ internally_approved)
        │                                              ▼
        │                                      sent_for_approval ──▶ approved
        │                                              │                 │
        │                                              └──▶ deemed_approved
        │                                                                ▼
        └──────────────────────────────────────────────────────▶ invoiced (03-11)
```

A deemed approval is **as valid an invoice input as an explicit one** (`M8-I16`, `M9-I15`), and the two
are visibly distinguished on the record.

## 4. Contested and constrained ownership

| Entity | Contest | Position held | Open item |
|---|---|---|---|
| `CategoryAttributeSet` definition | M3 or M4 defines the requisition-side attribute set | **03-04 owns one definition; 03-02/03-03 consume it as configuration** so requisition and candidate sides cannot drift | `OI-M3-01` (`AS-04`) |
| `AvailabilityConfidence` | M4 owns the candidate record; M5 computes the value | Column lives on `candidates.candidate`, written **only** through 03-06's service, read by 03-07 | Part A coupling 3 |
| `LinkRecipient` | Held per client, per location, per requisition or per placement? | Modelled with **all four scope columns, exactly one non-null**, so a decision is a data change not a migration | `OI-A-12` |
| `RejectionReason` taxonomy | M6 feature schema and M7 taxonomy are one design | Single list in `02-03`, consumed by 03-07 and 03-08; schema agreed in a joint session before either builds | Part A coupling 1 |
| Duplicate resolution | Migrated base via 03-13 or via 03-04's mechanism | **03-04 owns the merge**; 03-13 calls it, so there is one merge implementation and lineage is uniform | `OI-A-03` |

## 5. Conventions every entity obeys

| Rule | Detail |
|---|---|
| Identifier | `uuid` v7 primary key named `id`; human references (`REQ-2026-000431`, `INV-…`) are separate generated columns |
| Timestamps | `created_at`, `updated_at` (`timestamptz`, UTC); business dates are `date` in `Asia/Kolkata` |
| Attribution | `created_by`, `updated_by` referencing `identity.user.id`, or the literal `'system'` principal |
| Soft state | Reference data is deactivated, never deleted, and stays readable on records that used it (`M0-I5`) |
| Candidate data | **Never deleted.** A losing duplicate is merged with lineage to both sources (`M1-I12`, `M4-I21`) |
| Money | `numeric(14,2)` plus an ISO currency column; INR throughout Release 1 |
| Versioned commercial records | `Contract`, `RateCard`, `Offer`, `WeightSet`, `CategoryAttributeSet` are versioned; readers resolve **by effective date**, never "latest" |
| Snapshots | An invoice snapshots the terms it read; it does not re-resolve them later (`M9-I13`) |
