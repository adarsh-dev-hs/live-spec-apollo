Terms used precisely across these docs. Where the client and the engineering docs use different words
for the same thing, both are given.

## Business

| Term | Meaning |
|---|---|
| **Apollo** | Apollo Knowledge Services, the client. Also the platform's package scope `@apollo/*`. |
| **Hiresense** | The delivery team. |
| **Base A** | The permanent supply base. Availability is a **notice period**. Contacted on a long cycle. |
| **Base B** | The shift supply base. Availability is **time windows within a travel radius**. Contacted every 3–4 days across the whole base. |
| **Supply segment** | A candidate category × a supply base. Three categories × two bases = **six segments**, each with its own cadence, question set, decay schedule and ranking weights. |
| **Candidate category** | `nurse` \| `doctor` \| `allied_health`. Reference data (`02-03`), never a code branch. |
| **Care setting** | `hospital` \| `home_healthcare`. A dimension on client, site and requisition. Home healthcare has no department, no preceptor and no fixed workplace. |
| **Associate** | A Base B candidate who is actually working shifts for Apollo — i.e. has an `AssociateProfile` (`03-15`). |
| **Requisition** | One client demand record, whatever channel it arrived on. Carries category, care setting, positions, rate reference, completeness and owner. |
| **Shift demand line** | One shift on a contractual requisition, generated from a shift template. Ranked and filled individually. |
| **Owner vs allocation** | The **owner** is one accountable Apollo user. **Allocation** is which recruiters were put on it at the morning call — a record of a human decision, never a system assignment (until `03-18`). |
| **Verbal capture** | A site-resident recruiter typing in a requirement a client told them in person. A normal path, not an edge case — 15 of 22 recruiters sit inside hospitals. |
| **Retained pool** | Candidates kept indefinitely rather than deleted, including those whose verification came back red. In tension with DPDP erasure (`OI-HS-02`). |
| **Privileging** | Permission a specific hospital grants a specific doctor to practise there. Separate from council registration, required before joining, and applies to doctors only (`M8-I10`). |
| **Preceptor** | The nurse supervising a new placement during the trial. Does not exist in home healthcare. |
| **Trial period** | Day 0 → day 90 after joining, with check-ins at 0, 7, 30, 60 and 90. |
| **Deemed confirmation** | Retention treated as confirmed because the client did not answer the day-90 link within the per-client window. As valid an invoice input as an explicit answer. |
| **Deemed approval** | The same rule for timesheets. |
| **Guarantee period** | How long Apollo must replace a departed permanent placement. If it runs past day 90, credit and debit notes come back into Release 1 (`OI-A-13`). |
| **CTC** | Cost to company — the annual salary the 5–6% permanent placement fee is calculated on. |
| **CPAL** | The legacy tool Apollo's candidate data lives in today, migrated and retired in `03-13`. |
| **LMS** | Apollo's own learning system, built by another team. Outside scope; no Release 1 deliverable depends on it (`OI-HS-15`). |
| **Morning call** | The daily fulfilment meeting where recruiter allocation is decided. |

## Plan and traceability

| Term | Meaning |
|---|---|
| **`M<n>`** | Milestone. M0 foundations, M1–M9 the client's Release 1, M10–M15 Release 2. |
| **`M<n>-I<k>`** | The engineering index — one per buildable item. `M3-I12` is the fulfilment board. |
| **`D<n>` / `A<n>`** | The client's own deliverable number, carried unchanged. `D` = original or moved; `A` = added at revision. |
| **`F<nn>`** | A platform prerequisite Hiresense identified that the client's list assumes but never names. |
| **`OI-…`** | An open decision. `OI-A-…` from Part A, `OI-M3-…` from the Part B M3 chapter, `OI-HS-…` raised by Hiresense. |
| **`AS-<nn>`** | A working assumption held until an open item closes. |
| **`X<nn>`** | An external dependency — an account, contract, registration or access that must exist before build. |
| **Estimate blocker** | One of the 7 open items that must close before a fixed price can be committed. |
| **Effort band** | XS 0.5 · S 1.0 · M 2.0 · L 3.0 · XL 5.0 · XXL 8.0 person-days of **build** only. |
| **Confidence** | High = spec complete. Medium = an assumption covers a gap. Low = an open decision could change **what** gets built. 97 of 208 items are Low. |
| **Risk driver** | `EXT` external dependency · `SPEC` unresolved specification · `SHARED` shared component · `DATA` data volume/migration · `MODEL` accuracy-dependent · `COMP` compliance · `XMOD` cross-module contract. |

## Technical

| Term | Meaning |
|---|---|
| **Component** | The unit these docs are organised by: one spec, one implementation session, one owning package. |
| **Realm** | An identity population. Three exist and never mix: `staff`, `candidate`, `client_user`. A fourth pseudo-realm, `link`, is a single-record token principal with no account. |
| **Principal** | The authenticated subject on a request: realm, id, roles, and data scope. |
| **Client link** | A tokenised, unguessable, expiring URL reaching exactly one record and one action, with **no login and no account provisioning**. Four types (`02-14`). |
| **Billing trigger** | The evidence that permits an invoice: a `RetentionRecord` (permanent) or an approved `Timesheet` (contractual). Only the day-90 link type may produce the former. |
| **Freshness score / availability confidence** | A per-candidate value that decays on a per-segment schedule and resets on a confirmed response. Written by `03-06`, stored on the candidate record, read by `03-07`. |
| **Inbound stack** | The shared receive → queue → resolve sender → classify intent → retry pipeline (`02-08`), built once under A1 and consumed by A14 and the LMS path. |
| **Intent registration** | How a second consumer attaches to the inbound stack without modifying it (`M3-I29`). Its acceptance test *is* A14 registering. |
| **Outbox** | The table an event is written to inside the business transaction, then published by the worker. Guarantees the event exists if the change did. |
| **Mart** | A reporting table materialised from the event spine, never queried from operational tables (`M9-I17`). |
| **Adapter** | An implementation of one of the three market interfaces — identity, certification, qualification — returning green/amber/red on a common schema whatever the registry did (`02-13`). |
| **Traffic-light outcome** | `green` verified · `amber` flagged, needs a human · `red` rejected. Uniform across every registry and check type. |
| **Manual fallback** | What an adapter resolves to when a registry has no API or is down: document plus a person, behind the **same interface**. |
| **Deployable** | `api`, `worker`, `console`, `links`, `portal`, `mobile`. See `00-02`. |
| **Append-only** | No `UPDATE`, no `DELETE`, enforced by table grants. Applies to `AuditEntry`, `StatusTransition`, `AllocationRecord`, `RecruiterOverride`, `PlatformEvent`, `RetentionRecord`. |
| **DPDP** | India's Digital Personal Data Protection Act. Drives consent capture, Mumbai residency and retention (`02-12`). |
| **DLT registration** | Indian telecom registration required before an SMS template can be sent. |
| **BSP** | WhatsApp Business Solution Provider — carries every message and must approve each template before use. |
| **`ap-south-1`** | AWS Mumbai. No personal data leaves it, backups included. |
