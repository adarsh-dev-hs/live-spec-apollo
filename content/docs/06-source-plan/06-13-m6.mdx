*M6 · D5, D18, A8 · Months 4–5*

`Release 1` · `10 items` · `60 conditions` · `72.0pd` · `6 high risk` · `Ops/Admin`

Given a vacancy, produce a ranked list of candidates, best first, with a plain explanation of why each one ranked where they did and which requirements they do not meet. The weightings are different for each candidate category and each pool, so there are at least six sets. Recruiters can search manually and can move someone up or down the list, and every override is recorded. When a client or interviewer rejects someone with a reason, that reason feeds back in and affects later rankings.

### Built once, used elsewhere

The list of rejection reasons in M7 and the data the ranking model reads are one design, not two. If the ranking model has no slot for outcome data, feeding rejections back in later means rebuilding it. Agree both before either module is built.

### Records this milestone owns

- RankedSet — one ranked list for one vacancy or one shift, recording which weighting set produced it and when.
- RankEntry — one candidate in that list: their score, why they scored it, and what they do not meet.
- WeightSet — how much each factor counts. One per candidate category per pool, so at least six.
- RecruiterOverride — a manual move up or down, with a reason. Rows are only added, never changed.
- SavedSearch, TalentSegment — searches and candidate groups recruiters reuse.
- OutcomeSignal — rejection reasons and selection results fed back from M7.

### How records move

- RankedSet: generating → current → out of date (once the vacancy changes or new outcome data arrives)
- RankEntry: ranked → shortlisted → sent to client → outcome recorded
- OutcomeSignal: captured → written back → included in the next ranking run. This happens in the background and does not hold anything up.

### Not in this milestone

- Retraining the model automatically. We apply a configured set of weights; continuous learning is not in this contract.
- Showing candidates their own match score. Ranking is an internal tool only.
- Sending a shortlist to a client without a recruiter pressing the button.
- Using the clinical and communication rating. Nothing produces that value — see open item OI-A-07.

### Needs to exist first

- M3 for the vacancy. M4 for credentials and category fields. M5 for the freshness score. All three are needed; ranking cannot run on a partial set.

### What breaks without it

- M7 takes the shortlist. Everything after M7 depends on this indirectly.

#### M6-I1 — Candidate search

`D5` · `Screen` · `L · 3.0pd` · `AI High` · `Medium` · `SPEC` · `Low`

**Who uses it: Recruiter.** Search the candidate pool on skill, location, experience, credentials and availability.

##### Screens to build

1. **Candidate search**
  - Advanced search on skill, location, experience and status
  - Filters further by category, pool, specialty, credential state and availability
  - Saves the search so it can be run again later
  - Adds a candidate from the results to a shortlist

##### Conditions it must satisfy

- Search returns candidates filtered on availability confidence and last-confirmed recency (Part A stage 7)
- Specialty and acuity filters use the same taxonomy as capture, per category (M4-I26)
- Verification state is a filter, so an unverifiable candidate is excludable before shortlisting
- Search respects the user's data scope (OI-HS-01)
- Whether hand-assembly survives as a recruiter fallback is unresolved (OI-A-10)

#### M6-I3 — Ranked candidates

`D18` · `Screen` · `XL · 6.0pd` · `AI Medium` · `High` · `MODEL` · `Low`

**Who uses it: Recruiter.** The ranked list of candidates for a vacancy, best first.

##### Screens to build

1. **Ranked candidates**
  - Lists candidates for a requisition, best first, with their score
  - Shows each candidate's credentials, specialty, availability and location
  - Marks the set as out of date when the requisition changes
  - Runs the same way against a single shift for shift work
2. **Why this rank**
  - Opens from a candidate in the ranked list
  - Lists which requirements the candidate meets, partly meets and does not meet
  - Shows how fresh the availability behind the rank is
3. **Override rank**
  - Moves a candidate up or down the list
  - Requires a reason for the move

##### Conditions it must satisfy

- A ranked set is produced against a requisition with rationale and unmet or partially met criteria exposed per rank (Part A stage 8)
- Weights differ by candidate category and supply base - six combinations minimum (Part A M6)
- A set generated before a requisition revision is marked stale and regenerable
- Contractual ranking runs against a shift demand line, not only a requisition (Part A contractual stage 6)
- Ranking cannot run where category, credentials or availability are missing - it fails visibly rather than ranking on a partial input set
- The weighting model across inputs is unspecified (OI-A-11)
- Rationale names the specific criteria met, partially met and unmet, not a generic score breakdown (Part A stage 8)
- A candidate ranked highly on stale availability shows that staleness in the rationale
- The rationale is defensible to a client without exposing the weight model itself
- Verification state is visible in the rationale so a shortlist can be defended on it (Part A dependency table)
- Where the clinical and communication rating is unpopulated, its absence is stated rather than silently weighted at zero (OI-A-07)
- Overrides are recorded where applied and visible in the submitted shortlist (Part A stage 8)
- An override requires a reason, so override patterns are analysable
- Overriding does not silently retrain the model - Release 1 applies a configured weight set
- Override history is retained per requisition and exposed to M9 reporting

**Who uses it: System.** Score and order the candidates, and produce the reasoning at the same time.

##### Screens to build

1. **No screen**
  - Scores and orders candidates against a requisition or a single shift
  - Produces the reasons and the unmet requirements at the same time

##### Conditions it must satisfy

- Ranking runs against a requisition and against a shift demand line with the same engine

- A regeneration produces a new set; the prior set remains retrievable for audit
