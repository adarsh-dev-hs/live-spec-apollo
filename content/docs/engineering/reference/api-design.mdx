**REST/JSON over HTTPS, schema-first.** One shared contracts package is the single definition of
every request and response: the API validates against it, the OpenAPI document is generated from it,
and the console, link pages, portal and mobile app all import it. **The contract cannot drift from
the handler**, because the schema that validates a request is the schema that documents it.

## 1. Shape

| Rule | Detail |
|---|---|
| Base | `/v1` — the version is in the path and changes only on a breaking change |
| Resources | Plural kebab nouns: `/v1/requisitions`, `/v1/shift-demand-lines` |
| Sub-resources | `/v1/requisitions/:id/versions`, `/v1/candidates/:id/credentials` |
| State transitions | A `POST` to a named action, **not** a `PATCH` of a status field: `POST /v1/requisitions/:id/hold` |
| Verbs | `GET` read · `POST` create or act · `PATCH` partial update · `DELETE` only for genuinely removable things. **Never** for candidates, requisitions, invoices or any audited record |
| Files | Uploaded via a presigned URL, never multipart through the API |
| Time | UTC timestamps. Business dates mean `Asia/Kolkata`. |
| Money | An explicit amount and currency, as a string. **Never a float.** |

## 2. Envelopes

A single resource comes back under `data`. A collection comes back with cursor pagination
everywhere — offset pagination over a migrated base of unknown size is unpredictable.

```json
{
  "data": [ { "id": "…", "reference": "REQ-2026-000431", "status": "in_fulfilment" } ],
  "page": { "cursor": "eyJpZCI6…", "hasMore": true, "limit": 50 },
  "meta": { "totalApprox": 1284 }
}
```

The total is an **estimate and is labelled as such on screen**. An exact count is computed only when
a list is exported, because the export must return exactly the filtered rows.

## 3. Errors

RFC 9457 problem details, with a stable machine-readable `code` alongside human-readable text.

```json
{
  "type": "https://docs.apollo.internal/errors/precondition-failed",
  "title": "Close reason is required",
  "status": 422,
  "code": "REQUISITION_CLOSE_REASON_REQUIRED",
  "correlationId": "01JD8F…",
  "errors": [ { "field": "reasonId", "code": "required", "message": "Select a close reason." } ]
}
```

**Clients switch on `code`, never on the message.** Titles and details are human text and may change.

## 4. Listing

| Parameter | Form |
|---|---|
| `filter[field]` | `filter[status]=open,in_fulfilment` — repeated values are OR, different fields are AND |
| `sort` | `sort=-daysAged,clientName` — a leading minus is descending |
| `cursor`, `limit` | `limit` maximum 200, default 50 |
| `q` | Free-text search, where the resource supports it |
| `view` | A saved view id, expanding to a filter set |

**Every list endpoint applies the caller's data scope before any filter.** Scope is not a parameter
and cannot be widened by the caller.

## 5. Idempotency and concurrency

| Mechanism | Where it applies |
|---|---|
| An idempotency key header, **required** on requests that create money, messages or external calls | Invoices, offers, link issues, message sends, payroll submissions |
| Webhook idempotency on the provider's message id | Inbound and outbound — redelivery is normal and must not create a second record |
| Optimistic concurrency on records two people edit at once | Requisition, contract, candidate, rate card |
| A duplicate link submission returns the **original** response | Client link pages |

## 6. Auth realms

| Realm | Credential |
|---|---|
| Staff | Session cookie, HTTP-only, secure, with a sliding idle expiry from settings |
| Candidate | Short-lived bearer token plus a rotating refresh token |
| Client user | Session cookie, **separate cookie name and separate signing key** from staff |
| Link | An opaque token in the path, exchanged for a single-record, single-action session |
| Provider webhook | Signature verification per provider; unsigned providers are IP-allowlisted and share a secret |

**Realms never mix.** A candidate token presented to a staff route is a 401, not a 403.

## 7. The link surface is different on purpose

The public tokenised pages are the platform's largest exposure — tokens arrive over WhatsApp and can
be forwarded — so that surface is built to a stricter contract than the rest of the API.

| Rule | Why |
|---|---|
| **No collection endpoints at all** | A link reaches exactly one record. Enumerating another client's shortlist is the worst failure mode available here. |
| A link session can call only the endpoints its type allows | Same reason |
| Rate-limited per token and per IP | The token is not a secret once it has been forwarded |
| Responses omit every field the client does not need — internal reason codes, scores, notes | Clients see client-appropriate status, never internal reasoning |

## 9. Versioning and generated artefacts

- **Additive changes** — a new optional field, a new endpoint, a new enum value a client may ignore —
  go into `v1`.
- **Breaking changes** create a `v2` for that resource, with `v1` kept for one release behind a
  deprecation header.
- **Integration contracts are versioned independently**: the registry adapters, the finance export and
  the payroll interface have counterparties who are not on Apollo's release train.

| Generated | From | Used by |
|---|---|---|
| The OpenAPI document | Route schemas, at build time | Documentation, the client generator, **the technical documentation deliverable** |
| Contract types | The shared schema package | Console, link pages, portal, mobile |
| A typed API client | The OpenAPI document | All four clients |

**The technical documentation under `D11` is generated from this, not written by hand**, and is
versioned alongside the release.
