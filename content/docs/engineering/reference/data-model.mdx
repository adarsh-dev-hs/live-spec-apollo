One PostgreSQL database, **one schema per module**, and one rule that everything else follows.

> **Exactly one component writes an entity. Everything else reads it through that component's
> service or a view.**

That rule is enforced twice — in the repository by the project graph, and in the database by one role
per schema. It is what keeps a modular monolith modular.

## 1. Shared platform entities

| Entity group | Owner | Notes |
|---|---|---|
| Users, roles, permissions, site assignments | Identity | Three separate identity realms: staff, candidate, client user |
| Audit entries | Audit trail | **Append-only.** Written by every component, inside its own transaction |
| Settings, reference lists, categories, care settings | Settings | Editable data, never code |
| Documents and their versions | File storage | Every uploaded file in the platform |
| Inbound records and intent registrations | Inbound pipeline | The **raw payload is retained forever** |
| Templates, triggers, delivery log, preferences, opt-outs | Outbound messaging | One log per message and per candidate |
| Jobs, runs, dead letters | Job runtime | Every non-interactive execution |
| Platform events — outbox and log | Event spine | **Append-only**, partitioned by month |
| Consent, retention policies, erasure requests | Data protection | Consent is checked before any verification dispatch |
| Adapters and adapter calls | Market adapter layer | Each call records its cost |
| Client links, link types, recipients, responses | Client link surfaces | One mechanism, four configured types |

## 4. The lifecycles that cross modules

Every state machine lives in the module that owns it. These three cross enough boundaries to belong
here.

### Requisition

```
incomplete → awaiting_client → complete → open → in_fulfilment → partially_filled → filled
                   │                                    ▲   │
                   │  escalates to the owner on          │   └─▶ on_hold  (the aging clock stops)
                   │  window expiry                      └────── release  (aging resumes from held)
                   │
   revise at any point creates a new version and re-scores
   any state → closed, with a mandatory reason from the configured list
```

**Aging excludes held days.** A revision is a new version, not an edit. `awaiting_approval` is added
by [demand prioritisation](/docs/engineering/build/modules#demand-prioritisation-and-approval) in Part 3.

### Placement and the day-90 trigger

```
offered → joined → in_trial ─┬─▶ trial_survived   client confirms at day 90, or the window expires
                             └─▶ trial_ended      drop-out, with a reason
                                     │
        RetentionRecord written, immutable, snapshotting the terms in force
                                     │
                             BillingTrigger ──▶ Invoice (permanent)
```

The retention record records **whether the client acknowledged or the window simply expired**, and
both are valid invoice inputs. Only the day-90 link type can carry the billing-trigger flag.

### Timesheet

```
building → built → sent_for_approval ─┬─▶ approved           client answers the link
                                      └─▶ deemed_approved    the window expired
                                                │
                                        Invoice (shift)
```

## 5. Append-only, and why

Five things are append-only, with no `UPDATE` or `DELETE` granted at all: **audit entries, status
transitions, retention records, allocation records and ranking overrides**.

The reason is a single scenario. Apollo raises an invoice at day 90; months later the client queries
it. The answer has to be a record of who confirmed what, when, against which contract terms, that
nobody could have edited in between. If any link in that chain is mutable, the invoice cannot be
defended — and permanent placement is the whole of Part 1's revenue.

## 6. Conventions

| | |
|---|---|
| Schema | One per module. No module reads another module's tables directly. |
| Migrations | Numbered plain-SQL files, **forward-only**. Never rewrite an append-only table. |
| Money | Stored as a decimal amount with an explicit currency. Never a float. |
| Time | Timestamps in UTC. Business dates mean `Asia/Kolkata`. |
| Reference data | Categories, care settings and service lines are rows, not enums in code. |
| Settings versioning | Changing a setting does not retrospectively alter records created under the old value. |
| Deletion | Candidates, requisitions, invoices and any audited record are never deleted. |
