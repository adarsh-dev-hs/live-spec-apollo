The [release plan](/docs/release-plan) says **what ships when**. This page says **what order it is
built in**, which is a different question — a phase completes a component, a part releases a
capability, and most components are sliced across parts.

## 1. Build order

Seven phases. Each ends with a gate that has to be demonstrated, not asserted.

| Phase | What is built | Gate |
|---|---|---|
| **1 · Foundations** | Environments and pipeline · design system · identity and audit · settings · file storage · job runtime · market adapters · legacy profiling | A named recruiter signs in, sees only their permitted navigation, an administrator adds a candidate category **as data**, and every action appears on the activity trail |
| **2 · Client and candidate spine** | Clients, contracts and rate cards · candidate record and credentials · candidate app · list engine · data protection | A client, a contract and a rate card exist; a candidate registers in the app and a credential reaches the verification queue |
| **3 · Demand** | **Event spine** · requisitions and allocation · inbound pipeline · outbound messaging · demand intake | A requisition exists, ages correctly across a hold, and emits events from the first record |
| **4 · Engagement and matching** | Client link surfaces · matching and ranking · engagement and availability | A ranked shortlist reaches a client on a link, and a client answers it without an account |
| **5 · Selection, placement and attendance** | Selection and offers · placement and trial · attendance and timesheets | An offer is signed, a placement opens, and a shift check-in reaches a timesheet |
| **6 · Money and the rest** | Billing and receivables · client portal · associate onboarding · analytics · workforce operations · prioritisation | A day-90 confirmation produces a permanent invoice, and an approved timesheet produces a shift invoice |
| **7 · Remainders** | Payroll · timesheet extensions · collections | A pay run completes and a payment reconciles |

## 2. What cannot be resequenced

| Rule | Consequence of breaking it |
|---|---|
| **The event spine before the first requisition** | The Part 3 reports cannot cover the earlier period at all. **Not recoverable.** |
| Categories as editable data in Phase 1 | Doctors become a migration rather than a configuration change |
| Client link surfaces before selection, placement and timesheets | No client surface exists at all — the portal is not delivered until Part 2 |
| The adapter layer before the candidate record | No candidate can be verified |
| The candidate app before attendance | No attendance, no timesheet, no shift invoice |
| Contract terms before billing | Permanent billing does not run — **there is no fallback** |
| `A3`, `A4`, `A5` and `A14` together | Build any three and none of them does anything useful |
| The ranking and rejection schemas agreed before either module is built | `A8` becomes a rebuild rather than a layer |
| Workforce operations before timesheet extensions | The approval engine gets built twice |

## 3. If the schedule slips

Any slip in the early phases lands on the later ones, because that is the only thing left to cut. The
client's stated priority, if a period cannot hold everything, is **all three candidate categories on
a thinner remainder** — the category dimension reaches into the adapters, the weight model and the
trial question sets, and the remainder does not.

**Cut in this order:** collections → timesheet extensions → demand prioritisation → client portal →
payroll.

Payroll is cut last despite being least ready. Until it exists, payroll is manual, and that caps how
many shift workers Apollo can take on.

## 4. How quality is proven

**Every acceptance condition gets a test named after it, and the two lists are diffed in CI.** A
condition with no test fails the build. That is what makes a scenario catalogue a measurable thing
rather than a number in a plan.

| Layer | Covers |
|---|---|
| Unit | State machines, invariants, scoring, date and money arithmetic. Pure, no I/O |
| Integration | Service plus real SQL, real transactions, audit and outbox |
| Contract | What one module promises another; what an adapter promises the core |
| API | Route, auth, permission, scope, error shape |
| Component | The five standard states of every screen |
| End to end | The gate journeys only |
| Mobile | Offline queue, sync, permissions, check-in flows |
| Load | Fulfilment board, inbound ingestion, cadence run |

### The suites that exist because something must never happen

| Suite | Asserts |
|---|---|
| **Scope** | Every collection route rejects a cross-scope id, in every realm. A new route without a scope predicate fails |
| **Append-only** | An update or delete on any append-only table raises |
| **Billing trigger** | Only the day-90 link type can carry the billing-trigger flag; day 30 and 60 cannot be configured to; a duplicate trigger cannot produce a second invoice |
| **Intent registration** | A second consumer registers an intent set **without modifying** the receiver, queue, sender resolution or retry |
| **Adapter contract** | Every adapter returns the common traffic-light schema; a core change that breaks an existing adapter fails |
| **Channel parity** | The same vacancy on all live channels produces requisitions differing **only** in source channel and raw payload |
| **Response parity** | An availability answer from app, WhatsApp and voice produces one identical payload, and a response on two channels reconciles to one record |
| **Deemed paths** | Deemed confirmation and deemed approval are valid invoice inputs, visibly distinguished, falling back to the platform default where a client has no window |
| **Idempotency** | Webhook redelivery, offline check-in re-sync and duplicate link submission each produce exactly one record |
| **Partial failure** | A bulk import with bad rows names each bad row and still loads the good ones |
| **Personal data in logs** | No log line contains a phone, email, name, government identifier, account number or document text |
| **Residency** | No configured bucket, database, backup or provider endpoint is outside Mumbai |

### Definition of done, for one component

1. Every acceptance criterion has a passing, named test.
2. Every state is reachable only from its declared predecessor, tested.
3. Every event is emitted inside the business transaction, tested.
4. Every endpoint has auth, permission, scope and error-shape tests.
5. Every screen has its five standard states.
6. Migrations run forward against a copy of the previous release's schema.
7. New queries over a large table carry a query plan in the pull request.
8. Any open question that turned out to be blocking is **raised**, not worked around.
9. The documentation is updated in the same pull request when shipped behaviour differs from it.

## 5. Documentation, UAT and go-live

This is the `D11` and `D30` obligation, and it is delivered twice: once for Part 1's go-live, and once
for everything released after it.

| Deliverable | Shape |
|---|---|
| **Technical documentation** | Generated from the API contract and versioned alongside the release, not written by hand |
| **User documentation** | Per role, against the screens that role actually reaches |
| **UAT support** | Apollo-run, Service-Provider-supported. **Severity definitions and turnaround windows are agreed before testing starts**, not negotiated during it. Sign-off criteria agreed per module beforehand, and retest of a fixed defect evidenced |
| **Cutover and go-live** | Including legacy retirement, once the migrated base reconciles against the source total |

**Named recruiters need protected time booked in advance.** They carry fifteen to sixteen vacancies
each and will not test otherwise.

## 6. What is still open

Design decisions that are not yet made are carried as **explicit working assumptions**, applied
consistently, and revisited when the decision closes — never filled in with a quiet guess. The ones
that change more than a number:

| Open | Why it matters |
|---|---|
| **Whether a site-resident recruiter is scoped to their own site** | Touches every list query in the platform. Deciding it late means revisiting all of them |
| **The ranking weight model** | Not specified anywhere. Six weight sets exist; what goes in them does not |
| **The verification aggregator, and which registries have APIs** | Sets how much of verification is automated and how much is a person reading a document |
| **The voice, transcription, document-reading, e-signature, finance and payroll suppliers** | Each unnamed supplier is an unpriced integration |
| **How many client systems and spreadsheet formats exist** | Each is a separate connector, and the count is not stated |
| **The legacy data profile** | `A10` has no credible effort basis until profiling runs |
| **Recovery point and time objectives** | Until agreed, the restore rehearsal has no pass condition |
| **Backup retention against the erasure obligation** | Two policies that can contradict, needing one deliberate reconciliation |

The last two are the ones most often discovered late. Both are cheap to settle now and expensive to
settle after go-live.
