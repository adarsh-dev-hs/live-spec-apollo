## Purpose

> Introduction to the feature. **This is not the scope** — the scope is items 1 to 5 below.

Phase 1 verified one category by having a person read a document. Phase 2 does two things to that:
it makes verification **true verified, third party** — a registry answering rather than a reviewer
judging — and it opens the platform to the categories and care settings the business actually runs.
If the Phase 1 model was built correctly, all of that is configuration and adapters. **Whether it is
configuration or a rewrite is decided by what was built in Phase 1, not by what is done here.**

## Release in this phase

1. Third-party verified checking.
2. The remaining India council adapters.
3. Base B populated and worked as a separate supply base.
4. Doctor and allied health attribute sets.
5. Home healthcare as a care setting.

## 1. Third-party verified checking

**ClickUp item** — *link to be added* · **Delivers** `D16` (Phase 2 slice)

**Screens** — `/verification` · `/verification/pendency` · `/candidates/:id`

### Scenarios to cover

A credential is verified by resolving it against **the council appropriate to that candidate
category**, through the market adapter interfaces, rather than by a person reading a scan. The
verification method on the credential records which it was, so a green from a registry and a green
from a reviewer are never confused.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Check dispatch | Action | Yes | Automatic on credential creation, and re-runnable |
| 2 | Verification method | Field | Yes | Third-party verified, or document plus reviewer |
| 3 | Source and checked-at | Fields | Yes | Which registry answered, and when |
| 4 | Amber handling | Behaviour | Yes | A provider failure keeps the case open, never a green |
| 5 | Aggregator checks | Capability | Yes | EPFO and court records where the category requires them |
| 6 | Queue behaviour | Behaviour | Yes | A verified result closes the case without a reviewer |
| 7 | Re-check | Action | Yes | With a reason, producing a new result and keeping the old |

### Flow

1. A credential with an identifier dispatches a check through the adapter layer, after the consent
   gate.
2. A green closes the verification case automatically and records the source.
3. A red or amber routes to the verification queue with its reason.
4. Every result is retained; a re-check appends rather than overwrites.

### Scenarios to test

- A green from a registry closes a case with no reviewer action, and records the source.
- A red is never auto-closed and always carries its reason.
- A provider outage produces amber and leaves the case open.
- Re-checking keeps the earlier result readable.
- No check dispatches without the recorded verification consent.

## 2. The remaining India council adapters

**ClickUp item** — *link to be added* · **Delivers** `A12` (Phase 2 slice)

**Screens** — `/admin/registries`

### Scenarios to cover

The adapter set completes: **the NMC and the state medical councils, the allied health councils and
the Pharmacy Council**, each behind the existing certification interface, each in API or manual mode
according to what it offers. No core logic changes — that is the test of the Phase 1 design.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | NMC and state medical council adapters | Implementations | Yes | Doctor category |
| 2 | Allied health council adapters | Implementations | Yes | Allied health category |
| 3 | Pharmacy Council adapter | Implementation | Yes | |
| 4 | Council reference data | Reference list | Yes | Which council governs which state and category |
| 5 | Manual-mode councils | Configuration | Yes | Councils with no API |
| 6 | Contract tests | Test suite | Yes | Every adapter answers the same interface |

### Flow

1. Each adapter is registered against its interface, market and category.
2. A credential names its council; selection resolves the adapter.
3. Councils with no API run in manual mode through the verification queue.

### Scenarios to test

- Adding an adapter requires no change to the verification module.
- A doctor's registration resolves to the right state council.
- Every adapter passes the shared contract test suite.
- A council in manual mode produces the same response shape as one in API mode.

## 3. Base B populated and worked

**ClickUp item** — *link to be added* · **Delivers** `A2` (Phase 2 slice)

**Screens** — `/candidates` · `/candidates/:id`

### Scenarios to cover

The shift pool becomes real: candidates hold Base B membership, some hold both, and **one shared
credential record serves both**. A candidate is never duplicated to appear in two bases.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Base B membership | Record | Yes | Alongside any Base A membership |
| 2 | Dual membership | Behaviour | Yes | Both bases against one candidate and one credential set |
| 3 | Base filter | List filter | Yes | Working a base as a base |
| 4 | Base-specific fields | Fields | Yes | Where a base needs its own data, held per membership |
| 5 | Membership transitions | Append-only | Yes | Joining and leaving a base is recorded |

### Flow

1. A candidate joins Base B at sign-up or by a recruiter action.
2. Credentials already verified serve the new membership immediately.
3. Matching, engagement and ranking all query membership.

### Scenarios to test

- A candidate in both bases has one record and one credential set.
- A credential verified for Base A needs no re-verification for Base B.
- Base filters work as filters, not as separate candidate stores.
- Leaving a base is recorded and reversible without a new record.

## 4. Doctor and allied health attribute sets

**ClickUp item** — *link to be added* · **Delivers** `A9` (Phase 2 slice)

**Screens** — `/admin/settings` · rendered in `/candidates/:id`, `/requisitions/new`, `/app/profile`

### Scenarios to cover

The two remaining candidate categories get their attribute sets, defined the same way the nurse set
was: **once**, and served to candidate, requisition, app and ranking. If this is configuration
rather than code, Phase 2 spends days here rather than weeks.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Doctor attribute set | Reference data | Yes | Specialty, super-specialty, acuity, privileging needs |
| 2 | Allied health attribute set | Reference data | Yes | Discipline, specialty, acuity |
| 3 | Category activation | Reference data | Yes | Doctor and allied health as active categories |
| 4 | Both-sided rendering | Behaviour | Yes | Same definition on candidate and requisition |
| 5 | Ranking features | Mapping | Yes | The new attributes are readable by ranking |

### Flow

1. The sets are defined in settings and the categories activated.
2. Every consumer renders what it is served, with no per-category code branch.
3. Ranking reads the new attributes through the same feature extraction.

### Scenarios to test

- Activating a category makes it selectable on demand, candidate and app with no deploy.
- A doctor requisition renders doctor attributes and no nurse-only fields.
- Ranking reads the new attributes without a code change to the engine.
- Records created under the nurse-only configuration still render.

## 5. Home healthcare as a care setting

**ClickUp item** — *link to be added* · **Delivers** `A9` (Phase 2 slice)

**Screens** — `/clients/:id` · `/requisitions/:id`

### Scenarios to cover

Home healthcare is a second care setting, and it differs in ways that reach several features: sites
have no departments, the workplace changes between shifts so **the address lives on the demand
line**, and the trial question set has neither preceptor nor accommodation.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Care setting activation | Reference data | Yes | Home healthcare alongside hospital |
| 2 | Client and site care setting | Field | Yes | Held on both |
| 3 | Requisition care setting | Field | Yes | Defaulted from the site, overridable |
| 4 | Per-visit address | Field | Yes | On the shift demand line |
| 5 | Departmentless sites | Behaviour | Yes | A home healthcare site needs no department |

### Flow

1. The care setting is activated and set on the client and its sites.
2. A requisition inherits it and passes it to every downstream consumer.
3. Shift lines for home care carry their own visit address, which is also the geo-fence boundary.

### Scenarios to test

- A home healthcare requisition can be created against a site with no departments.
- A shift line for home care requires an address and rejects a blank one.
- The care setting reaches the trial question set and the geo-fence boundary correctly.
- Hospital behaviour is unchanged by the activation.
