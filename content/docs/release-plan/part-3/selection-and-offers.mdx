it with a tap, so the accepted offer is an executed document. Everything else about offers was built

## 1. Digital signature on the offer

**ClickUp item** — *link to be added*

**Screens** — `/offers` · `/app/applications`

### Scenarios to cover

An issued offer is sent for signature, the candidate signs on their phone, and the signed document
comes back and attaches to the offer. Acceptance and signature are related but distinct: **the
platform records which of the two happened and when**.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | E-signature integration | Provider | Yes | Client dependency; provider not named in the SOW |
| 2 | Send for signature | Action | Yes | From the issued offer |
| 3 | Signature status | Field | Yes | Sent, viewed, signed, declined, expired |
| 4 | Signed document | File | Yes | Returned and stored, versioned |
| 5 | Acceptance mapping | Behaviour | Yes | Signature completes acceptance where configured |
| 6 | Audit evidence | Record | Yes | Signer identity, timestamp, provider reference |
| 7 | Fallback | Behaviour | Yes | Manual acceptance remains available if the provider fails |

### Flow

1. An issued offer is sent for signature through the provider.
2. Status updates arrive asynchronously and are reconciled onto the offer.
3. A signed document is stored and the offer moves to accepted per the configured mapping.
4. The placement handover proceeds exactly as it did before.

### Scenarios to test

- A signed offer stores the executed document and the provider's evidence.
- A declined or expired signature leaves the offer in a clear state, not in limbo.
- A provider outage does not block the chain — manual acceptance still works and is recorded as such.
- The placement handover fires once, whichever route completed acceptance.
