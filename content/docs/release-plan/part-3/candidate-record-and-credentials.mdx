## Purpose

> Introduction to the feature. **This is not the scope** — the scope is items 1 to 3 below.

Three things that only matter at volume, and are therefore here rather than earlier. Extraction has
to work across every document type the whole base actually holds. **Duplicates have to be found and
merged — the single merge implementation in the platform**, which the legacy migration then depends
on. And a credential that expires without anyone noticing is a compliance failure, so expiry is
tracked across the base rather than checked at placement.

## Release in this phase

1. Document extraction at width.
2. Duplicate detection and merge.
3. Credential expiry tracking.

## 1. Document extraction at width

**ClickUp item** — *link to be added*

**Screens** — `/verification` · `/candidates/:id` · `/learner-matches`

### Scenarios to cover

Extraction covers every document type in the base, across the three candidate categories, with
accuracy measurable from the corrections reviewers have been making since Phase 1 — and with the
certification and learner-match handling the qualification side needs.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Document type coverage | Definitions | Yes | Every type in use across the three categories |
| 2 | Extraction accuracy view | Report | Yes | Built from retained corrections |
| 3 | Certification records | Records | Yes | Course, issuer, completion, validity |
| 4 | Learner-match queue | Screen | Yes | Matching a certification record to a candidate |
| 5 | Bulk review | Action | — | Working a queue by document type |

### Flow

1. Remaining document types are added behind the same extraction and review path.
2. Accuracy is measured from the corrections already retained.
3. Certification records that cannot be matched to a candidate queue at `/learner-matches`.

### Scenarios to test

- Every document type in use extracts and reviews through one path.
- Accuracy figures reconcile with the retained corrections.
- An unmatched certification queues rather than creating a candidate.
- A matched certification attaches to the right candidate and is auditable.

## 2. Duplicate detection and merge

**ClickUp item** — *link to be added*

**Screens** — `/candidates` · `/duplicates`

### Scenarios to cover

The same person exists twice: they signed up on two numbers, or a migrated record meets an app
registration. Detection surfaces the suspicion; merge resolves it. **This is the single merge
implementation in the platform** — the legacy migration calls it rather than writing its own.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Duplicate suspicion | Record | Yes | Pair, score, matched attributes |
| 2 | Detection rules | Configuration | Yes | Identity numbers, phone, name and date of birth |
| 3 | Comparison view | Screen | Yes | Both records side by side, field by field |
| 4 | Merge | Action | Yes | Survivor chosen, field-level selection, mandatory reason |
| 5 | Reference re-pointing | Behaviour | Yes | Applications, credentials, placements, attendance follow the survivor |
| 6 | Merge record | Append-only | Yes | What was merged, by whom, and from where |
| 7 | Not-a-duplicate | Action | Yes | Suppresses the pair, with a reason |

### Flow

1. Detection raises suspicions on a schedule and on new registrations.
2. A reviewer compares and merges, choosing the survivor and the fields.
3. Every reference re-points to the survivor in one transaction.
4. The merge is recorded and is not silently reversible.

### Scenarios to test

- After a merge no reference points at the merged-away record.
- A merge is recorded with enough detail to explain it a year later.
- Marking a pair not-a-duplicate stops it resurfacing.
- Merging two candidates with credentials keeps every credential and its evidence.
- The migration path calls this implementation rather than its own.

## 3. Credential expiry tracking

**ClickUp item** — *link to be added*

**Screens** — `/verification/pendency` · `/candidates/:id`

### Scenarios to cover

Credentials expire. Across the whole base, expiry is visible ahead of time, the candidate is asked
for a renewal, and **a lapsed credential affects eligibility rather than sitting green forever**.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Expiry monitor | Job | Yes | Over every credential with a validity period |
| 2 | Lead-time configuration | Setting | Yes | How far ahead to warn |
| 3 | Renewal request | Trigger | Yes | To the candidate, through notifications |
| 4 | Status transition | Behaviour | Yes | Expired credentials move out of green |
| 5 | Eligibility effect | Behaviour | Yes | Matching and shift acceptance respect it |
| 6 | Expiry view | Screen | — | Expiring and expired, by category and base |

### Flow

1. The monitor finds credentials approaching expiry at the configured lead time.
2. Renewal requests go to the candidate; the case appears in pendency.
3. On expiry the credential leaves green and eligibility changes accordingly.

### Scenarios to test

- A credential expiring tomorrow is not still green the day after.
- An expired credential removes the candidate from shift discovery and ranking eligibility.
- A renewal re-verifies through the adapter layer and restores eligibility.
- The monitor is idempotent across runs.
