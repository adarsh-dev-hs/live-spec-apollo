## Purpose

> Introduction to the feature. **This is not the scope** — the scope is items 1 to 6 below.

Everything Apollo holds about a healthcare professional: who they are, which supply base they belong
to, the extra fields that differ by candidate category, their credentials with issuer and validity
period, and the verification team's work queue. Two structural decisions here are load-bearing and
are made in Phase 1 even though Phase 1 only exercises half of each: **one candidate record spans
both supply bases against one shared credential object**, not a duplicated record with a status flag;
and **the per-category attribute set has a single definition**, served to the app, the console,
demand and ranking, so the two sides cannot drift apart.

## Release in this phase

1. Candidate list and record.
2. Supply base membership, modelled as membership.
3. The category attribute set for the nurse category.
4. Document capture and extraction: Aadhaar, PAN and certificates from a scan.
5. The credential object.
6. The verification queue with pendency tracking.

## 1. Candidate list and record

**ClickUp item** — *link to be added*

**Screens** — `/candidates` · `/candidates/:id`

### Scenarios to cover

A recruiter opens a candidate and sees, in one place, who they are, what they are qualified to do,
what has been verified, what documents are held, and everything that has happened to them. The list
is the recruiter's working surface and uses the shared list engine.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Name, phone, email | Text | Yes | Phone is the identity established at app sign-up |
| 2 | Candidate category | Reference | Yes | Phase 1: **nurse** |
| 3 | Location — current and preferred | Reference | Yes | Supply location and placement preference |
| 4 | Experience | Years and history | Yes | |
| 5 | Qualifications | Repeating block | Yes | Degree, institution, year |
| 6 | Category attributes | Attribute set | Per the set | From item 3 |
| 7 | Supply base membership | Panel | Yes | From item 2 |
| 8 | Credentials | Panel | — | From item 5, with status |
| 9 | Documents | Panel | — | Through the shared file store |
| 10 | Applications | Panel | — | What they have applied to and where it stands |
| 11 | Activity timeline | Shared component | — | From the audit trail |
| 12 | Candidate list | List screen | — | Shared list engine, with export |

### Flow

1. A candidate record is created by app sign-up, or by a recruiter creating one directly.
2. The record renders the panels above; each panel is owned by the item that builds it.
3. The list supports the recruiter's day: filter by category, location, experience and verification
   status.

### Scenarios to test

- A record created from the app and one created in the console are the same shape.
- The list export matches the current filter exactly.
- A candidate is never deleted; deactivation hides them from matching and keeps the history.
- Personal fields are redacted in logs and event payloads.

## 2. Supply base membership

**ClickUp item** — *link to be added* · **Delivers** `A2` (Phase 1 slice)

**Screens** — `/candidates/:id`

### Scenarios to cover

A candidate belongs to a supply base — the permanent pool, the shift pool, or **both** — and
membership is modelled as membership, **not as a status flag on the candidate**. Phase 1 populates
Base A only; the model still expresses both, because retrofitting a flag into a membership later
means rewriting matching, engagement and the candidate record together.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Membership record | Row per base | Yes | Candidate, base, joined date, status |
| 2 | Base A — permanent pool | Reference | Yes | Populated in Phase 1 |
| 3 | Base B — shift pool | Reference | Yes | **Modelled, not populated in Phase 1** |
| 4 | Shared credential link | Behaviour | Yes | One credential set serves every membership |
| 5 | Membership history | Append-only | Yes | Joining and leaving a base is a recorded event |

### Flow

1. A candidate signing up in Phase 1 is given a Base A membership.
2. Matching queries membership rather than a flag on the candidate.
3. Credentials are attached to the candidate, not to the membership, so one verification serves any
   base the candidate belongs to.

### Scenarios to test

- The schema permits a candidate to hold two memberships, and matching queries by membership.
- A credential verified once is visible from either membership without duplication.
- Membership changes are recorded and readable in order.
- No code path reads a base as a boolean column on the candidate.

## 3. The category attribute set — nurse

**ClickUp item** — *link to be added* · **Delivers** `A9` (Phase 1 slice)

**Screens** — `/admin/settings` · rendered inside `/candidates/:id`, `/requisitions/new`,
`/app/profile`

### Scenarios to cover

Specialty and acuity, and the other fields that differ by candidate category, defined **once** and
served to every consumer: the candidate record, the requisition form, the candidate app and ranking.
Phase 1 defines the set for the nurse category.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Attribute definition | Reference data | Yes | Key, label, data type, picker source, mandatory flag |
| 2 | Attribute set per category | Reference data | Yes | Which attributes apply to which category |
| 3 | Specialty | Attribute | Yes | Nurse specialties, from reference data |
| 4 | Acuity | Attribute | Yes | Care-intensity band |
| 5 | Both-sided rendering | Behaviour | Yes | The same set renders on candidate **and** requisition |
| 6 | Versioning | Behaviour | Yes | A change does not rewrite records created under the old set |

### Flow

1. An administrator defines the nurse attribute set in settings.
2. Every consumer requests the set for a category and renders what it is given — no consumer holds
   its own copy.
3. Ranking reads candidate attributes against requisition attributes using the same definitions.
4. Adding an attribute makes it available on all four surfaces without a code change.

### Scenarios to test

- Adding an attribute appears on candidate, requisition and app without a deploy.
- A mandatory attribute blocks completion on both the candidate side and the requisition side.
- A record created before an attribute existed still renders.
- Ranking reads the same definition the form wrote, verified by test.

<Callout title="Open item carried into design">
Requisition-side ownership of the specialty and acuity taxonomy is an open item in the SOW. Phase 1
resolves it in design, before the form and the attribute set are built — not after.
</Callout>

## 4. Document capture and extraction — Aadhaar, PAN, certificates

**ClickUp item** — *link to be added* · **Delivers** `D4` (Phase 1 slice)

**Screens** — `/candidates/:id` · `/verification`

### Scenarios to cover

Identity and certificate documents are captured **by scan** and read, and what is read is reviewed by
a person against the image before it is trusted. Which attributes are verified is configurable by
candidate category, by destination taken from the demand, and by the regulatory requirements of the
placement and supply locations. Corrections a reviewer makes are retained, so extraction accuracy can
be measured rather than guessed at.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Document type | Reference | Yes | Aadhaar, PAN, registration certificate, qualification certificate |
| 2 | Scan upload | Shared upload control | Yes | From the console or from the app |
| 3 | Extracted fields | Per document type | Yes | Number, name, date of birth, issuer, dates |
| 4 | Confidence per field | System | Yes | Drives what a reviewer is shown first |
| 5 | Review pane | Component | Yes | Extracted value beside the source image |
| 6 | Correction | Action | Yes | The corrected value is stored **with the original** |
| 7 | Verification attribute rules | Configuration | Yes | By category, destination and regulatory requirement |
| 8 | Consent gate | Behaviour | Yes | No extraction or check without the recorded consent |

### Flow

1. A document is uploaded from the app or the console into the shared file store.
2. Extraction runs and produces field values with confidences.
3. A reviewer sees the extracted values beside the image and accepts or corrects them.
4. The accepted values populate the credential in item 5 and the candidate record.
5. Both the original extraction and the correction are retained.

### Scenarios to test

- A low-confidence field is surfaced for review rather than silently accepted.
- A correction is stored alongside the original extraction, and both are readable.
- An unreadable scan produces a clear failure and a re-upload request, not an empty credential.
- No extraction runs without the recorded consent.
- The attribute rules change what is required when the category or the destination changes.

## 5. The credential object

**ClickUp item** — *link to be added* · **Delivers** `D16` (Phase 1 slice)

**Screens** — `/candidates/:id`

### Scenarios to cover

A credential is a first-class object from Phase 1: **issuer, validity period and verification
method**, shared across supply bases. The Phase 1 slice populates it from document review; the object
is built to its final shape because retrofitting issuer and validity later costs more than building
them once.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Credential type | Reference | Yes | Identity, registration, qualification |
| 2 | Issuer | Reference | Yes | The council or authority |
| 3 | Identifier | Text | Yes | Registration or document number |
| 4 | Valid from / valid to | Dates | Yes where applicable | |
| 5 | Verification method | Reference | Yes | Phase 1: document plus reviewer |
| 6 | Verification status | Traffic light | Yes | Green, amber, red — the shared response shape |
| 7 | Evidence link | Reference | Yes | The document and the review that produced the status |
| 8 | Ownership | Behaviour | Yes | Attached to the candidate, shared across memberships |

### Flow

1. A reviewed document produces or updates a credential.
2. The credential carries its method and its evidence, so how it was verified is never ambiguous.
3. Matching reads credential status; it does not read documents.

### Scenarios to test

- A credential without an issuer or a method cannot be saved.
- The status is one of exactly three values, whatever produced it.
- The evidence link resolves to the document and the review that produced the status.
- One credential is visible from every membership the candidate holds.

## 6. The verification queue with pendency tracking

**ClickUp item** — *link to be added* · **Delivers** `D16` (Phase 1 slice)

**Screens** — `/verification` · `/verification/pendency`

### Scenarios to cover

The verification team's working surface: what is waiting, what it is waiting **on**, and for how
long. Pendency is tracked **by cause**, because *waiting for the candidate to re-upload* and *waiting
for a council* are different problems with different owners.

### Elements

| # | Element | Type | Mandatory | Notes |
|---|---|---|---|---|
| 1 | Queue list | List screen | — | Candidate, category, document, age, cause |
| 2 | Verification case | Record | Yes | One case per credential being established |
| 3 | Pendency cause | Reference | Yes | Awaiting candidate, awaiting issuer, awaiting review, failed |
| 4 | Case detail | Screen | — | The document, the extraction, the review actions |
| 5 | Actions | Buttons | — | Accept, correct, reject with reason, request re-upload |
| 6 | Pendency view | Screen | — | Aged by cause, so a queue can be worked by cause |
| 7 | Assignment | Reference | No | The reviewer working a case |

### Flow

1. An uploaded document opens a verification case with a cause.
2. A reviewer works the case: accepting produces the credential, rejecting records a reason, a
   re-upload request messages the candidate through the sending path.
3. The cause changes as the case moves, and the pendency view ages by cause.
4. Closing a case writes its event and its audit entry.

### Scenarios to test

- A case shows the correct cause at each step, and its age is measured from the cause change.
- A rejection requires a reason and notifies the candidate.
- A re-upload request produces exactly one message and re-opens the case on receipt.
- Two reviewers cannot both complete the same case.
- The pendency view totals reconcile with the queue list.
