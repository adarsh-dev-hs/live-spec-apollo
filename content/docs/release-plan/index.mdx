This section reproduces it and then specifies it: the whole deliverable list, what falls in each of
the three parts, and — for each part — a **phase engineering spec** broken down feature by feature.

## 3. How each part is specified

Each part has **its own spec**, and each spec contains **only that part**. A part spec is one index
page plus one page per feature, and every feature page is written to the same template:

| Section | What it carries |
|---|---|
| **Header block** | The phase, the deliverables the feature draws on in *this* phase, the module reference in the engineering documentation, the screens, and the ClickUp item |
| **Purpose** | An introduction to the feature — **what it is for, not what is in scope** |
| **Release in this phase** | A numbered list of the buildable items released in this phase, kept as singular as possible |
| **One section per numbered item** | ClickUp item · Screens · Scenarios to cover · Elements · Flow · Scenarios to test |
| **Not in this phase** | A pointer table only — the capability a reader will look for, and the part page that specifies it |

**A numbered item is the unit of estimation, tracking and testing.** One item, one ClickUp card, one
set of test scenarios.

## 4. The rule that keeps the three specs separate

A deliverable split across parts appears in more than one part spec — but **each part page describes
only the slice released in that part**. The Part 1 page for a feature does not describe the Part 2
work on it, and vice versa; where a reader would go looking, the page carries a pointer and nothing
more.

Twenty-five of the fifty-one deliverables are split this way. They are listed, with the slice each
part takes, in the [deliverable matrix](/docs/release-plan/scope/matrix).

**Building a deliverable to completion when its part only asked for a slice is the most expensive
mistake available on this engagement.** Read the part spec before deciding how much of a feature to
build.

## 5. The rule that decides what goes in Part 1

Part 1 takes **one client, one candidate category, one line of business, one care setting** from
sign-in to a raised invoice. Anything on that line is in. Anything that widens it — a second
channel, a second category, home healthcare, a client login — waits for Part 2. Anything that
deepens it — reporting, payroll, collections, migration — waits for Part 3.

That is why the twelve `F` prerequisites are all in Part 1 and nowhere else: they are the floor the
first line stands on, and there is no thinner version of them worth building.
