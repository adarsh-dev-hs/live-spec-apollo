The AI-native healthcare talent platform Hiresense is building for Apollo Knowledge Services: permanent
placement and contractual shift staffing for nurses, doctors and allied health professionals across
hospital and home healthcare settings, in India.

**71 specifications. 208 buildable items. 1,062 conditions. 96 open decisions. 6 months.**

---

## 1. What this is, and how it differs from the requirement doc

`requirement_doc/Apollo_Delivery_Plan_6Month_v0.4.html` is the commercial document: sixteen milestones,
208 items, effort, risk and open items, organised by **when work is sold and scheduled**.

This is the **engineering translation**, organised by **what gets built and deployed**.

| | Requirement doc | `docs/` |
|---|---|---|
| Organised by | Milestone (M0–M15) | Component (platform, module, integration) |
| Unit | A buildable item with an effort band | A spec that is one implementation session |
| Audience | Client PM, UX team, commercial review | Engineers, and Claude |
| Answers | What are we selling, when, for how much | What exists, what it does, what it depends on, how to know it works |

The two are reconciled item by item in [00-04](/docs/00-foundation/00-04-component-map) §6: all 208 items
map to exactly one component, and every component traces back to at least one item.

The commercial document itself is reproduced verbatim in [`06-source-plan/`](06-source-plan/) so both
sides of that reconciliation can be read without leaving this docs set. It is a **read-only copy** —
converted, never rewritten, and never the place to record a decision. Sections 1–5 remain the source of
truth; when they disagree with `06-source-plan/`, the disagreement is a decision to register in
[05-03](/docs/05-delivery/05-03-open-decisions), not an error to silently correct in either direction.

**Nothing here is invented scope.** Where a component exists that the source does not name, it is marked
**[engineering addition]** with a justification — there is exactly one, `02-10`. Where the source is
silent or contradictory, it is recorded as an open decision with an explicit working assumption carried
forward consistently, never filled in with a quiet guess.

| Objects | S3, SSE-KMS, versioned | |

Undecided pieces are carried as explicit assumptions, not silent choices — see
[05-03](/docs/05-delivery/05-03-open-decisions) §6.

## 4. The eleven-section convention

Every spec in `02-platform/` and `03-modules/` — and, adapted, in `04-integrations/` and `05-delivery/`
— has the same eleven sections, in the same order:

| § | Section | Contains |
|---|---|---|
| 1 | **Purpose** | One paragraph: what it is for |
| 2 | **Scope** | In scope · explicitly out of scope · explicitly not built |
| 3 | **Plan traceability** | Which requirement items this covers, with effort bands |
| 4 | **Dependencies** | What must exist first · what consumes this · external |
| 5 | **Data model** | Tables, columns, types, indexes |
| 6 | **State machines** | Every lifecycle, as a transition table |
| 7 | **API surface** | Endpoints, shapes, permissions, errors |
| 8 | **Events and jobs** | Emitted · subscribed · scheduled |
| 9 | **Frontend** | Screens, routes, components |
| 10 | **Acceptance criteria** | Testable statements, each traced to a requirement condition |
| 11 | **Open questions** | Decisions blocking this component, each with a working assumption |

**A section that does not apply says N/A. It is never omitted** — a reader must always be able to tell
"nothing here" from "not written yet".

Each spec opens with a metadata line:

```
**Package** `@apollo/name` · **Schema** `name` · **Plan** <refs> · **Effort** ~Npd · **Risk** <level> · **Build in** Phase N · **Release** Part N
```

**Build in** is the build phase ([05-01](/docs/05-delivery/05-01-build-sequence)) — what order the
component is built in. **Release** is the part ([07-00](/docs/07-phases/07-00-release-model)) — which
release it reaches a user in. A component built in one phase can be released across two or three parts,
so `Release` names every part the spec is sliced across.

## 6. Traceability scheme

Short, stable identifiers used everywhere.

| Prefix | Means | Source | Example |
|---|---|---|---|
| `M<n>` | Milestone | Verbatim from the plan | `M3` — Demand Intake & Allocation |
| `M<n>-I<k>` | **The engineering index** — one per buildable item | Verbatim | `M3-I12` — fulfilment board |
| `D<n>` / `A<n>` | The client's own deliverable number | Verbatim | `D2`, `A13` |
| `F<nn>` | A platform prerequisite Hiresense identified, assumed by the client's list but named nowhere in it | Verbatim | `F14` — event recording |
| `OI-A-<nn>` | Open decision from Part A | Verbatim | `OI-A-13` — guarantee period |
| `OI-M3-<nn>` | Open decision from the Part B M3 chapter | Verbatim | `OI-M3-02` — dedupe rule |
| `OI-HS-<nn>` | Open decision raised by Hiresense. `01`–`18` from the plan; **`19`–`65` raised while writing these specs** | Verbatim / new | `OI-HS-29` — will a hospital click the link? |
| `AS-<nn>` | A working assumption held until an open item closes. `01`–`06` from the plan; `07`–`24` adopted here | Verbatim / new | `AS-04` — M4 owns the attribute definition |
| `X<nn>` | An external dependency: an account, contract, registration or access | Verbatim | `X29` — client link recipients |
| `NN-KK` | A spec in these docs | New | `03-07` — matching and ranking |
| `Part <n>` | A release part | New | `Part 2` — All Threads Open |
| `F-P<n>-<k>` | One scoped functionality inside Part `n` | New | `F-P1-3` — vacancy management |
| `SOW-<ref>` | A readability prefix on the client's own deliverable ids, used in the part files' scope tables. `SOW-D1` and `D1` are the same thing | New | `SOW-D1`, `SOW-A13`, `SOW-F14` |
| `FLAG_*` / `P<n>_*` | A feature flag gating a part's functionality in the app | New | `P2_SHIFT_STAFFING` |

**Rules.**

- Every acceptance criterion in a spec's §10 names the requirement item or condition it satisfies.
- Every `OI-…` referenced in a spec exists in [05-03](/docs/05-delivery/05-03-open-decisions).
- Every `AS-…` is listed in [05-03](/docs/05-delivery/05-03-open-decisions) §6 with every spec it applies
  to — assumptions are applied in more than one place by design, and they move together.
- Every one of the plan's 208 items appears in exactly one component's §3, indexed in
  [00-04](/docs/00-foundation/00-04-component-map) §6, and in at least one release part, indexed in
  [07-04](/docs/07-phases/07-04-traceability) §3. Both are true at once: one component, one or more parts.
- Every `F-P<n>-<k>` names the specs it draws on and the slice of each it takes.
- Anything present here but absent from the source is marked **[engineering addition]** with a
  justification.

## 7. The eight things most likely to hurt

Pulled out of the specs because they decide the shape of the engagement.

1. **`02-11` must be live before `03-03` writes its first requisition.** Build the event spine after M3
   and the M9 reports cannot cover the earlier period at all. Not recoverable.
2. **There is no client login until Part 2, and no full portal until Part 3.** Every client interaction
   in Part 1 is a tokenised link (`02-14`), and both invoice paths run through it.
3. **There is no attendance route but the app.** No app, no attendance, no timesheet, no shift invoice.
4. **Permanent billing has no fallback.** No contract terms at trigger time means it does not run.
5. **Seven estimate blockers are open**, including one — `OI-A-13` — that changes scope rather than a
   number.
6. **Half the suppliers are unnamed.** Each is an unpriced integration and a failure mode nobody can
   test against.
7. **The back half is compressed.** Five of the ten build steps begin in months five and six, each
   needing the one before it, so they cannot be parallelised by adding people.
8. **A spec is not one release.** Twenty-seven of the thirty-five specs are sliced across two or three
   parts. Building a spec to completion when its part only asked for a slice is the most expensive
   mistake available here — see [07-00 §5](/docs/07-phases/07-00-release-model#5-the-thin-slice-principle).
