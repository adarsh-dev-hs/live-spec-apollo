## What this documentation is

The delivery plan is a **commercial and scope document**: milestones, effort bands, risk, open
decisions. It is organised by *when work is sold and scheduled*.

This documentation is the **engineering translation**: it is organised by *what gets built and
deployed*. Each spec below is a self-contained, independently implementable unit with its own
data model, API surface, jobs, screens and acceptance criteria.

**One spec = one implementation session.** Hand a single file to an engineer (or to Claude) and it
contains everything needed to build that component without reading the other 50 files — beyond the
shared standards in `01-standards/`, which are read once.

## Stack

| Layer | Choice |
|---|---|
| Backend | Node.js 22 LTS · TypeScript · **Express 5** (modular monolith + separate worker process) |
| Frontend | **React 19 + Vite** · TypeScript · TanStack Query · React Router · Tailwind |
| Database | **PostgreSQL 16** (Amazon RDS, ap-south-1) |
| Cache / queue | **Redis 7** (Amazon ElastiCache) · BullMQ |
| Object store | **Amazon S3** (ap-south-1, versioned, KMS-encrypted) |
| Hosting | **AWS ap-south-1 (Mumbai) only**, Apollo-owned account, ECS Fargate behind ALB |
| Mobile | React Native (candidate app) — consumes the same API, specified in `03-07` |

All personal data stays in `ap-south-1`. This is a DPDP requirement, not a preference.

## Conventions used in every spec

Each component spec in `02-platform/` and `03-modules/` uses the same eleven sections:

```
1.  Purpose            — one paragraph, what it is for
2.  Scope              — in scope / explicitly out of scope
3.  Plan traceability  — which M<n>-I<k> items this covers
4.  Dependencies       — what must exist first / what consumes this
5.  Data model         — tables, columns, indexes
6.  State machines     — every lifecycle, as a transition table
7.  API surface        — endpoints, request/response shape
8.  Events & jobs      — what it emits, what it subscribes to, scheduled work
9.  Frontend           — screens, routes, components
10. Acceptance criteria— testable statements, traced to the plan's conditions
11. Open questions     — decisions blocking this component, with working assumption
```

If a section does not apply (a service with no screens), it says **N/A** rather than being omitted —
so a reader can always tell the difference between "nothing here" and "not written yet".

## Traceability

Every requirement in this documentation traces back to the delivery plan:

- `M<n>-I<k>` — engineering index from the plan (e.g. `M3-I12` = Fulfilment board)
- `D<n>` / `A<n>` — Apollo's own deliverable number (e.g. `D2`, `A13`)
- `F<nn>` — Hiresense-identified platform prerequisite (e.g. `F03` = role & permission model)
- `OI-…` — open decision (e.g. `OI-A-13`), catalogued in `05-03-open-decisions.md`
- `AS-<nn>` — working assumption held until an open item closes

Nothing in these docs is invented scope. If a spec contains something the plan does not, it is
marked **[engineering addition]** with a one-line justification.
