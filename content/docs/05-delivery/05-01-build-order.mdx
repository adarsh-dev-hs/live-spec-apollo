## 2. Three orderings that are not negotiable

### P09 before every module that emits events

> This is the one prerequisite that cannot be added afterwards. — `M3-I31`

A module built before P09 emits nothing, and the reporting period before it shipped is permanently
unreportable. There is no backfill. **Build P09 first in phase 3, before B04 and B03.**

### P10 before B10, B11, B12 and B13

> Build the link mechanism early — M8 and M9 both wait on it. — plan sequencing note

It is the only way to reach a client in Release 1. If it is late, the client side of M7 and **both
invoice paths in M9** stop.

### B02 early, not late

> D13 contract terms are sequenced early, not late, because M9 cannot invoice without them.

There is no fallback. Contracts in phase 2.

## 3. Two tracks in phases 2–5

The demand and supply sides touch different schemas and only meet at B09. Staff them separately.

```
        Phase 2         Phase 3          Phase 4          Phase 5
DEMAND  B01 clients ──▶ P09 events  ───▶ B03 intake ───┐
        B02 contracts   P07 messaging    (channels)    │
                        P08 inbound                     │
                        B04 requisitions                ├──▶ B09 matching
                                                        │
SUPPLY  B05 candidates ─────────────────▶ B06 creds ───┤
        B07 app (start!)                  B15 migration │
                                          ─────────────▶ B08 engagement
```

**B07 starts in month 2** despite being a phase-4 component — app store enrolment and first review are
calendar time (`04-01 §6`), and the app is on the revenue critical path for shift invoicing.

## 4. Within-module order

Where a spec is large, build it in this order:

| Module | Order |
|---|---|
| **B03 intake** (84pd) | Pipeline consumption → requisition creation from a clean payload → HRMS → email → WhatsApp text → spreadsheet → voice notes. Each channel is independently valuable; the two hardest are also the two blocked on unknown counts. |
| **B04 requisitions** (70pd) | Object + state machine + **age clock** → status transitions → record view → fulfilment board → shift templates → allocation |
| **B08 engagement** (107.5pd) | **The loop end-to-end on one channel first** (app → response → reset → next selection), then WhatsApp, then voice. Four channels before the loop closes gives four half-features. |
| **B09 matching** (72pd) | **Rationale first**, then the score around it. Then weight sets, then the simulator, then shortlists. |
| **B13 billing** (41pd) | **`billing_trigger.evidence` first**, then the permanent path, then the shift path, then export |
| **B16 portal** (44pd) | **Scoping mechanism and its adversarial test suite first**, then one read-only screen, then everything else |

## 5. Phase gates

A phase does not close until every item passes. From `00-05 §7`, restated as a checklist:

- [ ] Every acceptance criterion in each component spec passes as an automated test
- [ ] Migrations run forward on empty **and** on a restored copy of the previous environment
- [ ] Every state transition emits its domain event, and the event is in `event_store`
- [ ] **`pnpm events:reproject` rebuilds every projection from sequence 0**
- [ ] Every mutating action writes an audit entry with actor and before/after
- [ ] Every list screen uses P06; every external call goes through P12 with a fake
- [ ] Every screen has empty, loading, error, no-permission and partial-failure states
- [ ] RBAC verified by calling each mutating endpoint as the wrong role
- [ ] Runbook written for each new failure mode
- [ ] Open items touched by the phase re-checked against `05-03`

## 6. The end-to-end test that defines "working"

Phase 6 is not complete until this passes as an automated E2E flow (`01-08 §3`, flows 23–27):

```
Client emails a vacancy
  → requisition created, incomplete, chased on email, completed
  → ranked shortlist generated with rationale
  → shortlist link sent over WhatsApp; client opens it with no password and accepts
  → interview proposed, held, structured feedback captured
  → selection decision with a structured rejection reason for the others
      → the reason reaches ranking
  → offer generated, sent over WhatsApp, e-signed, mapped to the contract version
  → joining confirmed; the 90-day clock starts
  → day 0/7/30/60 check-ins fire on both sides
  → day-90 link sent; client answers "yes, still employed"
  → RetentionRecord written, immutable, attributed to a named person
  → contract terms resolved AS AT that moment and frozen
  → PERMANENT INVOICE RAISED with the evidence attached
```

And in parallel:

```
Shift demand line → candidate accepts in the app → checks in offline → syncs
  → attendance recorded at the candidate's timestamp
  → timesheet built, priced at the contract version in force
  → timesheet link sent; client does not respond
  → deemed window expires → timesheet deemed approved
  → SHIFT INVOICE RAISED, marked as deemed
```

Plus the negative case: **a day-30 or day-60 answer creates no billing trigger.**

## 7. Parallelisation

| Phase | Parallel streams | Notes |
|---|---|---|
| 0 | 3 | Infra · design system · adapter framework |
| 1 | 2 | iam+audit+config · files+list |
| 2 | 2 | clients+contracts · CPAL profiling |
| 3–4 | **2 tracks** | Demand (P09→P07→P08→B04→B03) ‖ Supply (B05→B06→B07→B15) |
| 5 | 1→2 | B08 alone, then B09 joins once inputs exist |
| 6 | 2 | P10→B10→B11 ‖ B12, converging on B13 |
| 7 | **4** | analytics ‖ portal ‖ (approvals→onboarding→workforce→payroll) ‖ collections |

**Phase 7 has the most parallelism and the least slack** — five build steps start in months 5–6, each
needing the one before it. Adding people does not fix a chain (`00-05 §3`).

## 9. If the schedule compresses

Cut in this order — decided now so it is not decided under pressure in month five (`00-05 §6`):

**B20 → B16 → B21 → B18 → B19 → B17**

**Never cut:** anything on the critical path
(`P01 → P03 → B01 → B02 → B04 → B05 → B06 → B09 → P10 → B10 → B11 → B13`), **P09** (cannot be
backfilled), or **P02** (the day-90 trigger is indefensible without it).

Note that cutting B19 payroll *"puts a hard ceiling on how many shift workers Apollo can take on"*
(`OI-A-16`) — it is the cheapest cut technically and the most expensive commercially.
