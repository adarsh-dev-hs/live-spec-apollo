How to take one spec from `docs/` to a merged pull request. Follow this and a spec becomes working
software without a second conversation.

## 1. Before you write code

**Read three things, in this order:**

1. The spec itself, end to end. **One spec is one implementation session** — it contains everything you
   need for that component beyond the shared standards.
2. `01-standards/` if you have not already. Read once, obeyed always.
3. Each dependency listed in the spec's **§4**, but only its **§7 API surface** — you need what it
   promises, not how it works.

Then answer three questions before opening an editor:

| Question | Where the answer is |
|---|---|
| Does everything in §4 "must exist first" actually exist? | `05-01`, and the code |
| Is any open question in §11 **blocking**, or does a working assumption cover it? | §11, and `05-03` |
| Which acceptance criteria in §10 are **negative tests** — things that must be proven not to happen? | §10, and `01-08` §3 |

If a dependency is missing, **stop and say so**. Building against a stub you invented is how two modules
end up with two different answers to the same question.

If an open question is blocking, **raise it in `05-03`** rather than picking an answer quietly. A
working assumption written down is fine; a working assumption in someone's head is not.

## 2. The order of work inside a component

Build outward from the invariants, not inward from the screen.

```
1. domain/         state machine + invariants, from §6. Pure. Unit-tested with no database.
2. migrations/     tables from §5, exactly as specified, additive-first.
3. repositories/   hand-written SQL, one method per query shape in §7. No business logic.
4. services/       §6 transitions + §8 events + audit, one transaction per method.
5. routes/         §7, thin. Validate → one service call → shape a response.
6. jobs/           §8 scheduled and queued work.
7. frontend/       §9 screens, all five states each.
8. tests/          §10, one named test per acceptance criterion.
```

Steps 1 and 2 first is not a style preference. The state machine in §6 is the thing another engineer
will rely on and the thing a defect will be traced back to.

## 3. Writing the code

Follow `01-02` (backend), `01-03` (frontend), `01-05` (database). Three things catch people out:

**Transactions.** The audit write and the event emit go **inside** the business transaction. The
`events.emit(tx, …)` signature requires `tx`, so this is a compile error rather than a review comment.

**Scope.** Every list query carries `scopeLocationIds` from the principal. It is not a filter parameter
and a caller cannot widen it. A new list endpoint without it fails the scope suite.

**No ORM.** Every query is hand-written and parameterised. A list endpoint issues **one** query — use
`LATERAL` + `jsonb_agg` for children. If you find yourself in a loop issuing queries, stop.

## 4. Tests

Every acceptance criterion in §10 gets a test **named after it**:

```ts
describe('M3-I15 hold, revise and close', () => {
  it('AC3 · placing a requisition on hold stops the aging clock', …)
  it('AC4 · closing without a reason is rejected and the requisition remains in its prior state', …)
})
```

CI diffs the spec's criteria against test names. **A criterion with no test fails the build.**

Pay particular attention to the criteria phrased as prohibitions — *"no automatic merge occurs
anywhere"*, *"no suggestion or optimisation of allocation occurs anywhere"*, *"day 30 and day 60 cannot
reach the billing trigger path"*. These are **negative tests** and they are the ones that protect scope.

## 5. Pull request

**Title:** `M3-I15 hold, revise and close` — the plan item, so the PR is traceable to the commercial
document without a lookup.

**Body:**

```markdown
Implements: 03-03 §… (M3-I15)
Spec: docs/03-modules/03-03-requisitions-and-allocation.md

## Acceptance criteria
- [x] AC38 hold stops the aging clock
- [x] AC39 release resumes from the held value, not zero
- [x] AC40 close without a reason is rejected
- [x] AC42 filled does not auto-close (negative test, OI-M3-12 pending)

## Deviations from the spec
None. / AC41 implemented as X because Y — spec updated in this PR.

## Query plans
EXPLAIN ANALYZE for the new board query (new index on demand.requisition(status, days_aged)).

## Open questions touched
OI-M3-12 — auto-close remains configurable and defaulted off.
```

**Rules:**

- One component per PR where possible; never one PR across two components' schemas.
- Migrations reviewed **first** and separately in your head — they are the part that cannot be rolled
  back.
- `EXPLAIN ANALYZE` in the body for any new query over a table expected past 100k rows. The migrated
  base volume is unknown (`OI-A-02`), so assume it is large.
- If the shipped behaviour differs from the spec, **update the spec in the same PR**. The docs are the
  source of truth; a doc that disagrees with the code is worse than no doc.

## 6. Definition of done

From `01-08` §7, restated because it is the checklist:

1. Every §10 criterion has a passing named test.
2. Every §6 state is reachable only from its declared predecessor, tested.
3. Every §8 event is emitted inside the business transaction, tested.
4. Every §7 endpoint has auth, permission, scope and error-shape tests.
5. Every §9 screen has loading, empty, error, no-permission and partial-failure states.
6. Migrations run forward on a copy of the previous release's schema.
7. New queries over a large table carry a query plan in the PR.
8. Any §11 question that turned out to be blocking is raised in `05-03`, not worked around.
9. `docs/` matches the code.

## 7. When the spec is wrong

It will be, somewhere. The spec was written from a commercial document, not from working code.

| Situation | Do |
|---|---|
| A field is missing or a type is wrong | Fix it in the spec **and** the code, in the same PR. No ceremony. |
| A state transition is impossible as written | Fix the spec, say so in the PR body, and check whether the same transition appears in another spec. |
| The requirement doc and the spec disagree | **The requirement doc wins.** Fix the spec and note it. |
| The spec adds something the requirement doc does not contain, unmarked | Raise it. Everything not in the source must be marked **[engineering addition]** with a justification. |
| An acceptance criterion cannot be satisfied without an open decision | Raise it in `05-03`. Do not choose an answer to unblock yourself. |

## 8. Gate weeks

Every three to four weeks a gate produces a **working demonstration**, not a document, with named
Apollo attendees (`00-05` §2). In a gate week:

- Freeze the branch two days before. A gate failing on a merge from the morning of the demonstration
  teaches nobody anything.
- Demonstrate against `uat` with anonymised data, not a local machine.
- Write down what was raised and what changed. That written record is a contractual expectation.
- **Feedback at a gate that concerns capability already inside the agreed scope completes the
  specification for that capability.** Feedback introducing new capability is a change. Say which, at
  the gate, out loud.
