**Package** `n/a` · **Schema** `n/a` · **Plan** all · **Risk** — · **Build in** Phase 0 · **Release** Parts 1–3

The dependency-ordered order of work, with a gate at the end of each phase.

**This file orders the build. It does not say what ships together** — that is the three-part release
model in [07-00](/docs/07-phases/07-00-release-model), and the two are reconciled in
[00-05 §8](/docs/00-foundation/00-05-delivery-roadmap#8-the-three-release-parts). A phase completes a
component; a part releases a capability, and **27 of the 35 specs below are sliced across two or three
parts**, so finishing a spec is not the same as finishing what the next release needs from it.

**There are no day counts or calendar dates in this file, deliberately.** Sequence and effort are
different questions and they get answered in different places: [00-05](/docs/00-foundation/00-05-delivery-roadmap)
holds the calendar and the milestone mapping, and [06-03](/docs/06-source-plan/06-03-timeline) holds the
client's own effort figures as they were quoted. This file answers only *what order*, *why that order*,
and *what must be true before the next phase starts*.

Every spec index used below is a link. The same indices appear on the component map
([00-04](/docs/00-foundation/00-04-component-map)), so a row here and a row there refer to the same thing.

the spec's §2 Scope disagree, the spec wins and this table is wrong — fix it here.

## 2. Phase 1 — Foundations

Nothing here has a prerequisite in the codebase. Two things start in parallel on day one:

design is finalised) and **[02-15](/docs/02-platform/02-15-environments-and-observability) environments**
(nothing can be built or tested without one).

**Gate G1:** a named recruiter signs in, sees only their permitted navigation, an administrator
adds a candidate category **as data**, and every action appears on the activity trail.

**Exit conditions:** four environments provisioned from one pipeline · a release promoted dev→prod
without hand-edited config · every list route carries the scope predicate · append-only grants proven
by test · the CPAL profiling figures delivered, or `OI-A-02` formally escalated.

depends on it ships.

## 10. If the schedule slips

The plan states it plainly: **any slip in the early phases lands entirely on Phases 6–7**, because that
is the only thing left to cut. The client's stated priority if the period cannot hold everything is
**three category modules on a thinner R2**, because the category dimension reaches into the adapters,
the weight model and the trial question sets, and the R2 remainder does not.

Cut in this order:

| Order to cut | Spec | Why it goes here |
|---|---|---|
| 1 | [03-20](/docs/03-modules/03-20-collections) collections | Nothing depends on it; chasing stays manual |
| 2 | [03-19](/docs/03-modules/03-19-timesheet-extensions) timesheet extensions | The thin-slice timesheet in [03-10](/docs/03-modules/03-10-attendance-and-timesheets) still bills |
| 3 | [03-18](/docs/03-modules/03-18-demand-prioritisation-and-approval) demand prioritisation | Prioritisation reverts to recruiter judgement |
| 4 | [03-14](/docs/03-modules/03-14-client-portal) client portal | The tokenised links already cover every client action |
| 5 | [03-17](/docs/03-modules/03-17-payroll) payroll | **Cut last despite being least ready** — until it exists payroll is manual, and that caps contractual volume (`OI-A-16`) |
