## 1. Purpose

The reconciliation between the client's 208 buildable items and the three release parts. Every item
appears here exactly once as a row, with the part it is released in and the scoped functionality that
carries it. Where an item is **split** across parts, every part it touches is named and the split is
stated in [§4](#4-split-items).

This file is the counterpart of [00-04 §6](/docs/00-foundation/00-04-component-map#6-requirement-item--component-index),
which maps the same 208 items to components. **Both are true at once**: an item belongs to exactly one
component and is released in one or more parts.

## 2. Scope

### In scope

- Item → part → functionality, for all 208 items, in plan order
- Functionality → items, the reverse index
- The split items, and what each part's share of them is
- What is deliberately absent from Part 1, and the reason in each case

### Explicitly out of scope

- Effort and calendar. See [06-03](/docs/06-source-plan/06-03-timeline) and
  [00-05](/docs/00-foundation/00-05-delivery-roadmap).
- Component ownership. See [00-04 §6](/docs/00-foundation/00-04-component-map#6-requirement-item--component-index).

### Explicitly not built

- A second numbering of the items. `M<n>-I<k>` is the plan's own index and is reproduced verbatim.

## 5. What is deliberately absent from Part 1

Read this before asking why something is missing from the first release. In each case the reason is the
[classification rule](/docs/07-phases/07-00-release-model#3-the-classification-rule), not an oversight.

| Absent from Part 1 | Where it lands | Why not Part 1 |
|---|---|---|
| Shift staffing, in every form | Part 2, `F-P2-1` | A second money path. Part 1's claim is that **one** path closes; carrying two doubles the surface without strengthening the claim |
| Every intake channel but the console | Part 2, `F-P2-2` | A vacancy typed by a recruiter produces the same requisition record. Intake changes how it arrives, not what it is |
| Engagement cadence and availability | Part 2, `F-P2-3` | Ranking in Part 1 uses availability that candidates confirm themselves in the app. Cadence improves the freshness; it is not needed to rank |
| Doctors and allied health | Part 2, `F-P2-4` | Category is reference data from Part 1, so this is **configuration**. Building it in Part 1 would prove nothing the nurse path does not |
| Home healthcare | Part 2, `F-P2-5` | Same argument, on care setting |
| The client portal | Part 2, `F-P2-6` | Every client action in Part 1 runs on a tokenised link, and the link is the thing that has to be **proven** |
| Associate onboarding | Part 2, `F-P2-7` | It exists to feed payroll, and there is no payroll until Part 3 |
| Legacy migration | Part 2 (profiling), Part 3 (the rest) | Nothing in Part 1 depends on historical data. Profiling is pulled into Part 2 only because it sizes the Part 3 work |
| Every report | Part 3, `F-P3-3` | **The events are being written from Part 1**, so nothing is lost by reporting late. This is the whole reason `M3-I31` is in Part 1 |
| Payroll, collections, workforce operations, prioritisation, leave and overtime | Part 3 | None is on the shortest path from a vacancy to an invoice |
| CV reading, document OCR, duplicate resolution, electronic signature, automated calls | Part 3, `F-P3-6` | Each **automates** something Part 1 does by hand. Doing it by hand first is what makes the automation specifiable |
