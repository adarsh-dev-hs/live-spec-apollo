## 1. Purpose

One admin area for every configurable list and waiting period in the platform. The plan counts at
least nine of them; without a shared home they become nine separate screens built by nine different
people at nine different times.

This is also the mechanism that stops business rules being hardcoded. A close reason, a follow-up
window, a required-field set — none of these should need a release to change.

---

## 2. Scope

**In**
- Key/value settings with **per-client override over platform default**
- Reference lists (`ListEntry`) with add, rename, reorder, deactivate
- Waiting-period settings with a platform default and per-client values
- One settings administration area
- `config.get()` / `config.list()` API with caching and invalidation
- Change history and audit

**Out**
- Client-specific business configuration that belongs to a client record — rate cards, contract
  terms → `03-02`. Those are commercial data, not settings.
- Feature flags → environment config (`01-09 §8`)
- Per-category attribute *definitions* → `03-05`. They are richer than a flat list.
- Message templates → `03-08`. They need channel, versioning and provider approval.

## 5. Data model

### 5.1 Settings

```sql
CREATE TABLE platform.setting_definition (
  key          text PRIMARY KEY,              -- 'demand.follow_up_window_days'
  module       text NOT NULL,
  name         text NOT NULL,
  description  text NOT NULL,
  value_type   setting_value_type_enum NOT NULL,  -- 'integer'|'decimal'|'boolean'|'string'|'duration'|'json'
  unit         text,                              -- 'days' | 'hours' | 'percent'
  is_client_overridable boolean NOT NULL DEFAULT false,
  validation   jsonb,                             -- {min,max} / allowed values
  default_value jsonb NOT NULL                    -- the PLATFORM default
);

CREATE TABLE platform.setting_value (
  id          uuid PRIMARY KEY,
  key         text NOT NULL REFERENCES platform.setting_definition(key),
  client_id   uuid,                               -- NULL = platform level
  value       jsonb NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  updated_by  uuid NOT NULL
);
CREATE UNIQUE INDEX uq_setting_value__key_client
  ON platform.setting_value (key, COALESCE(client_id, '00000000-0000-0000-0000-000000000000'::uuid));
```

**Resolution order:** client value → platform value → definition default. It never returns
`undefined`; if a definition exists, a value exists. This is what makes *"a client onboarded without
a configured window does not stall invoicing"* (`M2-I10`, `OI-A-05`) structurally true rather than a
thing someone remembers to check.

`setting_definition` rows are **seeded from code** on deploy. A module declares its settings; a
deploy-time sync inserts new ones and reports orphans. Nobody adds a setting through the UI, because
nothing would read it.

### 5.2 Reference lists

```sql
CREATE TABLE platform.list_definition (
  key          text PRIMARY KEY,              -- 'demand.close_reason'
  module       text NOT NULL,
  name         text NOT NULL,
  description  text NOT NULL,
  is_client_scoped boolean NOT NULL DEFAULT false,
  allows_custom_entries boolean NOT NULL DEFAULT true
);

CREATE TABLE platform.list_entry (
  id           uuid PRIMARY KEY,
  list_key     text NOT NULL REFERENCES platform.list_definition(key),
  client_id    uuid,                          -- NULL = platform level
  code         text NOT NULL,                 -- stable machine value, NEVER changes
  label        text NOT NULL,                 -- display, CAN change
  sort_order   integer NOT NULL DEFAULT 0,
  is_active    boolean NOT NULL DEFAULT true,
  metadata     jsonb,                         -- e.g. {"maps_to_outcome":"lost"} for rejection reasons
  retired_at   timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  created_by   uuid NOT NULL
);
CREATE UNIQUE INDEX uq_list_entry__key_code
  ON platform.list_entry (list_key, COALESCE(client_id,'00000000-0000-0000-0000-000000000000'::uuid), code);
```

**`code` is immutable, `label` is editable.** Records store the code. Renaming "Position withdrawn"
to "Withdrawn by client" must not orphan five hundred closed requisitions.

**Deactivation, never deletion.** *"A deactivated list entry stays readable on records that already
used it"* (`M0-I5`). Deactivated entries are excluded from pickers and included in reads.

### 5.3 Change history

Every write goes through `audit` (P02) with `entityType: 'setting' | 'list_entry'`, before and after.
No separate history table.

---

## 6. State machines

**ListEntry:** `active → retired`. Retired entries remain readable on existing records and are
excluded from new selections. Reactivation is permitted and audited.

**SettingValue:** no lifecycle — a value is either set at a level or not. Clearing a client override
falls back to the platform value.

## 7. API surface

### 7.1 Exported service — the primary interface

```ts
export const config = {
  /** Resolves client → platform → default. Throws if the key is undefined. */
  get<T>(key: string, opts?: { clientId?: string }): Promise<T>

  /** Batch, to avoid N+1 in hot paths like the cadence engine. */
  getMany(keys: string[], opts?): Promise<Record<string, unknown>>

  /** Active entries only, ordered. */
  list(listKey: string, opts?: { clientId?: string }): Promise<ListEntry[]>

  /** Includes retired — for rendering an old record's stored code. */
  listAll(listKey: string, opts?): Promise<ListEntry[]>

  /** Throws ValidationError if the code is not an ACTIVE entry. Use on every write. */
  assertListEntry(listKey: string, code: string, opts?): Promise<ListEntry>

  /** Resolves a stored code to a label, retired or not. Use on every read. */
  labelFor(listKey: string, code: string): Promise<string>
}
```

`assertListEntry` on write and `labelFor` on read is the pattern. It is what makes "reason from the
configured list is mandatory" enforceable without every module reimplementing the check.

### 7.2 HTTP — `/api/v1/settings` (permission `platform.setting.*`)

| Method | Path | Notes |
|---|---|---|
| GET | `/definitions` | All settings and lists, grouped by module — drives the settings index |
| GET | `/values?clientId=` | Resolved values with their source level shown |
| PUT | `/values/:key` | Set platform value |
| PUT | `/values/:key/clients/:clientId` | Set client override |
| DELETE | `/values/:key/clients/:clientId` | Clear override → falls back to platform |
| GET | `/lists/:listKey?clientId=&includeRetired=` | |
| POST | `/lists/:listKey/entries` | Add |
| PATCH | `/lists/:listKey/entries/:id` | Rename, reorder, metadata. **`code` is not patchable.** |
| POST | `/lists/:listKey/entries/:id/retire` · `/restore` | |
| PUT | `/lists/:listKey/order` | Reorder in bulk |

### 7.3 Public read for the frontend

`GET /api/v1/settings/lists/:listKey` is readable by any authenticated user with read access to the
owning module — a recruiter needs the close-reason list to close a requisition without holding
`platform.setting.write`.

## 8. Events and jobs

**Emits**

| Event | When | Consumed by |
|---|---|---|
| `platform.setting.changed` | Any value set or cleared | Cache invalidation across tasks |
| `platform.list_entry.changed` | Add, rename, retire, reorder | Cache invalidation |

**Subscribes:** nothing.

**Caching**

| | |
|---|---|
| Store | Redis, `cfg:setting:<key>:<clientId\|_>`, `cfg:list:<key>:<clientId\|_>` |
| TTL | 300s |
| Invalidation | On write, publish to a Redis channel; every task drops the key |
| Local | A short in-process LRU (5s) in front of Redis for hot keys like the cadence engine's |

**Jobs:** none. This component is synchronous.

## 9. Frontend — `/settings`

### Settings index (`M0-I5`)

`<DataTable/>` listing every configurable list and waiting period, grouped by module, showing name,
type, current platform value, and how many clients override it. Search by name.

This is the screen the plan's requirement rests on: *"Close reasons, hold reasons, rejection reasons
and category fields are all edited here, not in nine screens."*

### Edit list

Entries in order, with drag-to-reorder. Add, rename, retire, restore. Retired entries shown greyed
with a "used by N records" count so nobody retires something in active use without knowing.
Client-scoped lists get a client selector.

### Edit waiting period

Platform default, plus a table of per-client overrides with add/edit/clear. The platform default is
visually distinguished as the fallback, because that is exactly the value that stops invoicing
stalling for an unconfigured client.

### Change history

The `<ActivityPanel/>` from P02, filtered to this key.

## 11. The nine known settings

Named explicitly in `M0-I5`. Each has a definition, a platform default, and an owning module.

| # | Key | Type | Client override | Owner | Notes |
|---|---|---|---|---|---|
| 1 | `demand.close_reason` | list | No | `03-04` | Mandatory on close. **Taxonomy open (`OI-M3-11`).** |
| 2 | `demand.hold_reason` | list | No | `03-04` | Whether one is wanted is open (`OI-M3-11`) |
| 3 | `select.rejection_reason` | list | No | `03-10` | Shared with ranking feedback in `03-09` |
| 4 | `supply.required_fields.<category>` | json | No | `03-05` | Drives completeness scoring. **No doctors owner named (`OI-M3-07`).** |
| 5 | `engage.contact_schedule` | json | No | `03-08` | Per segment. Drives message volume — and therefore running cost (`OI-HS-05`). |
| 6 | `bill.retention_confirmation_window_days` | integer | **Yes** | `03-02` | **Default not supplied by Apollo (`OI-A-05`)** |
| 7 | `bill.timesheet_approval_window_days` | integer | **Yes** | `03-02` | **Default not supplied (`OI-A-05`)** |
| 8 | `demand.follow_up_window_days` | integer | **Yes** | `03-03` | Per client or platform-wide is open (`OI-M3-08`) |
