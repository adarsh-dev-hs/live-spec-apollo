## 5. Data model

**Redis only.** BullMQ owns its own key structure. No Postgres tables.

One exception by convention: anything that must survive a Redis loss lives in Postgres in the owning
module — the outbox (`02-09`), the message table (`02-07`), migration batches (`03-15`). **Redis is
never a system of record** (`00-02 §6`); losing it costs in-flight work, not business state.

---

## 6. State machines

**Job:** `waiting → active → completed` \| `→ failed → waiting (retry) → … → dead`.
Standard BullMQ. A job reaching `dead` lands in the DLQ, raises an alarm, and is never silently
dropped.

**Scheduler:** registered at boot, idempotent by key. Re-registering with a changed cron replaces the
old schedule rather than adding a second one — otherwise every deploy accumulates duplicate
repeatables, which is a classic way to double-send a cadence run.

## 7. API surface

### 7.1 Defining a queue

```ts
export const parseInboundQueue = defineQueue({
  name: 'intake.parse',
  payload: z.object({ inboundId: z.string().uuid() }),
  concurrency: 10,
  attempts: 3,
  backoff: { type: 'exponential', delay: 30_000 },
  /** Deterministic id → BullMQ dedupes. */
  jobId: (p) => `intake.parse:${p.inboundId}`,
})
```

### 7.2 Consuming

```ts
export const parseInboundConsumer = defineConsumer(parseInboundQueue, async ({ payload, job }) => {
  await job.updateProgress({ stage: 'parsing' })
  await IntakeService.parse(payload.inboundId)
})
```

Consumers receive **validated** payloads. A payload failing its schema fails fast and dead-letters
rather than throwing three layers in.

### 7.3 Enqueuing

```ts
await jobs.enqueue(parseInboundQueue, { inboundId }, { priority: 'normal', delay: 0 })
await jobs.enqueueBulk(sendQueue, recipients.map(r => ({ ... })))
```

Priority lanes: `high` (OTP, offers, links), `normal` (transactional), `bulk` (cadence). An OTP must
never queue behind 20,000 cadence messages (`02-07 §8`).

### 7.4 Scheduling

```ts
export const decaySchedule = defineSchedule({
  name: 'engagement.decay',
  cron: '0 * * * *',
  timezone: 'Asia/Kolkata',            // ALWAYS explicit — see §11
  handler: () => EngagementService.decayConfidence(),
  /** Revenue-critical: alarm if a run is missed, not only if one fails. */
  heartbeat: true,
})
```

`heartbeat: true` is set on the schedules whose failure mode is silent — `links.deem`,
`attendance.approval-deem`, `placements.retention-deem`, `engagement.cadence-select`. If those stop
running, invoices stop being raised and nobody notices until month end (`01-09 §10`).

### 7.5 Locks

```ts
await jobs.withLock('migration:batch', async () => { ... }, { ttl: 3600_000 })
```

Used where the plan requires it explicitly: *"a batch cannot be started twice concurrently"*
(`M1-I2`), one pay run at a time (`M13-I1`), one invoice per trigger (`03-13`).

### 7.6 Admin HTTP — `/api/v1/jobs` (permission `platform.job.manage`)

| Method | Path | Notes |
|---|---|---|
| GET | `/queues` | Depth, active, failed, DLQ per queue |
| GET | `/:jobId` | Status and progress — backs the 202 pattern in `01-04 §11` |
| GET | `/dead-letter` | Failed jobs with their error |
| POST | `/dead-letter/:id/replay` | Audited |
| POST | `/schedules/:name/trigger` | Fire now. Audited. Non-prod by default. |
| GET | `/schedules` | Registered schedules, cron, last run, next run |

## 8. Events and jobs

**Emits:** `platform.job.dead_lettered`, `platform.schedule.missed`.

**Jobs:** none of its own beyond a DLQ-depth reporter.

### Graceful shutdown

On `SIGTERM`: stop accepting new jobs, finish in-flight work up to a 60s grace period, close
connections. A deploy mid-cadence-run must not leave 5,000 messages half-sent — the remainder returns
to the queue and the next task picks it up, which works only because every consumer is idempotent.

## 9. Frontend

### Queue health — `/settings/platform/jobs`

Per queue: depth, active, completed today, failed today, DLQ depth. Per schedule: cron, timezone,
last successful run, next run, heartbeat status.

DLQ list with error message, payload, attempt count, and a replay action.

An admin-only screen. In `dev`/`qa`/`uat` the Bull Board UI is also exposed; in `prod` it is
read-only behind the same permission.

## 10. Acceptance criteria

| # | Criterion |
|---|---|
| 1 | Every queue declares a typed payload, validated on consume |
| 2 | Every job has a deterministic id; enqueuing the same work twice runs it once |
| 3 | Every consumer is idempotent and has a test that runs it twice with the same result |
| 4 | A permanently failing job lands in the DLQ, alarms, and is replayable — never silently dropped |
| 5 | Every schedule declares an explicit timezone |
| 6 | Re-registering a schedule with a changed cron replaces it rather than duplicating it |
| 7 | Revenue-critical schedules alarm on a **missed** run, not only on failure |
| 8 | `SIGTERM` completes in-flight jobs within the grace period and returns the rest to the queue |
| 9 | A long-running job reports observable progress while it runs |
| 10 | Priority lanes prevent bulk work delaying an OTP |
| 11 | Distributed locks prevent concurrent migration batches and concurrent pay runs |
| 12 | The worker starts with zero queues registered and fails loudly if a module declares a duplicate queue name |

## 11. Notes for the implementer

**Timezones are not a detail here.** Apollo operates on Indian business hours. A daily job at
`0 6 * * *` UTC fires at 11:30 IST, which is not "daily morning" to anyone using the system. Every
schedule declares `Asia/Kolkata` explicitly, and the linter rejects a `defineSchedule` without a
timezone.

**One worker process, all queues, in Release 1.** Splitting workers per queue is premature at this
scale. The design permits it later — `WORKER_QUEUES=messaging.*,engagement.*` selects a subset — but
do not start there.

**Never use `node-cron`, `setInterval`, or OS cron.** Three ECS tasks each running their own
`setInterval` sends the cadence three times. BullMQ repeatable jobs are cluster-safe; nothing else in
reach is.

**Payloads carry ids, never entities.** A job enqueued at 09:00 and run at 09:40 must read current
state. A serialised requisition in a payload is a stale snapshot that will eventually cause a bug
nobody can reproduce.
