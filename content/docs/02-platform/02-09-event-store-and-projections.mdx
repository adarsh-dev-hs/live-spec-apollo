## 1. Purpose

Every module writes an event as things happen, and the reports in M9 read those events later.

> **This is the one prerequisite that cannot be added afterwards.** — the delivery plan, `M3-I31`

> D28 stage-level conversion loss **cannot be computed retrospectively** without it. — `M3-I28`

Everything else in this documentation can be built late and retrofitted. This cannot. A module that
ships without emitting its events makes the entire period before that ship date permanently
unreportable, and no amount of later work recovers it.

---

## 2. Scope

**In**
- Transactional outbox: write an event in the caller's transaction
- Outbox relay: publish to subscribers and persist to the event store
- `event_store` — append-only, partitioned, 7-year retention
- Event registry: every event's name, schema and owner, validated on emit
- Subscriber runtime: registration, idempotency, retry, dead-lettering
- Projection framework: build reporting tables from events, rebuildable from zero
- Replay tooling

**Out**
- The reports themselves → `03-14`. This component provides the substrate; that one draws the charts.
- Audit trail → `02-02`. **Different purpose** — see `02-02 §11`.
- Requisition status transitions → `03-04` owns the table, but the projection reads it here
- Queue infrastructure → `02-13`

## 5. Data model

### 5.1 Outbox

```sql
CREATE TABLE platform.outbox (
  id             uuid PRIMARY KEY,
  event_name     text NOT NULL,
  aggregate_type text NOT NULL,
  aggregate_id   uuid NOT NULL,
  payload        jsonb NOT NULL,
  actor_type     actor_type_enum,
  actor_id       uuid,
  occurred_at    timestamptz NOT NULL DEFAULT now(),
  published_at   timestamptz
);
CREATE INDEX idx_outbox__unpublished
  ON platform.outbox (occurred_at) WHERE published_at IS NULL;
```

Rows are deleted after successful publish. The table stays small; the durable copy is `event_store`.

### 5.2 Event store

```sql
CREATE TABLE platform.event_store (
  id             uuid PRIMARY KEY,
  sequence       bigserial NOT NULL,
  event_name     text NOT NULL,
  event_version  integer NOT NULL DEFAULT 1,
  aggregate_type text NOT NULL,
  aggregate_id   uuid NOT NULL,
  payload        jsonb NOT NULL,
  actor_type     actor_type_enum,
  actor_id       uuid,
  occurred_at    timestamptz NOT NULL,
  recorded_at    timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (occurred_at);

CREATE INDEX idx_event_store__aggregate ON platform.event_store (aggregate_type, aggregate_id, sequence);
CREATE INDEX idx_event_store__name_time ON platform.event_store (event_name, occurred_at DESC);
CREATE INDEX idx_event_store__sequence  ON platform.event_store (sequence);

REVOKE UPDATE, DELETE ON platform.event_store FROM apollo_app;
```

Monthly partitions, created a year ahead by a scheduled job. Retention 7 years (`01-10 §6`), aligned
with the billing-record retention that `OI-HS-14` will settle.

### 5.3 Subscriber checkpoints

```sql
CREATE TABLE platform.subscriber_state (
  subscriber_name text PRIMARY KEY,
  last_sequence   bigint NOT NULL DEFAULT 0,
  updated_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE platform.subscriber_delivery (
  subscriber_name text NOT NULL,
  event_id        uuid NOT NULL,
  delivered_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (subscriber_name, event_id)
);
```

`subscriber_delivery` is the idempotency backstop: at-least-once delivery means a subscriber will see
the same event twice, and a primary-key conflict is a cheap way to make that harmless.

### 5.4 Projections

```sql
CREATE TABLE report.projection_state (
  projection_name text PRIMARY KEY,
  last_sequence   bigint NOT NULL DEFAULT 0,
  status          text NOT NULL DEFAULT 'live',   -- 'live'|'rebuilding'|'failed'
  rebuilt_at      timestamptz,
  updated_at      timestamptz NOT NULL DEFAULT now()
);
```

Projection tables themselves are defined in `03-14`. This component provides the framework, the
checkpointing and the replay.

## 6. State machines

**Outbox row:** `pending → published → deleted`. A row unpublished for more than 60 seconds raises
the outbox-lag alarm (`01-09 §10`).

**Projection:** `live → rebuilding → live` \| `→ failed`. A rebuilding projection serves the previous
table until the rebuild completes and swaps — reports do not go blank while a projection is rebuilt.

## 7. API surface

### 7.1 Emitting

```ts
// Inside the caller's transaction. Always.
await events.emit(tx, 'demand.requisition.closed', {
  requisitionId: req.id,
  clientId:      req.clientId,
  reasonCode:    reason.code,
  positionsUnfilled: req.positions - req.filled,
}, { actor })
```

| Rule | |
|---|---|
| Takes the transaction | An event for a rolled-back change asserts something that did not happen |
| Payload validated against the registered schema on emit | A malformed event fails the transaction, loudly, in development |
| Past tense, always | It already happened |
| IDs plus the few facts a subscriber needs | Not the whole entity |
| Additive versioning only | Never remove or repurpose a field |

### 7.2 Registry

```ts
export const events = defineEvents({
  'demand.requisition.closed': {
    version: 1,
    aggregate: 'requisition',
    schema: z.object({
      requisitionId: z.string().uuid(),
      clientId:      z.string().uuid(),
      reasonCode:    z.string(),
      positionsUnfilled: z.number().int().min(0),
    }),
  },
})
```

Registered per module in `src/events/index.ts`, collected at boot. **Emitting an unregistered event
throws.** The full cross-module catalogue is in `01-06 §4`.

### 7.3 Subscribing

```ts
export const onRequisitionClosed = defineSubscriber({
  event: 'demand.requisition.closed',
  name:  'matching.invalidate-ranked-set',   // unique; the idempotency key
  handler: async ({ payload, eventId }) => {
    await MatchingService.invalidateFor(payload.requisitionId)
  },
})
```

### 7.4 Projections

```ts
export const funnelProjection = defineProjection({
  name: 'report.funnel',
  events: [
    'demand.requisition.created',
    'match.shortlist.sent',
    'select.interview.completed',
    'select.decision.recorded',
    'select.offer.signed',
    'place.placement.created',
    'place.dropout.recorded',
  ],
  handler: async (tx, event) => { /* upsert into report.funnel_stage */ },
  /** Must be able to rebuild from sequence 0 with no other input. */
  rebuildable: true,
})
```

### 7.5 HTTP — `/api/v1/events` (permission `platform.event.read`)

| Method | Path | Notes |
|---|---|---|
| GET | `/` | Cursor-paginated. Filter by name, aggregate, actor, date. Admin/support tool. |
| GET | `/aggregate/:type/:id` | Every event for one record, in order |
| GET | `/projections` | Status and lag of each projection |
| POST | `/projections/:name/rebuild` | 202 + job. Admin only, audited. |

## 8. Events and jobs

**Emits:** `platform.projection.rebuilt`, `platform.event.dispatch_failed`.

**Jobs**

| Job | Queue | Concurrency | Notes |
|---|---|---|---|
| Outbox relay | `platform.outbox-relay` | **1** | Polls every 1s. Single consumer — ordering matters. Writes to `event_store` first, then publishes. |
| Dispatch | `platform.event-dispatch` | 10 | Fan-out to subscribers. Partitioned by `aggregate_id` where a subscriber needs ordering. |
| Project | `analytics.project` | 5 | Advances projections from their checkpoint |
| Rebuild | `analytics.rebuild` | 1 | Replays from sequence 0 into a shadow table, then swaps |
| Partition maintenance | `platform.partitions` (monthly) | 1 | Creates next year's partitions, drops expired ones |

**Order of operations in the relay is deliberate:** persist to `event_store`, *then* publish. If the
process dies between the two, the event is durable and redelivery is safe. The other order loses
events.

## 9. Frontend

Two admin screens under `/settings/platform`, plus the reports in `03-14` which are the real
consumers.

### Event explorer

`<DataTable/>` over `event_store`: name, aggregate, actor, occurred at, payload preview. Filter by
name, aggregate type/id, actor, date range. Row expands the payload.

Primarily a support tool: "what actually happened to requisition REQ-2026-00142 and in what order" is
a question that comes up constantly and is otherwise answered by reading logs.

### Projection health

Each projection: name, status, last sequence, **lag behind the event store**, last rebuild. Rebuild
action, admin-only, with a confirmation stating that the report will serve stale data during the
rebuild.

## 10. Acceptance criteria

| # | Criterion | Source |
|---|---|---|
| 1 | Every module writes an event as things happen, and M9 reports read those events later | `M3-I31` |
| 2 | **Events must be written as work happens or the M9 reports cannot cover the earlier period** | `M3-I31` |
| 3 | An event emitted inside a transaction that rolls back is never published | §7.1 |
| 4 | An event emitted in a committed transaction is always eventually published, even if the process dies | §8 |
| 5 | `event_store` rejects `UPDATE` and `DELETE` at the database level | §5.2 |
| 6 | Emitting an unregistered event, or one failing its schema, throws | §7.2 |
| 7 | A subscriber receiving the same event twice produces the same result once | §5.3 |
| 8 | A failing subscriber retries, then dead-letters and alarms — never silently drops | `01-06 §5` |
| 9 | **Every projection can be rebuilt from `event_store` alone, from sequence 0** | §7.4 — CI gate |
| 10 | Stage-level conversion loss is computable for any historical period since go-live | `M3-I28` |
| 11 | Outbox lag over 60 seconds raises an alarm | `01-09 §10` |
| 12 | A projection rebuild does not blank the reports while it runs | §6 |

**Criterion 9 is a CI gate, not a manual check.** `pnpm events:reproject` runs against the seed
dataset on every PR. If projections cannot be rebuilt from events alone, the events are incomplete —
and that is exactly the failure the plan warns cannot be fixed later.

## 12. Notes for the implementer

**Build this first in phase 3, before intake and requisitions.** Not because it is hard, but because
every module built after it will emit events as a matter of course, and every module built before it
will need retrofitting.

**Events are for reporting and reaction — they are not the write model.** Current state lives in
normal tables. Do not reconstruct a requisition by replaying its events; read the row.

**Resist the temptation to emit "changed" events with a diff.** `demand.requisition.updated` with a
patch object is useless to a subscriber and useless to a report. Emit what happened —
`demand.requisition.held`, `demand.requisition.allocated`, `demand.requisition.revised` — because
that is the question a report will ask.

**The `01-06 §4` catalogue is the contract.** When you implement a module, its spec lists the events
it must emit. Those events are what a later module or report will depend on, so an unimplemented one
is a silent dependency failure that surfaces months later in phase 7.
