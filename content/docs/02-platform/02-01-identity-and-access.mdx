## 1. Purpose

How anyone gets into the platform and what they may reach once inside. The client's deliverable list
asks for "role-based access control" as a phrase but never says how anyone signs in, and asks for a
requisition owner from "the Apollo internal user list" without anything creating that list. This
component builds both, plus the permission and data-scope machinery every other module depends on.

---

## 2. Scope

**In**
- Apollo staff sign-in, session, password reset, lockout
- Apollo user management: create, edit, role assignment, site assignment, deactivate, bulk import
- Role and permission model, permission checking middleware, data-scope resolver
- Console frame: nav filtered by permission, header, user menu, session handling (`M1-I1`)
- Candidate phone + OTP authentication (`M4-I21`) — separate identity, same package

**Out**
- Client portal login → `03-16` (M10). The `ClientUser` table is created there, not here.
- Client link tokens → `02-10`. Links need no account.
- Editing a role's permission set on screen — held in configuration (`M0-I3`, stated)
- SSO / SAML / Active Directory — not asked for; note as a likely M2-phase request

## 5. Data model

### 5.1 Users and sessions

```sql
CREATE TABLE platform.app_user (
  id             uuid PRIMARY KEY,
  email          citext NOT NULL UNIQUE,
  full_name      text NOT NULL,
  password_hash  text,                          -- NULL until activation
  status         app_user_status_enum NOT NULL DEFAULT 'invited',
  last_login_at  timestamptz,
  failed_attempts integer NOT NULL DEFAULT 0,
  locked_until   timestamptz,
  is_active      boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  created_by uuid, updated_by uuid,
  version    integer NOT NULL DEFAULT 1
);
-- 'invited' | 'active' | 'deactivated'

CREATE TABLE platform.password_reset (
  id          uuid PRIMARY KEY,
  user_id     uuid NOT NULL REFERENCES platform.app_user(id),
  token_hash  text NOT NULL,
  expires_at  timestamptz NOT NULL,
  used_at     timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

Sessions live in **Redis**, not Postgres: `session:<hash>` → `{ userId, createdAt, lastSeenAt, ip, userAgent }`,
TTL = idle timeout, refreshed on use, with an absolute cap.

### 5.2 Roles, permissions, sites

```sql
CREATE TABLE platform.role (
  id           uuid PRIMARY KEY,
  key          text NOT NULL UNIQUE,            -- 'recruiter'
  name         text NOT NULL,
  description  text,
  scope_kind   scope_kind_enum NOT NULL,        -- 'all' | 'sites' | 'client'
  is_system    boolean NOT NULL DEFAULT true    -- system roles are config-defined
);

CREATE TABLE platform.permission (
  key          text PRIMARY KEY,                -- 'demand.requisition.close'
  module       text NOT NULL,
  resource     text NOT NULL,
  action       text NOT NULL,
  description  text NOT NULL
);

CREATE TABLE platform.role_permission (
  role_id        uuid NOT NULL REFERENCES platform.role(id),
  permission_key text NOT NULL REFERENCES platform.permission(key),
  PRIMARY KEY (role_id, permission_key)
);

CREATE TABLE platform.user_role (
  user_id  uuid NOT NULL REFERENCES platform.app_user(id),
  role_id  uuid NOT NULL REFERENCES platform.role(id),
  PRIMARY KEY (user_id, role_id)
);

CREATE TABLE platform.user_site (
  user_id     uuid NOT NULL REFERENCES platform.app_user(id),
  location_id uuid NOT NULL,                    -- clients.location — ID only, no FK across schemas
  PRIMARY KEY (user_id, location_id)
);
```

`permission` and `role_permission` are **seeded from configuration** on deploy, not edited at
runtime. Each module declares its permissions in `permissions.ts`; a migration-time sync inserts any
new ones and reports orphans.

### 5.3 Candidate authentication

```sql
CREATE TABLE platform.candidate_auth (
  candidate_id  uuid PRIMARY KEY,               -- supply.candidate — ID only
  phone_e164    text NOT NULL UNIQUE,
  is_locked     boolean NOT NULL DEFAULT false,
  last_login_at timestamptz
);

CREATE TABLE platform.refresh_token (
  id           uuid PRIMARY KEY,
  candidate_id uuid NOT NULL,
  family_id    uuid NOT NULL,                   -- rotation family, for reuse detection
  token_hash   text NOT NULL,
  device_label text,
  expires_at   timestamptz NOT NULL,
  used_at      timestamptz,
  revoked_at   timestamptz
);
CREATE INDEX idx_refresh_token__family ON platform.refresh_token (family_id);
```

OTPs live in Redis only: `otp:<phone>` → `{ hash, attempts }`, 5-minute TTL, single use.

## 6. State machines

**AppUser**

| From | To | Trigger | Rules |
|---|---|---|---|
| — | `invited` | Admin creates user | Invitation email sent; no password yet |
| `invited` | `active` | User sets password from invite link | Link single-use, 7-day expiry |
| `active` | `deactivated` | Admin deactivates | Cannot sign in; **all sessions revoked immediately**; stays visible on records they created |
| `deactivated` | `active` | Admin reactivates | New password required |
| `invited` | `deactivated` | Admin cancels invite | |

**PasswordReset:** `issued → used` \| `issued → expired`. Single use. Using it revokes all sessions.

**Session:** `created → active → expired` (idle or absolute) \| `→ revoked` (logout, deactivation, password change).

## 7. API surface

### 7.1 Apollo authentication — `/api/v1/auth`

| Method | Path | Notes |
|---|---|---|
| POST | `/login` | Email + password → session cookie. Rate limited 5/15min per account and per IP. |
| POST | `/logout` | Revokes session |
| GET | `/me` | Current user, roles, **resolved permission set**, scope |
| POST | `/forgot-password` | Always returns 204, whether or not the email exists |
| POST | `/reset-password` | Token + new password. Revokes all sessions. |
| POST | `/accept-invite` | Token + password → `active` |

### 7.2 User management — `/api/v1/users` (perm `platform.user.*`)

| Method | Path | Notes |
|---|---|---|
| GET | `/` | Paginated, filter by role, site, status. Uses `<DataTable/>`. |
| POST | `/` | Create + send invite |
| GET | `/:id` · PATCH | ETag-guarded |
| POST | `/:id/deactivate` · `/:id/reactivate` | |
| PUT | `/:id/roles` · `/:id/sites` | |
| POST | `/import` | CSV. **202 + job.** Reports row-level errors by row number and still loads valid rows. |
| GET | `/lookup?q=&role=` | Capped, searchable. Used by "requisition owner" pickers — **active users only**. |

### 7.3 Roles — `/api/v1/roles` (perm `platform.role.read`)

| Method | Path | Notes |
|---|---|---|
| GET | `/` | Roles and what each reaches — **read only** (`M0-I3`) |
| GET | `/:key/permissions` | The permission set, grouped by module |

### 7.4 Candidate authentication — `/api/v1/candidate-auth`

| Method | Path | Notes |
|---|---|---|
| POST | `/request-otp` | Phone → OTP by SMS/WhatsApp. 3/hour per phone, 10/hour per IP. |
| POST | `/verify-otp` | → access JWT (15 min) + refresh token (30 days) |
| POST | `/refresh` | **Rotating.** Reuse of a used token revokes the whole family and logs a security event. |
| POST | `/logout` | Revokes this device's family |

### 7.5 Exported service interface

```ts
export const IamService = {
  getUser(id): Promise<User | null>
  getUsers(ids): Promise<User[]>                       // batch — avoids N+1 in composed responses
  listActiveUsers(filter): Promise<User[]>
  userHasPermission(userId, key): Promise<boolean>
  resolveScope(userId): Promise<Scope>
  assertRole(userId, roleKey): Promise<void>           // 'a recruiter allocated must hold a recruiter role'
}
```

### 7.6 Middleware exported to every module

```ts
requireAuth()                              // → 401
requirePermission('demand.requisition.close')  // → 403
requireCandidate()                         // JWT
applyScope(query, actor.scope)             // row-level, used inside repositories
```

## 8. Events and jobs

**Emits**

| Event | When |
|---|---|
| `platform.user.invited` / `.activated` / `.deactivated` | Status change |
| `platform.user.roles_changed` / `.sites_changed` | Assignment change — **invalidates the permission cache** |
| `platform.auth.login_failed` / `.locked_out` | Security signal |
| `platform.candidate.authenticated` | First login on a device |
| `platform.security.token_reuse_detected` | Refresh token replay — alarms |

**Subscribes:** none. IAM is a leaf dependency by design.

**Jobs**

| Job | Cadence |
|---|---|
| `iam.import-users` | On demand, from CSV upload |
| `iam.expire-invites` | Daily — invites older than 7 days |
| `iam.prune-refresh-tokens` | Daily |

**Permission cache:** Redis, key `perms:<userId>`, TTL 60s, **explicitly invalidated** on role or site
change. This is what makes "removing a permission takes effect on the user's next request, not their
next login" true (`M0-I3`).

## 9. Frontend

### 9.1 Sign in — `apps/ops`, unauthenticated routes

| Screen | Elements |
|---|---|
| Sign in | Email, password, submit, forgot-password link. Generic error on failure — never "no such user". |
| Forgot password | Email, submit. Always shows the same confirmation. |
| Set new password | New password twice, strength meter, submit |
| Accept invite | Same, from the invite link |
| Locked | Plain explanation and who to contact |

### 9.2 Users — `/settings/users`

| Screen | Elements |
|---|---|
| User list | `<DataTable/>`: name, email, role(s), site(s), status, last login. Filter by role/site/status. Search by name or email. |
| User form | Name, email, roles (multi), sites (multi), save, deactivate |
| Bulk import | Upload, preview, **per-row error report**, "load valid rows anyway" |

### 9.3 Roles — `/settings/roles`

Read-only list of roles; opening one shows its permissions grouped by module, and which users hold
it. A banner states that permission sets are configuration-managed.

### 9.4 Console frame (`M1-I1`)

Left nav generated from the permission set — a user sees only entries their role permits. Header with
global search and user menu. Session expiry shows an **in-place re-authentication dialog** and
resumes the pending request; it does not navigate away and lose an unsaved form.

Filter state is held in the URL (`01-03 §2`), which is what preserves it across module switches
within a session.

## 10. Acceptance criteria

| # | Criterion | Source |
|---|---|---|
| 1 | A user signs in and reaches the console with the navigation their role permits | `M0-I1` |
| 2 | A session times out after the configured idle period and returns the user to login | `M0-I1` |
| 3 | A password reset link works once and expires | `M0-I1` |
| 4 | Every login, failed login and lockout is written to the audit trail | `M0-I1` |
| 5 | Candidate logins are completely separate — phone and code, no shared table or code path | `M0-I1`, `M4-I21` |
| 6 | A user can be created, assigned a role, and assigned to one or more sites | `M0-I2` |
| 7 | A deactivated user cannot sign in but stays visible on records they created | `M0-I2` |
| 8 | A requisition owner can only be chosen from **active** users | `M0-I2` |
| 9 | A recruiter allocated to a requisition must hold a recruiter role | `M0-I2` |
| 10 | Site assignment distinguishes the 15 site-resident recruiters from the 7 floating ones | `M0-I2` |
| 11 | Bulk import reports row-level errors **and still loads the valid rows** | `M0-I2` |
| 12 | Removing a permission takes effect on the next **request**, not the next login | `M0-I3` |
| 13 | A user with no role can sign in but reaches nothing — a proper screen, not an error on every page | `M0-I3` |
| 14 | Every permission change is written to the audit trail | `M0-I3` |
| 15 | The role set covers every Apollo user across every module — no module builds its own access rules | `M0-I3` |
| 16 | Session expiry redirects to login **without losing unsaved form state** | `M1-I1` |
| 17 | Switching between modules preserves filter state within a session | `M1-I1` |
| 18 | Refresh token reuse revokes the whole family and raises a security event | `01-07` |
| 19 | Calling any mutating endpoint as the wrong role returns 403 | `01-08` |

## 11. Open questions

| ID | Question | Impact | Working assumption |
|---|---|---|---|
| **`OI-HS-01`** | Does a site-resident recruiter see only their own site's requisitions and candidates, or the whole base? | **Row-level scoping is a different build from screen-level permissions and touches every list in the platform.** Cheap now, expensive to retrofit. | **`AS-02`** — build the scope mechanism from day one and apply it in every repository, defaulting `recruiter` to `all`. Switching the default is then a config change. |
| `OI-A-04` | Confirm R1 provisioning covers Apollo internal users only | D12 is deferred and A13 needs no login, so there should be no client-side identity in R1 | Apollo users only. `ClientUser` is created in `03-16`, not here. |
| `OI-HS-08` | Candidate app platform — native or cross-platform | Affects the OTP/refresh flow only marginally, but store review cycles are calendar time | React Native; token flow is identical either way |
| — | SSO / AD integration | Not requested anywhere in either client document | Not built. Design the auth layer so an OIDC provider could be added behind the same session mechanism, but do not build it. |

**Escalate `OI-HS-01` in week one.** It is the single cheapest open item to close and one of the
most expensive to leave open.
