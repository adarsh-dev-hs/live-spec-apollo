## 1. Purpose

Four environments, a way to move a release between them, and enough monitoring to know when something
has broken before a user tells us. Plus the deployment of the platform onto Apollo's own AWS account in
Mumbai, with the credential and on-call boundary settled before the first deployment rather than after
it. This is the D11 obligation and the F10 prerequisite, built as one thing because they are one thing.

## 2. Scope

### In scope

- Terraform modules and one root stack per environment: `dev`, `qa`, `uat`, `prod`
- Docker images for `api`, `worker` and the four `edge-*` Lambda handlers
- GitHub Actions pipeline: verify on PR, build and publish on merge, promote with approvals
- Deployment to **Apollo's own AWS account** in `ap-south-1`, with rollback to the prior release
- Monitoring, alerting and the on-call routing described in `01-09` §6
- Backups, point-in-time recovery, and a **rehearsed and evidenced** restore before go-live
- Anonymisation of production data for the three non-production environments

### Explicitly out of scope

- Go-live itself, legacy retirement and hypercare — `05-05` (`M1-I9`).
- The migration that must reconcile before cutover — `03-13`.
- UAT support and documentation — `05-05` (`M1-I6`, `M1-I7`, `M1-I8`).
- Application-level observability decisions (what to log, what to trace). Those are `01-02` and
  `01-09`; this provisions the collectors.

### Explicitly not built

- Multi-region or cross-region replication. DPDP residency argues against it and RPO/RTO are unset.
- A Kubernetes platform. Two EC2 Auto Scaling Groups and four Lambdas is the whole compute surface.
- Blue/green or canary deployment. Rolling with health checks, on a product with 22 internal users and
  a candidate app.
- Self-service environment creation.

## 6. State machines

### Release

| From | Event | To | Rule |
|---|---|---|---|
| — | merge to `main` | `built` | Image tagged with the git SHA; **never rebuilt per environment** |
| `built` | migrate + deploy `dev` | `in_dev` | Migrations run **before** the new containers start |
| `in_dev` | smoke + E2E gate journeys pass | `in_qa` | Automatic |
| `in_qa` | manual promote (GitHub Environment approval) | `in_uat` | Apollo-visible approval |
| `in_uat` | approved release | `in_prod` | Rolling, one instance at a time, halted on health-check failure |
| `in_prod` | rollback | previous SHA `in_prod` | Redeploy the prior image; **forward-only migrations mean no un-migration**, which is what makes rollback lossless |

## 7. API surface

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/healthz` | Liveness — process is up |
| `GET` | `/readyz` | Readiness — database ping, Redis ping, migrations current. The ALB uses this. |
| `GET` | `/version` | Git SHA, build time, migration version |
| `GET` | `/metrics` | Prometheus-format metrics scraped into CloudWatch |

No business API. The pipeline's interface is GitHub Actions workflows, not HTTP.

## 8. Events and jobs

**Events emitted:** `platform.release.deployed` (environment, SHA, actor) — recorded so a defect can be
correlated with a release without reading a chat log.

**Jobs**

| Job | Schedule | Purpose |
|---|---|---|
| `platform.backup-verify` | daily | Confirms the latest snapshot exists and is in region |
| `platform.restore-rehearsal` | monthly, and **before go-live** | Restores to a scratch instance, runs a data-integrity check, records the evidence |
| `platform.anonymise-refresh` | on demand | Refreshes `uat` from a production snapshot **through the anonymiser** |
| `dp.residency-verify` | daily (owned by `02-12`) | Re-asserts every resource region |

## 9. Frontend

| Screen | Route | Note |
|---|---|---|
| System health | `/admin/system` | Version per environment, migration state, queue depths, dead-letter counts, last backup, last restore rehearsal |

One screen, admin only. Dashboards live in CloudWatch; this exists so an Apollo administrator can
answer "is it running and when was it last backed up" without an AWS login.
