**Package** `@apollo/audit` · **Schema** `audit` · **Plan** F04 · **Effort** ~5.0pd · **Risk** Medium `COMP` · **Build in** Phase 1

## 1. Purpose

One place that records who did what and when. Five milestones need it — M3 status changes, M6
overrides, M7 selection decisions and link responses, M8 corrections, M9 invoice raising — and building
it six times would be six different answers. It is also the evidence layer behind the day-90 billing
trigger: without a defensible record of who did what, an invoice cannot be justified in a billing
query.

## 2. Scope

### In scope

- An append-only entry per audited action: actor, timestamp, entity, action, before and after values
- The `audit.record()` call every service makes **inside its own transaction**
- The shared activity-timeline component rendered on the requisition, candidate and placement screens
- Export of everything touching one record for a given period

### Explicitly out of scope

- Business events for reporting. Different mechanism, different table, different purpose — `02-11`.
  Audit answers "who did this"; events answer "how many happened".
- Notification and message delivery history — `02-09`.
- Version history of a record's content (`RequisitionVersion`, `ContractVersion`, `OfferVersion`).
  Those are business records owned by their modules; audit records the *act* of versioning.

### Explicitly not built

- Audit retention configuration. It is a fixed policy, not a configuration screen — the plan removes
  this explicitly in its scope discipline.
- A global audit search screen. The trail is reached from the record it belongs to, plus the export.
- Tamper-proofing beyond append-only grants (no hash chain, no WORM storage). Raised as `OI-HS-20`
  rather than assumed in.

## 5. Data model

```sql
CREATE TABLE audit.audit_entry (
    id            uuid PRIMARY KEY DEFAULT uuidv7(),
    entity_type   text NOT NULL,      -- 'requisition' | 'candidate' | 'placement' | 'invoice' | …
    entity_id     uuid NOT NULL,
    action        text NOT NULL,      -- 'hold' | 'close' | 'override' | 'raise_invoice' | …
    actor_type    text NOT NULL CHECK (actor_type IN ('staff','candidate','client_user','link','system')),
    actor_id      uuid,               -- null when actor_type = 'system'
    actor_label   text NOT NULL,      -- denormalised name at the time, so a rename does not rewrite history
    occurred_at   timestamptz NOT NULL DEFAULT now(),
    correlation_id text,
    summary       text NOT NULL,      -- human sentence rendered on the panel
    before        jsonb,              -- only the changed fields, personal data redacted
    after         jsonb,
    reason_code   text,               -- FK-by-value to settings.list_entry where the action needs a reason
    reason_text   text,
    context       jsonb NOT NULL DEFAULT '{}'::jsonb   -- ip, user agent, link token id, job id
);

CREATE INDEX ON audit.audit_entry (entity_type, entity_id, occurred_at DESC);
CREATE INDEX ON audit.audit_entry (actor_id, occurred_at DESC);
CREATE INDEX ON audit.audit_entry (occurred_at);       -- BRIN candidate once volume is known

REVOKE UPDATE, DELETE ON audit.audit_entry FROM PUBLIC;   -- and from every app_* role
```

`before`/`after` hold **only changed fields** and are redacted by the same rules as logging: no phone,
email, Aadhaar, PAN, bank details or document text — ids and field names only (`01-10`).

## 6. State machines

**N/A** — entries are immutable facts with no lifecycle. The one invariant: an entry can be inserted
and never modified or removed, from any screen or any service (`M0-I4`).

## 7. API surface

| Method | Path | Permission | Purpose |
|---|---|---|---|
| `GET` | `/v1/audit?entityType=&entityId=&cursor=` | `audit:read` scoped to the entity's own permission | Timeline for one record, newest first |
| `GET` | `/v1/audit/export?entityType=&entityId=&from=&to=` | `audit:export` | CSV/JSON of everything touching one record in a period |
| `GET` | `/v1/audit/by-actor?actorId=&from=&to=` | `audit:export` | Supports a regulatory or HR query |

There is **no** write endpoint. Entries are created only through the in-process `audit.record(tx, …)`
call, which is why the write cannot happen outside the business transaction.

```ts
// the only way to write
await audit.record(tx, {
  entityType: 'placement', entityId, action: 'retention_deemed',
  actor: SYSTEM, summary: 'Retention deemed confirmed — client did not respond within 14 days',
  after: { retentionRecordId }, context: { linkId, windowDays: 14, windowSource: 'client_config' },
})
```

## 8. Events and jobs

**Events emitted:** none. Audit is a sink, not a source — mirroring it as events would double every
write for no consumer.

**Events subscribed:** none.

**Jobs**

| Job | Schedule | Purpose |
|---|---|---|
| `audit.export` | on demand | Builds a large export in the background and delivers a signed link (`02-04`) |

## 9. Frontend

| Component | Where it appears | Item |
|---|---|---|
| `<ActivityTrail entityType entityId />` | Requisition (`03-03`), candidate (`03-04`), placement (`03-09`) — **one component, three screens** | `M0-I4` |
| Export control | Inside the panel, permission-gated | `M0-I4` |

Renders newest first, grouped by day, each line reading as a sentence: *"Priya Nair placed the
requisition on hold — 14 Aug 2026, 09:12"*. System actions are attributed to "Apollo platform" with the
cause named. Loading, empty ("Nothing has happened to this record yet"), error and no-permission states
per `01-03`.

## 10. Acceptance criteria

| # | Criterion | Traces to |
|---|---|---|
| AC1 | Every status change, allocation, decision and configuration change is recorded with who did it | `M0-I4` |
| AC2 | Records can be added but never edited or deleted, from any screen or any service | `M0-I4` |
| AC3 | The same timeline component appears on the requisition, candidate and placement screens | `M0-I4` |
| AC4 | An auditor can export everything touching one record for a given period | `M0-I4` |
| AC5 | M3 status transitions, M7 selection decisions and the M9 billing trigger are all present in the trail | `M0-I4` |
| AC6 | An entry is written in the **same transaction** as the change it describes — a rolled-back change leaves no entry, and a committed change always leaves one | `M0-I4`, `01-02` |
| AC7 | A system action is attributed to `system` with the cause named, never to the last human who touched the record | `M0-I4` |
| AC8 | Actor name is captured at the time, so renaming a user does not rewrite history | `M0-I4` |
| AC9 | No entry contains personal data beyond identifiers | `M4-I27`, `01-10` |
| AC10 | An `UPDATE` or `DELETE` against the table raises, proven by test | `01-08` |
