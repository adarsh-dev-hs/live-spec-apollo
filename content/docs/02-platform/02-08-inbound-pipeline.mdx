## 1. Purpose

Everything that arrives at the platform from outside, on any channel, in any shape, lands here first.
Receives on every channel, writes the `InboundRecord`, resolves the sender to a client, classifies
what kind of message it is, and dispatches it to whichever module registered for that type.

The plan settles the ownership question explicitly:

> **CLOSED — Ownership of the shared inbound pipeline.** The channel receiver, queue, sender identity
> resolution, parser dispatch, intent classification, unparseable-message handling and retry are
> **built once under A1 in M3**. A14 consumes that stack with a candidate-response intent schema.

So: **built once here, two message types registered.** Demand (a client sending a vacancy) and
candidate response (a nurse answering an availability question) arrive on the same WhatsApp number
and must be told apart.

---

## 2. Scope

**In**
- Channel receivers: WhatsApp, email, HRMS webhook, spreadsheet upload, manual entry
- `InboundRecord` — one row per incoming message or file, **raw payload retained forever**
- Sender identity resolution → exactly one client, location, department
- Unmatched sender handling — nothing is ever discarded
- **Message type detection** — demand vs candidate response, with a confidence threshold and fallback
- Message type registration contract — how a module subscribes to a type
- Parser dispatch by channel and content type
- Unparseable handling → manual entry queue
- Reclassification — correcting a wrongly typed record without re-ingestion
- Retry and dead-lettering

**Out**
- Channel *integrations* — the WhatsApp/email/HRMS adapters themselves → `03-03` and `04-*`
- Requisition *parsing* — extracting fields to the requisition schema → `03-03` (`M3-I20`)
- Candidate response parsing → `03-08` (`M5-I15`)
- The requisition object → `03-04`
- Outbound messages → `02-07`

The split is: **this component decides what a message is and who should have it. The consuming
module decides what it means.**

## 5. Data model

### 5.1 Inbound record

```sql
CREATE TABLE demand.inbound_record (
  id                uuid PRIMARY KEY,
  reference         text NOT NULL UNIQUE,            -- 'IN-2026-004821'
  channel           inbound_channel_enum NOT NULL,   -- 'whatsapp_text'|'whatsapp_voice'|'email'|
                                                     -- 'spreadsheet'|'hrms'|'manual'|'portal'
  direction         text NOT NULL DEFAULT 'inbound',
  provider_message_id text,                          -- for dedupe
  sender_address    text NOT NULL,                   -- email / phone / hrms tenant key
  sender_display    text,
  received_at       timestamptz NOT NULL,
  raw_payload       jsonb NOT NULL,                  -- KEPT FOREVER
  raw_body_text     text,
  attachment_ids    uuid[],                          -- platform.document ids
  status            inbound_status_enum NOT NULL,
  client_id         uuid,                            -- resolved
  location_id       uuid,
  department_id     uuid,
  sender_identity_id uuid,
  message_type      text,                            -- 'demand' | 'candidate_response'
  type_confidence   numeric(4,3),
  consumed_by       text,                            -- module that took it
  consumed_entity_id uuid,                           -- requisition id / response id
  consumed_at       timestamptz,
  failure_reason    text,
  attempt_count     integer NOT NULL DEFAULT 0,
  created_at        timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_inbound__provider_msg
  ON demand.inbound_record (channel, provider_message_id) WHERE provider_message_id IS NOT NULL;
CREATE INDEX idx_inbound__unmatched
  ON demand.inbound_record (received_at DESC) WHERE status = 'unmatched';
CREATE INDEX idx_inbound__unparseable
  ON demand.inbound_record (received_at DESC) WHERE status = 'unparseable';
CREATE INDEX idx_inbound__list
  ON demand.inbound_record (status, received_at DESC);
```

**`raw_payload` is kept forever, including after the requisition is created**, so a disputed vacancy
can be traced back to what the client actually sent (`M3-I10`). This is not a debugging convenience;
it is the evidence trail for a commercial disagreement.

### 5.2 Type detection log

```sql
CREATE TABLE demand.inbound_classification (
  id              uuid PRIMARY KEY,
  inbound_id      uuid NOT NULL REFERENCES demand.inbound_record(id),
  classified_type text NOT NULL,
  confidence      numeric(4,3) NOT NULL,
  method          text NOT NULL,          -- 'sender_rule'|'keyword'|'model'|'manual'
  model_version   text,
  reasoning       jsonb,
  classified_at   timestamptz NOT NULL DEFAULT now(),
  classified_by   uuid                    -- set when a human reclassified
);
```

Kept so classification accuracy is measurable, and so a reclassification has a before-and-after.
Accuracy here directly sets manual-queue load, which is an operational staffing number, not just a
technical one (`OI-M3-06`).

### 5.3 Sender identity (owned by `03-01`, read here)

```sql
-- clients.sender_identity
--   id, client_id, location_id?, department_id?, kind ('email'|'whatsapp'|'hrms'),
--   address (normalised), is_active
```

Resolution is an exact match on a normalised address. **Fuzzy matching is deliberately not used** —
a wrong client on a requisition is worse than a row in the unmatched queue.

## 6. State machines

**InboundRecord**

| From | To | Trigger |
|---|---|---|
| — | `received` | Receiver wrote the record |
| `received` | `identified` | Sender resolved to exactly one client |
| `received` | `unmatched` | Sender resolved to **zero or more than one** client |
| `unmatched` | `identified` | A human mapped the sender (and it is reprocessed) |
| `identified` | `classified` | Message type determined above threshold |
| `identified` | `needs_classification` | Below threshold → human decides |
| `needs_classification` | `classified` | Human classified |
| `classified` | `parsed` | Consuming module extracted a payload |
| `classified` | `unparseable` | Parser failed → manual entry queue |
| `unparseable` | `parsed` | Human typed it in |
| `parsed` | `consumed` | A requisition or response was created from it |
| any | `discarded` | Explicitly marked not-relevant, **with a reason**. Never deleted. |

*"InboundRecord: received → identified (we know the client) or unmatched (we do not). Then parsed, or
unparseable. Then consumed once a requisition is made from it"* (`00-03 §4`).

**Nothing is ever discarded silently.** Every terminal state that is not `consumed` sits on a screen
where a person can act on it. `M3-I2` states the principle: *"so that no payload is ever discarded"*.

## 7. API surface

### 7.1 Exported service

```ts
export const inbound = {
  /** Called by every channel receiver. Idempotent on (channel, providerMessageId). */
  receive(input: {
    channel: InboundChannel
    providerMessageId?: string
    senderAddress: string
    senderDisplay?: string
    receivedAt: Date
    rawPayload: unknown
    bodyText?: string
    attachments?: Array<{ fileName, contentType, buffer }>
  }): Promise<InboundRecord>

  get(id): Promise<InboundRecord>
  list(request, scope): Promise<Page<InboundRecord>>

  resolveSender(channel, address): Promise<SenderMatch>   // 0 | 1 | many
  assignSender(inboundId, senderIdentityId, actor): Promise<InboundRecord>   // reprocesses

  classify(inboundId, type, actor?): Promise<InboundRecord>
  reclassify(inboundId, newType, actor, reason): Promise<InboundRecord>      // no re-ingestion

  markParsed(inboundId, module, payload): Promise<void>
  markUnparseable(inboundId, reason): Promise<void>
  markConsumed(inboundId, module, entityId): Promise<void>
  discard(inboundId, actor, reason): Promise<void>
}
```

### 7.2 Message type detection

```ts
interface TypeDetector {
  detect(record: InboundRecord): Promise<{ type: string; confidence: number; method: string }>
}
```

Detection runs in order, stopping at the first confident answer:

1. **Sender rule** — the address is a registered *client* sender → `demand`. The address is a known
   *candidate* phone → `candidate_response`. Confidence 1.0. This resolves the large majority.
2. **Conversation context** — a reply within N hours to an outbound message we sent → that message's
   type. Confidence 0.95.
3. **Keyword/structure** — template button payloads and structured HRMS bodies are unambiguous.
4. **Model** — free text, via the classification port (`04-01`).

Below the configured threshold → `needs_classification`, surfaced to a human.

### 7.3 Message type registration (`M3-I29`)

The contract that lets `03-08` consume this stack without rebuilding it inside M5:

```ts
inbound.registerType({
  type: 'candidate_response',
  owner: 'engagement',
  detector: candidateResponseDetector,     // optional extra signals
  handler: async (record) => {
    return EngagementService.handleInboundResponse(record)
  },
})
```

Two types registered in Release 1: `demand` (owned by `03-03`) and `candidate_response` (owned by
`03-08`). A third — client portal submissions — is enumerated for M10.

## 9. Frontend

### 9.1 Inbound list (`M3-I1`) — `/intake`

`<DataTable/>`: reference, channel, sender, received, status, type, resolved client, what it became.
Filter by channel, status, type, client, date. **Single view of every inbound message or file across
all live channels, in whatever state it has reached.**

Row opens a detail panel with the raw content — including an **audio player for voice notes**
(`M0-I6`) — the classification trail, and the resulting entity if consumed.

### 9.2 Unmatched senders (`M3-I2`) — `/intake/unmatched`

Inbounds whose sender resolves to zero clients or to more than one. Actions: map this address to a
client (creating a `SenderIdentity`), map just this record, or discard with a reason.

Mapping an address offers to reprocess every other unmatched record from the same sender — a new
client emailing for the first time typically produces several before anyone notices.

### 9.3 Reclassify (`M3-I17`)

An action on the inbound detail: "This is actually a candidate response" / "…actually a vacancy".
Requires a reason, is audited, routes to the correct module, and **does not re-ingest** — the record,
its reference and its raw payload are unchanged.

## 12. Notes for the implementer

**This is the highest-leverage component in phase 3.** Two modules consume it, five channels feed it,
and the plan's own analysis returns *three* estimate lines for it: the pipeline once, A1 schema and
routing, A14 schema and routing. Build the pipeline generically and resist letting requisition
concepts leak into it — this component knows about *messages*, not about vacancies.

**Persist before you interpret.** The receiver's only job is to get the raw payload into Postgres and
return 200. Everything else is a job. A provider retrying because we were slow to acknowledge is a
duplicate-message problem you do not want.

**Sender matching is exact, not fuzzy.** Attaching a vacancy to the wrong hospital is a worse
outcome than a queue entry, and the unmatched queue exists precisely so that being strict is safe.
