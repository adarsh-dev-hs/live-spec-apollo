**Package** `@apollo/inbound` · **Schema** `inbound` · **Plan** A1 (shared stack) · **Effort** ~31.5pd · **Risk** High `SHARED` · **Build in** Phase 3 · **Release** Parts 2, 3

## 1. Purpose

The plumbing under every message that arrives from outside: receive it on any channel, write down
exactly what was sent, work out which client or candidate sent it, decide what kind of message it is,
and hand it to whoever registered for that kind — retrying and never discarding anything on the way.

Part A closed the ownership question explicitly: the channel receiver, queue, sender identity
resolution, parser dispatch, intent classification, unparseable handling and retry are **built once
under A1 in M3**, and A14 in M5 consumes that stack with a candidate-response intent schema. This
component is that stack. It must accept a second kind of message from the start, not be retrofitted for
one.

## 2. Scope

### In scope

- Channel receivers writing an `InboundRecord` per message or file, with the **original raw payload
  retained forever** (`M3-I18`)
- Deduplication of redelivered provider messages
- Sender identity resolution against the M2 sender list — exactly one client, or the unmatched queue
  (`M3-I19`)
- Intent classification with a shared confidence threshold and fallback (`M3-I21`)
- The intent-registration contract that lets a second consumer attach without modifying the stack
  (`M3-I29`)
- Reclassification of a record between intent sets without re-ingestion (`M3-I17`)
- Learner and certification records as a third registered message type (`M3-I32`)
- Queue, retry and dead-letter behaviour, observable throughout

### Explicitly out of scope

- Parsing a demand payload into requisition fields — `03-02` (`M3-I20`).
- Completeness scoring and the follow-up chase — `03-02` (`M3-I22`).
- Candidate response handling and availability write-back — `03-06` (`M5-I15`, `M5-I16`).
- The channel connectors themselves — WhatsApp `04-01`, email `04-03`, STT `04-05`, HRMS `04-07`,
  spreadsheets `04-08`. They deliver to this component; they are not part of it.
- The screens that work the queues — `03-02` owns the inbound list, unmatched senders, manual entry
  and suspected duplicates.

### Explicitly not built

- The client portal as a channel. It is **enumerated but not enabled** in Release 1 (`AS-05`,
  `OI-A-06`); `03-14` switches it on in Phase 6 as configuration, not a schema change.
- Structured reply handling for SMS and email. Both are outbound-only in Release 1 (`OI-A-17`); an
  inbound reply on them is recorded and routed to manual entry rather than parsed.
- Automatic merging of anything. Duplicates surface for a human while `OI-M3-02` is open.
- Model retraining. A configured threshold is applied; continuous learning is not in this contract.

## 5. Data model

```sql
CREATE TABLE inbound.inbound_record (
    id             uuid PRIMARY KEY DEFAULT uuidv7(),
    channel        text NOT NULL CHECK (channel IN
                     ('email','spreadsheet','whatsapp_text','whatsapp_voice','hrms','portal','verbal')),
    provider_message_id text,          -- dedupe key for redelivery
    received_at    timestamptz NOT NULL DEFAULT now(),
    sender_raw     jsonb NOT NULL,      -- address, number, tenant id — exactly as received
    sender_identity_id uuid,            -- clients.sender_identity(id) once resolved
    client_id      uuid,                -- denormalised on resolution
    candidate_id   uuid,                -- for candidate-response intents
    state          text NOT NULL DEFAULT 'received' CHECK (state IN
                     ('received','identified','unmatched','parsed','unparseable','consumed','discarded')),
    intent_set     text,                -- 'demand' | 'candidate_response' | 'learner_record'
    intent_confidence numeric(4,3),
    raw_payload    jsonb NOT NULL,      -- retained forever, even after the requisition is created
    raw_document_id uuid,               -- files.document — attachment, spreadsheet, voice note
    transcript     text,                -- from 04-05 for voice notes
    consumed_by    text,                -- 'requisition:<id>' | 'availability_response:<id>' …
    discard_reason text,
    correlation_id text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ON inbound.inbound_record (channel, provider_message_id)
  WHERE provider_message_id IS NOT NULL;         -- redelivery cannot create a second record
CREATE INDEX ON inbound.inbound_record (state, received_at DESC);
CREATE INDEX ON inbound.inbound_record (client_id, received_at DESC);

CREATE TABLE inbound.intent_registration (       -- the M3-I29 contract, as data
    intent_set     text PRIMARY KEY,             -- 'demand' | 'candidate_response' | 'learner_record'
    owner_component text NOT NULL,               -- '03-02' | '03-06' | '03-04'
    target_schema  text NOT NULL,                -- name of the Zod schema in @apollo/contracts
    handler_queue  text NOT NULL,                -- queue the record is dispatched to
    classifier_hint jsonb NOT NULL DEFAULT '{}'::jsonb,
    is_enabled     boolean NOT NULL DEFAULT true,
    registered_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE inbound.classification (            -- append-only; reclassification adds a row
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    inbound_record_id uuid NOT NULL REFERENCES inbound.inbound_record(id),
    intent_set text NOT NULL,
    confidence numeric(4,3) NOT NULL,
    decided_by text NOT NULL CHECK (decided_by IN ('model','human')),
    decided_by_user_id uuid,
    previous_intent_set text,                    -- set when this row is a reclassification
    decided_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE inbound.channel_receipt (           -- observability of the receiver itself
    id uuid PRIMARY KEY DEFAULT uuidv7(),
    channel text NOT NULL,
    received_at timestamptz NOT NULL DEFAULT now(),
    accepted boolean NOT NULL,
    rejection_reason text,
    latency_ms integer
);
```

## 6. State machines

### `InboundRecord` (`M3-I18`, `M3-I19`, `M3-I21`)

| From | Event | To | Rule |
|---|---|---|---|
| — | message received on any enabled channel | `received` | Channel, sender, receipt timestamp and payload written before anything else |
| `received` | sender resolves to exactly one client or candidate | `identified` | |
| `received` | zero matches | `unmatched` | **Payload intact, never discarded** (`M3-I2` AC3) |
| `received` | two or more matches | `unmatched` | Routed for manual selection, **never auto-picked** (`M3-I19` V1) |
| `unmatched` | a human links the sender to a client | `identified` | Writes back to `SenderIdentity` so the next send resolves automatically |
| `unmatched` | escalated to BD | `unmatched` | Notification raised; the record stays unmatched |
| `identified` | intent classified above threshold | `parsed` | Dispatched to the registered handler queue |
| `identified` | confidence below threshold | `unparseable` | Manual entry queue, payload attached |
| `identified` | parser failure | `unparseable` | Payload intact (`M3-I20` E2) |
| `identified` | transcription failure | `unparseable` | **Audio retained and playable** (`M3-I23` E3) |
| `unparseable` | human converts it | `parsed` → `consumed` | No re-keying of sender, channel or timestamp |
| `parsed` | handler creates the target record | `consumed` | `consumed_by` records what it became |
| `parsed`/`identified` | human reclassifies | same state, new `intent_set` | **No re-ingestion**; a `classification` row is appended (`M3-I17`) |
| any | discarded | `discarded` | Requires a reason and a permission |

An `InboundRecord` stays retrievable after it is `consumed` — a disputed requirement must be traceable
to what the client actually sent (`M3-I1`).

## 7. API surface

Mostly internal. The externally reachable entry points are the Lambda-fronted webhooks (`01-09`).

| Method | Path | Caller | Purpose |
|---|---|---|---|
| `POST` | `/hooks/whatsapp` | `edge-webhook` | Signature-verified, deduped, writes the record |
| `POST` | `/hooks/email` | `edge-email-inbound` | SES → raw MIME + attachments |
| `POST` | `/hooks/hrms/:tenant` | `edge-webhook` | Structured payload; **skips parsing** |
| `GET` | `/v1/inbound?state=&channel=&cursor=` | staff `inbound:read` | Backing the inbound list (`03-02`) |
| `GET` | `/v1/inbound/:id` | staff `inbound:read` | Record with raw payload and transcript |
| `POST` | `/v1/inbound/:id/link-sender` | staff `inbound:resolve` | Link to a client → re-enters parsing |
| `POST` | `/v1/inbound/:id/escalate` | staff `inbound:resolve` | To BD; stays unmatched |
| `POST` | `/v1/inbound/:id/reclassify` | staff `inbound:resolve` | Demand ⇄ candidate response |
| `POST` | `/v1/inbound/:id/discard` | staff `inbound:discard` | Reason required |
| `GET` | `/v1/inbound/registrations` | staff `settings:read` | The registered intent sets |

In-process contract used by consumers:

```ts
inbound.register({
  intentSet: 'candidate_response',
  owner: '03-06',
  targetSchema: AvailabilityResponseSchema,
  handlerQueue: 'engagement.handle-response',
})
```

Registration requires **no change** to the receiver, queue, sender resolution or retry (`M3-I29` AC7).

## 8. Events and jobs

**Events emitted**

| Event | When | Consumed by |
|---|---|---|
| `inbound.record.received` | every message | `03-12` channel performance |
| `inbound.record.unmatched` | sender unresolved | `02-09` notifies; ops dashboard |
| `inbound.record.classified` | intent decided | The registered handler |
| `inbound.record.reclassified` | human correction | `03-12` — recurring misclassification must be measurable |
| `inbound.record.unparseable` | below threshold or parse failure | Manual-entry queue load metric |
| `inbound.record.consumed` | target record created | `03-02`, `03-06` |

**Jobs**

| Job | Trigger | Purpose |
|---|---|---|
| `inbound.resolve-sender` | on receipt | Sender identity resolution |
| `inbound.classify` | after resolution | Intent classification via `04-06` |
| `inbound.dispatch` | after classification | Hands to the registered handler queue |
| `inbound.retry` | every 5 min | Retries transient failures; dead-letters permanent ones, visibly and re-queueably |

## 9. Frontend

**N/A** — no screens of its own. The four queues that surface this component's states are owned by
`03-02`: inbound list (`M3-I1`), unmatched senders (`M3-I2`), manual entry queue (`M3-I3`), and

## 10. Acceptance criteria

| # | Criterion | Traces to |
|---|---|---|
| AC1 | Every channel writes an `InboundRecord` with channel, sender identity, receipt timestamp and payload | `M3-I18` |
| AC2 | A redelivered message does not create a duplicate `InboundRecord` | `M3-I18` |
| AC3 | Queue retry and dead-letter behaviour is observable | `M3-I18` |
| AC4 | The stack accepts a second registered intent set **without modification** to the receiver, queue, sender resolution or retry | `M3-I18`, `M3-I29` AC7 |
| AC5 | A sender resolving to exactly one client moves the record from `received` to `identified` | `M3-I19` |
| AC6 | Zero matches routes to unmatched, payload intact, never discarded | `M3-I19`, `M3-I2` AC3 |
| AC7 | Two or more matches routes to unmatched for manual selection, **never auto-picked** | `M3-I19` V1 |
| AC8 | A manual link resolves the record and feeds the resolver, so the next send from that sender resolves automatically | `M3-I19` |
| AC9 | No requisition is created before sender resolution, on any channel | `M3-I19` BR1 |
| AC10 | A demand intent above threshold moves `identified` → `parsed` | `M3-I21` |
| AC11 | Confidence below threshold moves `identified` → `unparseable` | `M3-I21` |
| AC12 | A candidate response is not classified as demand, and vice versa | `M3-I21` E6 |
| AC13 | A misrouted item is re-routable to the other intent set **without re-ingestion**, and the reclassification is recorded with actor, timestamp and original classification | `M3-I21`, `M3-I17` |
| AC14 | The threshold is configurable and **shared across A1 and A14**, not tuned per consumer | `M3-I21` BR5, `AS-03` |
| AC15 | Registering the A14 candidate-response intent set against this stack is the acceptance test | `M3-I29`, `M5-I14` |
| AC16 | A1 slipping blocks A14; A14 slipping does not block A1 | `M3-I29` |
| AC17 | An automated contract test prevents a later A1 change silently breaking A14 | `M3-I29`, `M5-I14` |
| AC18 | A learner record registers as a **further** message type rather than a separate stack, and an unmatched learner is queued for a person, never discarded | `M3-I32` |
